# Рабочий процесс

Типичный путь в MAIster: зарегистрировать проект, создать задачу, запустить
Flow, наблюдать прогон, ответить на HITL, проверить изменения и приземлить
их в целевую ветку.

## 1. Зарегистрировать проект

Проект в MAIster — это внешний git-репозиторий с `maister.yaml`.
Минимальная идея манифеста:

```yaml
schemaVersion: 2
project:
  name: myapp
  repo_path: /repos/myapp
  default_branch: main
  branch_prefix: maister/
flows:
  - id: bugfix
    source: github.com/org/maister-flow-bugfix
    version: v1.2.3
```

В интерфейсе откройте `/projects/new`, укажите путь к директории с
`maister.yaml` и дождитесь проверки. MAIster валидирует проект, Flow-пакеты,
исполнителей и уникальность `slug`/`repo_path`.

## 2. Создать задачу

На странице проекта создайте задачу: название, запрос, Flow и при
необходимости переопределение исполнителя. Задача попадает в Backlog и может
иметь несколько попыток: если прогон упал или был остановлен, задачу можно
запустить снова.

## 3. Запустить прогон

Кнопка Launch создаёт рабочую копию и отправляет супервизору запрос на
ACP-сессию. Перед запуском MAIster проверяет:

| Проверка | Зачем |
| -------- | ----- |
| Родительский репозиторий чистый | Чтобы прогон начинался с понятной базы |
| Ветка свободна | Чтобы не перетереть чужую работу |
| Путь `worktree` свободен | Чтобы не смешать артефакты прогонов |
| Исполнитель доступен | Чтобы ACP-адаптер реально стартовал |
| Глобальный лимит не превышен | Чтобы не перегрузить хост и бюджет |

Если лимит занят, прогон становится `Pending` и ждёт свободный слот.

## 4. Следить за выполнением

Откройте страницу прогона. Там важны:

- состояние прогона и активного узла/сессии;
- шкала событий;
- логи и поток обновлений;
- рабочая копия, файлы, изменения и доказательства;
- HITL-запросы, если агенту нужно решение человека.

Супервизор пишет события и вывод на диск, а веб-интерфейс читает их через SSE.
Поэтому после повторного подключения интерфейс может восстановить контекст по
сохранённым событиям.

## 5. Ответить на HITL

HITL бывает нескольких видов:

| Вид | Пример |
| --- | ------ |
| Разрешение | Агент просит разрешить действие |
| Форма | Flow ждёт структурированные поля |
| Проверка человеком | Человек возвращает комментарии на доработку |

Ответ отправляется из интерфейса. Для запросов разрешения веб-интерфейс
передаёт решение в супервизор, а тот возвращает его в живую ACP-сессию. Для
форм и проверки человеком ответ записывается как артефакт в `.maister/`
атомарно, чтобы исполнитель не прочитал
полузаписанный JSON.

## 6. Проверить изменения и доказательства

Перед слиянием смотрите не только “успешно/неуспешно”, а набор доказательств:

- какие файлы изменены;
- какие проверки проходили;
- что написано в логах;
- есть ли комментарии проверки;
- не исчерпаны ли лимиты доработки и бюджета;
- готова ли сводка готовности.

## 7. Приземлить работу

Когда результат принят, можно продвинуть изменения:

- локальное слияние в целевую ветку;
- продвижение через PR, если настроены учётные данные провайдера;
- ручной перехват, если человеку нужно закончить работу в `worktree` руками.

`local_merge` не требует CLI провайдера или токенов. Продвижение через
`pull_request` зависит от провайдера: для GitHub нужен `gh` или `GH_TOKEN`,
для GitLab — `glab` или `GITLAB_TOKEN`, для Gitea/GitVerse — соответствующий
API-токен и учётные данные для `git push` на веб-хосте.

Если слияние конфликтует, MAIster не пытается “магически” решить конфликт:
он останавливает продвижение и показывает, что нужно ручное вмешательство.

## Ежедневная шпаргалка

| Нужно | Куда идти |
| ----- | --------- |
| Посмотреть, что требует внимания | `/inbox` или бейдж Needs-you |
| Запустить новую задачу | Доска проекта |
| Запустить свободную агентную сессию | Запуск scratch-сессии |
| Понять, что делает агент | Страница прогона |
| Проверить итог | Изменения, доказательства, готовность |
| Настроить исполнителей | `/settings` |
| Работать с Flow-пакетами | `/studio` |
