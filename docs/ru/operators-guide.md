# Операторский гид

Эта страница для человека, который отвечает за MAIster-инстанс: подключает
проекты, следит за исполнителями, помогает команде разбирать прогоны и держит
систему в рабочем состоянии.

## Базовый цикл оператора

| Действие | Где смотреть |
| -------- | ------------ |
| Проверить здоровье инстанса | Строка состояния, `/settings`, логи супервизора |
| Проверить, кто ждёт человека | `/inbox`, бейдж Needs-you |
| Проверить активные работы | Portfolio и блок активных рабочих копий в боковой панели |
| Разобрать упавший прогон | Страница прогона, шкала событий, логи, статус супервизора |
| Обновить исполнителей или Flow-пакеты | `/settings`, `/studio` |
| Принять результат | Изменения, доказательства, готовность, действие продвижения |

## Подключение нового проекта

1. Убедитесь, что репозиторий доступен на хосте MAIster.
2. Добавьте или проверьте `maister.yaml` в проекте.
3. Откройте `/projects/new`.
4. Выберите режим подключения и укажите путь к проекту.
5. Проверьте найденные Flow-пакеты и исполнителей.
6. Зарегистрируйте проект и откройте доску.

Важно: MAIster ожидает чистую и понятную git-базу. Если родительский
репозиторий грязный, прогон может не стартовать, потому что `worktree` должен
создаваться из предсказуемого состояния.

## Настройка исполнителей

Runner должен быть не только создан, но и готов к запуску:

- исполняемый файл адаптера доступен на `PATH`;
- токены окружения провайдера заданы на стороне веб-интерфейса и супервизора;
- проверки готовности прошли;
- модель и провайдер совместимы с адаптером;
- политика разрешений соответствует режиму работы.

Если прогон не стартует, сначала смотрите готовность исполнителя, потом логи
супервизора, потом ошибку предварительной проверки в интерфейсе.

## Работа с HITL

Оператору важно не просто “утвердить”, а понять контекст:

1. Откройте HITL-запрос из ящика входящих запросов.
2. Проверьте прогон, узел, запрос и последние события.
3. Если это запрос разрешения, выберите безопасный вариант.
4. Если это проверка человеком, дайте конкретные комментарии: что исправить,
   где проверить, какой результат нужен.
5. После ответа проверьте, что прогон вернулся в работу или корректно
   возобновился.

## Разбор проблем

| Проблема | Первые действия |
| -------- | --------------- |
| Прогон завис в `Pending` | Проверить глобальный лимит и активные `Running` |
| Прогон ушёл в `NeedsInputIdle` | Ответить на HITL, затем проверить возобновление |
| Исполнитель недоступен | Проверить исполняемый файл адаптера, окружение и готовность |
| Изменения неожиданные | Открыть рабочую копию, шкалу событий и логи |
| Конфликт слияния | Передать работу в ручной перехват или решить конфликт вручную |
| Супервизор недоступен | Проверить процесс, порт `7777`, `MAISTER_SUPERVISOR_URL` |

## Безопасная эксплуатация

- Не храните секреты провайдера в клиентском коде или Flow-файлах.
- Не давайте исполнителю шире прав, чем нужно конкретному Flow.
- Проверяйте изменения и доказательства до продвижения.
- Используйте доверие к пакету осознанно: оно открывает настройку и включение
  ревизии по жизненному циклу пакета, но не выдаёт произвольные права времени
  выполнения вне этой процедуры.
- Не удаляйте служебные артефакты выполнения руками, если прогон ещё нужен для аудита.
- Перед разрушительным `reset` остановите веб-интерфейс и супервизор.

## Когда использовать черновой прогон (scratch run)

Черновой прогон подходит, если задача ещё не оформлена как задача на доске:

- исследовать проблему;
- попросить агента прочитать код и предложить план;
- выполнить маленькую ручную правку;
- проверить гипотезу до создания Flow-задачи.

Для повторяемой доставки лучше создавать задачу и запускать Flow.
