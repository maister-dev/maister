# Проверка результата и слияние

Перед слиянием смотрите не «успешно/неуспешно», а набор доказательств:
изменённые файлы, пройденные проверки, логи, комментарии проверки, остаток
лимитов доработки и бюджета, сводку готовности.

## Изменения

Вкладка «Диф / Файлы» показывает изменения рабочей копии: дерево файлов со
статистикой и построчный просмотр. Срез выбирается фильтром — весь ран,
текущее ревью, с прошлого ревью, последняя нода или незакоммиченное.

![Просмотр изменений прогона](images/07-diff.png)

Комментарии можно привязывать к строкам дифа; при возврате на доработку они
уходят агенту одним пакетом.

## Git-панель прогона

Когда агент больше не пишет в рабочую копию — прогон на ревью, упал,
завершился с ошибкой, завершён или брошен, — все git-действия с ней собраны
в одной **git-панели**. Её открывает кнопка действий прогона; из карточки на
доске, из портфеля и из инспектора ведут ссылки прямо в нужный раздел.
Доступ к серверу по SSH не нужен.

Обычный путь выглядит так:

1. **Коммит.** Раздел «Рабочее дерево» показывает незакоммиченные изменения;
   «Коммит» сохраняет их одним коммитом в ветке прогона.
2. **Публикация.** «Опубликовать» отправляет ветку на удалённый репозиторий под
   понятным именем, по умолчанию `feature/<ключ задачи>-<название>`: например,
   `feature/ABC-12-fix-login` (кириллица в названии переводится в латиницу).
   Имя можно поправить перед первой публикацией. После неё оно закрепляется, и
   повторная публикация дописывает ту же ветку. Если на удалённой ветке уже
   лежит другая история (например, от прошлой попытки), панель спросит
   подтверждение: назовёт ветку, коммит, который будет заменён, и открытый на
   ней PR. Перезаписан будет ровно этот коммит — если за это время в ветку
   успели запушить ещё что-то, панель спросит снова, уже про новый коммит.
3. **Pull request.** «Открыть PR» создаёт PR из опубликованной ветки в целевую:
   заголовок и описание подставляются из задачи, можно отметить черновик. У
   scratch-прогона целевая ветка закреплена и не редактируется. Если
   такой PR уже открыт, панель вернёт его как есть. Статус прогона при этом не
   меняется.
4. **Завершение.** «Завершить по PR» переводит прогон в `Done`, когда PR — это и
   есть результат. На ревью действуют обычные проверки готовности. Для
   упавшего или брошенного прогона решение за вами, панель спросит
   подтверждение. Завершение привязано к коммиту, который несёт сам PR: если
   PR слит без последних коммитов рабочей копии, панель откажет и предложит
   открыть для них новый PR.

Раздел «Обновление» подтягивает изменения извне: из базовой ветки, из целевой
или из опубликованной ветки — так в прогон возвращаются ваши собственные
пуши, например с ноутбука. При конфликте панель ничего не ломает: копия
возвращается к исходному коммиту, а список конфликтных файлов показывается.
Разрешение конфликтов агентом доступно только для прогона на ревью.

Если push обновления удалил бы коммиты, которые есть только в опубликованной
ветке (правка ревьюера, suggestion, закоммиченный в PR), панель ничего не
отправит и спросит. Основное действие — «Сначала обновить из публикации»: те же
настройки, но из опубликованной ветки, и эти коммиты войдут в прогон. Второе —
«Перезаписать N коммитов»: перезаписан будет ровно названный коммит, а если
ветка за это время ушла дальше, панель спросит снова. Внешний API и
автоматический промоушен такие коммиты не удаляют никогда.

«Отменить изменения» сначала сохраняет всё незакоммиченное (включая новые
файлы) в служебную ссылку `refs/maister/rescue/…` и только потом очищает
копию. Команда для восстановления показывается сразу, её можно скопировать:
она возвращает рабочую копию. Если в индексе было что-то другое (файл
добавлен в индекс в одной версии, а потом изменён, или добавлен и затем
удалён), индекс сохраняется вторым родителем этой ссылки (`<ссылка>^2`).

Если рабочую копию удалили (архив, удаление, сборка мусора), панель
предлагает «Вернуть рабочую копию»: она пересоздаётся из локальной ветки, из
опубликованной или из архивной ссылки — из первой, которая найдётся.

Архивация и удаление предупреждают о коммитах и файлах, которых нет ни на
одном удалённом репозитории, и предлагают сначала опубликовать ветку.

С рабочей копией одновременно работает кто-то один. Пока идёт git-действие или
завершение по PR, «Восстановить» у упавшего прогона не сработает: панель
попросит повторить, когда операция закончится. И наоборот: если прогон
восстановили, пока вы запускали git-действие, оно не начнётся — копия снова
принадлежит агенту.

## Готовность и слияние

Сводка готовности собирает блокирующие гейты Flow: проверки, вердикты,
обязательные артефакты, проверку человеком. Пока блокирующий гейт красный,
продвижение закрыто.

Блок «Ревью и промоут» показывает путь изменений: базовая ветка → ветка
прогона → целевая ветка, отставание от цели («позади N · впереди M») и
действие «Синхронизировать ветку», если цель уехала вперёд.

![Промоушен: синхронизация ветки, режим и кнопка продвижения](images/07-promote.png)

Когда результат принят, выберите режим промоута и продвиньте ветку:

| Режим | Что происходит |
| ----- | -------------- |
| Локальное слияние (Merge) | `git merge --no-ff` в целевую ветку на хосте; токены провайдера не нужны |
| Pull request | Ветка публикуется и открывается PR; для GitHub нужен `gh` или `GH_TOKEN`, для GitLab — `glab` или `GITLAB_TOKEN` |
| Ручной перехват | Вы забираете рабочую копию и заканчиваете руками; прогон переходит в `HumanWorking` |

Отдельно настраивается **авто-промоушен**: проект может автоматически
продвигать безопасные классы изменений (документация, тесты) при зелёной
готовности. По умолчанию выключен.

При конфликте MAIster не решает его «магией»: продвижение останавливается,
интерфейс показывает репозиторий, ветки и команду, на которой всё встало.
Решите конфликт руками или через ручной перехват и повторите продвижение.

Если PR-промоушен со сжатием истории удалил бы коммиты, которые есть только в
ветке PR, это не конфликт слияния: ничего не меняется, а блок ревью ведёт в
раздел «Обновление» git-панели. Сначала обновите прогон из публикации, затем
повторите продвижение.
