# ADR-171: User-scoped attention SSE stream

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-10
**Status:** Accepted

**Context:** The cross-project work table and activity feed need to stay fresh
while a reader watches them. The obvious move — "reuse the existing run stream" —
does not exist to be reused. The repository has exactly two SSE routes and both
are single-entity:

- `web/app/api/runs/[runId]/stream/route.ts` — one run.
- `web/app/api/projects/[slug]/evaluations/studies/[studyId]/stream/route.ts` —
  one evaluation study.

A reader of `/work` or `/activity` watches *n* runs across *m* projects, and that
set changes as work starts and finishes. Opening one `EventSource` per visible run
would scale connections with the table's row count and would still miss the row
that has not launched yet.

The constraint that shapes the answer is the root operating contract's ban on
`fs.watch`, `chokidar`, or polling **as a state-transition mechanism**. That rule
is about what drives the FSM, not about how a browser learns a read model moved.
The study route already sits on the correct side of that line and says so in its
own header: it is a *"Server-side read-model poll of the DURABLE
evaluation_events log (NOT a state-transition trigger — the FSM is CAS-driven by
the dispatcher)"*.

**Decision:** Add one **user-scoped attention stream** at
`GET /api/attention/stream`, built on the study route's shape.

**D1 — One connection per client, scoped to the user.** The stream is addressed by
the session user, not by a run, a project, or a filter. A reader holds a single
`EventSource` for the whole surface; the set of runs it covers may change without
the client opening or closing anything.

**D2 — It is a server-side poll of durable read models, pushed as SSE.** The
server polls the same durable rows the page rendered from and pushes a frame when
they move. No client timer, no client-side `setInterval` refetch, and **no
participation in any state transition** — the stream never writes run state,
never resolves a HITL deferred, and never advances a cursor. It is a read path
that happens to push.

**D3 — Frames are ticks, not a log.** A frame carries "what changed, and the
counters as of now" — enough for the client to refetch the affected region. The
client hook follows `useRunStream`'s `retain: false` idiom
(`web/lib/use-run-stream.ts:36`): a tick that triggers a refetch, never an
accumulated event list in React state. A visibility surface that a reader leaves
open for a working day must not grow a per-event array.

**D4 — `lastEventId` replay, from the durable rows.** Reconnect sends
`Last-Event-ID` (header, or `lastEventId` query for clients that cannot set it);
the server replays the tail from the database, exactly as the study route's
`parseLastEventId` does. There is no in-memory replay buffer, so a server restart
costs a reader nothing but a reconnect.

**D5 — Bounds are module constants, not environment variables.** Poll interval,
heartbeat and a maximum quiet period live in the route module, matching the study
route's `POLL_INTERVAL_MS` / `HEARTBEAT_MS` / `MAX_QUIET_MS`. An idle stream is
closed by the quiet cap rather than held open forever. These are deliberately not
tunable: an env var nobody asked for is a dev/prod skew surface, and this
milestone adds no deployment knob before the notification work.

**D6 — RBAC is enforced per frame, not only at connect.** Every frame is filtered
through the reader's currently visible projects. A project that leaves a reader's
visibility mid-stream stops producing frames for them without requiring a
reconnect, and no frame ever references a project the reader cannot see.

**Consequences:**

- One durable, replayable liveness path for every cross-project surface, at one
  connection per reader.
- The poll interval bounds staleness. This is a read model catching up, not a
  transition being detected, so the latency floor is a UX number rather than a
  correctness one.
- A third SSE route now shares a shape with two others. If the frame formatting
  duplicates the study route's, the shared helper is extracted rather than
  copied — `formatSseFrame` already lives in
  `web/lib/evaluations/dispatcher/events.ts` and is the natural seam.
- Readers who keep the page open all day hold an open connection each. The quiet
  cap is what keeps that bounded.

**Alternatives Considered:**

- **One `EventSource` per visible run.** Rejected: connections scale with row
  count, and a not-yet-launched task has no run to subscribe to.
- **Client-side polling with `setInterval`.** Rejected: it moves the poll to *n*
  clients instead of one server, and it is the pattern the house rules exist to
  prevent even where it would be merely wasteful rather than incorrect.
- **A shared broadcast channel fed by the domain-event dispatcher.** Rejected for
  this milestone: it needs a per-user fan-out and an in-memory subscriber
  registry that does not survive a restart, to replace a durable poll that does.
  It stays available if the poll interval ever becomes the bottleneck.
- **Widen the existing run stream to accept a run-set.** Rejected: it would turn a
  single-entity route with a live FSM relationship into a cross-project read
  aggregator, mixing two very different trust and lifetime models in one handler.

**Amendments:**

- **2026-09-26 — D7: the render is the first cursor.** A connect without
  `Last-Event-ID` answered with a snapshot tick, and the client refreshed on it
  to close the gap between the server render and the subscription. So every
  load rendered each page on the server twice. When the refresh reached a page
  whose streamed markup React 19.2 had not yet revealed (it reveals on a
  ~300 ms throttle), React client-rendered the page into `<main>` beside its
  parked hidden copy, which is what the e2e "resolved to 2 elements" flakes
  were. The scan now closes that gap instead:
  - The `(app)` layout takes the render's cursor (`Date.now()`, before any
    read) and passes it to the client with the `decisions` and `updates`
    counts it already renders.
  - The client's first connect sends them as `lastEventId`, `decisions` and
    `updates`.
  - The server scans from that cursor, as for any resume, and treats the
    counts as already sent. A reader whose render is current gets no tick at
    all.
  - A reconnect sends the last tick's cursor and counts, so it no longer causes
    a refresh either.
  - A baseline that does not parse is ignored rather than half-trusted.
    Without a cursor the stream still opens with a snapshot.
  - What the scan does not watch was never live through this stream, and no
    longer gets the incidental connect-time refresh.
