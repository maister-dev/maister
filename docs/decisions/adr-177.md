# ADR-177: Evidence-first crash classification

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-21
**Status:** Implemented; amended 2026-09-23 (host-evidence settlement; the current turn across `node`, `permission_resume` and gate variants; the boundary re-reads its command under lock)

**Context:** The reconcile sweep classifies a `Running` flow run with no live
agent session by **age alone**. Past the 90 s grace window it answers
`crash / agent-session-gone` (`web/lib/reconcile.ts`, arm 10c) — a single
classification that means "the session vanished and I do not know why". The
sweep reads no command evidence at all: `ReconcileInput` carries no
`execution_commands` field, by construction.

That was sound while the only durable fact about a turn was whether an ACP
session answered. Stage A and Stage B changed it. Every `session.prompt` is now
a durable, owned command with a settled terminal state, a receipt the host can
re-derive, and an `application_state` that says whether its result reached the
ledger. **The sweep crashes runs whose outcome is already recorded one table
over.**

Three concrete failures follow.

**First — a run is crashed while its result is still on its way.** A turn that
finished on the host but whose terminal event has not been ingested, or whose
settled command the owner worker has not applied yet, looks identical to a dead
session. Past grace the sweep crashes it and the applied result is then
discarded. The grace window is a timer standing in for evidence that exists.

**Second — a lost turn permanently burns the run, and `Failed` is not
recoverable.** When the supervisor restarts mid-turn it commits the `turn_lost`
pair at startup, and the manager settles the command `failed` with
`reason = "turn_lost"`. Traced hop by hop on the code this ADR changes:

| Hop | Site | Effect |
| --- | --- | --- |
| 1 | `flows/graph/node-prompt-owner.ts` | the lost turn decodes into an ordinary `FlowActionCompletion` with `errorCode` — `details` is dropped and never reconstructed |
| 2 | `flows/graph/runner-graph.ts` | `!result.ok` → `markNodeFailed` → attempt `status='Failed'`, `decision` stays **NULL** |
| 3 | `scheduleAutoRetry` | returns `"fail"` — the code is not in `RETRYABLE_ERROR_CODES` (`SPAWN`, `EXECUTOR_UNAVAILABLE`, `CHECKPOINT`, `ACP_PROTOCOL`), and a flow author **cannot** opt in: the zod schema restricts `retry_policy.on_errors` to the same four |
| 4 | `runner-graph.ts` | the traversal breaks; `runs.status='Failed'` |
| 5 | `queries/run.ts` `isRunRecoverable` | requires `status === "Crashed"` → **the run is not recoverable** |

So a host restart mid-turn does not merely record the wrong reason: it
terminalizes the run in a state the operator has no remedy for. That is a
strictly worse outcome than the `agent-session-gone` crash the sweep would have
produced, and it is the severity this ADR answers.

**Third — the same host restart produces two different run states depending on a
60 s race.** The owner's `Failed` write CAS-guards on `Running`. Sweep-first
yields `runs.status='Crashed'` with the attempt `Failed`/`decision=NULL`;
worker-first yields `runs.status='Failed'` with the same attempt. One cause, two
terminal shapes, decided by which writer got there first.

**Decision:** The classifier reads the current attempt's newest owned
`session.prompt` command and answers from **what the evidence says**, falling
back to the grace window only when there is no evidence at all.

**D1 — Evidence is resolved by the caller; the classifier stays pure.**
`classifyRunReconcile` is a pure function with a 51-case unit suite, and every
impure input it already carries (`crashRecoverPending`, `liveRunStepSession`,
`parentStatus`) is pre-resolved by the sweep and documented as such. Evidence
follows that shape exactly: the sweep's per-candidate enrichment block resolves
a `PromptEvidenceClass` and a `promptEvidenceStreamLost` boolean; the classifier
gains two pure fields and no I/O.

The derivation itself is one pure function, `classifyPromptEvidence` in
`web/lib/reconcile-evidence.ts`, shared by the sweep, its unit suite and this
table. Its order is load-bearing:

| # | Row condition | Class |
| --- | --- | --- |
| 1 | no owned `session.prompt` for the current attempt | `none` |
| 2 | `state ∈ {queued, delivering}` | `none` — nothing the host could have lost |
| 3 | `application_error.reason = 'prompt_terminal_conflict'` | `quarantined` |
| 4 | `application_state = 'poisoned'` | `poisoned` |
| 5 | `application_state ∈ {applied, superseded}` | `applied` |
| 6 | `application_state = 'applying'` | `applying` |
| 7 | settled ∧ `turn_lost` | `turn_lost` |
| 8 | settled ∧ `application_state = 'pending'` | `pending_application` |
| 9 | `state = 'accepted'`, no terminal evidence → one `GET /commands/{id}` probe | `inflight` \| `pending_ingest` \| `turn_lost` \| `none` |

Row 3 **must** precede row 5: `quarantine()` writes
`application_state = completion_applied_at ? "applied" : "poisoned"`, so a
conflict found after application reads as `applied` with `application_error`
set. Keying the quarantine arm on `poisoned` alone would silently classify that
case as healthy. Row 7 **must** precede row 8 for the same class of reason: a
settled lost turn is the boundary, not something to wait for.

Row 9 is the only arm that costs a host call, and `turn_lost` is the only
answer it may return that can terminalize a run — so the probe must **prove** a
lost turn rather than infer one from a missing signal. Two receipt shapes look
like a lost turn and are not: a `rejected` receipt is also what
`completeAsync`'s catch writes for an ordinary errored turn (only the
`turn_lost` reason separates them, so the rest read `pending_ingest`), and a
**v2** `accepted` receipt carries no liveness at all — `receiptToResponse` drops
the `inflight` argument for `requestVersion = 2` because the v2 wire shape has
no such field, and `normalizeCommandReceiptV2` then hardcodes `false`. Since v2
is the production request schema, reading that as `turn_lost` crashed healthy
turns. It classifies as `none` instead of `pending_ingest`: `pending_ingest`
asserts a named writer owes the next move, and here nobody is asserted, so
answering it would skip forever whenever the terminal event never arrives.
`none` is the one class that falls through to the grace anchor — which both
refuses to crash a turn inside its window and keeps the long-standing safety net
for one long past it.

`turn_lost` is matched on the settled command's error **reason**, never on an
HTTP status and never on the error code. The reason is carried two ways and both
are accepted: nested (`last_error.details.reason`, written when the supervisor's
terminal event is ingested — the common path after a restart) and flat
(`last_error.reason`, written by `foldReceipt`'s accepted-with-no-terminal
fallback). The code differs by path — `PRECONDITION` from a rejected receipt,
`ACP_PROTOCOL` from the fallback — which is precisely why it is not the
discriminator.

**D2 — The decision table, applied before the grace anchor, on one arm only.**
Reached only when `run_kind='flow'`, no live session, the node is
`ai_coding | orchestrator`, and the ADR-175 `crashRecoverPending` route has
already been declined:

| `promptEvidence` | Decision | Reason | Writer that owns the follow-up |
| --- | --- | --- | --- |
| `applied` | SKIP | `evidence-applied` | flow continuation worker (~1 s) |
| `applying` | SKIP | `evidence-pending` | the worker holding the application claim |
| `pending_application` | SKIP | `evidence-pending` | prompt-owner worker (~1 s) |
| `pending_ingest` | SKIP | `evidence-pending` | the event consumer |
| `inflight` | SKIP | `evidence-inflight` | the host — the turn is still running |
| `pending_ingest` / `inflight` ∧ stream `lost` | CRASH | `stream-lost` | nobody — the evidence can never arrive (since 2026-09-23 a `completed` probe first tries host-evidence settlement; see Amendments) |
| `turn_lost` | CRASH | `turn-lost` | the boundary (D3); Recover is offered |
| `quarantined` / `poisoned` | CRASH | `owner-poisoned` | an operator |
| `none` | *fall through* | — | the existing grace / `agent-session-gone` arms, unchanged |

The skip arms fire **regardless of grace**. That is the point, and it restates
rather than deletes the runs.md invariant: *the grace guard applies only when no
command evidence exists*. `evidence-pending` is bounded by
`commandStreamLost()` — the state the stream-health pass writes earlier in the
same sweep — never by a new timer.

That bound applies to exactly the two classes whose evidence is still ON THE
HOST. `pending_application`, `applying` and `applied` are deliberately excluded:
their evidence has already been ingested — that is what made the command settled
— and the writer that owes the next move reads it from Postgres, not from the
stream. A dead stream cannot stall them, and crashing them would discard a
result that already landed, which is the precise failure these arms exist to
prevent.

**D3 — One crash boundary, fenced on the command's application.** A sweep-side
boundary that closes the attempt and crashes the run but leaves the command
`pending` produces a row set that can **never** be retired
(`classifyCommandRetirement` answers `owner_unapplied`) and that
`execution_commands_protected_evidence` then refuses to delete. The claim is
three-sided — `runs.status`, `node_attempts.status`, and
`execution_commands.application_state` — so all three move in ONE transaction,
`applyTurnLostBoundary` in `web/lib/runs/turn-lost-boundary.ts`:

- close the attempt: `status='Reworked'`, `decision='turn_lost'`,
  `error_code='CRASH'`, `ended_at`, guarded on
  `status='Running' AND ended_at IS NULL AND action_completion IS NULL`;
- `crashRunningRun(runId, 'turn-lost', {fromStatuses:['Running']})`, which
  already carries the full terminal contract (HITL close, sync-claim release,
  assignment release, `run.crashed` webhook and domain event);
- the command → `application_state='applied'`, `completion_applied_at=now()`,
  claim columns cleared, guarded on `completion_applied_at IS NULL`.

`completion_applied_at IS NULL` — **not a new lock** — is the single-winner
mechanism, because the invariant is "this command is applied exactly once" and
the guard is keyed on exactly that object. It is the same guard
`applyCrashedTurnEvidence` already relies on. Zero rows from any guard rolls the
whole transaction back: never a second close, never a half-apply.

Two refinements the guards needed, both narrowing:

- **The attempt's `action_completion IS NULL` — not the command's guard — is
  what protects a real result.** So a command that is ALREADY `applied` or
  `superseded` means the discharge obligation is met, not that a race was lost,
  and the boundary proceeds without rewriting it. That state is reachable on
  exactly one arm: `quarantine()` writes `application_state =
  completion_applied_at ? "applied" : "poisoned"`, so a conflict found after
  application arrives already stamped. Requiring the CAS there would leave the
  run `Running` forever with a disagreeing turn nobody could see. *(Narrowed
  2026-09-23, see Amendments: only that quarantined shape counts as
  discharged; an `applied` or `superseded` command without the quarantine is a
  successful application, and the boundary yields to it.)*
- **`application_error` is preserved, not nulled.** For `owner-poisoned` it is
  the only record of why the application failed, and `applied` with a non-null
  `application_error` is already a valid shape in this schema — `quarantine()`
  writes exactly it.

`error_code` is normalized to `CRASH` rather than copied from the settled
command. It is an Observatory clustering key (`errorKey = errorCode ?? exitCode
?? "unknown"`), and the two source codes would split one root cause across two
clusters. Which recovery path terminalized the turn survives on the command's
`last_error`, which is the durable evidence.

A gate's lost turn takes the same boundary and additionally marks its
`gate_results` row **`stale`**. Not `failed`: recording a host restart as a gate
verdict would send the run to rework or block promotion on a decision no judge
made. Not left `running` either — that is the stuck shape `runGateStepGuarded`
exists to prevent.

**D4 — Flow goes through the boundary; agent and scratch keep their own choke
points.** Only the flow path has two writers that genuinely race. An agent run
has one (`finalizeAgentRun`, whose `AgentTerminalOutcome` already admits
`"Crashed"`) and scratch has one (`markScratchCrashed`, which also owns
`scratch_runs.dialog_status`). Wrapping a ready single choke point in a shared
boundary would buy nothing and would force `crashRunningRun` onto scratch. What
those two owe is narrower and is the load-bearing half: the failed-turn command
must reach `application_state='applied'`, or it strands `owner_unapplied`.
`Crashed` buys an agent run no recovery — `isRunRecoverable` resolves the node
kind from `resume_target_step_id`, which an agent run has none of — so the
status change is for truthfulness and parity, not for a new remedy.

The `agent-observer-*` and `live-scratch-session` classifier arms are untouched:
they have their own owners and gain no evidence field.

**D5 — Recover declines a lost turn, and discharges it.** ADR-175's
`applyCrashedTurnEvidence` adopts agreeing terminal evidence the owner never
applied. A lost turn is not a result, so it gains one filter arm and a new
`"turn-lost"` outcome that the caller routes like `"absent"` — close the crashed
attempt, dispatch one fresh prompt.

Declining is not enough. Left at `application_state='pending'` the old command
would strand `owner_unapplied` forever — the exact failure D3 exists to prevent,
reintroduced by the fix. The arm therefore settles it
`application_state='superseded'` before the recover re-dispatches. The split is
deliberate: the **D3** boundary writes `applied` because it acted ON the evidence
— the crash IS the application; **D5** writes `superseded` because a fresh
attempt replaced the lost turn and nothing was applied. `superseded` is the
existing first-class disposition for exactly that, and retirement already
accepts it.

`completion_applied_at` stays **NULL** there.
`execution_commands_application_shape_check` opens with an EQUIVALENCE —
`(application_state = 'applied') = (completion_applied_at IS NOT NULL)` — so
stamping it beside `superseded` is refused by the database. Nothing is lost:
`classifyCommandRetirement` never reads that column; `superseded` alone
discharges. The existing owner-application writer already has this shape
(`completionAppliedAt: outcome === "applied" ? now : null`), so the guard for
this write is `application_state = 'pending' AND completion_applied_at IS NULL`.

**D6 — Accounting and surfacing.** `turn_lost` joins `NON_CORRECTION_DECISIONS`,
which fans out by construction to both Observatory correction counters and the
rework budget: a host restart is not an agent correction.
`MAISTER_MAX_OPERATOR_RESTARTS` is deliberately **unaffected** — both budget
sites filter on an allow-list of one value, not on the complement — and that is
asserted as a negative regression rather than changed.

`clusterRetrySignals` does **not** filter on `decision`, so `turn_lost` attempts
do reach the signal clusters. That is chosen, not inherited: a host that keeps
restarting is a real operational signal, unlike a correction counter, which
measures agent quality. The `CRASH` normalization is what keeps that signal in
its own cluster instead of contaminating genuine failures.

The durable record is `node_attempts.decision` + `error_code`. No new run status
and no new `runs` error column — a run-level error surface is its own item.

**D7 — No migration.** `node_attempts.decision` is unconstrained `text`;
`error_code` is `text` and `CRASH` is already a `MaisterErrorCode`;
`application_state` already admits `applied` and `superseded`, and the coupled
`execution_commands_application_shape_check` is satisfied by stamping
`completion_applied_at`. Boundedness comes from `commandStreamLost()`, not from a
durable timer, so there is no retry or backoff column. No index is added either:
the probe filters `run_id` and sorts `created_at`, which
`execution_commands_run_created_idx` on `(run_id, created_at)` serves as a short
index scan.

**Consequences:** A run whose turn is still in flight, still being ingested, or
already applied is no longer crashed for being old. A supervisor restart
mid-turn produces one terminal shape — `Crashed`, attempt closed `turn_lost`,
command discharged, Recover offered — regardless of which writer gets there
first. A poisoned or disagreeing application surfaces as its own reason instead
of hiding inside `agent-session-gone`.

The cost is one conditional HTTP receipt probe on a rare candidate class inside
the 60 s sweep, six new `ReconcileReason` members, three new `CrashReason`
members, and a second consumer of the crash transaction.

**Alternatives Considered:**

- **Reorder the sweep instead of probing.** Moving
  `executionCommandReconcilePass()` ahead of `runReconcileSweep()` would make
  most evidence fresh. Rejected: `recoverExecutionCommands` reads
  `lostStreamHostIds`, which `runEventStreamHealthSweep` writes **earlier in the
  same pass**, so `streamHealth → commandRecovery` is load-bearing and **two**
  stages would have to move over four intervening passes. And the probe would
  still be required for the `accepted`-with-no-terminal-evidence window. Full
  cost, no saving.
- **Map `turn_lost → errorCode:"CRASH"` in the decoder and let the graph
  terminalize.** `runner-graph.ts` already turns a `CRASH`-coded node failure
  into `runs.status='Crashed'` with the full webhook and domain event, so this
  would be one line. Rejected: that branch never stamps `resume_target_step_id`,
  so `isRunRecoverable` resolves `currentNodeKind = null` → `discard-only` — the
  run would be `Crashed` **and unrecoverable**. It would also leave the attempt
  `Failed`/`decision=NULL`, forfeiting the accounting and the label entirely.
  (The same gap makes *every* graph-CRASH run unrecoverable. That predates this
  work and is filed separately.)
- **Widen `RETRYABLE_ERROR_CODES` so a lost turn auto-retries.** Rejected: it
  would let a flow author opt any `PRECONDITION` into a paid re-prompt, and a
  lost turn's remedy is an operator decision about a host, not a retry budget.

**Consequence for [ADR-175](adr-175.md), recorded because it is not obvious.**
Its Scope-2 arm — *Recover applies agreeing terminal evidence the owner never
applied, so a recover never buys a turn the host already finished* — keeps its
contract but LOSES its most common entry path. Reaching that arm needs a
`Crashed` run holding unapplied agreeing evidence, and until now the sweep
manufactured exactly that state: it crashed the run for being old while its
result was still being applied. That is the defect this ADR removes, so the
sweep no longer produces it. The arm stays reachable through the population D5
already names — a run crashed for some OTHER reason (`worktree-gone`,
`orphaned-child`, `cli-not-retry-safe`, or a boot reconcile that saw no evidence
yet) while its evidence was unapplied — and through every row already crashed
before this ships. Nothing about ADR-175's behaviour changes; only how often the
system walks into it.

**Accepted residual windows:**

- **Nothing bounds `pending_application` or `applying`.** `commandStreamLost()`
  bounds the two HOST-side classes, and a worker that keeps FAILING poisons the
  command through its own attempt budget, which the `poisoned` arm then crashes
  — so a failing worker is bounded. What is unbounded is a prompt-owner worker
  that never runs at all: its run then holds `Running`, and its concurrency
  slot, indefinitely. Accepted rather than timed out, because a timer here is a
  guess about a writer's cadence and the worker is a boot-critical singleton
  whose absence is a liveness failure the health surface owns (PRM-11), not a
  reconcile concern. Before this change such a run was crashed after 90 s and an
  operator could Recover it; that is the cost, and it is the same cost as
  keeping a finished turn's result.
- `commandStreamLost()` answers per HOST, and a host can hold several stream
  rows — a `lost` one from a stalled incarnation beside an `active` one from the
  reconnect. It therefore means *"a stream was given up AND none is live"*; an
  `active` stream disqualifies the impasse outright. Reading one arbitrary row
  (as it did before this ADR made the answer terminal) made a recovered host a
  coin flip.
- **A v2 `accepted` receipt keeps the old grace behaviour, false crash and all.**
  That shape carries no liveness in either direction, and its command carries no
  ingested evidence either, so there is genuinely nothing to read: the choice is
  between the pre-ADR-177 grace net (which can still crash a turn that is alive
  and quiet past 90 s, because the sweep snapshots sessions before it loads
  candidates) and an unconditional skip. The skip is the worse of the two — it
  is unbounded, and a run whose terminal event never arrives would then be
  passed over by every sweep forever, with no writer that owes the next move and
  no operator affordance. A crash is recoverable; a permanent stall is not. So
  this one window keeps the behaviour that shipped before this ADR, and gets no
  better until the v2 receipt carries a liveness field.
- A host whose event stream is still `active` but whose consumer is wedged holds
  its run `Running` on `evidence-pending` indefinitely. That is the existing
  command-impasse signal's job, not a new timer.
- Rows applied as ordinary failures **before** this change ships stay `Failed`. A
  repair migration is deliberately not attempted — the completion is already
  consumed.
- On the periodic tick the reconciler still sees command evidence up to one
  60 s tick stale, and a stream is marked `lost` only after reconcile has
  classified. The receipt probe is what makes the decision correct anyway, which
  is why it is load-bearing rather than an optimization.

**Amendments:**

- 2026-09-21 — amends [ADR-175](adr-175.md): its Recover no longer adopts a
  `turn_lost` result as the node's outcome. Amends, does not replace, ADR-033.
- 2026-09-23 — host-evidence settlement ([ADR-167](adr-167.md) D5 amendment).
  In the **stream-lost branch only**, a `pending_ingest` command whose probe
  answered `completed` is first offered to the host-evidence feed (direct
  binding of the receipt-named terminal event, then the verified host span).
  A settled command is re-classified by the D1 table and follows its D2 row; a
  span that cannot be read or verified crashes `stream-lost` as before. Only a
  read that ANSWERED is that verdict, and the answer is durable:
  `execution_commands.host_span_verdict` (migration `0178`) holds the outcome of
  the latest read that ran without settling — `refused`, or `busy` when the host
  kept asking for a retry or a retryable write failed — and a read clears it when
  it claims the command. The resolver crashes on a recorded `refused` whoever
  recorded it, including another reader whose retry delay keeps the resolver
  from reading itself, and on a command the host span cannot settle at all. It
  SKIPs (`evidence-pending`) only while a read is in flight (no verdict), after
  `busy`, or while another reader still holds the receipt claim. That wait is
  on the next answer, never on a timer: every read ends in a verdict or a
  settlement, and the resolver reads itself whenever the claim is free. (A first
  cut deferred on any denied claim; a flow continuation re-drives the wait and
  re-takes the claim every 5 s, so that crash happened only when the sweep won
  the claim by chance.) A transport failure is a refusal: it cannot be told
  from a host that is gone for good. The
  non-lost branch is unchanged: `pending_ingest` still SKIPs, because the
  waiting driver or the continuation worker settles it through the same feed.
  The duration watchdog reuses `loadPromptEvidence` / `probeReceipt` with an
  explicit list of every `flow_node_attempt` variant; the default lookup here
  stays `variant = 'node'`.
- 2026-09-23 — **the current attempt's turn is not only its `node` command.**
  The D1 lookup filtered `owner_ref->>'variant' = 'node'`, but a permission
  answer resumes the SAME action as a newer `permission_resume` command (same
  attempt, same prompt ordinal), and `ai_judgment`/`skill_check` gates run on
  the same `Running` attempt after the action applied, as `gate_ai`/`gate_skill`
  commands. During either turn the newest `node` command is the finished turn
  before it, so the classifier answered `applied` (SKIP `evidence-applied`) for
  a turn it never read — and a lost, stream-lost or poisoned resume or gate turn
  was skipped forever. The lookup now reads the newest command among
  `CURRENT_TURN_VARIANTS = node | permission_resume | gate_ai | gate_skill`
  (`web/lib/reconcile-evidence-db.ts`), still one short scan served by
  `execution_commands_run_created_idx`. The consensus variants are excluded: a
  consensus node is outside the D2 evidence gate (`ai_coding | orchestrator`).
  `loadPromptEvidence` no longer has a default — every caller names its set
  (this classifier `CURRENT_TURN_VARIANTS`, the duration watchdog every
  `flow_node_attempt` variant) — which retires the "default stays `node`" clause
  of the amendment above. The D1 derivation and the D2 table are unchanged; they
  now read the right row. D3's gate sentence is now true on the sweep side too:
  for a gate command `applyTurnLostBoundary` makes the gate owner's writes —
  the evaluation must belong to the attempt (else nothing is written), the close
  admits the action's existing `action_completion` (the action's result is
  preserved), and an evaluation still `pending`/`running` becomes `stale`; a
  verdict already recorded (a conflict found after application) is kept. The
  boundary's own fallback lookup, used when no command is named, is the same
  `loadPromptEvidence` call. Recover's closed-attempt quarantine refusal
  (`quarantinedOnClosedAttempt`, `crash-recover.ts`) reads the same set, because
  the `owner-poisoned` boundary can now close an attempt whose quarantined turn
  is a resume or a gate; reading `node` there answered `absent` and re-prompted
  a disagreeing turn. The ADR-175 open-attempt adoption still reads `node`
  only, deliberately: it decodes a node action's completion, and taking a newer
  gate command there would skip the action's applied completion and buy the
  action again.
- 2026-09-23 — **the boundary re-reads its command under lock** (adversarial
  review). The sweep classifies outside any transaction, and two writers can
  land before D3 writes: a host-span reader settling the turn, and the owner
  applying it. Neither guard refused them. A freshly settled command still has
  `completion_applied_at IS NULL`, so the CAS stamped it `applied` and the
  readable result was discarded. A gate's close admits the action's
  completion, so an applied gate — read as "already discharged" — was crashed
  and Recover would buy the action again. `applyTurnLostBoundary` now locks the
  command row LAST in its transaction (after the domain writes, as the owner
  application does; the run row comes FIRST — see the 2026-09-24 amendment) and
  re-classifies it with the D1
  derivation, without a probe. The crash proceeds only when that class still
  justifies its reason: `turn-lost` ← `turn_lost` or an unchanged
  `pending_ingest` (what a probe-proved lost turn reads without its probe);
  `stream-lost` ← an unchanged `pending_ingest`; `owner-poisoned` ←
  `quarantined` or `poisoned`. Anything else rolls the transaction back
  (`lost-cas`, guard `command`, the observed class logged), and the next tick
  classifies the new state. This narrows D3's "already `applied` or
  `superseded` is discharged" refinement to the one shape that reaches it
  legitimately — a quarantine stamped after application.
- 2026-09-24 — **the boundary takes the run lock first, and the stream-lost
  offer never throws.** Both could throw out of the sweep, and one candidate's
  throw rejects the whole pass (`runWithConcurrency` is a `Promise.all`), so
  every other candidate waited a tick. (1) The owner's apply locks run →
  assignment → session → attempt → gate evaluation (`lockFlowPromptOwner`);
  the boundary took the attempt (and a gate's evaluation) first and reached the
  run only inside the crash. Racing on the same lost turn — the sweep's
  boundary and the owner's own lost-turn arm — the two deadlocked, and the
  aborted boundary threw `40P01`, not a `TurnLostCasLost`. The boundary now
  locks the run row FOR UPDATE as its first statement, so the two queue on one
  row; the node path had the same inversion and gets the same fix
  (`turn-lost-boundary.integration.test.ts`, the run-lock-first cases, which a
  second connection replaying the owner's order deadlocked before). (2)
