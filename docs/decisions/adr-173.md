# ADR-173: User notification subscriptions and web push over the widened outbound-webhook engine

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-10
**Status:** Accepted

**Context:** A visibility layer that only works while a tab is open is half a
product: the reader still has to remember to look. Reaching them when a decision
starts waiting needs a delivery path.

MAIster already has one, and it is run-shaped. The ADR-077 outbound-webhook engine
owns a transactional outbox, a singleton drainer, HMAC signing, a retry curve and
a delivery ledger — all of it keyed to a project and a run:

- `webhook_events.project_id` and `.run_id` are both `NOT NULL`, and
  `emitWebhookEvent` (`web/lib/webhooks/outbox.ts`) requires both as
  non-optional `string`s.
- `webhook_subscriptions` has **no user axis** at all. Its `project_id` *is*
  already nullable, where `NULL` means "platform-wide".

A per-user `attention.digest` has no run and no project. So the choice is: a
second outbox for user-scoped events, or widen the one that exists.

**Decision:** Widen the ADR-077 engine. **No second outbox, no second drainer, no
second retry curve.** Add a user axis to subscriptions, make the event's project
and run optional, and deliver over both `web_push` and the existing `webhook`
transport.

**D1 — Three migrations, and the widening gets its own number.** `0163` adds
`push_subscriptions` and `notification_subscriptions`. `0164` widens
`webhook_events.run_id` and `.project_id` to nullable and adds
`webhook_subscriptions.owner_user_id`. The widening is **never folded into
0163**: it is a cross-cutting change to a shipped, live table with existing rows,
and it must be revertable and reviewable on its own. It widens; it drops nothing.

**D2 — A column going nullable is a new-value fan-out, so every reader is
enumerated.** This is the real cost of "no second outbox", and it is paid
explicitly rather than discovered in production. Each of these reads
`project_id`/`run_id` today and must be shown a project-less, run-less event:
`emitWebhookEvent`, `subscriptionMatches` (`web/lib/webhooks/match.ts`),
`replay.ts`, `send.ts`, `ping.ts`, the deliveries UI, and the drainer's
fanout / drain / prune passes
(`web/lib/scheduler/handlers/webhook-delivery.ts`). A reader that structurally
cannot see a NULL row is the defect shape this enumeration hunts.

**D3 — `subscriptionMatches` is wrong the moment the column is nullable, and
fixing it is the point of this ADR.** It computes today:

```ts
const scopeOk = sub.projectId === null || sub.projectId === event.projectId;
```

`sub.projectId === null` means "platform-wide, matches every project". Once
`event.projectId` can also be `null`, that first disjunct makes **every
platform-wide subscription match every user event** — a reader who subscribed to
platform-wide run activity would start receiving other people's personal
attention notifications. Scope therefore becomes two axes that are matched
independently, not one nullable field:

- A **project-scoped** event matches project-scoped and platform-wide
  subscriptions, and **never** a user subscription.
- A **user-scoped** event matches only the subscription owned by that user, and
  **never** a platform-wide one.

Both directions are contractual, and both are tested. Getting only one direction
right is the failure mode that leaks.

**D4 — The wire envelope does not change.** `WebhookEnvelopePayload`
(`web/lib/webhooks/taxonomy.ts`) already types `project: WebhookProjectRef | null`
and `run: WebhookRunRef | null`. Existing consumers are already obliged to handle
both as null, so a user-scoped event is a shape they were built for. No
`apiVersion` bump, no envelope migration.

**D5 — The event source is one new `domain_events` consumer, and no new clock.**
`attention.decision_opened | decision_closed | decisions_changed | digest` are
emitted by a single entry appended to `DOMAIN_EVENT_CONSUMERS`
(`web/lib/domain-events/consumers.ts`) plus its cursor row — which is exactly
what ADR-086 promised a consumer would cost. Its `handle` is idempotent, because
domain-event dispatch is at-least-once: a redelivery must converge to one
notification, not a second buzz.

**D6 — Triggers are deltas and digests only.** A notification fires on a change
in the `decisions` count and on the scheduled digest. **Never per event, and
never by default.** A per-event stream is the anti-pattern that trains a reader
to mute the channel within a week, at which point the whole delivery path is
dead weight. The digest payload is the deterministic sentence from the digest
read model — same clock and same rows produce byte-identical output, which is
what makes it safe to send twice.

**D7 — The sender is a two-phase commit against a DB row plus a downstream HTTP
call.** Intent is persisted **before** the send; the idempotency marker
(`delivered_at`) is stamped **after** it succeeds. Each failure class is
classified explicitly as retryable or terminal: a push `410 Gone` is terminal and
**deletes the subscription**, since the endpoint is permanently invalid; other
failures follow the existing backoff curve. This is how `webhook_deliveries`
already behaves — the obligation here is not to regress it.

**D8 — Secrets are `env:` references only.** Signing material follows
`webhook_subscriptions.signing_secret_ref`: an `env:NAME` reference resolved
server-side, never a plaintext secret in a column, a log line, or a payload.

**D9 — Ownership comes from the authenticated context, never the request body.** A
personal token may CRUD only its own owner's subscriptions; an unknown id answers
`404` rather than `403`, so the API does not confirm the existence of another
user's rows.

**D10 — The two new scopes are withheld from agents.** `decisions:read` and
`notifications:subscriptions` are absent from `AGENT_TOKEN_SCOPES` and from
`CROSS_PROJECT_AGENT_SCOPES`. An agent has no business reading a human's decision
queue or editing where that human gets notified, and the omission is asserted
rather than assumed.

**D11 — Missing VAPID configuration degrades, never crashes.** With the VAPID
variables unset the app boots and reports "push unavailable" with a clear log
line. Web push is an optional capability of a self-hosted deployment; a missing
optional key must not take the web process down.

**Amendments:**

- **2026-09-11 (implementation).** Four notes; none reverses a decision.
  1. **`0164` widens `webhook_deliveries` as well.** D7 stamps `delivered_at`,
     which is a `webhook_deliveries` column, but that table's `subscription_id`
     was `NOT NULL` to `webhook_subscriptions` — and a push endpoint has neither
     an HTTP subscription nor an HMAC secret, so there was nowhere to record a
     push attempt. The same migration therefore makes `subscription_id`
     nullable, adds `push_subscription_id` (FK to `push_subscriptions`,
     `ON DELETE CASCADE`) and enforces `webhook_deliveries_one_target`:
     `(subscription_id IS NULL) <> (push_subscription_id IS NULL)`. This keeps
     D1's promise literally — one outbox, one drainer, one retry curve, one
     ledger — and makes `NTF-05`'s deletion cascade the attempts away with the
     endpoint rather than leaving them dangling. It still widens only.
  2. **D2's enumeration found the bug it was written to find, one layer above
     `subscriptionMatches`.** `web/lib/webhooks/subscriptions.ts` expressed
     "platform-wide" as `project_id IS NULL`, and a user subscription is also
     `project_id IS NULL` — so the admin settings surface began listing, reading,
     deleting and exposing the deliveries of other people's PERSONAL
     subscriptions. "Platform" now means
     `project_id IS NULL AND owner_user_id IS NULL` at all four call sites. This
     is D3's reasoning applied to the scope PREDICATE rather than to the match
     predicate, and it is the most valuable thing the enumeration produced.
  3. **The digest trigger rides `system_sweep`.** A new
     `scheduler_jobs.job_kind` would be a migration, for a pass whose cadence is
     bounded by the digest WINDOW rather than by the tick. The delta trigger is
     the domain-event consumer D5 specifies; there is no third trigger.
     Separately, the trigger injects the UNCACHED `computeDecisionsQueue` into
     `getNowTileCounts`: the React-`cache`d default is correct in a render (the
     Desk's tiles and its Decisions region must be one computation, `ATN-05`) but
     has no request to scope it inside a long-lived sweep.
  4. **D8's deployment wiring lands in `.env.example` and
     `docs/configuration.md` only.** The plan asked additionally for the `web`
     service `environment:` block of three compose files; no such block exists —
     ADR-023 runs web on the host, so `compose.yml` and
     `compose.production.yml` define only `postgres`. This follows the
     `MAISTER_WEBHOOK_*` precedent, which those same docs already mark
     "never `compose.yml`".
- **2026-09-11 (renumber, Phase 8).** The three migrations landed one index
  higher than D1 names them: `0163` `user_activity_cursors` (emitted a phase
  early, in Phase 4), `0164` `push_subscriptions` +
  `notification_subscriptions`, `0165` the widening. While this branch sat
  unmerged across nine phases, `master` took `0162` for `event_skip_ledger`, so
  every index above it shifted by one on the rebase. D1's substance is
  untouched — three migrations, and the widening still holds a number of its
  own, never folded into its predecessor — only the indices moved. Read the
  `0163`/`0164` above as `0164`/`0165`.
- **2026-09-14 (renumber, second rebase).** `master` then took `0163` for
  `token_lifecycle_events` and **ADR-168** for post-issuance token mutation, so
  both namespaces shifted again. The FINAL numbers, stated plainly so no reader
  has to chain two amendments: this ADR is **173**; the migrations are **`0164`**
  `user_activity_cursors`, **`0165`** `push_subscriptions` +
  `notification_subscriptions`, **`0166`** the widening. Their journal `when`
  values were re-stamped above `0163_token_lifecycle_events`'s, because Drizzle's
  incremental migrator compares `when` against the ledger high-water mark and
  SILENTLY SKIPS anything at or below it — a database that had already run
  master's `0163` would otherwise never apply these three. D1's substance is
  still untouched.

**Consequences:**

- One outbox, one drainer, one retry curve, one delivery ledger — and one
  nullable-column fan-out to pay for it, enumerated in D2.
- `subscriptionMatches` gains a second scope axis. It is the highest-risk edit in
  this milestone and the most heavily tested.
- Migration 0164 touches a live shipped table. It widens only, so a rollback is a
  schema question rather than a data-loss question.
- Delivery is opt-in per user, so the default deployment behaves exactly as it
  does today.
- The digest's determinism (D6) becomes load-bearing twice: once for the UI
  sentence, once as an at-least-once-safe notification payload.

**Alternatives Considered:**

- **A second, user-scoped outbox and drainer.** Rejected: two engines drift, and
  the second one gets the less-tested retry curve. The nullable fan-out is a
  bounded, enumerable cost; a duplicate engine is an unbounded ongoing one.
- **Keep `project_id` NOT NULL and store a sentinel project.** Rejected: a
  sentinel row that every query must remember to exclude is worse than a NULL the
  type system forces every reader to handle.
- **Add `user_id` to `webhook_events` and match on it in the existing single
  disjunct.** Rejected: it is D3's bug with an extra column — one scope expression
  covering two independent axes.
- **Email instead of web push.** Rejected for this milestone: it needs an SMTP
  dependency, a deliverability story and a template system, none of which the
  self-hosted target has today.
- **Per-event notifications with client-side muting.** Rejected per D6.
