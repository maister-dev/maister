# ADR-170: Derived work-stage vocabulary distinct from the board columns

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-10
**Status:** Accepted

**Context:** MAIster already carries three overlapping "stage" vocabularies, and a
cross-project work surface needs a fourth answer — *where is this piece of work* —
that none of them gives.

| Existing | Meaning | Where |
| --- | --- | --- |
| `tasks.stage` column | `"Backlog" \| "Prepare"` — the pre-launch spec phase | `web/lib/db/schema.ts:1406` |
| `TaskStage` type | a type alias of that column | `web/lib/board.ts:56` |
| `deriveStage() -> BoardColumn` | the seven derived board **columns** | `web/lib/board.ts:83` |
| `StageChip {label, type}` | the inbox card's **node** chip | `web/lib/queries/hitl-stage.ts:14` |

`BoardColumn` is the closest fit and is still wrong for the job: it is a
**per-project Kanban lane**, tuned for a board that shows one project's tasks in
seven columns. A cross-project work table needs a status a reader can compare
across projects and against work that has never launched a run — `Triage`, `Held`,
`Ready` are not board columns, and the board deliberately collapses
`Failed`/`Abandoned` into `Backlog` because its job is "can I relaunch this",
not "what happened".

Renaming any of the four is out of the question: `tasks.stage` is a persisted
column, `deriveStage` drives the board, and `StageChip` is on the inbox card.

**Decision:** Add a fourth, deliberately separate vocabulary — **`WorkStage`**,
produced by **`deriveWorkStage`** in `web/lib/work/stage.ts`. Nothing above is
renamed, moved, or re-pointed.

**D1 — The classifier is pure and total.** `deriveWorkStage(input)` takes
`{ taskStatus, taskStage, triageStatus, runStatus, runKind, promotionState,
workspaceRemoved, blockingRelationCount, progress }` and returns
`{ stage, blocked, progress, promotedKind }`. It performs no IO: no database
handle, no clock, no `server-only` import. The run-status axis is an exhaustive
`satisfies Record<RunStatusValue, …>` map over
[`web/lib/runs/run-status-values.ts`](../../web/lib/runs/run-status-values.ts), so
adding a twelfth run status is a **compile error** at this map rather than a
silently mis-rendered row.

**D2 — The full mapping, normatively.** `RUN_STATUS_VALUES` has **eleven**
members. Every one is mapped:

| Run state | `WorkStage` | Why |
| --- | --- | --- |
| `Pending` | `Queued` | above the concurrency cap; the queue-position badge already exists |
| `Running` | `Executing` (k/N) | k/N comes from the batched node-attempt spine |
| `NeedsInput` | `WaitingOnHuman` | |
| `NeedsInputIdle` | `WaitingOnHuman` | idle is a checkpoint, not a different stage |
| `HumanWorking` | `WaitingOnHuman` | covers the ADR-030 takeover and the ADR-160 rework claim |
| `WaitingOnChildren` | `Executing` | a parked orchestrator is still executing; the board already buckets it in `InProduction` (`web/lib/board.ts:80`) |
| `Review` | `Review` | |
| `Crashed` | `Crashed` | owes recover/discard |
| `Done` + `promotion_state='done'` | `Promoted` (`promotedKind:"merge"`) | |
| `Done` + `promotion_state='none'` | `Promoted` (`promotedKind:"result"`) | ADR-165 result-only completion never promotes — there is no branch. Rendering it `Executing` or `Review` would be a lie |
| `Abandoned` | `Abandoned` | |
| `Failed` | `Ready` | the root operating contract returns a `Failed`/`Abandoned` task to Backlog and Launch reappears; `Crashed` is the documented exception |
| *no run* + `triage_status IS NULL` | `Triage` | |
| *no run* + `triage_status='flagged'` | `Held` | |
| *no run* + `triage_status='triaged'` | `Ready` | |

**D3 — `promotedKind` is total over `promotion_state`, which has five values, not
two.** `runs.promotion_state` is an untyped `text` column whose value domain is
`none | claiming | done | failed | reopened`. Only `done` and `none` are reachable
together with a `Done` run — `claiming` is transient inside the promotion claim,
and `failed`/`reopened` leave the run in `Review` — but a classifier that is total
by construction may not depend on that reachability argument. `promotedKind` is
therefore derived as `promotionState === "none" ? "result" : "merge"`: exact for
the two reachable pairs, and defensible for the three that are not, since any
non-`none` promotion state means a promotion path was engaged. No five-way branch,
no unreachable-case `throw`.

**D4 — `blocked` is an attribute, never a stage.** A task held by a blocking
relation still has a real stage — usually `Ready`. `blocked` rides beside `stage`
as a boolean, so a filter can ask for either independently and neither counter in
[ADR-169](../decisions.md#adr-169-two-canonical-attention-counters-decisions-and-updates)
can mistake a blocked task for one that needs a human.

**D5 — `Intake` and `Delivered` are not members yet.** Both were proposed as
reserved values. They are omitted instead: a member nothing can produce is dead
vocabulary that reads as a UI gap and invites a renderer for a state that cannot
occur. `Delivered` arrives with the delivery-report work (brief C2) and `Intake`
with PO intake (brief C3); the exhaustive `satisfies` map of D1 makes each a
one-line, compile-checked widening at that point — which is the safety "reserved"
was reaching for.

**D6 — No `WorkStage` value is ever persisted.** There is no column, no enum, no
migration. It is computed per read, from rows that already exist. A persisted copy
would be a cache with no invalidation owner and would drift from `runs.status` the
first time a status moved without the work table being read.

**Consequences:**

- Four "stage" vocabularies now coexist. This ADR is the map between them; a fifth
  needs a very good reason.
- The work table, the inbox card and the board flight card render a `WorkStage`
  chip **beside** the node `StageChip` rather than replacing it — they answer
  different questions ("where is this task" vs "which node is asking").
- A twelfth run status breaks the build at one map instead of degrading three
  surfaces at runtime. That is the intended cost of the exhaustive `satisfies`.
- `Failed -> Ready` means the work table shows a failed run's task as relaunchable
  rather than as a failure. The failure stays visible in the run history and the
  activity feed; the work table's column is about what to do next.

**Alternatives Considered:**

- **Reuse `BoardColumn`.** Rejected: it has no pre-launch vocabulary
  (`Triage`/`Held`/`Ready`), it collapses `Failed`/`Abandoned` into `Backlog`, and
  widening it would change the board — a surface this milestone is not touching.
- **Persist a `work_stage` column, maintained by triggers or the run writer.**
  Rejected per D6: a denormalized copy with no single invalidation owner, for a
  value that is cheap to derive.
- **Rename `deriveStage` to `deriveBoardColumn` to free the name.** Rejected: a
  repo-wide rename of a working function to improve one new function's name, in a
  milestone that touches neither the board nor the task state machine.
- **Reserve `Intake` and `Delivered` now.** Rejected per D5.
