# ADR-194: Operational agents with frozen completion contracts

[Back to ADR index](../decisions.md#adr-194-operational-agents-with-frozen-completion-contracts)

**Date:** 2026-10-29
**Status:** Accepted

**Context:** GitHub intake needs normal shell or external MCP access, but the
standalone agent finalizer interprets an allocated worktree as a code deliverable.
It records Review even when an operation failed and no source change was intended.
Workspace access cannot determine business outcome or delivery policy.

**Decision:** Introduce a defaulted `code_delivery` versus `operational` definition
kind, independently of execution mode, workspace access and permission policy.
Operational standalone sessions require the built-in versioned `operational_v1`
result contract. Launch freezes kind, schema, semantic-validator version and
package provenance. Existing definitions and historical runs retain their behavior.

The platform validates structured reported results and source integrity before
committing its effective terminal decision. Success becomes Done without promotion;
partial, blocked, failed or invalid results become Failed. Cancellation remains
Abandoned and lost execution remains Crashed. Validated failure diagnostics remain
readable without being represented as successful collected answers.

Terminal decision metadata and cleanup intent commit with result, status and
events. Disposal preserves unexpected bytes locally before deletion and does not
shorten evidence retention. All cleaners respect the same intent, including
rowless directories. Normal HITL, tool permissions, isolation and admission caps
remain authoritative. Kind never grants permission or automatic approval.

Implementation is **Implemented** with owning integration tests and EN/RU browser
acceptance. Qualification and release evidence remain local; no deployment is implied.
The normative contracts are [definitions](../system-analytics/operational-agents.md),
[results](../system-analytics/operational-agent-results.md) and
[lifecycle](../system-analytics/operational-agent-lifecycle.md).

**Consequences:** The additive schema records immutable launch/terminal facts and
per-reader attention acknowledgements. Engine compatibility must also cover
agent-only packages. Release the platform before the new core package. Drain old
writers during upgrade; older binaries must not finalize or clean operational runs.

**Alternatives Considered:** Agent-ID special cases, empty-diff auto-promotion,
prose/exit-code success inference, and hiding Review rows do not enforce the
operation's contract. New run statuses are unnecessary. Replacing the existing
result/event/lifecycle ledgers would duplicate durable state.

**Checks:** [Traceability](../system-analytics/operational-agents-traceability.md)
maps all requirements and edges to owning implementation tasks and primary tests.
