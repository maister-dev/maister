# ADR-193: Rootless Linux namespace isolation for production test fixtures

[Back to ADR index](../decisions.md#adr-193-rootless-linux-namespace-isolation-for-production-test-fixtures)

**Date:** 2026-10-03
**Status:** Accepted

**Context:** The production isolation harness has a Darwin `sandbox-exec`
driver and Linux process inspection, but no Linux filesystem isolation driver.
The hosted Intel lane timed out without a complete report; successful Darwin
ARM64 evidence does not qualify Linux or hosted Intel. The web must access
application code, its workspace, HTTP and Postgres while supervisor-private
storage remains inaccessible to it and its descendants.

**Decision:** Add one rootless Bubblewrap driver with fresh mount, user and PID
namespaces, a private proc mount, the existing host UID and host networking.
Explicit read-only and writable binds define its filesystem view. Never bind
the host root; supervisor-private storage, the invocation ledger, credentials
and control sockets remain outside. The immutable policy validates canonical
paths, overlaps, source identities, nested mounts and known protected inodes.
The trusted fixture must never export private inodes or descriptors into
allowed material. This is a filesystem boundary, not network isolation.

A trusted outer Node launcher retains host process inspection and the existing
parent watchdog. A small namespace child bridge reports actual application
exit code and signal, avoiding Bubblewrap's shell-status ambiguity. The bridge
has no host inspection or signaling authority. The outer launcher forwards
verified graceful signals while retaining the namespace reaper; namespace
death contains all descendants, including detached process groups. Identity
checks remain UID/PID/start-time/exact invocation tag based. Failed capability,
policy or inspection checks refuse launch or signal explicitly; no unisolated
fallback exists.

The complete contracts and their named controls are owned by
[test infrastructure](../system-analytics/test-infrastructure.md#linux-production-fixture-isolation-designed).
Implementation and local/hosted qualification are **Designed** until their
recorded gates pass. Acceptance of this decision does not amend the existing
macOS-specific hosted gate. A prospective hosting-contract amendment and CI
change require complete local Ubuntu 24.04 amd64 qualification at Node
24.15.0 and 24.19.0 first. Hosted acceptance then requires the exact owner-pushed
SHA, complete reports, fixed budget and zero leaks.

**Consequences:**

- Requires an authenticated distro Bubblewrap package supporting all required
  options, permitted unprivileged namespaces, applicable AppArmor policy and
  readable host proc identities; Linux labeling alone proves none of them.
- Adds a launcher/status protocol to preserve process ownership and drain
  semantics across private proc. Access probes use the same policy and lifecycle.
- Retains the Darwin driver and its separate regression evidence.
- Adds no product HTTP/event/error contract, database migration, configuration
  DSL or production deployment change. Browser lifecycle and separate-user
  deployment remain separate deliverables.
- Linux speed remains an empirical question. A failed boundary or budget gate
  keeps hosting unqualified and preserves the prior CI recipe.

**Alternatives Considered:**

- Distinct UID and private 0700 roots: kernel DAC is useful, but the current
  runner cannot inspect or signal a different UID. Account/group provisioning,
  workspace grants and a privileged exact-identity broker broaden this task.
  Evaluate it in separate-user production deployment.
- Host-root read-only bind plus masks: aliases, host proc and inherited private
  descriptors undermine the intended boundary.
- Privileged namespaces or silent ordinary exec: violate the harness authority
  and fail-closed contracts.

**Checks:** The owning Linux controls, I1–I4, O-identity, separate I-CI preflight,
complete platform manifest validation, enforcement falsification and exact-SHA
hosted gate enforce the decision; their requirements and phase dependencies
are specified in the [implementation plan](../../.ai-factory/plans/s53a-linux-isolation.md).

**Amendments:**

- 2026-10-03 — Startup registration includes a one-purpose trusted Node preload
  acknowledgement before application main. It closes its temporary descriptor
  before releasing main, preserving exact host identity for fast access probes
  without exporting a host broker or extra descriptor to application code.
- 2026-10-03 — The trusted inner status bridge also requires process-inspection
  separation from its application descendants: restrictive existing Yama
  policy and disabled SIGUSR1 debugger activation, with real pidfd/ptrace and
  status-socket controls. Missing capability refuses; provisioning never
  changes a host-wide ptrace sysctl. This remains Designed until qualified.
