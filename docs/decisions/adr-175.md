# ADR-175: Operator Recover of a crashed agent node re-enters the flow graph

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-18
**Status:** Accepted

**Context:** [ADR-034](adr-034.md) gave Recover a hybrid shape: a session-less
node is re-dispatched through the flow graph, an agent node continues its prior
ACP session. The second half stopped working once owned prompts became
generation-fenced, and it stopped working **silently**.

`crashRunningRun` releases the run's assignment and touches no `node_attempts`
row, so the crashed attempt stays open, `Running`, bound to the **retired**
epoch. Phase 1 of Recover mints epoch N+1 beside it. The agent arm then called
`createSession({resumeSessionId})` and handed the session to
`scheduleResumedSessionDrive` — the NeedsInput *permission* driver. That driver
takes its `runFlow` shortcut only when a pending permission resume or a durable
flow session exists, and both predicates require
`execution_assignment_id = runs.execution_assignment_id`, which a crashed attempt
cannot satisfy. So it issued a node prompt directly, and `admitNodePrompt`
refused it with `PromptOwnerInvariantError("node_admission_generation")` because
the attempt's assignment is not the current one.

The driver classifies that refusal as a **yield** — `yielded = true`, and
`if (yielded) return;` precedes every terminal decision and the
`finally { deleteSession }` cleanup. The run is left `Running` with a fresh,
**idle** session nobody drives. The reconcile sweep then either re-attaches it
with a bare `runFlow(runId)` — which the already-owned graph guard no-ops — or,
past the grace window, crashes it again as `agent-session-gone`. Every operator
click reproduced the loop. The only exit was Discard.

The eligibility contract already described the fix as existing:
`execution-prompt-lifecycle.md` lists the `Crashed` row as
`H until explicit recovery claim`. The claim it names had no implementation for a
crashed agent node. That is the defect, and it is exactly the "missing variant"
risk K04 of the A/B stabilization plan warned would block S2.

**Decision:** The agent arm takes **the same door the `redispatch` arm already
takes** — `runFlow(runId, { crashResume: { targetStepId }, db, executionHosts })`.
No new driver, no new run status, no new prompt-owner variant, no new
`action_resume` kind, and **no migration**.

Five properties make that a fix rather than a re-route:

1. **The fence is satisfied by construction, never relaxed.** For a crashed
   attempt `resumingThisNode` is false, so the graph appends a **fresh**
   `node_attempts` row stamped with the new epoch and `applyCreateAck` re-binds
   it. `admitNodePrompt` passes without any guard being widened, and because the
   prompt's logical operation key is
   `flow_node_attempt:<variant>:<attemptId>:<ordinal>`, a fresh attempt id also
   makes `command_invariant_conflict` impossible.

2. **The retained handle rides the existing ADR-081 session policy**, which
   resolves from the **node's own** attempt row. That answers the session-identity
   hazard structurally: for a crashed run every incarnation is terminal, so
   `loadActiveRunSession`'s liveness key ties false and a finished `gate-*` or
   `*-verify-*` substep — always bound later, since `run_sessions.updated_at` is
   bumped only by the create ack — would otherwise win. A substep row is not an
   attempt row for this node and can never be selected. An absent or refused
   handle already degrades observably via `session_fallback`.

3. **Evidence comes before dispatch.** The crashed attempt's last
   `session.prompt` is reconciled first, outside every transaction. Agreeing
   terminal evidence the owner never applied is applied through the existing
   owner path — re-binding that attempt's `execution_assignment_id` to the new
   epoch inside the application transaction, which keeps `staleSessionBinding`
   meaning what it says — and the graph continues with **no second paid turn**. A
   quarantined disagreement is never converted into a re-prompt.

4. **Provenance rides `node_attempts.decision = 'crash_recover'`.** The column is
   unconstrained `text`, so no migration is needed; the precedent values
   `review_rework_claim` and `operator_interrupt` ship the same way. The
   alternative — a fifth `action_resume` kind — would have required a migration,
   because `node_attempts_action_resume_check` whitelists exactly four.

5. **The durable authorization is unchanged.** Phase 1's single transaction
   (scheduler lock → `FOR UPDATE` → CAS `Crashed → Running|Pending` writing
   `resume_started_at` and `current_step_id` → `mintPlacement(reason:"recover")`)
   already commits before any host call. Its `resume_started_at` marker is both
   the single-winner claim the graph CAS-clears and the recovery predicate a
   reconcile sweep uses to re-enter after a web death — with no second operator
   click.

**The attempt shape is a fresh row, and the deciding argument is the cost
ledger.** Reusing the crashed row with a bumped prompt ordinal would have read
more naturally — one visit, no accounting carve-out. It was rejected because
`node_attempt_cost_rollups` is `UNIQUE(node_attempt_id, model)`: the pre-crash
turn and the post-recover turn would upsert into the **same row** and become
permanently indistinguishable. Two ACP turns were paid for; the ledger must show
two. That loss would be silent and unrecoverable after the fact, which is the
worst property a defect can have. Three secondary arguments agree: a fresh row
closes the stale open attempt `crashRunningRun` leaves behind, it avoids opening
the `staleSessionBinding` guard on the dispatch path, and it is what the docs
already promised ("re-running it once as a fresh attempt").

Because the attempt counter advances, `crash_recover` is carved out of
`rework.maxLoops` and out of **both** Observatory correction counters — moving
only one leaves the metric inflated. It is deliberately **not** added to the
`MAISTER_MAX_OPERATOR_RESTARTS` budget: a crash is not an operator action, and a
blanket "add it everywhere `operator_interrupt` appears" sweep would let crashes
consume an operator's restart allowance.

Three consequences of the same reasoning ship with it:

- **`judge` joins the classifier's agent set.** It runs an ACP session and
  `admitNodePrompt` already accepts it; only `classifyRecover` disagreed. This is
  an observable behavior change — a crashed `judge` with `retry_safe: false`
  previously answered `409 discard-only` and now resumes. The reconcile **sweep**
  still classifies a session-less `judge` as `gate-redispatch`, deliberately: the
  sweep acts with no operator decision and may never resume a mid-turn agent
  implicitly.
- **A crashed orchestrator branches on its children** through the existing
  settled-children predicate. Children unsettled → it is handed back to its
  existing wait gate rather than re-prompted (re-prompting would re-delegate
  children that are still running); all settled → it re-enters through
  `orchestratorResume`, which reuses the parked `NeedsInput` attempt and threads
  the coordinator's own handle; none ever created → the ordinary crash-resume
  path. `crashResume` and `orchestratorResume` are mutually exclusive by
  construction.
- **The success body's `runStatus` reports the committed row.** It was derived
  from the result state, which the orchestrator wait arm would have turned into a
  lie (`resumed` + `Running` for a run parked as `WaitingOnChildren`). Reflecting
  the row removes a class of lie instead of enumerating one more case, and keeps
  the `RecoverResult` union at eight arms so both exhaustive switches keep their
  compile-time safety net.

**Consequences:** Recover becomes a real recovery for every agent node kind, and
the loop that forced Discard is gone. The blast radius is the recover path, the
reconcile sweep's `reattach` arm, the scheduler's queued-recover promotion, and
the three provenance consumers — plus four published contract surfaces (internal
OpenAPI, ext OpenAPI, the MCP tool description, the EN/RU catalogs) that all move
in the same commit.

Two things are deliberately left undone. Recover still emits **no** domain event
or webhook on the `Crashed → Running` flip, so no consumer can distinguish a
recovered run from one that never crashed; adding `run.recovered` is a six-file
change plus a `domain_events_kind_check` migration and is out of scope. And a
crash-recover re-entry carries **no per-run bound** — it is bounded only by the
grace window and `crashRunningRun`, which is safe today because each re-entry
needs an explicit operator or token decision. It becomes a defect the moment
crash-recover is automated; recorded here rather than pre-empted with an env var
nobody has a number for.
