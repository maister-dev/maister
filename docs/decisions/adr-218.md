# ADR-218: Shared human-facing task status

> Part of the ADR log. See the [index and editing rules](../decisions.md).

**Date:** 2026-11-23
**Status:** Accepted

**Context.** Board, task detail, Work, Desk, Inbox and the external API read
the same tasks through different workflow models. A task can acquire a
different visible status as the reader moves between these surfaces.

**Decisions**

1. Use one read-time resolver and presentation catalog. The
   [task status contract](../system-analytics/tasks.md#human-facing-task-status-designed)
   defines precedence. Terminal task state wins, followed by the latest
   relevant Flow state, then the pre-execution rules. This supersedes the
   visible task-status clauses of
   [ADR-170](../decisions.md#adr-170-derived-work-stage-vocabulary-distinct-from-the-board-columns).
   Its workflow stages, raw API stage, action grouping and progress remain
   available to existing consumers. Task and run writes retain their current
   transition and admission rules.
2. Group Board cards by the shared key. Incoming membership remains under
   `incomingWorkPredicate()`. The Incoming tab displays the full authorized
   count, and its members are excluded from ordinary columns.
3. Expose an additive display object with the stable key, English label and
   semantic tone on authorized external task reads. Retain raw fields and
   existing grants. Only decisions with an authorized task reference
   carry a task status.

**Trade-offs.** A persisted status would require coordinated writes across
task, qualification, run and blocker lifecycles. Local presentation adapters
would let precedence drift again. An Incoming lane would duplicate the
separate tab's job. MCP client inference would require clients to duplicate
the rules and widen access to internal task facts. A shared read projection
adds bounded query work and keeps inference under server authority.
