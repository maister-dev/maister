# ADR-207: Task completion after a confirmed pull-request merge

> Implementation status is maintained in the [current contract](../system-analytics/tasks.md#completion-after-a-confirmed-merge). The accepted decision below retains its original design-stage wording.

[Back to ADR index](../decisions.md#adr-207-task-completion-after-a-confirmed-pull-request-merge)

**Date:** 2026-11-15
**Status:** Accepted

**Context:** Pull-request delivery finished a Run when the PR was opened, but nothing moved the task to `Done` when the PR merged; operators completed tasks by hand long after merge. As-plan child tasks were marked `Done` on `run.done` without delivery evidence. Run Git panel PRs can merge on the provider before the Run is finalized, so a merge observation alone cannot always complete.

**Decision:** The platform completes a task automatically only from confirmed merge evidence. `pr_state_scan` emits a `run.pr_merged` domain event in its merged-edge transaction; a `taskDeliveryCompletion` consumer evaluates `run.pr_merged` and `run.done` identically under the task lock: silent skip until the newest flow Run's workspace is merged, then complete through the existing completion evidence (`Done` + promotion `done` + `pull_request` + `pr_state='merged'`) when the task is `InFlight`, the merged Run is the newest flow Run and the Run's snapshotted `resolvesTask` is true. Otherwise one deduplicated `delivery_completion_not_applied` activity records the reason. `run.pr_merged` is not an agent trigger and not a run-terminal kind. Generated PR bodies carry `Closes <owner>/<repo>#N` only for a resolving GitHub binding on the project's own GitHub host. As-plan PR-delivered children complete only through this path. `task_complete` stays human-only.

**Consequences:** Statement edits are already refused while a task is not `Backlog`, so no statement-revision check is needed. Local-merge, rebase, result-only and `publish_branch` deliveries keep their current completion behavior. A one-time dry-run-first reconciliation completes InFlight tasks whose newest Run is already merged. Actual issue closure on the provider is not observed here.

**Alternatives Considered:** Completing on `run.done` of PR open (claims unmerged work is done); agent-owned completion (gives agents a human-only power); reading provider state in the consumer (failed reads would need terminal handling); a statement-revision refusal (unreachable for InFlight tasks and refuses every legacy Run).
