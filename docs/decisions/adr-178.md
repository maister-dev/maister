# ADR-178: Observatory overview table, day-aligned period, URL views, and auto-apply filters

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-21
**Status:** Implemented (2026-09-21)

**Context:** Three defects are visible on `/observatory` today.

1. **The first screen is the wrong ledger.** The page opens with the flow-ledger
   summary — three correction tiles plus the node heatmap in a two-column grid
   whose left column stretches to the height of a 360px aside (Autonomy Score,
   Signals, Artifacts). On a window with no flow `node_attempts` the left column
   is three zeros and an empty "Nodes" card while the aside is three empty
   states, so the viewport fills with nothing. Scratch- and agent-heavy projects
   see that permanently.
2. **There is no per-project view.** `getPortfolioObservatory` already computes
   `projects[]` and `flows[]`; neither is rendered. The first questions asked of
   the section — how much did each project launch, where is it now, what came
   out — are not answerable anywhere in it.
3. **The period is one `windowDays` number.** No presets, no custom range, and
   the cost panel ignores it outright: token totals are lifetime, which the label
   admits ("Stored lifetime cost; lookback does not filter token rollups").

The filter form also demands an explicit Apply, and half of its fields (flow,
node, artifact kind, artifact definition) are drill-down keys of the flow ledger
that mean nothing on a portfolio first screen.

The Desk answers "what is true now" with no window (ADR-174 D3). The Observatory
is its windowed counterpart, so the two must share one vocabulary rather than
introduce a third stage naming.

Design record:
[`../plans/2026-09-21-observatory-overview-and-navigation-design.md`](../plans/2026-09-21-observatory-overview-and-navigation-design.md).

**Decision:**

### D1 — Period: whole UTC days, presets plus a custom range

- URL: `windowDays=7|30|90` (preset) **or** `from=YYYY-MM-DD&to=YYYY-MM-DD`
  (custom, both inclusive). When both are present, `from`/`to` wins. Absent →
  `windowDays=30`. Any other `windowDays` value is accepted and clamped to
  `1..365` as today, so every existing drill-down link keeps working.
- Resolution to `[since, until)`: preset `N` → `since = startOfUtcDay(now) −
  (N − 1) days`, `until = startOfUtcDay(now) + 1 day`; custom → `since =
  dateStart(from)`, `until = nextDateStart(to)` — the exact helpers `/runs`
  already uses. A span over 365 days is clamped by moving `since` forward; the
  bar renders the effective values, never the requested ones. `from > to`, or an
  unparsable date, drops the custom range and the preset default applies.
- Every windowed read in the section switches from `now − windowDays` to
  `[since, until)`: correction, autonomy, signals, artifacts, harness and the
  node drill-down (`runs.started_at`); budget (`domain_events.occurred_at`);
  agentization (daily buckets; the cache horizon is `REPO_DELIVERY_WINDOW_DAYS =
  365` and ROLLING — rewritten wholesale on every scan — so the rollup verifies
  CONTIGUOUS bucket coverage of `[since, until)` and reports "insufficient" for
  a range the cache reaches only in part, not merely for one it misses
  entirely); **and cost** (new, D5).
- Why day-aligned: the drill-down target (`/runs`) filters by whole UTC days, so
  a rolling `now − 30d` bound can never yield the same count as the list it links
  to. Day alignment makes "count = list" hold by construction. The only
  observable change versus today is that a preset window starts at 00:00Z of its
  first day rather than at the current time of day.

### D2 — "Work launched": runs by start, tasks by overlap

Runs are events. A run counts in the period when `runs.started_at ∈ [since,
until)`, bucketed by `run_kind` (`flow | scratch | agent`); orchestrator children
count as runs of their own kind.

Tasks are states. A task counts as **in work in the period** when it has at least
one `flow` run whose in-work interval overlaps the period — `started_at < until
AND settled_at > since`, both bounds strict, so a run that settled exactly at
`since` belongs to the previous period rather than to both.

The interval is `[started_at, settled_at)`. A run is **settled when its D3
outcome bucket is one of the settled five** (`runSettledSql`), not by a second
status list: `settled_at = ended_at` for a settled bucket, and the interval is
open otherwise. A promoted run receives a fresh `ended_at` at promotion finalize
(`web/lib/runs/promote.ts`), so for a delivered run `settled_at` is the
promotion time. A settled run carrying no `ended_at` stays OPEN — we cannot
prove when it settled, and claiming it settled before `since` would silently
drop the task from the period.

Asking D3 is what keeps the two axes from disagreeing. A `Review` or `Crashed`
run is in flight — a crashed run owes a recover/discard decision and a Review
run awaits promotion — **until its workspace is removed**, which D3 already
calls `Abandoned` (the board's historical-evidence rule). A separate status list
would have said "Review and Crashed are never settled", so one crashed run
nobody ever discarded would have kept its task in "in work" in every future
window, forever.

The secondary number, **taken into work in the period**, counts tasks whose
earliest flow run started in the period.

The table's empty state therefore asks about BOTH axes. A task whose only flow
run started before `since` and has not settled counts in "in work" while every
run cell reads zero, so a runs-only emptiness test would delete the table that
carries the number this decision adds.

No new column is needed. `tasks.status = 'InFlight'` is written in the same
transaction as the launching run's insert (`web/lib/services/runs.ts`), so
`min(runs.started_at)` per task is the durable "taken into work" moment.

### D3 — One outcome bucket per run, shared by the overview and the ledger

Every run falls into exactly one bucket. The in-flight buckets are
`WORK_IN_FLIGHT_STAGES` by name; the settled buckets refine `WorkStage`'s
`Promoted` / `Abandoned` / `Ready`(Failed) with the PR lifecycle (ADR-140/141):

| Bucket | Rule |
| --- | --- |
| `Queued` | `status = Pending` |
| `Executing` | `status ∈ {Running, WaitingOnChildren}` |
| `WaitingOnHuman` | `status ∈ {NeedsInput, NeedsInputIdle, HumanWorking}` |
| `Review` | `status = Review` and the workspace is not removed |
| `Crashed` | `status = Crashed` and the workspace is not removed |
| `Delivered` | `status = Done` and `workspaces.promotion_state = 'done'` and (`promotion_mode <> 'pull_request'` or `pr_state = 'merged'`) |
| `PrOpen` | `status = Done` and `promotion_state = 'done'` and `promotion_mode = 'pull_request'` and `pr_state ∈ {open, NULL}` |
| `ResultOnly` | `status = Done` and (`promotion_state = 'none'` or no workspace row) — ADR-165 result-only flows, agent runs without a worktree |
| `Failed` | `status = Failed` |
| `Abandoned` | `status = Abandoned`; **or** `Done` + `pull_request` + `pr_state = 'closed'` (closed without merge); **or** `Review` / `Crashed` with `workspaces.removed_at` set (the board's "historical evidence" rule in `deriveStage` / `deriveWorkStage`) |

Workspace columns are read from the run's **latest** `workspaces` row (`ORDER BY
created_at DESC, id ASC LIMIT 1`) — `workspaces.run_id` is not unique and the
`/runs` ledger already selects the branch this way, so both surfaces read the
same row.

`Done` is not expected to coexist with `promotion_state ∈ {claiming, failed,
reopened}` (a finalize failure leaves the run in `Review`; reopen flips it back
to `Review`), so the `Delivered` rule above reads `promotion_state = 'done'`.
Nothing ENFORCES that pairing, though — `workspaces.promotion_state` is a plain
`text NOT NULL DEFAULT 'none'` with no CHECK and no coupling to `runs.status` —
so the SQL does not gate `Delivered` on it: those three combinations fall
through the refinements to the status map and classify as `Delivered`, and the
D3 matrix asserts exactly that. A row nobody expects must land somewhere
explicit rather than vanish from a total.

The classification is **one SQL `CASE` fragment** (`runOutcomeBucketSql`) used by
the overview's `GROUP BY`, the `/runs` ledger's new `bucket` predicate, and —
through `runSettledSql` — the D2 task-overlap rule, so a cell's count, the list
it opens and the task columns beside it cannot disagree — the ADR-169 "one
query, one meaning" principle. A compile-time `satisfies` pins the in-flight bucket names
to `WorkInFlightStage`; an integration matrix over all 11 run statuses ×
promotion / PR / removed-workspace combinations pins the rules. No `WorkStage` or
bucket value is ever persisted (the M51 `STG` rule).

### D4 — Rows: visible projects plus one Platform row

- One row per visible project (`getVisibleProjects`), sorted by name, and a
  totals row.
- **Platform row**: runs with `project_id IS NULL`. Today that is exactly the
  Studio assistant scratch run (ADR-097). Agent runs always carry a project —
  `agent_project_links.project_id` and `agent_schedules.project_id` are NOT NULL
  and `launchAgentRun` requires `projectId` — so "platform runs on their own row"
  is satisfied structurally and stays correct if a project-less agent kind appears
  later. Visible to global `admin` only; rendered only when it holds at least one
  run in the period; task cells empty.
- Project page: the project's own row, then a breakdown — one sub-row per flow
  (`flows.flow_ref_id`) for flow runs, plus `scratch` and `agent` sub-rows.

### D5 — Cost is windowed and gains "By flow"

`getCostSummary` already joins `runs`; it now applies `runs.started_at ∈ [since,
until)` to both rollup tables. The "stored lifetime" caveat disappears; the Cost
view says "for the selected period". A third breakdown card, **By flow**, keys
`run_cost_rollups.flow_id → flows.flow_ref_id`, with `scratch` and `agent`
pseudo-rows for flow-less kinds. Tokens only — USD stays out (an M51 non-goal;
ADR-101 defers pricing).

### D6 — Navigation: four URL views under one filter bar

`view=overview|cost|quality|harness`, default `overview`; default `quality` when
`flowId`, `nodeId`, `artifactKind` or `artifactDefId` is present without `view`,
so pre-existing drill-down links still land where their filters apply. Rendered
with the shared `Tabs` primitive in href mode ([`../screens/components.md`](../screens/components.md));
the project page keeps `ProjectTabs` above it. `Tabs` takes no hooks of its own,
so it adopts its importer's environment — the view tabs render from a Client
Component (they need the in-flight filter patch, D7) and are still real `<Link>`s
that push.

| View | Portfolio | Project |
| --- | --- | --- |
| Overview | overview table with totals and the Platform row; compact cost strip (period total, top models / runners / flows, link to Cost) | overview row plus per-flow breakdown; compact cost strip; Agentization; Run autonomy funnel |
| Cost | token tiles, By model, By runner, **By flow**, By run kind, Budget pressure | same |
| Quality | correction tiles; **per-project quality table** (`projects[]`: flow runs, rework, retries, correction rate, autonomy, wait); node heatmap; Autonomy Score; Signals; Artifacts | correction tiles; **per-flow quality table** (`flows[]`); heatmap; Autonomy Score; Signals; Artifacts; node drill-down |
| Harness | Sensor firing, Control effectiveness, Coverage map | same |

For `runKind ∈ {scratch, agent}` the Quality and Harness views render the existing
not-applicable state as the whole view. The Quality layout drops the fixed 360px
aside: cards flow in a responsive grid with `items-start`, so an empty ledger is
one short empty-state card, not a viewport.

### D7 — Filter bar without Apply

A client component owns the bar. Every change calls `router.replace` with the new
query (`scroll: false`) inside a transition, and the bar shows a busy indicator
(`aria-busy`) until the server component has re-rendered. Controls commit on
`change` (presets, selects, date inputs) and on blur / Enter (free-text flow, node
and artifact fields). Fields per view: period and run kind everywhere; project
(portfolio only, `project=<slug>`); flow and node on Quality and Harness; artifact
kind and definition on Quality. Clearing a field removes its param. This is the
first no-Apply filter bar in the app; other screens receive their own task.

That table is ENFORCED, not merely rendered. `parseObservatorySearchParams`
drops every drill-down param the resolved view does not own, so the applied
`filters` and the rendered `current` are derived from the same ownership rule
and a bookmark, a pasted URL or a stale tab href cannot narrow a read model
through a control the bar never shows. The view default (D6) is still read from
the RAW params, so a pre-view drill-down link still lands on Quality holding its
keys.

Because the bar's `current` is a SERVER prop, it does not change until a
round-trip lands — so each commit composes onto the ones still in flight rather
than rebuilding from the pre-edit state. Without that, a second control touched
before the first response arrives overwrites the first edit, and the discarded
control — uncontrolled, re-keyed on a value that never changed — goes on showing
the choice the page just dropped. The accumulated patch is discarded as soon as
the URL the state represents changes, whether that is our own navigation landing
or the reader following a drill-down link.

**The view tabs read that same patch.** They are `<Link>`s and still PUSH (D6),
but their hrefs are built client-side from `current` PLUS whatever is in flight,
so the two surfaces cannot disagree about what the filters are. A server-built
href is stale by construction: a period preset and a tab are two clicks in one
gesture, and clicking a tab BLURS the focused text field, which commits — so the
commit the click itself causes has to ride along with it. The patch is therefore
held as state rather than only as a ref: a ref keeps the bar right and leaves
the tabs exactly as wrong as before. Ownership lives above both
(`observatory-filter-state.tsx`), and the provider is mandatory — a permissive
default would let a surface that forgot it keep working while silently dropping
every composed edit.

This supersedes the earlier reading, under which a tab click legitimately
stranded an in-flight commit and the not-applied hint was the whole mitigation.
The hint remains, for the navigations the bar does NOT build: Back, and
drill-down links.

### D8 — Drill-down into the ledger

A numeric run cell of the overview links to `/runs` with `project`, `from`, `to`,
`kind` and `bucket`; task cells link to the project board. The ledger gains
`kind=flow|scratch|agent` and `bucket=<D3 name>`, both parsed by
`normalizeRunsListFilters` through the existing `oneOf` guard and both rendered as
selects in its filter form; `bucket` filters through the D3 fragment. The
Observatory writes those param names by CALLING the ledger's own
`filtersToParams` (`web/lib/runs/list-params.ts`), not by re-spelling them.

**A cell's link carries every kind constraint it was counted under** — the bar's
selected `runKind`, the row's own kind, and (in the Runs columns) the column's
kind. The read model applies the selection to every count, so a project row
under `runKind=scratch` holds scratch runs alone and an unkinded link opens all
three. A cell whose constraints name different kinds counts nothing and renders
as a plain number: the Flow column of a `scratch` sub-row is `0` because the row
holds no flow run, and `kind=flow` would open the project's whole flow list
behind it.

**A cell links only when the ledger can reproduce it.** Two row classes cannot
be, and so render as plain numbers:

- a **per-flow sub-row** — the ledger has no flow filter, so the list would hold
  every flow's runs in that bucket;
- the **Platform row** — it counts `project_id IS NULL` runs and the ledger is
  `INNER JOIN projects`, so those runs are unreachable there. A link with no
  `project=` does not narrow to them, it widens to every project's runs.

Giving `/runs` a project-less mode (`project=__platform__` → `project_id IS
NULL` over a `LEFT JOIN projects`) would make the Platform cells linkable and is
on the Phase-2 backlog; it changes the ledger's query shape, param vocabulary
and RBAC surface, so it is not folded in here. A link that opens a different
population is worse than no link: the whole point of D3 is that a cell's count
and its list are the same number.

### Resolved questions (owner, 2026-09-21)

1. Platform row visibility: **global admin only** — project-less runs have no
   membership to scope by.
2. "PR closed without merge" and removed-workspace `Review` / `Crashed` fold into
   **`Abandoned`** by the one explicit rule in D3; five settled columns, no sixth.
3. `from > to` (or an unparsable date) **drops the custom range**; the preset
   default applies and the bar shows the effective period.

**Consequences:**

- Day-aligned windows shift preset lower bounds to 00:00Z of the first day. A
  preset window is therefore up to 24 h wider than the rolling window it replaces,
  and a row seeded at exactly `now − 30d` may move in or out of a 30-day preset.
  Boundary-sensitive fixtures were migrated with the change.
- Cost stops being lifetime. A project whose spend predates the selected period
  now reads zero tokens where it previously read its whole history; the Cost view
  states the period explicitly and `costBreakdown.storedLifetime` is deleted.
- Filter changes are NOT history entries. `router.replace` overwrites the
  current entry, so Back leaves the Observatory rather than stepping through
  earlier filter states. Deep links and refresh still reproduce a page exactly,
  and the view tabs — plain `<Link>`s — do push, so Back does step between
  views. Making filter changes navigable would mean `push`, which D7 rejects.
  A tab therefore pushes ONE entry carrying both the new view and any filter
  edit still in flight, rather than pushing a view and dropping the edit.
- The `/runs` ledger gains two search params (`kind`, `bucket`) and two selects.
  Its `bucket` predicate and the overview's `GROUP BY` share one SQL fragment, so
  a cell count and the list it opens are the same number by construction — for
  every cell that links at all (D8).
- Because D2 now asks D3 what "settled" means, discarding a crashed run's
  workspace also drops its task out of "in work". That is the intended reading —
  the same evidence already moves the run into the `Abandoned` column — but it
  is a behaviour change relative to a status-list rule, and a long-parked
  crashed run leaves the task columns the moment its worktree is GC'd.
- The task-overlap aggregate is deliberately unbounded in time (`min(started_at)`
  must see a task's whole history), so it grows with the scoped projects' total
  flow-run count rather than with the period. An index — or a
  `tasks.first_run_started_at` column — becomes an explicit migration task if
  volume proves the need (ADR-059); it is not one today.
- The Desk digest `tokens` tile opens `/observatory?view=cost` instead of the
  section root, because the section root no longer shows cost.
- e2e headings move under `?view=…`: a spec asserting a Quality or Harness heading
  must carry the view param.
- No migration, no new index, no new HTTP route, no env var, no new dependency and
  no SSE change. An index becomes an explicit migration task only if volume proves
  the need (ADR-059).

**Alternatives Considered:**

- **Keep the rolling `now − windowDays` window.** Rejected: the drill-down target
  filters by whole UTC days, so "count = list" could not hold; the discrepancy
  would be small, silent, and permanent.
- **HeroUI `DateRangePicker` for the custom range.** Rejected: `/runs` already
  uses native `<input type="date">` and the two surfaces must agree on the day
  semantics they present; a second date idiom buys nothing here.
- **A third stage vocabulary for the outcome columns.** Rejected: the in-flight
  names are `WORK_IN_FLIGHT_STAGES` verbatim (ADR-170/172), so the Desk and the
  Observatory read the same words; only the settled half is refined, and only by
  PR lifecycle facts that `WorkStage` deliberately does not carry.
- **Classify buckets in TypeScript and filter the ledger separately.** Rejected:
  two classifiers over the same rows is exactly the drift ADR-169 forbids; the
  `CASE` is generated from `BUCKET_BY_RUN_STATUS` so TS and SQL cannot diverge.
- **A separate `/observatory/overview` list page.** Rejected: it would fork the
  filter state and the period across two routes; a URL view keeps one bar, one
  period and one set of deep links.
- **A portfolio-level agentization headline.** Rejected: ADR-134 keeps
  agentization per project because its denominator is a single target branch.
- **A sixth settled column for "PR closed without merge".** Rejected by the owner:
  a closed-unmerged PR is abandoned work, and a sixth column buys a distinction
  the reader can get from the ledger.

**Amendments:**

- 2026-09-21 — **Review remediation, same branch. Three corrections, one of
  them a behaviour change.**
  1. **D8: the Platform row's cells do not link.** The first cut linked them
     with no `project=` param. `/runs` is `INNER JOIN projects`, so a
     `project_id IS NULL` run is unreachable there and the link opened every
     project's runs instead — the opposite of the count-equals-list guarantee
     the same section states. The Platform row now joins the per-flow sub-row
     as a class whose cells render as plain numbers; a project-less ledger mode
     is on the Phase-2 backlog. Pinned by
     `runs-list.integration.test.ts` ("cannot reach a project-less run") and
     `overview-table.test.ts`.
  2. **D2: "settled" is asked of D3, not of a second status list** — a
     behaviour change. `TASK_IN_WORK_SETTLED_STATUSES` said `Review` and
     `Crashed` are never settled, so a crashed run nobody discarded kept its
     task in "in work" in every future window. D3 already classifies a
     removed-workspace `Review`/`Crashed` run as `Abandoned`; `runSettledSql`
     now drives both axes from that one answer. The overlap bound also
     tightened from `ended_at >= since` to `> since` (a run that settled at the
     boundary was counted in two adjacent periods).
  3. **D3: the `Done` × in-flight-promotion-state cells are asserted, not
     assumed.** Nothing in the schema couples `workspaces.promotion_state` to
     `runs.status`, so "unreachable" was an argument, not a guarantee — and the
     test that claimed to document it compared a local constant with itself.
     The matrix now seeds `claiming` / `failed` / `reopened` beside every status
     and pins what the CASE returns.
