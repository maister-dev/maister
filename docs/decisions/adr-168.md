# ADR-168: Post-issuance mutation of API tokens

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-11
**Status:** Implemented

**Context:** A project token for a real project was issued without
`hitl:respond:human`, `flows:read`, and `runners:read`. Nothing in the product
could add them. The only remedy available was a hand-written
`UPDATE project_tokens SET scopes = … ` against Postgres — an operation with no
authorization gate, no audit trail, and no way to tell afterwards that it
happened.

The first question was whether token-row immutability was a deliberate security
decision that the missing UI merely reflected. It was not. Five pieces of
evidence, taken together, show it is an uncovered scenario rather than a
defended boundary:

1. **[ADR-046](../decisions.md#adr-046) never decided it.** Its threat model is
   that a compromised token "must grant only the addressed project's API, must
   be revocable, and must leave an audit trail". Mutation appears nowhere — not
   in the decision, not in the consequences, not in the four rejected
   alternatives.
2. **The documented state machine describes, it does not forbid.** The token
   lifecycle FSM in `system-analytics/external-operations.md` recorded
   `active → revoked | expired | owner_blocked` because that is what was built.
   No prose forbade a self-transition.
3. **This repository records real invariants adjacently and compulsively** —
   "Do not introduce `fs.watch`", and, three lines from the code in question,
   "The 403 body MUST NOT leak which scopes the token holds". There is no such
   note anywhere near the token row. In this codebase the absence of a
   prohibition is evidence.
4. **The row is already mutated in production.** `bumpTokenLastUsed`
   (`web/lib/tokens/audit.ts`) issues an `UPDATE project_tokens` on every
   authenticated call.
5. **Even `name` — a pure label — was frozen.** No trust model requires
   freezing a human-readable label. That is an unwritten route, not a decision.

**Decision:** Build the missing write path. Two session-auth routes —
`PATCH /api/projects/{slug}/tokens/{tokenId}` and
`PATCH /api/account/tokens/{tokenId}` — mutate a **managed** token's `scopes`,
`expires_at`, and `name`, each change recorded in a new append-only
`token_lifecycle_events` ledger. The full domain contract lives in
[`../system-analytics/token-lifecycle.md`](../system-analytics/token-lifecycle.md).

**D1 — Mutability matrix.** Three columns move; the rest are frozen, each for
its own stated reason rather than by default:

| Column | Mutable | Why |
| --- | --- | --- |
| `scopes` | yes, audited | the originating gap. Widen and narrow. |
| `expires_at` | yes, audited | extend, shorten, clear, or revive an expired token. |
| `name` | yes, audited, guarded | see D3 — not a cosmetic edit. |
| `revoked_at` | **no** — terminal | un-revoking re-arms a repudiated secret. |
| `token_hash`, `prefix` | **no** — out of scope | rotation is a distinct feature with its own unanswered questions (the old secret's fate, an overlap window). Deferred deliberately, not forgotten. |
| `project_id`, `token_kind`, `owner_user_id`, `agent_id` | **no** — identity | moving a token between projects or owners silently rewrites the meaning of every `token_audit_log` row it already wrote. |

Reviving an **expired** token is allowed: expiry is a policy timer, not a
repudiation, and the secret was never disavowed. GitHub and GitLab both permit
extending a personal access token. `revoked_at` IS a repudiation and stays
terminal.

**D2 — One managed-token predicate, two consumers.** A kind-only check
(`token_kind !== 'agent'`) is **wrong**, and finding out why was the sharpest
result of the design pass: `issueOrchestratorRunToken`
(`web/lib/agents/tokens.ts`) inserts `token_kind: "project"` with the name
`orchestrator-run:<runId>` ([ADR-098](../decisions.md#adr-098)). A live
orchestrator credential would have passed a kind-only check and had its scopes
or expiry mutated under a running delegation. It is visible in the project
token table today, because `listTokens` filters on `project_id` alone.

```
isManagedToken(row) =
  row.token_kind !== 'agent'
  && !/^(orchestrator-run|agent-run):/i.test(row.name)
```

One predicate governs **both** editability (a PATCH against a non-managed
token is refused `PRECONDITION` before any write) and ledger membership
(`token_lifecycle_events` holds managed tokens only). Spelling the rule twice
is how the two halves drift apart.

**D3 — `name` is load-bearing; the reserved-prefix guard runs both ways.**
`parseBoundRunId` derives `boundRunId` from the token name via
`^(orchestrator-run|agent-run):(.+)$`, and that `boundRunId` is the
**authorization subject** on the run-bound ext routes
(`/api/v1/ext/runs/{promote,delegate,collect,cancel,rework,message,plan}`),
which are instructed to take the binding from `ctx.actor.boundRunId` and never
from body fields. `actorLabel` (`token:<name>`) also lands in
`token_audit_log.actor_label`, so a rename rewrites future audit attribution.

**No live escalation exists today**, and this record does not overstate one.
Two things make that true, and only two:

1. Run-bound ext routes call `handleExt` with no `slug` and no
   `resolveProjectId`, so a global personal token (`project_id IS NULL`) is
   refused 403 before reaching the binding.
2. Naming a *project-bound* token requires `editSettings` (admin), while
   `promoteRun`'s minimum is `member` — admin ≥ member, so no new authority
   appears.

That is one guard plus a role coincidence. The forging surface exists and is
merely inert: `POST /api/account/tokens` accepts any `name` matching
`z.string().trim().min(1).max(120)`. It goes live the day someone adds
`allowGlobalActorWithoutProject` or a `resolveProjectId` to a run-bound route.
So the reserved prefix is refused with `CONFIG` on the two new PATCH routes
**and on both existing POST routes** — closing it on edit while leaving
issuance open would be incoherent. This is a deliberate widening beyond "add
PATCH", stated rather than smuggled.

The guard is **route/service layer, never a table CHECK**: the machine path
legitimately writes exactly those names, and a CHECK constraint would break
agent launches.

**D4 — Atomicity and the accepted concurrency residual.** One `db.transaction`
per PATCH: the `project_tokens` UPDATE and every implied
`token_lifecycle_events` INSERT commit together or not at all. The UPDATE
carries `isNull(revoked_at)` as a CAS predicate; a zero-row result is
`PRECONDITION`, never a silent success.

Two admins editing the same token is **last-write-wins on field values** —
accepted, not overlooked. There is no `If-Match` header and no version column.
The collision window is two humans editing one token within seconds, and both
edits write ledger rows, so the sequence is reconstructible after the fact.
Optimistic concurrency here would be machinery without a demonstrated need.

**D5 — The 403 disclosure boundary is narrowed, not eroded.** `ext-handler.ts`
carries a hard invariant: the insufficient-scope body must not leak **which
scopes the token holds**. The scope a route *requires* is a different fact — it
is published in `operations.openapi.yaml`, printed in the route source, and
identical for every caller. Disclosing it reveals nothing about any token, and
withholding it is what made the original misconfiguration hard to diagnose. The
403 body gains `details.requiredScope`; the adjacent invariant comment is
amended in place so the next reader cannot mistake the loosening for an
erosion.

**D6 — No synthetic history.** Migration `0163` is purely additive: one
`CREATE TABLE` plus two indexes. Tokens issued before it have no `issued` row,
and none is invented. The trail starts at the migration. A fabricated
provenance row is worse than an absent one, because it cannot be told apart
from a real one.

**Consequences:**

- A misconfigured token is fixed through the product, under the same
  authorization gate that minted it, leaving an audit trail — instead of
  through an ungated, untraceable `UPDATE` against Postgres.
- `token_lifecycle_events` answers "what did this token look like when it was
  created, and who changed it since" for every managed token issued after
  migration `0163`. It does not answer it for older tokens.
- A live orchestrator or agent credential is uneditable by construction, and
  the predicate that makes it so is also what keeps it out of the ledger.
- The reserved-name guard closes a forging surface that is currently inert,
  at the cost of refusing two name prefixes on routes that previously accepted
  any label.
- Concurrent edits are last-write-wins. A future need for optimistic
  concurrency would add a version column and an `If-Match` header; nothing in
  this decision blocks that.
- Secret rotation and un-revoking remain impossible. Rotation is deferred to
  its own decision; un-revoking is refused permanently.

**Alternatives Considered:**

- **Revoke-and-reissue as the only remedy** (the status quo made explicit):
  rejected — it invalidates every consumer of the secret to change a label or
  add one scope, and in practice pushes operators toward the raw `UPDATE` that
  prompted this ADR.
- **Mutate everything except the secret** (including `project_id` and
  `owner_user_id`): rejected — re-parenting a token silently rewrites the
  meaning of its existing `token_audit_log` history, which is exactly the
  evidence the audit trail exists to preserve.
- **Kind-only editability check** (`token_kind !== 'agent'`): rejected on
  evidence — `issueOrchestratorRunToken` mints `token_kind='project'`, so the
  check would have admitted live run-bound credentials.
- **A DB CHECK constraint on the reserved name prefix**: rejected — the machine
  path legitimately writes `orchestrator-run:` and `agent-run:` names, so a
  table-level constraint would break agent launches. The guard belongs where
  human input enters.
- **Optimistic concurrency (`If-Match` + version column)**: rejected for now —
  no demonstrated need, and the ledger already makes a collision
  reconstructible. See D4.
- **Backfilling synthetic `issued` rows for existing tokens**: rejected — an
  invented provenance row is indistinguishable from a real one and corrupts the
  ledger's only value. See D6.

**Amendments:**

- 2026-09-11 — Adversarial review of the shipped diff recorded two precisions
  that do not change the decision:
  - **D5's "identical for every caller" does not hold on one route.**
    `POST /api/v1/ext/runs/{runId}/hitl/{hitlRequestId}/respond` resolves its
    required scope dynamically from the addressed HITL request's `kind`
    (`hitl:respond:human` for a human-only request, `hitl:respond` otherwise).
    There `details.requiredScope` is a fact about the addressed resource, not
    about the endpoint. It is still never a fact about the token's held scopes —
    the invariant that matters — and reaching the refusal already requires a
    token scoped to that project, which can read the same `kind` from the HITL
    inbox. Recorded rather than special-cased: suppressing `details` for
    dynamic labels would make the one route hardest to diagnose the only one
    that stays undiagnosable.
  - **D2's authorization rationale is imprecise for one token class.** The
    project gate is justified as "a principal who could mint this exact scope
    set a minute ago may add a scope now". That is exactly true for ownerless
    `token_kind='project'` rows and NOT true for `token_kind='user'` rows owned
    by someone else: `POST /api/projects/{slug}/tokens` always sets
    `owner_user_id` to the ACTING user, so an admin can never mint a token owned
    by another member, yet `listTokens` filters on `project_id` alone and the
    PATCH gate admits those rows. The outcome is nonetheless bounded and the
    gate is kept: token creation already requires `editSettings`, so such a row
    is always owned by another ADMIN of the same project; the editor never holds
    that token's secret, so this grants capability to someone else's credential
    rather than the ability to act as them; and every such change now writes a
    `scopes_changed` row naming the actor, which is the mitigation this ADR
    adds. Recorded so a future reader does not mistake the rationale for a proof.
  - **The reserved-name guard now tests the TRIMMED name.**
    `POST /api/projects/{slug}/tokens` validates `name` as
    `z.string().min(1)` with no `.trim()`, so `" orchestrator-run:<id>"` passed
    the anchored pattern. No escalation followed, because `parseBoundRunId` is
    anchored identically and also rejected it — the forgery was blocked by a
    coincidence between two regexes rather than by the guard. The guard now
    stands on its own.
