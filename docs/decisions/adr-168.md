# ADR-168: Two canonical attention counters, `decisions` and `updates`

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-10
**Status:** Accepted

**Context:** One cross-project attention number exists today —
`getNeedsYouCount` (`web/lib/queries/needs-you.ts:13`), defined as
`getCrossProjectHitlInbox().count + getUnreadInboxCount()` — and every
cross-project surface reads it. It has two defects that a team-visibility surface
cannot carry.

*It sums two different kinds of demand.* A pending HITL request is blocked on a
human answering it. An unread comment is not blocked on anything. Adding them
produces a number whose only honest reading is "things", which is exactly the
number a reader learns to ignore.

*It double-counts every mention.* `fanoutToSubscribers`
(`web/lib/social/inbox.ts:22`) writes an `inbox_items` row **and** a
`task_activity` row for the same `comment_added` / `task_mentioned` event. The
current definition only reads the inbox side, so it is internally consistent
today — but the moment activity joins the sum (which a visibility surface needs),
one comment counts twice.

Meanwhile several genuinely blocking things are counted **nowhere**: a run
mechanically ready to promote, a `Crashed` run owing recover/discard, and a task
a triage verdict flagged.

**Decision:** Replace the single `needsYou` with **two canonical counters**, each
with one owning query, one meaning, and one badge tone.

**D1 — The definitions.**

```
decisions = respondable pending HITL (cross-project)
          + mechanically promotable runs
          + Crashed runs owing recover/discard
          + tasks flagged by triage (Held)

updates   = unread inbox_items (read_at IS NULL)
          + activity newer than the user's read cursor
            MINUS rows already represented by an unread inbox_item
```

Everything in `decisions` is answerable, promotable, recoverable or clearable **by
the reader, now**. Nothing in `updates` waits on anyone.

**D2 — The `MINUS` is load-bearing, and it has a key.** The overlap is subtracted
on `inbox_items.source_ref->>'activityId'` — `InboxSourceRef`
(`web/lib/db/schema.ts:7330`) already carries `activityId` on every row, so the
join needs no migration and no backfill. Without the subtraction a single mention
increments `updates` twice, and the counter is wrong on the most common event in
the system.

**D3 — With no cursor row, `updates` counts a bounded 24-hour window.** An absent
`user_activity_cursors` row means "never looked", not "has seen nothing ever".
Counting all history would render a four-digit badge on a first visit — a number
that is technically correct, useless, and trains the reader to dismiss the badge
permanently. The 24-hour bound matches the digest's own fallback window.

**D4 — Membership changes do not rewind the cursor.** The cursor is a single
global timestamp per user, so a user newly added to a project either floods
(stale cursor) or never sees that project's backlog (fresh cursor). The chosen
behaviour is: **activity is filtered by *current* visibility, and the cursor is
never rewound.** A new member therefore sees that project's activity from the
moment they joined forward. This is stated so it is a decision rather than an
emergent property of whichever query ran first.

**D5 — Relation-blocked tasks count in neither counter.** A task held by a
blocking relation looks like it needs a human and does not — nothing the reader
can do advances it until its blocker moves. It is a `/work` filter, not a badge.
This is the concrete test case for D7.

**D6 — Ordering is HITL criticality, then age.** `HitlItem.criticality` is
`low | medium | high | critical | null` (`web/lib/queries/hitl.ts:139`);
`tasks.priority` is `low | normal | high | urgent`
(`web/lib/tasks/criticality.ts`, ADR-121). They are different vocabularies for
different jobs: `tasks.priority` governs **admission**, and borrowing it here
would create a second ordering authority over the same queue. The decision queue
orders by HITL criticality, then age. A `null` criticality ranks with `medium` —
below an explicitly raised item, above an explicitly lowered one. Non-HITL kinds
carry a fixed rank: `crashed` = high, `promotable` = medium, `flagged` = low.

**D7 — A badge means "your participation is required".**

| Badge | Counter | Tone | Says |
| --- | --- | --- | --- |
| Inbox | `decisions` | **attention** (amber; existing `data-testid="inbox-nav-badge"`) | "N things are blocked on you" |
| Activity | `updates` | **neutral** | "N things happened you have not seen" |

**Nothing non-actionable may wear the attention tone.** This is the rule a future
counter must satisfy before it is allowed a badge at all, and D5 is the case that
proves it bites.

**D8 — Each counter is computed once per layout, and its count and its list come
from one query.** Every surface reads the same layout-level value rather than
recomputing its own; a `decisions` count that can disagree with the decision list
it labels is precisely the bug the one-number rule exists to prevent. This
restates, for both counters, the expectation
[`social-board.md`](../system-analytics/social-board.md) states today for
`needsYou`.

**D9 — `needsYou` is retired, not deprecated.** `web/lib/queries/needs-you.ts` is
deleted and every internal consumer re-pointed. A deprecated alias would leave a
second way to compute a canonical number, which is the drift this decision exists
to remove.

**D10 — The external pulse contract does not change.**
`web/app/api/v1/ext/activity/route.ts:63` carries an explicit ADR-152 D4 note that
`needsYouCount` stays HITL-only; every deployed assistant reads it. That field
keeps its exact current semantics **forever**, and `decisionsCount` /
`updatesCount` are added beside it. The internal retirement of D9 stops at the
`web/lib/ext-activity/**` boundary.

**D11 — i18n mechanics for count-bearing strings.** Count strings loaded as client
templates use **`$count`, not `{count}`** — `intl-messageformat` treats `{count}`
as an ICU variable and throws when it is not supplied. Numeric totals render
through `Intl.NumberFormat(locale)` from the active `next-intl` locale, never a
fixed `en-US` and never a raw integer, with RU-grouped regression coverage.

**Consequences:**

- Two badges instead of one, with deliberately different tones. A reader can tell
  "act" from "read" without opening either.
- Four kinds of blocking work that were invisible (promotable, crashed, flagged,
  plus HITL) become one queue with one number.
- The `MINUS` makes `updates` a join rather than two independent counts, so it
  cannot be computed as a sum of two cheap queries. That is the price of not
  double-counting the most common event in the system.
- `needsYouCount` on the ext pulse now means something narrower than the UI's
  `decisions`. The two are documented as different fields on purpose; naming them
  the same thing would have been the actual breakage.
- Every surface that shows a count gains a dependency on the layout that computes
  it, rather than on a query it calls itself.

**Amendments:**

- **2026-09-10 (Phase 4 execution).** D10 said `decisionsCount` / `updatesCount`
  are "added beside" the ext pulse's `needsYouCount`. They are not, and cannot
  be: `needsYouCount` is a **telemetry field on a project-scoped pulse**
  (`app/api/v1/ext/activity/route.ts`), and a project token has no owner — there
  is no reader whose cross-project counters could be computed there. The
  additive surface is instead `GET /api/v1/ext/decisions` (scope
  `decisions:read`), which requires a global personal token and therefore does
  have a reader. D10's freeze on `needsYouCount` stands unchanged and is pinned
  by `CT-ATN-06`; `ATN-06` in
  [`attention.md`](../system-analytics/attention.md) is narrowed to the half
  that is true.
- **2026-09-10 (Phase 4 execution).** `ExtDecisionItem.taskKey` and
  `.createdAt` are **nullable** in
  [`operations.openapi.yaml`](../api/external/operations.openapi.yaml). A
  scratch-run HITL is a real decision with no owning task, and a source row may
  carry no timestamp; dropping those entries or fabricating a value would each
  be worse than an explicit null.

**Alternatives Considered:**

- **Keep one number and widen it.** Rejected: it is the "things" number, and
  widening it to include promotable/crashed/flagged would silently redefine a
  series the ext pulse already publishes.
- **Three or more counters** (split HITL from promotable from crashed). Rejected:
  the reader's question is binary — "must I act, or may I read" — and a third
  badge would need its own tone, which D7 has no room for.
- **Subtract the overlap by `(taskId, createdAt)` proximity instead of
  `activityId`.** Rejected: a heuristic where an exact key already exists on the
  row.
- **Count all history when no cursor exists.** Rejected per D3.
- **Order the decision queue by `tasks.priority`.** Rejected per D6.
