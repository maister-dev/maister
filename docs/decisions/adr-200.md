# ADR-200: Explicit task launch authorization

> Implementation status is maintained in the [current contract](../system-analytics/task-launch-admission.md). The accepted decision below retains its original design-stage wording.

[Back to ADR index](../decisions.md#adr-200-explicit-task-launch-authorization)

**Date:** 2026-11-02
**Status:** Accepted

**Context:** Qualification currently governs both automated delivery and an intentional human Launch. A failed qualifier can therefore prevent a configured manual request from executing. Actor IDs and manual-looking trigger strings also occur on automated callers and cannot establish a human decision.

**Decision:** Separate immutable task launch intent from assessment. The session-authenticated explicit Launch boundary records one authorized input/settings revision without manufacturing qualification; automated roots require current accepted readiness. Persist trusted principal provenance, frozen execution input, resolution and admission basis before effects, and consume that authority only for its bound run. New successor execution requires new authority; same-run continuation retains its immutable request. A server-owned reservation and first-dispatch fence serialize competing admission and request edits.

The contract is **Designed**. [Task launch admission](../system-analytics/task-launch-admission.md) owns transitions, refusal rules, API compatibility and executable expectations. This changes the universal manual-admission portion of ADR-198; its assessment/evidence/publication protections remain applicable. No historical receipt is relabeled.

**Consequences:** Additive intent/snapshot storage and a compatible-writer cutover are required. Async intent receipts are distinct from existing run-bound API successes. UI keeps findings visible and makes assessment authoring optional. Capacity, isolation, trust, RBAC and Flow validation remain independent gates.

**Alternatives Considered:** A client bypass flag, changing required tasks to legacy, fabricated accepted assessments, and enabling only the UI button cannot provide durable scoped authorization or protect dispatch/recovery.
