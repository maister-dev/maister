**Context:** The librarian turns explicit instructions into effects — create,
update, comment, relate, triage, launch, stop, message — and must make each
effect observable and exactly-once from the owner's point of view: a lost
response is pending reconciliation, never an invitation to repeat (LIB-09).
Human-only decisions need the real user's click bound to what was reviewed
(LIB-08), "create" must not arm automatic launch, and results must come back to
the conversation without a model turn (LIB-16). Facts verified against the
working tree at `8c77218` (2026-09-26):

- `handleExt` never hands a transaction to `work`; each mutating route opens its
  own transaction and writes its success audit inside it through
  `recordRequiredTokenAudit(input, tx)`. The ext launch passes that write into
  `launchRun`'s run-insert transaction as `recordSuccessAudit(tx)`.
- `applyTriageVerdict` arms `launch_mode='auto'` exactly when `enqueue`
  (`web/lib/services/triage.ts:187-222`, the arm at `:216`);
  `sendTaskToTriageInTransaction` clears `triage_status`, `launch_mode` and
  `launch_armed_at` (`triage.ts:376-392`); the C2 candidates are
  `triaged` + `launch_mode='auto'` + flow + not paused
  (`web/lib/scheduler/c2-eligibility.ts:75-120`). The triager's `auto_enqueue`
  config (ADR-111/112) is read only by the agent — no server code reads it.
- `run_cancel`, `run_rework`, `run_message` and `run_plan` are coordinator
  routes bound to `actor.boundRunId`; the human stop is `stopWorkbenchRun`
  (session, `recoverRun`) with a token twin `stopWorkbenchRunForToken`
  (`web/lib/workbench-lifecycle/service.ts:1955-1970`, `:2047`).
- `agent_turns` has no `source` column: its identity is `variant` plus
  `logical_key`, unique per run, and `sendAgentMessage(requestKey)` writes
  `logical_key = 'message:request:' || requestKey`
  (`web/lib/agents/turns.ts:53-57`). A scratch message row (`run_messages`)
  carries no request key.

**Decision:** Every librarian effect is an operation row committed before the
effect and settled in the effect's own transaction or by a lookup on a unique
result reference; human-only effects run only from the owner's click on a card
bound to the reviewed revision; the owner's launch intent is recorded on the
task and bounds the triage automation; and task and run events come back as
deterministic, deduplicated update cards.

**D6 — Operation ledger.** `librarian_operations` (`0185`): UNIQUE
`librarian_operations_key_uq (conversation_id, idempotency_key)`, status
`admitted | succeeded | refused | failed | unknown`, CHECK
`librarian_operations_terminal_shape_check` (`refused`/`failed` carry
`error_code`), index `librarian_operations_segment_digest_idx`.

- Every effectful MCP tool takes `operationKey`; the facade sends it as
  `Idempotency-Key`. `handleExt` gains the option `idempotency: "required"`
  beside `successAuditInWork`: for a librarian token a missing key is refused
  `422 CONFIG`; the validated body is canonicalized (sorted keys, arrays in
  order, minus the key and `allowDuplicate`) into `request_digest`, and the
  operation is upserted `admitted` in its own committed transaction before
  `work` runs (LOP-01, `IT-LOP-01`).
- Same key and digest on a terminal row → the stored result, no second effect;
  same key while `admitted`/`unknown` → the current receipt (`202`), `work` is
  not re-run; same key, other digest → `CONFLICT
  {details.reason:"idempotency_payload_mismatch"}`; a new key whose digest
  equals a `succeeded` operation of the same segment → `CONFLICT
  {details.reason:"duplicate_of_operation", details.operationId}` unless the
  request says `allowDuplicate: true` (LOP-02, `IT-LOP-02`).
- The finalize rides the route's own audit write: `recordRequiredTokenAudit`'s
  input gains `operation?: {id, result}` and UPDATEs the operation to
  `succeeded` in the same transaction as the effect and its audit row. A `4xx`
  from `work` settles it `refused` with the code; an unexpected throw leaves it
  `unknown`.
- **Result references.** Every librarian effect either commits inside the
  route's transaction together with the finalize, or writes a UNIQUE reference
  the reconcile can look up; an effect with neither is not exposed as an
  operation. References: `tasks.created_via_operation_id`
  (`tasks_created_via_operation_uq`, `0184`), `task_comments.via_operation_id`
  (`task_comments_via_operation_uq`), `task_clarifications.requested_via_operation_id`
  (ADR-187), `runs.librarian_operation_id` (`runs_librarian_operation_uq`,
  `0183`), and for D10b the agent turn's `logical_key`
  (`agent_turns_run_logical_key_uq`) and `run_messages.via_operation_id`
  (new, UNIQUE, `0185`). Stop settles by state (D10b).
- **Reconcile (LOP-03).** An `admitted` or `unknown` operation older than
  `MAISTER_LIBRARIAN_OPERATION_RECONCILE_SECONDS` (default 120, web-only) is
  settled by lookup — reference found → `succeeded`, none →
  `failed{reason:"not_applied"}` — and is never re-issued. The admission pass
  refuses to admit a turn while such an operation exists and runs the lookup
  first; the `system_sweep` admission backstop (ADR-183 D10) does the same for
  an idle conversation (`IT-LOP-03`).
- **Batches (LOP-04).** Each item is its own key and row; the receipt lists
  per-item status; a retry re-submits the same keys, so terminal items return
  their stored results and only non-terminal items run (`IT-LOP-04`,
  `EDGE-LOP-02`).

**Crash windows (normative; each row has a test in T3.2 or T3.7).**

| Window | State left | Recovery owner |
| --- | --- | --- |
| op inserted, domain tx not committed | op `admitted`, no result reference | reconcile: none after the window → `failed{reason:"not_applied"}`; safe because the domain tx is atomic with the finalize |
| DB effect committed with the finalize | op `succeeded` | none needed |
| `launchRun` row committed, supervisor spawn pending or lost | op `succeeded{runId}`, run `Pending`/`Crashed` | existing run reconcile; the receipt reads live run status (ADR-186 read model) |
| run launch tx failed | op `admitted`, no run with that `librarian_operation_id` | reconcile → `failed` |
| operator message accepted by the run's service, finalize not written | op `admitted`/`unknown`, reference written by the service's own commit | reconcile lookup → `succeeded` |
| response lost to the model | op terminal | the next call with the same key returns the stored result (`EDGE-LOP-01`) |

**D7 — Cards (proposals and confirmations).** `librarian_cards` (`0185`):
kind `statement_proposal | confirmation | memory_suggestion`, status
`pending | accepted | rejected | expired | superseded | cleared_by_reset`,
`target`, `target_revision`, `payload_digest`, `requires_owner`, `expires_at`,
index `librarian_cards_pending_idx`. The librarian proposes through
`POST /api/v1/ext/librarian/cards` (tool `librarian_card_propose`, scope
`librarian:cards`, librarian kind only). A confirmation binds exact ids and the
reviewed revision:

| Target | Bound revision |
| --- | --- |
| task statement or content | `tasks.revision` (ADR-186) |
| run promotion | the reviewed head SHA |
| HITL answer | request id + the question's stored revision |
| discard | run id + run status |

The owner decides through `POST /api/librarian/cards/{cardId}/decide
{decision, expectedRevision}` (session). The route locks the card (status CAS
from `pending`), re-reads the target under lock and refuses drift or expiry with
`CONFLICT{details.reason:"target_changed"}`; otherwise it executes through the
service the existing UI uses — `respondToHitl` with `HitlActor{kind:"user"}`,
`promoteRun` (`web/lib/runs/promote.ts:2541`) with the expected head SHA,
`discardWorkbench` (`web/lib/workbench-lifecycle/service.ts:1380`), statement
accept (ADR-186) — recording an operation with key `card:<cardId>`, so a double
click is one effect (LOP-08, LOP-09; `IT-LOP-08`, `IT-LOP-09`). TTL
`MAISTER_LIBRARIAN_CONFIRMATION_TTL_MINUTES` (default 60): expiry is applied
lazily on decide and by the card-expiry sweep pass. Reset marks pending cards
`cleared_by_reset` (ADR-188). Explicit, fully resolved instructions run as
operations inside the owner-message turn without a card (LIB-08); a card is
required for every human-only action and whenever the target is ambiguous.

**D8 — Launch intent.** `tasks.launch_intent` (`0184`), nullable text CHECK
`none | triage_only | triage_then_launch`; NULL is today's behaviour.

- Only librarian operations write it: a librarian `task_create` writes `none` in
  the create transaction; the new route
  `POST /api/v1/ext/projects/{slug}/tasks/{taskId}/send-to-triage {launchIntent}`
  (scope `tasks:triage`, effectful) writes `triage_only` or `triage_then_launch`
  inside `sendTaskToTriageInTransaction`. Every other writer leaves the value as
  found, and a human Launch click ignores it (LOP-05, LOP-06).
- `applyTriageVerdict` arms `launch_mode='auto'` iff `enqueue` and
  `launch_intent` is NULL or `triage_then_launch`; otherwise it stamps `triaged`
  and leaves `launch_mode` and `launch_armed_at` NULL. `loadC2CandidateRows`
  additionally excludes `launch_intent='none'`, which covers both the
  `auto_launch_triaged` tick and the slot-free gate that share it.
- The triager verdict route never admits the librarian kind (ADR-184 D5):
  verdicts stay the triager's; the owner's intent is the only librarian input.

Interaction table (normative; the parameterized `IT-LOP-06` in T3.5):

| `launch_intent` | triager `enqueue` | `launch_mode` after the verdict | C2 eligible |
| --- | --- | --- | --- |
| NULL | false | NULL | no |
| NULL | true | `auto` | yes (today) |
| `none` | false | NULL | no |
| `none` | true | NULL | no (`EDGE-LOP-04`) |
| `triage_only` | false | NULL | no |
| `triage_only` | true | NULL | no |
| `triage_then_launch` | false | NULL | no |
| `triage_then_launch` | true | `auto` | yes |

The plan's third axis, "project auto-launch enabled/disabled", has no server
setting: the triager's `auto_enqueue` config only decides whether the triager
sends `enqueue`, so it folds into the `enqueue` column. Per-project
`task_queue_settings.maxInFlightAuto` and per-task `queue_paused` decide *when*
C2 admits an armed task, never *whether* it is armed; the test adds one boundary
row (`queue_paused=true` × armed → not admitted).

**D10b — Existing-work actions and the operator message seam.**

- **Launch.** `run_launch` (`POST /api/v1/ext/runs`, `runs:launch`) admits the
  kind with `launchRun`'s preconditions unchanged (cap → `Pending` with a queue
  position; relations, trust, runner readiness). `runs.librarian_operation_id`
  and the finalize are written in the run-insert transaction through the
  route's `recordSuccessAudit(tx)`; the receipt carries the actual run id and
  `Pending` or `Running` (LOP-07, `IT-LOP-07`, `EDGE-LOP-03`).
- **Recover, sync, reopen** admit the kind under live RBAC (`runs:recover`;
  `runs:sync` → `promoteRun`, ADR-141).
- **Stop.** New route `POST /api/v1/ext/runs/{runId}/stop` (scope `runs:cancel`,
  mapped to `recoverRun`, the action `stopWorkbenchRun` authorizes) wraps
  `stopWorkbenchRunForToken` and admits the `librarian` and `user` kinds only;
  the coordinator's `run_cancel` stays bound to its own children. Stop is
  idempotent and settles by state: the run out of the live statuses →
  `succeeded`.
- **Rework** is not a librarian operation: the ADR-160 claim hands the worktree
  to the clicking human. The receipt names the run page's control.
- **Operator message.** `POST /api/v1/ext/runs/{runId}/operator-message
  {message, operationKey}` → `{outcome: delivered | queued |
  refused_requires_rework, reason?}`, scope `runs:message`, never
  `runs:delegate`:
  - scratch run, only when `runs.created_by_user_id` is the owner →
    `sendScratchUserMessage` (`web/lib/scratch-runs/service.ts:2686`):
    `prompted`/`steered` → `delivered`, `queued` → `queued`; the appended
    `run_messages` row carries `via_operation_id`. A state whose own path
    refuses a message (`Starting`, `NeedsInput`; ADR-182 D7) refuses with that
    path's code and the operation settles `refused`.
  - persistent agent run → `sendAgentMessage`
    (`web/lib/agents/launch.ts:2317`) with `mode: "steer"` and
    `requestKey = 'librarian-op:' || operationId`: `steered` → `delivered`,
    `queued` → `queued`. Attribution is a new nullable
    `agent_turns.requested_by_user_id` (`0185`, `ON DELETE SET NULL`), written
    at insert and made immutable by re-deriving `guard_agent_turn_source`
    (`web/lib/db/migrations/0180_agent_turn_steering.sql:34`); the variant stays
    what `sendAgentMessage` chooses.
  - flow run → `refused_requires_rework`, naming the node-interrupt and rework
    controls (ADR-160/161) on the run page.
  - any other run, or a run the owner cannot act on → `404`.

  LOP-10, `IT-LOP-10`.

**D11 — Follow-up updates.** A domain-event consumer `librarian_followup` joins
`DOMAIN_EVENT_CONSUMERS` (`web/lib/domain-events/consumers.ts:64`) for
`run.done | run.failed | run.crashed | run.abandoned | run.review |
run.review_opened | run.needs_input | run.escalated | run.rework_claimed |
run.rework_returned | gate.failed | task.clarification_answered |
task.clarification_cancelled` (the last added by ADR-187; there is no
`run.launched`). A conversation follows a task when a `librarian_task_links`
row or a succeeded operation targets it.

- `librarian_updates` (`0187`): UNIQUE `librarian_updates_event_uq
  (conversation_id, domain_event_id)`, CHECK
  `librarian_updates_failed_has_error_check`. Delivery inserts an
  `author_kind='update'` message with a deterministic card — no model turn, no
  token. The queued→running transition has no event; the card reads live run
  status at render (LOP-11, `IT-LOP-11`).
- Access is checked at insert and at render; lost access →
  `skipped_no_access`.
- "Explain" (`POST /api/librarian/updates/{updateId}/explain`) enqueues an
  `explain` turn holding `LIBRARIAN_READ_SCOPES` (ADR-184 D3).
- The card label comes from `deriveWorkStage` (ADR-170) plus promotion facts;
  "deployed" is never claimed — a merged run reads "merged · deployment
  unknown" (L-12).
- At-least-once dispatch, idempotent by the unique; at most 5 attempts with
  backoff; a deterministic failure (e.g. the conversation is gone) records
  `failed` with evidence and the cursor advances, so one poison event never
  stalls the consumer, and no delivery repeats a business effect (LOP-12,
  `IT-LOP-12`).

**Consequences:**

- A lost response, a restart or a second tab can never produce a second task,
  comment, clarification, launch or message: the key, the digest and the result
  references settle every window in the table above.
- The finalize rides an existing mandatory write, so no route grows a second
  transaction; the price is that every new librarian effect must name its
  result reference or commit with the finalize before it is exposed.
- "Create" never arms auto-launch, and the owner's triage choice survives the
  triager's own `enqueue` opinion. A human can still launch at any time.
- Cards cost one click for human-only actions and ambiguous targets only.
- Follow-up delivery spends no tokens; explanations do, on demand, with
  read-only authority.
- Two schema additions beyond the first plan draft — `run_messages.via_operation_id`
  and `agent_turns.requested_by_user_id` — replace a `source` enum that does not
  exist.

**Alternatives Considered:**

- **Idempotency by the model's own restraint:** rejected — L-07 requires one
  effect under retry, restart and two tabs regardless of model behaviour.
- **A separate finalize transaction after the effect:** rejected — it opens a
  window where the effect exists and the ledger says `admitted`, which a lookup
  then has to guess at for DB-only effects.
- **Letting the librarian write triage verdicts with `enqueue`:** rejected —
  verdicts are the triager's (ADR-112); the owner's choice is an intent, not a
  verdict.
- **Confirmation for every effect:** rejected — LIB-08 forbids a redundant
  approval round for explicit instructions.
- **Model-written follow-up summaries:** rejected — they spend tokens on every
  event and can misstate results; the deterministic card reads live state.
- **Reusing `run_message` (`runs:delegate`) for operator messages:** rejected —
  it is a coordinator operation, and the librarian must not impersonate one.
