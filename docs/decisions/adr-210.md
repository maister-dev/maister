# ADR-210: ACP context observations and overflow recovery

**Date:** 2026-11-20

**Status:** Accepted

**Context:** Scratch and Studio previously inferred context usage from transcript messages. A logical session and its ACP handle can survive the process that measured usage. Adapters also report compaction and token limits through distinct, sometimes vendor-specific, ACP shapes.

**Decision:** Project usage and compaction from the [canonical event plane](adr-167.md), keyed by the physical session and its fenced assignment. The browser updates a shared meter through the existing run stream. Compaction summaries use the authorized transcript read path. Preserve `ACP_PROTOCOL` and add allow-listed prompt failure reasons. `retry_policy.on_reasons` can select input overflow and start a fresh session on the same workspace as specified by [ADR-080](adr-080.md) and [ADR-081](adr-081.md).

**Consequences:**

- A resumed process needs a new measurement. A historical attempt keeps its own attributable observations.
- Token counts, failure reason codes, and status are safe projections. Compaction text inherits transcript access and retention.
- Adapter behavior is verified on the negotiated wire. An adapter that omits a failure discriminator can require a fixed pin before its overflow support qualifies.

**Alternatives Considered:**

- Transcript scans couple monitoring to pagination and can show the previous process’s usage.
- A new execution domain event duplicates ACP notification identity and ordering.
- A platform condenser changes the context owned by the adapter. ACP provides the agent’s ordinary command path when it advertises manual compaction.

See the [context analytics contract](../system-analytics/acp-context.md).
