# ADR-182: Steering a running agent turn as a durable fenced command

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-25
**Status:** Implemented

> **Amends [ADR-167](../decisions.md#adr-167-durable-execution-host-event-and-runtime-data-plane)**
> (D5: a second command kind may sit inside a prompt's span) and
> **[ADR-114](../decisions.md#adr-114-unified-flow-runner-config-first-class-sessions-per-project-connect-time-bindings-and-runsessions-as-the-sole-run-runner-source-of-truth)**
> (a first-class session incarnation records the adapter's steering
> advertisement). Both records carry a dated amendment bullet.

**Context:** An ACP session runs one prompt turn at a time. A second
`session/prompt` while a turn is in flight is refused by the host
(`command_in_progress`), so an operator who wants to correct a running agent
had two options, both bad: wait for the turn to end, or stop it and lose the
work in flight.

Two adapters now advertise an extension that answers the need. On
`initialize` they return `_meta.steering.supported: true` and accept the
extension request `_session/steering {sessionId, prompt, _meta}`, which
injects a user message into the RUNNING turn and answers one of
`injected | promptRequired | startedNewTurn` (codex also answers `failed`
instead of throwing on a non-`RequestError` failure). `promptRequired` means
"no turn is running — send a prompt instead"; `startedNewTurn` means the
adapter found no running turn and started one of its own from the steer text.
Adapters that do not advertise the extension reject the method as unknown.

Two run kinds hold a persistent dialog with a running agent: a persistent
**agent run** (`sendAgentMessage`, the ext `run_message` operation and its
MCP tool) and a project **scratch dialog** (`POST /api/scratch-runs/{runId}/messages`).
Neither could reach a running turn. The agent path queued the message as the
next turn; the scratch route refused a message unless the dialog was
`WaitingForUser`, and the composer kept an in-browser "send after Stop" queue
that a reload lost.

Four properties of the existing seam constrain any design:

- Every host-bound command is enveloped, epoch-fenced and receipted
  (ADR-166). A bare extension call from the manager would be none of these.
- A prompt's evidence is its own span of the host stream
  `[acceptedSequence, terminalSequence]`; output inside that span is bound to
  the prompt by `sourceCommandId` (ADR-167 D5, ADR-177). The host stamps that
  id from the session's active prompt, so any output the steered agent
  produces is attributed to the parent prompt.
- The manager must never learn which adapter it drives; behaviour follows the
  capability advertisement, never an adapter id.
- Neither adapter emits a live user echo for a steer, and agent runs recorded
  no user transcript rows at all — a steered message would be invisible
  unless the manager records it.

**Decision:** A message reaches a running turn as **`session.steer`**, the
twelfth execution-host command kind: enveloped, fenced and receipted exactly
like `session.input`, addressed to the parent prompt by its command id, and
converted to an ordinary queued message whenever the host cannot inject it.

**D1 — Capability, uniformly.** The host records one boolean per ACP
connection from its own `initialize`: `capabilities.steering.supported =
(initResp._meta?.steering?.supported === true)`. It is exposed on the
`GET /sessions` entry, the `POST /sessions` 201 body (`steeringSupported`) and
the `session.created` event payload, and — per adapter family, from the smoke
cache — as `/diagnostics` `smoke.steering`. The manager persists it per
incarnation at the create ACK (`run_session_incarnations.steering_supported`,
NULL = not observed). No adapter id is consulted anywhere.

**D2 — One host command.** `POST /sessions/{id}/steer` takes a v1 command
envelope whose payload is `{contentBlocks, parentCommandId}` (the prompt
route's content-block shape, confined and resolved by the same helper). It
runs through the same fence → receipt → execute → receipt path as
`/input`. The host refuses, with `409 CONFLICT` and a `rejected` receipt,
before any ACP call:

- `steer_unsupported` — the connection did not advertise steering;
- `steer_no_active_turn` — `parentCommandId` is not the session's active
  prompt (none is running, a stale id, or the parent already completed).

Otherwise it calls `_session/steering` with
`_meta.steering.idleBehavior: "promptRequired"`. Only `injected` succeeds
(200 `{outcome: "injected", parentCommandId, latencyMs}`). Every other
answer — `promptRequired`, `startedNewTurn`, `failed`, an ACP error — is the
refusal `steer_no_active_turn` with `adapterOutcome`; an adapter that does not
answer within `STEER_ACP_TIMEOUT_MS = 30 000` is the refusal `steer_timeout`.
`startedNewTurn` is an **unowned turn**: the host cancels it at once
(`session/cancel`) and cancels every pending permission it raised before
writing the refusal.

**D3 — Ordering on the host.** While a steer's ACP call is in flight the
session holds a `steerInFlight` barrier; the next prompt awaits it (bounded by
the same 30 s) before it is written to the adapter. A prompt therefore never
overtakes an unanswered steer and a steer never lands in the wrong turn.

**D4 — Evidence.** The steer's evidence is its own receipt and its own
`session.command{kind: "session.steer"}` pair. The parent's request digest,
receipt and span are untouched: the steered output rides the parent's
`sourceCommandId`, and the span verifier already steps over `session.command`
rows. The transcript projector treats an accepted steer as a boundary that
closes the open assistant text/thought row without starting a new usage row.

**D5 — Manager model: intent, then outcome.** A steer is accepted only inside
one transaction that finds an eligible parent — a `session.prompt` command in
`accepted` on the run's current assignment whose incarnation has
`steering_supported IS TRUE`. In that transaction the manager writes the
steer's domain row, issues the `session.steer` ledger row (queued before the
wire), and appends the user transcript row the operator will see
(`prompt_dispatch_key = steer:<commandId>`). The wire call runs after commit.
The outcome is applied by ONE settlement function, called by the live path,
the receipt fold and the orphan pass, and always in the same transaction as
the ledger's terminal write:

- `injected` → ledger `succeeded`, steer row `applied`;
- a definitive refusal (the three reasons above) or `FENCED` → ledger
  `failed`/`fenced`, steer row `superseded`, and the message becomes an
  ordinary queued message (agent: a successor `live_message |
  persistent_message` turn; scratch: the row's `delivery` flips to `queued`);
- an unknown outcome → nothing is converted; the receipt decides later.

A message is therefore delivered exactly once: converted only on a definitive
host answer, never on an unknown one.

**D6 — Persistent agents.** `sendAgentMessage` gains `mode: "steer" |
"queue"` (default `queue`) and answers `delivery: "steered" | "queued"`; the
caller never learns the adapter. A steer row is `agent_turns.variant =
'steer'` with `parent_turn_id`, is inserted `dispatched` (already bound to its
command) and ends `applied | superseded`, and is invisible to every owned-turn
reader
(`OWNED_TURN_VARIANTS`). A same-key retry answers the steer row or, after a
conversion, its successor. Runs in `NeedsInput` accept messages in both modes.
Every agent prompt — initial, resume, rework, message — is also recorded as a
bounded user transcript row at dispatch, so the agent transcript is the full
dialog.

**D7 — Scratch.** A message sent while the dialog is `Starting | Running`
is appended immediately and either steered (`delivery = 'steered'`) or queued
(`delivery = 'queued'`); the dialog status is not touched. Queued rows are
dispatched FIFO by one function, `dispatchQueuedScratchMessages`, called
detached after the previous turn's `WaitingForUser` commit, after a refusal
conversion, and by the next send. The browser-side auto-send queue is
deleted: while the agent is busy the composer's primary action is **Send**
and **Stop** is secondary.

**D8 — Semantics are adapter-owned.** The manager promises "delivered to the
running turn", never "immediately". When an injected message takes effect
(before or after an in-flight tool call, while a permission is pending) is
the adapter's decision and is measured, not assumed
([acp-runners.md](../system-analytics/acp-runners.md#steering-implemented--adr-182)).

**Consequences:**

- A prompt's span can now contain a second command kind. Nothing about the
  parent's settlement changes; the steer is settled by its own receipt.
- The operator gets one uniform contract across adapters: a message is either
  injected into the running turn or queued for the next one, and the response
  says which. An adapter without the advertisement behaves exactly like
  before (queue).
- The only reachable double delivery is an adapter that injects AFTER the
  30 s host bound: the manager has already converted the message into a
  queued one. It needs an adapter defect (claude's check-and-push is
  synchronous; codex answers a finished turn with an error, not silence) and
  is recorded as `EDGE-STR-06`.
- Transcript order is the manager's acceptance order, not the adapter's: the
  steered row sits where the operator sent it (`EDGE-STR-07`).
- **Open item — A4.** A scratch row left `queued` while the dialog is
  `WaitingForUser` (a process death between the previous turn's completion
  commit and the detached dispatch, W5/W6) has no automatic re-drive in this
  decision. The row is durable and visible ("Queued"), and the next send
  flushes the queue FIFO; the automatic re-drive belongs to the scratch
  grace/Recover work (A4). This is an explicit dependency, not a handled case.
- **Follow-ups.** The local-package assistant composer keeps its
  `WaitingForUser`-only gate (separate actor/lock model, ADR-097); per-family
  composer copy and a "nudge" for running flow nodes are separate items.
  Flow nodes, consensus roles, gate chat and HITL answers do not steer.

**Alternatives Considered:**

- **A bare `extMethod` call from the manager.** Rejected: unfenced and
  unreceipted, so a stale driver could steer a newer generation's turn and a
  lost acknowledgement could not be reconciled.
- **A second `session/prompt` while a turn runs.** Rejected: the host refuses
  it (`command_in_progress`), and it would give one turn two owners.
- **Branching on the adapter id** (e.g. "claude steers, codex queues").
  Rejected by the capability rule: behaviour follows the advertisement.
- **Emulating steering for adapters that do not advertise it** (cancel and
  re-prompt). Rejected: it discards work in flight and changes the meaning of
  the operator's action.
- **A separate queue table for scratch messages.** Rejected: the
  `run_messages` row already is the scratch turn's identity (the prompt owner
  keys on its id and sequence), so the queue state lives on that row.
