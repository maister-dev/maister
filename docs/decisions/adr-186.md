# ADR-186: Task statements, task revision and conversation provenance

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-26
**Status:** Accepted

> Relies on [ADR-121](../decisions.md#adr-121) (the Backlog gate on task
> configuration fields) and on the continuation seams of
> [ADR-160](../decisions.md#adr-160) and [ADR-161](../decisions.md#adr-161); it
> changes neither. Effects made through the librarian are wrapped by the operation
> ledger of [ADR-185](../decisions.md#adr-185-librarian-operation-ledger-confirmation-cards-and-launch-intent)
> and authorized by [ADR-184](../decisions.md#adr-184-librarian-delegated-authority-per-turn-owner-bound-tokens-with-live-rbac).
> Owns requirement family `TST`
> ([task-statements.md](../system-analytics/task-statements.md)).

**Context:** The personal librarian ([brief](../pv/personal-librarian.md), LIB-03,
LIB-10) turns a discussion into an agreed statement and hands it to a task. Tasks own
work; the conversation is private to its owner. Three facts in the current tree
shape the decision:

- **A task has one free-text requirement and no revision.** `tasks.prompt` is the
  only requirement text an executor reads. `updateTask`
  (`web/lib/services/tasks.ts:414-482`) is a plain SELECT → UPDATE → SELECT with no
  row lock and no version, so two concurrent edits are last-write-wins. `TaskDTO`
  (`tasks.ts:253-274`) carries no revision. The UI route sends both its PATCH
  (`patchBodySchema`) and its PUT (`putBodySchema`, the full card editor) through
  the same `handleTaskUpdate` → `updateTask`
  (`web/app/api/projects/[slug]/tasks/[number]/route.ts:21-43`, `:46-63`,
  `:108-153`); the ext PATCH accepts `{title?, prompt?}` `.strict()` and calls
  `updateTask` inside its own transaction
  (`web/app/api/v1/ext/projects/[slug]/tasks/[taskId]/route.ts`). The UI route
  passes no database handle, so today its `updateTask` call runs outside any
  transaction.
- **The Backlog gate already exists.** `BACKLOG_GATED_FIELDS`
  (`tasks.ts:361-372`) lists `title` and `prompt` among the fields `updateTask`
  refuses with `PRECONDITION` unless `tasks.status = 'Backlog'` (`tasks.ts:435-440`).
- **There is no launch snapshot of the requirement.** A flow run re-reads the task
  row at every entry: `runFlow` calls `loadRun` (`web/lib/flows/runner.ts:43`,
  `:98`), which selects the task (`web/lib/flows/graph/runner-core.ts:193-197`), and
  the graph folds `loaded.task.prompt` into its clarification projection and run
  context (`web/lib/flows/graph/runner-graph.ts:2782-2821`). Launch, resume,
  recover, rework and interrupt all re-enter through `runFlow`. An agent run builds
  its prompt on every `startAgentSession` (`web/lib/agents/launch.ts:2919`,
  `:3375`) through `buildAgentPrompt` → `taskContextBlock`, which re-reads
  `tasks.prompt` (`launch.ts:1769-1807`). A requirement rewritten under a running
  task therefore changes what the executor is told at its next re-entry.

**Decision:** An agreed statement is a typed, immutable **statement revision**
rendered deterministically into `tasks.prompt`; every edit of a task is guarded by
a task-level `revision` counter under a row lock; the task-side Backlog gate is the
only protection of an executing requirement; and conversation provenance is a
separate, owner-private link table that no task reader can follow.

**D1 — Statement shape.** A statement is
`{context, goal, acceptance[], constraints[], outOfScope[], links[], openQuestions[]}`,
validated by one zod schema in `web/lib/tasks/statement.ts`: `goal` is non-empty,
`acceptance` has at least one item, the other lists may be empty, every string and
list is length-bounded by that schema, and `links[]` are `{label, url}` whose `url`
is `http(s)` or a task key. A link into the librarian surface (`/api/librarian/…`,
a conversation or message id) is refused `CONFIG` by the schema, so a statement can
never carry a path back into a private transcript (TST-01, TST-05; `IT-TST-01`).

**D2 — Immutable revisions.** `task_statement_revisions` (migration `0185`) has PK
`(task_id, revision)`, `statement jsonb`, `author_actor_type`, `author_actor_id` and
`via_operation_id`. Trigger `task_statement_revisions_immutable` raises on UPDATE and
DELETE; task deletion still cascades (`task_id … ON DELETE CASCADE`). A later accept
writes revision N + 1; nothing rewrites revision N (TST-01; `IT-TST-01`).

**D3 — `tasks.revision` guards every edit.** Migration `0184` adds
`tasks.revision integer NOT NULL DEFAULT 0` and `tasks.statement_revision integer
NULL`. `updateTask` becomes: open a transaction when the caller did not pass one
(the `inTransaction` pattern of `persistPendingQuestion`,
`web/lib/services/agent-question.ts:124-142`), `SELECT … FOR UPDATE` the task row,
compare the optional `expectedRevision`, apply the existing Backlog and pause gates,
write, and set `revision = revision + 1` in the same UPDATE. A mismatch refuses
`CONFLICT{reason:"stale_revision"}` and writes nothing. `TaskDTO` gains `revision`;
the UI PATCH **and** PUT schemas and the ext PATCH accept `expectedRevision`
(If-Match precedent: `parseIfMatch`, `web/lib/scheduled-launches/http.ts:65-76`),
and the UI routes' `{ok:true}` gains `revision`. The field stays optional for
existing clients; the board card editor always sends it, and an ext PATCH or
statement accept made with a librarian token without it is refused `CONFIG` (the
brief's "re-read the current task revision before applying it") (TST-02;
`IT-TST-02`).

The counter counts **edits**: every successful write through `updateTask` (content,
launch configuration or the pause valve) and every statement accept. Machine writes
that are not edits — triage verdicts (`web/lib/services/triage.ts`), as-plan and
delegation stamps, run-lifecycle and queue writes — do not bump it. The two-racer
test for `IT-TST-02` asserts the loser parked on the row lock in
`pg_stat_activity` and refused, never overwriting.

**D4 — Accept is one transaction.** `acceptStatement` (`web/lib/tasks/statement.ts`)
runs under the task row lock and, in order: compares `expectedRevision` (required
here); applies the Backlog gate (D6); inserts revision N + 1; sets
`tasks.prompt = renderStatementPrompt(statement)`; sets `tasks.statement_revision =
N + 1` and bumps `tasks.revision`; writes the provenance link (D7) with meaning
`created_from` (task created in the same operation) or `refined_in`; and records
`task_activity` kind `statement_accepted` through `recordTaskActivity`
(`web/lib/social/activity.ts:82`, the only activity writer) with payload
`{statementRevision, taskRevision, operationId?}` — never statement text. The
finalize of the wrapping operation rides the same transaction (ADR-185), so the
effect and its receipt commit together. Migration `0185` re-derives
`task_activity_event_kind_check` with `statement_accepted`;
`inbox_items_event_kind_check` does not gain it (an accept fans out to no inbox).
A task created with a statement starts at `revision = 1`, `statement_revision = 1`;
one created without starts at `revision = 0` (TST-03, TST-04; `IT-TST-04`).

`tasks.statement_revision` names the revision whose rendering **is** the current
`tasks.prompt`. A `prompt` write through `updateTask` sets it to NULL, so a
statement card always diffs against the live prompt rather than a stale statement
(`IT-TST-02`).

**D5 — The rendering contract.** `renderStatementPrompt(statement): string` is
pure — no IO, no clock, no locale, no environment — and total over the D1 schema.
Its output is markdown with fixed English headings in this order, each section
omitted when its source is empty (Goal and Acceptance criteria never are):

| Order | Heading | Source |
| --- | --- | --- |
| 1 | `## Context` | `context` |
| 2 | `## Goal` | `goal` |
| 3 | `## Acceptance criteria` | `acceptance[]` |
| 4 | `## Constraints` | `constraints[]` |
| 5 | `## Out of scope` | `outOfScope[]` |
| 6 | `## Links` | `links[]`, each an inline markdown link whose text is `label` and whose target is `url` |
| 7 | `## Open questions` | `openQuestions[]` |

List items render as `- item` in input order; each string is trimmed, line endings
normalize to `\n`, continuation lines of a multi-line item are indented two spaces,
sections are separated by exactly one blank line, and the result has no trailing
whitespace. The rendering carries no conversation id, message id, author or
timestamp: the executor gets a self-contained assignment and nothing that points at
the private conversation. Answered clarifications are **not** part of it; they keep
folding through `composeEffectivePrompt` (ADR-187). `UT-TST-03` asserts byte-identical
output for equal input and the fixed order (TST-03).

**D6 — The Backlog gate is the protection.** Statement accept and every librarian
title/prompt edit go through `updateTask`'s existing `BACKLOG_GATED_FIELDS` gate:
refused `PRECONDITION` unless `tasks.status = 'Backlog'`. Because there is no launch
snapshot (Context), relaxing the gate would silently rewrite what a flow run reads
at its next resume, recover, rework or interrupt, and what an agent run reads at its
next session. The refusal carries `details: {reason: "task_not_backlog",
taskStatus, nextSteps: ["operator_message", "rework_claim"]}`: the operator-message
seam (ADR-185 D10b — delivered, queued or `refused_requires_rework`) and the ADR-160
rework claim with its ADR-161 node interrupt are the only ways to change what
running work does. `tasks.prompt` is unchanged by a refused accept (TST-07;
`IT-TST-07`, `EDGE-TST-01`).

**D7 — Provenance links.** `librarian_task_links` (migration `0185`):
`conversation_id` (CASCADE), `task_id` (CASCADE), `meaning ∈ {created_from,
refined_in, mentioned}`, `from_message_id` / `to_message_id` (`ON DELETE SET NULL`
to `librarian_messages`), `statement_revision`, index
`librarian_task_links_task_idx`. The relation is many-to-many: one conversation
links many tasks and one task can be linked from many owners' conversations. Links
are read only by owner routes under `/api/librarian/*` and by
`getLinkedWork(ownerId)`; no task-scoped route, board read or ext task read returns
them. A link whose message refs are NULL renders an explicit unavailable state
(TST-04, TST-06; `IT-TST-04`, `IT-TST-06`, `EDGE-TST-02`). A link never widens
automatic recall: the composer does not follow a link into an older segment
(ADR-188, `IT-LMM-04`).

**D8 — Excerpts are publications.** Sharing conversation text with a task's
audience is the explicit `task_publish_excerpt` operation: a task comment quoting
the excerpt, written as the owner with `task_comments.via_operation_id`
(UNIQUE `task_comments_via_operation_uq`), plus a `mentioned` link. The comment then
lives under the task's visibility and lifecycle; it grants no access to the
transcript, and every `/api/librarian/*` resource stays owner-only (TST-05;
`IT-TST-05`). Reset, history deletion and retention never delete tasks, statement
revisions or published excerpts (TST-06; `IT-TST-06`).

**D9 — Chips and receipts read live.** A task chip or operation receipt shows the
task key and current state from one batched, visibility-filtered read,
`getLinkedWork(ownerId)` in `web/lib/librarian/read-models.ts`; a task the owner can
no longer read renders unavailable, never its last known title (TST-08; `IT-TST-08`).

**Consequences:**

- Concurrent edits stop being last-write-wins for every client that sends
  `expectedRevision`; a client that omits it keeps today's behaviour but still bumps
  the counter, so a librarian card built on the old revision is refused
  `target_changed` (ADR-185 D7).
- Every `updateTask` call now takes a row lock, including the UI route's, which
  previously ran without a transaction. Peer writers of `tasks` take the task lock
  first and never touch librarian rows, so the ADR-185 lock order
  (conversation → operation → task) has no inversion.
- The executor-facing prompt is readable without the conversation, in English
  headings regardless of the owner's UI locale; the statement's own text keeps
  whatever language it was written in.
- A statement cannot follow work into execution. Changing a running task's intent
  is an explicit continuation act with its own guards, which is the behaviour the
  brief asks for ("never silently rewrite the executing requirement snapshot").
- A pause toggle or a launch-configuration edit invalidates a pending statement
  card. That is accepted: the card is re-proposed against the live revision rather
  than applied over a change the owner never saw.
- Triage verdicts do not bump `revision`. A card bound to a task revision is not
  invalidated by a verdict; verdict fields are not statement content.

**Alternatives Considered:**

- **Snapshot the prompt at launch and let accepts through off-Backlog.** Rejected:
  every re-entry path (resume, recover, rework, interrupt, agent session) re-reads
  the task row today; a snapshot would touch all of them and still leave the
  question of which text a resumed run should see.
- **Store the statement in the conversation and let executors read it.** Rejected by
  LIB-10: an executor must never need a private conversation, and task readers
  would need transcript access.
- **Render with the owner's locale.** Rejected: rendering would stop being pure
  (locale input) and the same statement would produce different prompts per owner.
- **Bump `revision` on every `tasks` write.** Rejected: triage, queue and lifecycle
  writes would invalidate every open card without any edit having happened.
- **A trigger-maintained revision.** Rejected: the lock, the comparison and the
  refusal have to happen before the write in application code anyway, and a trigger
  would also count the machine writes D3 excludes.
- **Put provenance on the task row (`created_from_conversation_id`).** Rejected: it
  is one-to-one, and it would expose a private conversation id to every task reader.
