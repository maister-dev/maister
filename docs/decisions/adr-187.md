# ADR-187: Addressed task clarification before execution

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-26
**Status:** Accepted

> **Amends [ADR-169](../decisions.md#adr-169-two-canonical-attention-counters-decisions-and-updates)**
> (a fifth `decisions` population, `clarification`, and the classification of the
> clarification event kinds) and
> **[ADR-170](../decisions.md#adr-170-derived-work-stage-vocabulary-distinct-from-the-board-columns)**
> (the `clarificationPending` attribute beside `blocked`). Each record carries a
> dated amendment bullet. Owns requirement family `CLR`
> ([task-clarifications.md](../system-analytics/task-clarifications.md)).

**Context:** The brief ([personal librarian](../pv/personal-librarian.md), LIB-11,
journey "Ask a teammate") needs a question addressed to a named person about a task
that may have no run at all. Today every task clarification is agent-origin:

- `task_clarifications` (`taskClarifications` in `web/lib/db/schema.ts`) requires
  `source_hitl_request_id`, `origin_run_id`, `origin_agent_id` and `question_schema`
  (all NOT NULL) and `retrigger_mode ∈ {agent, triage}`
  (`task_clarifications_retrigger_mode_check`). A row exists only because a running
  agent asked (`persistPendingQuestion`, `web/lib/services/agent-question.ts:131-283`,
  which locks the task row and allocates `seq = max + 1`, `:136-142`, `:230-236`).
- Answers reach executors through `composeEffectivePrompt`
  (`web/lib/tasks/clarifications.ts:76`); its filter `orderedAnsweredClarifications`
  (`:39-63`) reads `answered_at`, `superseded_at` and `answer` — never the origin.
- `hitl_requests.run_id` is NOT NULL: a HITL row cannot exist without a run.
- The existing `task.clarification_answered` event is a **directed hand-off to the
  asking agent**: `handleAgentQuestionResponse` emits it only for `retrigger_mode='agent'`
  (`web/lib/services/hitl.ts:5980-6000`; the triage branch requeues instead), and the
  agent-trigger consumer resumes the requester from its payload
  `{clarificationId, hitlRequestId, requestingAgentId}`
  (`web/lib/agents/triggers.ts:329-353`, `:581`).
- The attention plane classifies every `domain_events` kind into exactly one of
  three lists — `TASK_ACTIVITY_TWINNED_EVENT_KINDS`, `ATTENTION_EVENT_KINDS`,
  `DECISION_OPENING_EVENT_KINDS` (`web/lib/domain-events/taxonomy.ts:135`, `:147`,
  `:174`), pinned by `UT-ATN-09` (`taxonomy.test.ts:121`). A kind whose fact is also
  a `task_activity` row is twinned and must stay out of `ATTENTION_EVENT_KINDS`,
  because `getUpdatesCount` (`web/lib/queries/updates.ts:54`) already counts every
  `task_activity` row (ADR-169 amendment of 2026-09-10).
- `domain_events_kind_check` in `schema.ts` lists 13 kinds while migration
  `0167_decision_opening_events.sql:11` installed 15 (`run.review_opened` and
  `run.needs_input` are missing from the Drizzle CHECK): the schema has drifted
  from the database.

**Decision:** A user-origin clarification is a second **origin** of the existing
`task_clarifications` row, addressed to one recipient, delivered through the inbox
and the recipient's `decisions` queue, able to hold launch through a launchability
value and a work-stage attribute, and never backed by a dummy run.

**D1 — One table, two origins.** Migration `0186` widens `task_clarifications`:
`origin_kind text NOT NULL CHECK (origin_kind IN ('agent_run','user'))` (existing
rows backfilled `agent_run`, then the default dropped); `source_hitl_request_id`,
`origin_run_id`, `origin_agent_id` and `question_schema` become NULL-able (UNIQUE
`task_clarifications_source_hitl_request_uq` stays — NULLs are distinct);
`task_clarifications_retrigger_mode_check` gains `none`; new columns
`requester_user_id`, `recipient_user_id`, `reason`,
`answer_format` (`text`, `choice` or `yes_no`),
`blocking boolean NOT NULL DEFAULT false`,
`status` (`open`, `answered`, `cancelled` or `superseded`), `cancel_reason`, `superseded_by_clarification_id`,
`source_message_id` (`REFERENCES librarian_messages ON DELETE SET NULL`) and
`requested_via_operation_id` (UNIQUE). CHECK `task_clarifications_origin_shape_check`
discriminates the two shapes: an `agent_run` row keeps all four agent columns and a
`retrigger_mode <> 'none'`; a `user` row has NULL `source_hitl_request_id`,
`origin_run_id`, `origin_agent_id`, `retrigger_mode = 'none'`, and non-NULL
`requester_user_id`, `recipient_user_id`, `reason` and `answer_format` — so a user
row always **carries** what CLR-01 lists. `requestClarification`
(`web/lib/tasks/clarification-requests.ts`) takes the task row lock and allocates
`seq` exactly like `persistPendingQuestion`, so both origins share one
`task_clarifications_task_seq_uq` sequence (CLR-01; `IT-CLR-01`).

**D2 — Status and supersession shape.** Backfill: `superseded` where
`superseded_at IS NOT NULL`, else `answered` where `answered_at IS NOT NULL`, else
`open`. CHECK `task_clarifications_status_shape_check` is:
`(status <> 'answered' OR answered_at IS NOT NULL) AND (status NOT IN
('open','cancelled') OR answered_at IS NULL) AND (status <> 'cancelled' OR
cancel_reason IS NOT NULL) AND ((status = 'superseded') = (superseded_at IS NOT
NULL))`. A `superseded` row may carry an answer: an answered row is corrected by
first inserting its successor and then setting `superseded_at` and
`superseded_by_clarification_id` on it, so the answer already consumed is never
overwritten. `task_clarifications_supersession_check` is re-derived so a superseded
row names exactly one of `superseded_by_hitl_request_id`, `superseded_by_run_id`,
`superseded_by_clarification_id`. Because supersession always sets `superseded_at`,
`orderedAnsweredClarifications` drops the corrected answer with no change to its
filter (CLR-04; `IT-CLR-04`).

**D3 — No HITL row, no dummy run.** A user-origin clarification writes no
`hitl_requests` row and inserts no run; `hitl_requests.run_id` stays NOT NULL. The
row is task-bound, so it stays actionable whether the requester's librarian session
is running, idle or gone. **Nullable fan-out**: every reader of `origin_run_id`,
`origin_agent_id` or `source_hitl_request_id` gains an `origin_kind` branch — the
projection query (`web/lib/queries/task-clarifications.ts:44-60`), the agent answer
path (`web/lib/services/hitl.ts`), `agent-question.ts`, the agent-trigger target
parser (`triggers.ts:329`), the ext-activity mapper
(`web/lib/ext-activity/domain-events.ts:70`) and the triage prompt. T4.1 lists every
file it touches (`IT-CLR-01`).

**D4 — Recipient eligibility, live.** The recipient must hold the `answerHitl`
action's minimum project role, `member` (`PROJECT_ACTION_MIN.answerHitl`,
`web/lib/authz.ts:69`), checked by `requestClarification` at creation and by
`answerClarification` at answer time. A recipient who later drops below `member`
cannot answer (`UNAUTHORIZED`); the row stays `open`, task detail and the
requester's card render "recipient can no longer answer" from a live role read, and
the requester can cancel. `member` is also the floor of the decisions queue's
"projects the reader can act in", so an eligible recipient always sees the item
(CLR-02; `IT-CLR-02`, `EDGE-CLR-01`).

**D5 — Answer once, humans only.** Two routes answer: the session route
`POST /api/projects/{slug}/tasks/{number}/clarifications/{id}/answer` and its ext
twin `POST /api/v1/ext/projects/{slug}/tasks/{taskId}/clarifications/{id}/answer`.
Both require the actor to be the row's `recipient_user_id`. The ext twin admits only
a global personal token (`tokenKind='user'`, no project) holding the exact scope
`hitl:respond:human`, the precedent of the human-HITL respond route
(`app/api/v1/ext/runs/[runId]/hitl/[hitlRequestId]/respond/route.ts:151-163`,
`tokenHasExactScope`); a librarian or agent token is refused. `answerClarification`
locks the row, CASes `status='open'` → `answered`, validates the answer against
`answer_format`, and writes `answer`, `answered_by_user_id` and `answered_at` under
the unchanged `task_clarifications_answer_shape_check`; a second answer or an answer
to a non-open row is refused `CONFLICT{reason:"clarification_not_open"}` (CLR-04,
CLR-09; `IT-CLR-09`, `EDGE-CLR-02`).

**D6 — An answer changes nothing else.** Answering never rewrites a statement,
never bumps `tasks.revision`, never launches and never re-triggers: `retrigger_mode
= 'none'`. It may lead the requester's librarian to propose a `statement_proposal`
card in a later owner turn (ADR-185). The answer is visible on task detail at once;
it reaches the requester's conversation through the ADR-185 `librarian_followup`
consumer, which delivers only while the requester can read the task (CLR-06, CLR-07;
`IT-CLR-06`, `IT-CLR-07`).

**D7 — Cancellation.** `cancelClarification` ends an open row `cancelled` with a
`cancel_reason` and one event, from three causes: the recipient's account is
deactivated (the users service, same transaction; `recipient_deactivated`), the
task is abandoned (the task status path; `task_abandoned`), or the requester — or a
project `admin`, so a hold never outlives its requester — cancels
(`requester_cancelled`), through `DELETE …/clarifications/{id}` or task detail.
Each cause yields a delivered update (ADR-185 D11) (CLR-08; `IT-CLR-08`).

**D8 — Activity, inbox and events.** `TASK_ACTIVITY_EVENT_KINDS` gains
`clarification_requested | clarification_answered | clarification_cancelled` and
`task_activity_event_kind_check` is re-derived; `inbox_items_event_kind_check` (11
kinds today) gains `clarification_requested` only; `InboxSourceRef` gains
`{kind:"clarification", taskId, clarificationId, activityId}`. Creation writes one
`inbox_items` row for the recipient, keyed to the activity row by `activityId`.
`DOMAIN_EVENT_KINDS` gains `task.clarification_requested` and
`task.clarification_cancelled`; `task.clarification_answered` is reused, and every
answer of **either** origin now writes the `clarification_answered` activity row in
the transaction that emits the event. Payloads carry ids and flags only
(`{clarificationId, originKind, requesterUserId?, recipientUserId?, blocking}`),
never question or answer text. The agent-trigger consumer skips an
`originKind:"user"` answer before target parsing (`triggers.ts:581`), so a user
answer never resumes an agent (`IT-CLR-07`). `0186` re-derives
`domain_events_kind_check` from `0167`'s 15 kinds plus the two new ones, and T4.1
corrects the 13-kind Drizzle CHECK in `schema.ts` in the same change.

**D9 — Event classification (ADR-169 amendment).** With a `task_activity` twin,
`task.clarification_answered` and `task.clarification_cancelled` are
**twinned**: they join `TASK_ACTIVITY_TWINNED_EVENT_KINDS`, and
`task.clarification_answered` **leaves** `ATTENTION_EVENT_KINDS` — kept there, one
answer would score twice in `updates`. `task.clarification_requested` opens a
decision for its recipient, so it joins `DECISION_OPENING_EVENT_KINDS` and wakes the
attention consumer (`web/lib/notifications/attention-consumer.ts:57`); its activity
twin still reaches every other project member's `updates`. A closing answer or
cancellation moves the recipient's `decisions` count through the existing
`system_sweep` backstop, as a HITL answer does today. `UT-ATN-09`'s partition stays
three-way and total; its case "keeps task.clarification_answered on the attention
side" (`taxonomy.test.ts:159`) is migrated to assert the twinned classification
(`IT-ATN-02` proves no double count).

**D10 — The fifth decisions population (ADR-169 amendment).**
`computeDecisionsQueue` (`web/lib/queries/decisions.ts:178`) reads a fifth source,
`listOpenClarificationsForRecipient(userId, projectIds)` — `origin_kind='user'`,
`status='open'`, `recipient_user_id = reader` — inside the same `Promise.all`
(`:203`) into the same array, so `count = items.length` (`:326`) keeps ATN-01 by
construction. The new kind `clarification` fans out to `DECISION_KINDS` (`:52`),
`NON_HITL_RANK` (`:120`, fixed rank `medium` — ADR-169 D6's rule that a non-HITL kind
carries a fixed rank; `blocking` shows on the card, not in the order),
`STAGE_BY_KIND` (`:160`, `WaitingOnHuman`: the stage of the demand, a human answer),
the ext decisions route's `nextActionOf` (`answer`) and `ExtDecisionItem`
(`kind` + `clarification`, `nextAction` + `answer`), and the inbox card. The ADR-169
D5 relation-blocked filter (`:302-309`) skips this kind: answering is the
recipient's own act and waits on no blocker. Agent-origin rows are never listed
(their `recipient_user_id` is NULL); their decision is the `hitl` item. The
recipient's unread `clarification_requested` inbox row is **not** counted by
`getUpdatesCount`, though its `activityId` still keys the MINUS: a decision must
never also count as an update (ADR-169 D1) (CLR-03; `IT-CLR-03` asserts the
recipient's `decisions` +1 and `updates` +0, the requester's neither).

**D11 — Launch hold.** `TaskLaunchability` (`web/lib/runs/launchability.ts:16-23`)
gains `clarification_pending`. All three classifiers — `classifyTaskLaunchability`
(`:65`), `classifyManualTaskLaunchability` (`:123`) and
`classifyForceRelaunchLaunchability` (`:160`) — take a clarification gate
`{openBlocking: number}` beside the relation gate, and return it with precedence
`target_terminal > crashed > busy > flagged > clarification_pending > blocked >
unconfigured > launchable`; like `flagged`, it never masks an active run's state.
Only an `open`, `blocking`, user-origin row counts. The force classifier's refusal
list grows from two task gates to three. Verified consumers fan out:
`services/runs.ts:708-713` (refusal `PRECONDITION`, "classification:
clarification_pending"), `services/hitl.ts:4047-4051`,
`scheduler/c2-eligibility.ts:287` (C2 skips), `runs/task-launch-config.ts:290`,
`app/api/runs/launch-options/route.ts:490`, `:498`, the task page
(`app/(app)/projects/[slug]/tasks/[number]/page.tsx:179`, `:203`), and
`run-schedules/dispatch.ts:274` whose `decideFire` (`:58`) gains an explicit arm
returning `skipped_clarification_pending` after `flagged`, keeping a `queue_one`
flag. `RunScheduleFireOutcome` gains that value; `run_schedules.last_fire_outcome`
has no DB CHECK (migration `0038_run_schedules.sql:15`), so no migration. The
hand-mirrored board rule (`components/board/board.tsx:172-194`) and the popover's
`LAUNCH_UNAVAILABLE_REASON_KEY` (`components/board/launch-popover.tsx:186`) gain the
value, with a parity test against the shared classifier. No task status is added
(CLR-05; `IT-CLR-05`).

**D12 — Work-stage attribute (ADR-170 amendment).** `DeriveWorkStageInput`
(`web/lib/work/stage.ts:39-58`) gains `openBlockingClarificationCount`, and
`WorkStageResult` gains `clarificationPending = openBlockingClarificationCount > 0`,
computed beside `blocked` (`:142-153`). It is an attribute, never a `WorkStage`
member and never persisted; the task's stage stays what the run and triage axes say.
Both callers — `queries/work-table.ts:321` and `queries/board.ts:795` — batch the
count in one grouped query per page. `UT-STG-01` asserts totality over the new input
(CLR-05; `IT-CLR-05`).

**D13 — Prompt folding.** `composeEffectivePrompt` folds answered user-origin rows
exactly like agent-origin ones: same `seq` order, same `### Clarification N` block,
same bounds, no author name in the prompt. Attribution lives on task detail and in
the requester's conversation. `task-clarifications.ts` selects the new columns so the
projection can render origin and recipient (CLR-10; `IT-CLR-10`).

**Consequences:**

- A person can be asked before any run exists, and the question survives the
  requester's session, the librarian runtime and a restart, because it is a task
  row.
- The decisions queue gains a population whose actor is exactly one user; for the
  first time an inbox row is also a decision, and the updates counter has to know
  that (D10).
- Moving `task.clarification_answered` to the twinned list changes where an
  answer is counted (the activity row, not the event) without changing how many
  times; an agent-origin answer on the triage path, which emitted no event, now
  becomes visible as activity.
- `clarification_pending` joins every launch path, including force relaunch, the
  scheduler's C2 and cron fires. A blocking question therefore holds even an
  additive concurrent run; the requester or a project admin releases it by
  cancelling.
- A recipient who loses access leaves a visible, cancellable hold rather than an
  automatic cancellation, so re-granting access restores the request.
- The schema's `domain_events_kind_check` stops disagreeing with the database.

**Alternatives Considered:**

- **A parallel `task_questions` table.** Rejected: `composeEffectivePrompt`, the task
  detail history and the `seq` order would each need a union, and a second table
  for the same concept invites two supersession rules.
- **A `hitl_requests` row on a dummy run.** Rejected by LIB-11 and by
  `hitl_requests.run_id` NOT NULL: it would invent a run to address a person and put
  that run in every run-scoped read model.
- **A new task status `NeedsClarification`.** Rejected: task status is a four-value
  latch (Backlog | InFlight | Done | Abandoned); a hold is launchability, exactly as
  relations (`blocked`) and triage (`flagged`) are.
- **Rank a blocking clarification `high`.** Rejected: ADR-169 D6 gives non-HITL kinds
  a fixed rank; a per-row rank would make the comparator read a second input.
- **Keep `task.clarification_answered` in `ATTENTION_EVENT_KINDS`.** Rejected: with
  the new activity twin one answer would count twice in `updates`.
- **Cancel automatically when the recipient loses membership.** Rejected: membership
  can be restored, and a membership change is not a clarification write; the live
  role read already makes the state visible.
