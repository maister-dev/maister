# ADR-176: Automated crash-recover re-entry — the flow continuation worker owns the committed intent under a bounded per-run budget

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-21
**Status:** Accepted

**Context:** [ADR-175](adr-175.md) gave the committed recover intent its own
classifier arm in the reconcile sweep: a `Running` flow run carrying
`resume_started_at` and a `current_step_id` is handed to `driveResume` rather
than crashed a second time. That arm fires on the sweep's cadence — **≤ 60 s** —
because the sweep is the only thing that looks at the state.

The three durable workers (prompt-owner recovery, flow continuation, agent
continuation) wake on a **~1 s** idle cadence and are activated in the
production web boot by the same change that carries this ADR. The flow
continuation worker already scans `runs` for stalled flow work, so the
crash-recover state sits one predicate arm away from a re-entry latency
measured in seconds instead of a minute.

Two things block a naive adoption, and both are the subject of this decision.

**First, the predicate is not a dispatch decision.** The reconcile classifier
computes exactly this predicate (`reconcile.ts`, `crashRecoverPending`) and then
routes it **by session liveness** into two arms that call *different* functions:
no live session past grace → `recover` → `driveResume`; a live session → `reattach`
→ `runFlow(crashResume)` directly. `driveResume` runs `closeCrashedNodeAttempts`
before dispatching. Applied to a LIVE session — the `runningIdleSession` state
ADR-175 itself added a counter for — that closes a `Running` attempt the session
is still producing, and the re-prompt then **double-spends the turn**. A worker
arm built on the raw SQL predicate has no liveness discrimination and would ship
that defect on day one.

**Second, `driveResume` is deliberately re-entrant with no backoff.**
`recover.ts` returns `{state:"transient"}` for a fenced error and for
`EXECUTOR_UNAVAILABLE`, leaving the run `Running` and un-rolled-back so "an
operator/sweeper can retry". That is a correct design against a 60 s cadence. At
1 s across two slots, each attempt doing host I/O (`applyCrashedTurnEvidence`)
before failing again, a supervisor outage becomes an unbounded hot retry loop
against an already-failing supervisor. ADR-175's own Consequences section names
this boundary and declines to cross it: *"a crash-recover re-entry carries no
per-run bound … It becomes a defect the moment crash-recover is automated;
recorded here rather than pre-empted."* Automating it is what this ADR does, so
the bound is this ADR's to supply.

**Decision:** Ownership of the crash-recover-pending state moves from the ≤ 60 s
reconcile sweep to the ~1 s flow continuation worker, behind **one shared routing
decision** and a **durable per-run retry budget**.

**D1 — One recover-vs-reattach decision, shared by both callers.** The liveness
routing is extracted into a pure helper, `routeCrashRecover` in
`web/lib/runs/crash-recover-route.ts`, returning `"recover" | "reattach" | "wait"`:

| Liveness | Grace | Route | Dispatcher |
| --- | --- | --- | --- |
| live session | — | `reattach` | `runFlow(runId, {crashResume})` — **never** `driveResume` |
| no live session | past grace | `recover` | `driveResume` |
| no live session | inside grace | `wait` | none — yield, a dispatch may be in flight |

`reconcile.ts` is refactored to call the same helper for its `crashRecoverPending`
branch, so exactly one implementation of the decision exists. The sweep's arm,
its ADR-175 counters and its externally observable behaviour are unchanged; only
the decision's implementation moves to one place. A second copy of a predicate
drifts — and here the copy would not merely drift, it would be wrong on day one.

**D2 — Liveness is a probe, not a column.** The sweep resolves it from one
`hosts.local().listSessions()` call per tick and skips the whole tick when that
call throws. The worker calls the same API **only** for a candidate that has
already passed the cheap SQL filter and the grace guard — a state that exists
only after a web death, so the probe is per-rare-candidate, never per-tick. A
throwing probe **yields the candidate to the sweep** and dispatches nothing,
mirroring the sweep's own skip-on-probe-failure.

**D3 — The per-run bound ADR-175 declined to pre-empt.** Migration `0171` adds
two columns to `runs`:

- `crash_recover_next_retry_at timestamptz` (nullable)
- `crash_recover_attempts integer NOT NULL DEFAULT 0`, CHECK `>= 0`

`recordCrashRecoverContinuationOutcome` writes them per dispatch outcome:

| Outcome | Write |
| --- | --- |
| `transient` | `attempts = attempts + 1`, `next_retry_at = clock_timestamp() + least(2^attempts, 60) seconds` — exponential, capped at 60 s, converging on the sweep's own honest cadence |
| `resumed` \| `redispatched` | clear both to `(NULL, 0)` |
| `unresumable` | clear both to `(NULL, 0)` — the run is terminal via `crashRunningRun`; a clean row keeps a future unrelated crash unbiased |
| `reattach` route | **no budget write** — that arm is the sweep's existing behaviour and carries no new bound |

The budget is `CRASH_RECOVER_CONTINUATION_MAX_ATTEMPTS = 5`, a module constant
rather than an env var: this change adds **zero** deployment touchpoints beyond
the migration, and an env var nobody has a number for is what ADR-175 refused.

**D4 — The budget is intent-scoped, and it is reset at every claim-marker WRITE
site.** `resume_started_at` has three write sites (`recover.ts` ×2 and the
scheduler's `Pending → Running` promotion) and five release sites. Two of the
release sites are reparks, which would strand a non-zero `crash_recover_attempts`
into an unrelated future intent. Zeroing both columns **in the same transaction
that stamps `resume_started_at`** makes every new intent start from zero
regardless of how the previous one ended; chasing the five release sites does
not. The marker contract is normative and enumerated in full in
[`../system-analytics/execution-prompt-lifecycle.md`](../system-analytics/execution-prompt-lifecycle.md#crash-recover-marker-contract-implemented):

| Column | Write sites (stamp) | Release sites (clear) | Read / predicate consumers |
| --- | --- | --- | --- |
| `resume_started_at` | `runs/recover.ts:252`, `runs/recover.ts:278`, `scheduler.ts:912` | `flows/graph/runner-graph.ts:2410`, `runs/crash-recover.ts:358`, `runs/recover.ts:645`, `runs/state-transitions.ts:1376`, `runs/state-transitions.ts:1473` | `reconcile.ts` classifier + loaders, `scheduler.ts:555`, `queries/inbox-context.ts:666`, the worker's crash-recover arm |
| `crash_recover_next_retry_at` | the same three write sites (reset to `NULL`) + `recordCrashRecoverContinuationOutcome` on `transient` | `recordCrashRecoverContinuationOutcome` on `resumed` / `redispatched` / `unresumable` | the worker's candidate predicate |
| `crash_recover_attempts` | the same three write sites (reset to `0`) + `recordCrashRecoverContinuationOutcome` on `transient` | as above | the worker's candidate predicate and its budget-exhausted log line |

**D5 — Poison-item policy: one bad run never stalls the worker.** At the cap the
worker stops serving the run, logs
`flow-continuation-crash-recover-budget-exhausted` once, and the run falls back
to the reconcile backstop. Ineligibility drops the row **out of the candidate
set** rather than parking it at the keyset head, so row N+1 stays reachable and
the cursor keeps rotating.

**D6 — The reconcile `recover` arm is unchanged and remains the backstop.** It
serves every candidate the worker yields: a failed liveness probe, a run past the
budget, a run whose `execution_assignment_id` is NULL (a pre-Stage-A row the
worker's inner join drops, and which `driveResume` would crash anyway), and a run
whose assignment is not `active`. The worker is a latency improvement over a
path that still works without it, never a replacement for it.

**D7 — The worker does not take `claimFlowDriver`.** The claim already
serializes dispatch inside `runFlow`, from its single call site; a worker-side
claim would make that call return `null` and the dispatch a silent no-op. Four
racers reach the same serializer — the worker, the reconcile `reattach` arm, the
scheduler's queued-recover promotion, and an operator's own Recover click — and
one of them wins. The pre-dispatch stretch is idempotent by construction:
`applyCrashedTurnEvidence` answers `evidenceAlreadyApplied` on a lost handoff and
`closeCrashedNodeAttempts` is a guarded update.

**Consequences:** A crashed web process that left a committed recover intent
behind is re-entered in about a second instead of up to a minute, on the path the
operator already clicked, with a bound that a supervisor outage cannot turn into
a hot loop. The cost is a migration, a second consumer of the routing decision
(now shared rather than duplicated), and a liveness probe on a rare path.

The normative recovery-window table — each `status × liveness × mode` cell naming
its arm — lives in
[`../system-analytics/reconciliation-gc.md`](../system-analytics/reconciliation-gc.md);
the worker lifecycle, start order and health surface live in
[`../system-analytics/execution-event-plane.md`](../system-analytics/execution-event-plane.md)
and
[`../system-analytics/execution-prompt-lifecycle.md`](../system-analytics/execution-prompt-lifecycle.md).
This ADR records the automation decision and nothing else: the boot wiring, the
composed owner registry and the health aggregate are the execution of an already
accepted contract, not a new decision.

One thing is deliberately left undone. The worker's arm is **not** widened beyond
this predicate — in particular the `consensus` node type stays outside the flow
worker's `node_type` set, and reconcile-by-evidence in the sweep stays where it
is. Each is its own item with its own evidence.
