# ADR-163: Flow-target delegation — carrier task, shared admission, canonical Flow launcher

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).


**Date:** 2026-09-01
**Status:** Implemented

**Context:** An `orchestrator` node (ADR-098/099/100) can delegate only to a
**catalog agent**. `POST /api/v1/ext/runs/delegate` and `POST /api/v1/ext/runs/plan`
both parse a `target` object that already carries `flowId`, the external OpenAPI
already documents `flowId`, and the MCP `run_delegate` tool already advertises it
— but the route answers every flow target with
`CONFIG "flow-target delegation is not yet supported"`. A coordinator therefore
cannot compose a governed multi-node process (its own graph, gates, review,
promotion) as a unit of work; it can only fan out single-session agents.

Closing that gap touches six structural facts of the current system, each
established by inspection rather than assumption:

1. **A Flow run cannot exist without a task.** `assertFlowRunInvariant` throws
   `CONFIG` unless `taskId && flowId`; `loadRun` throws `PRECONDITION` on a
   missing task; and the Flow prompt entry point *is* `task.prompt`
   (`buildRunContext` writes `intent` / `task.prompt` / `task.effectivePrompt`
   from it, and `{{ task.prompt }}` is the manifest idiom). `tasks` has no
   visibility / hidden / internal column.
2. **A Flow run reaching `Review` emits no domain event** — only
   `emitWebhookEvent`. Its `Failed` / `Crashed` siblings emit `emitDomainEvent`
   with `parentRunId`. A delegated Flow child would therefore park forever and
   its parent would deadlock in `WaitingOnChildren`.
3. **`auto_launch_run_plan` hard-excludes non-agent children**
   (`if (payload.runKind !== "agent") continue;`), so a Flow child in an as-plan
   DAG would never auto-promote, never advance its task, and never release its
   `requires` dependents.
4. **Three independent edges create a delegated child** — `run_delegate`,
   `run_plan`'s source launch, and `auto_launch_run_plan`'s candidate launch —
   and the limits they enforce disagree: `run_delegate` checks depth only,
   `run_plan` checks a per-call batch bound, and the auto-launcher has never
   checked either. None of the three serializes its check.
5. **The canonical Flow launcher already does the hard part.**
   `launchRunStaged` runs the full trust sequence (enablement allow-list →
   trust → pinned revision → package status → setup status → schema version →
   engine compatibility → host requirements) *before* any workspace exists,
   inserts the run, commits, and only then starts execution. What it lacks is a
   delegation input surface: the insert writes no `parent_run_id`,
   `root_run_id`, `launch_mode`, or `delegation_snapshot`.
6. **`childTasks` is additive on the board.** A `parent_of` child renders as its
   own top-level card *and* as a reference under the orchestrator's card;
   `getBoardData` has no task filter at all. So a child task that is *not*
   linked is not hidden — it is an orphan card with no provenance.

**Decision:** Add a Flow arm to delegation that runs through the **canonical
Flow Run pipeline**, is admitted by **one shared helper on every creation edge**,
and is preceded by a **trust resolver that cannot launch anything**.

- **D1 — A Flow target always mints a carrier task, always links it `parent_of`
  under the orchestrator's task, and always honours `title` — in both modes.**
  Fact 1 makes a task mandatory, so the only open question was whether to link
  it. Fact 6 answers it: an unlinked child costs the same board card and
  carries zero provenance. `mode` therefore stays meaningful for Agent targets
  (where it genuinely decides whether a task exists) and is, for Flow targets,
  documented as *not* a board-visibility switch. The response always returns
  `childTaskId`. The carrier task is `launch_mode='manual'`, and its `flowId` is
  the **selected** flow — never inherited from the orchestrator's task.

- **D2 — `run_rework` on a Flow child is refused with `PRECONDITION`** at the
  route, before `reworkChildRun`. A Flow child owns an internal `human` /
  `rework` loop; grafting the coordinator's prompt onto it would need a new
  re-entry contract that overlaps ADR-160's rework claim. `run_message` is
  refused the same way (it addresses a persistent agent session, which a Flow
  child does not have).

- **D3 — One shared fan-out cap per orchestrator, counted across both child
  kinds.** `MAISTER_MAX_ORCHESTRATOR_FANOUT` now bounds *live children of any
  kind* rather than the size of one `run_plan` batch. This tightens the shipped
  `run_delegate` path, which enforced depth only.

- **D4 — The Flow-target field allow-list is `target.flowId`, `mode`, `prompt`,
  `title?`, `runnerOverride?`.** `workspace`, `workspaceMode`, `persistent`,
  and `addressableKey` are **refused** with `CONFIG`, never ignored: a Flow run
  always provisions a worktree, so `workspace` is meaningless; `workspaceMode:
  shared` would require the agent launcher's shared-tree allocator ported onto
  the Flow path; `persistent` / `addressableKey` describe an addressable agent
  session. Enforcement is a **strict target object with an exactly-one
  refinement** (both or neither identifier is `CONFIG`) plus a **per-kind option
  allow-list applied at the route before any lookup**
  (`refuseUnsupportedDelegationOption`), so an agent-only key on a Flow target is
  refused with its own message rather than silently dropped — a bare
  `z.union` would report only "no matching variant".

- **D5 — No migration.** `run.review` is already in `DOMAIN_EVENT_KINDS` *and*
  in the `domain_events_kind_check` CHECK; `runs.parent_run_id` /
  `root_run_id` / `launch_mode` / `delegation_snapshot` all exist; both
  `runs.delegation_snapshot` and `tasks.delegation_spec` are `jsonb` whose TS
  `$type<>` unions widen without DDL. Both DB doc surfaces are still updated for
  the jsonb semantic widening.

- **D6 — No delegation idempotency key in this cut.** A duplicate
  `run_delegate` produces a second governed child, bounded by the shared
  fan-out cap and visible via `run_collect`. This is parity with the shipped
  agent path. A SELECT-then-INSERT pre-check and a "recent identical prompt"
  heuristic were both rejected on purpose: each leaves a race window, and
  shipping either under the name "idempotency" is worse than a documented
  residual, because the next reader trusts it.

- **D7 — A delegated Flow child's `baseBranch` and `targetBranch` both resolve
  to `project.mainBranch`,** and both are recorded in `delegation_snapshot`.
  The carrier task carries neither, so `launchRunStaged`'s existing chain falls
  through to the project default; the delegation body accepts no branch field.
  This matches the agent path, keeps the target inside the project's validated
  branch allow-list, and leaves branch topology (a child branching off its
  parent, for recursive assembly) as a deliberate future decision rather than an
  emergent one. The integration model is therefore **N independent promotes into
  a shared target**, not "accumulate in the parent, merge once"; inter-child
  conflicts surface at the second child's promote as `CONFLICT`, and the
  coordinator cannot rebase a child out of the way (`ORCHESTRATOR_TOKEN_SCOPES`
  carries no `runs:sync`).

- **D8 — One `admitDelegatedChild()` helper, called from all three
  child-creation edges, serialized by a per-orchestrator advisory lock.**
  `pg_advisory_xact_lock` keyed on the parent run id — deliberately **not**
  `SCHEDULER_LOCK_KEY`, which would serialize every delegation platform-wide
  against the scheduler. Depth and fan-out are counted under that lock, and the
  carrier task (the Flow-target reservation) is inserted in the same
  transaction. A guard on one of N edges is a guard on none.

- **Trust separation.** The order is **locate → establish trust → execute**, and
  it is enforced physically, not by convention:
  `web/lib/orchestrator/delegation-target.ts` owns the *wire shape* and touches
  no database; `web/lib/flows/delegatable-flow.ts` owns *trust resolution* and
  **must not import a launcher** — asserted by a static test that reads the
  module's import list; `web/lib/orchestrator/admission.ts` owns *limits*. No
  module does two of the three. Every refusal produced by the resolver writes
  zero rows.

- **Admission ordering.** Pre-flight (field allow-list → token → bound run →
  flow trust) writes nothing. The carrier task and its `parent_of` relation are
  then created in **one** transaction that also takes the per-orchestrator lock
  for the fast-path depth/fan-out count; the DECISIVE admission runs again
  inside the launcher's run-insert transaction (see the D8 amendment).
  `launchRunStaged` follows with its own workspace and run transaction, commits,
  and only then starts execution. On `run_delegate` a post-commit re-read of the
  parent closes the window where the parent terminalized during launch: the
  just-born child is cascaded to `Abandoned` and its live supervisor session is
  torn down. `run_plan`'s source launches and the as-plan auto-launcher have no
  such re-read — their `launch_mode='auto'` tasks are what the parent's cascade
  abandons.

- **A Flow child wakes its parent through `run.review`.** The graph runner's
  `Review` branch emits `run.review` as a **domain** event inside the same
  transaction as the status flip, gated on `parent_run_id != null` — matching
  the agent launcher's existing rule that a top-level `Review` emits nothing.
  The webhook emit is unchanged. Blast radius at the moment of the change is
  exactly zero, because no delegated Flow child exists yet.

- **Two budgets, one tree.** `poolForRunKind` gives a Flow child the `flow` pool
  (`MAISTER_MAX_CONCURRENT_RUNS`) and an agent child the `agent` pool
  (`MAISTER_MAX_CONCURRENT_AGENTS`). Global concurrency accounting is unchanged;
  only the per-orchestrator fan-out cap is shared.

**Consequences:**

- **`run_cancel` on a Flow child ends it `Abandoned`** (owner decision at the
  2026-09-02 review, closing the review's finding that a cancelled child parked
  in `Review` still counted as LIVE for the shared fan-out cap while D2 refused
  `run_rework`/`run_message`, leaving the coordinator no way to reclaim capacity
  except promoting a half-done diff). The worktree is retained until GC, the
  slot is freed, and `run.abandoned` wakes the parent. A HUMAN stop (UI stop,
  ADR-161 node-interrupt `stop`) keeps the operator semantic `Review`.
- **Every Review flip of a delegated child emits `run.review`, through one
  helper** (`emitDelegatedReviewIfChild`): the graph runner's Review branch, the
  operator stop, the ADR-160 rework-claim release and both ADR-141 sync-resolver
  returns. Before the review only the runner emitted, so a child stopped by a
  human while its parent waited never woke it, and reconcile then crashed the
  parent as `orchestrator-stuck` and cascade-abandoned every child.
- **A failed launch ABANDONS the carrier task** instead of deleting it (see
  Alternatives): `runs.task_id` and `domain_events.task_id` cascade on delete.
  The `parent_of` relation stays as provenance.
- **Delegation trust equals board launchability.** One shared gate
  (`lib/flows/launchability-gate.ts`) is evaluated by the canonical launcher,
  the delegation resolver and the board projection; the resolver additionally
  requires a Ready platform runner and an executable stored manifest, exactly
  as the board does, so a flow the board shows as not launchable can no longer
  pass trust and fail after the carrier task exists.
- **`run_plan` refusal codes follow `run_delegate`.** Per-kind option
  violations are refused `CONFIG` 422 before resolution (every violating entry
  reported at once); resolution failures keep their own code when the batch
  agrees and aggregate to `PRECONDITION` 409 when mixed, each line tagged
  `[CODE]`. `run_plan`'s depth bound also moved from `depth + 1 >= max` to the
  documented `depth >= max` when both routes adopted the one admission helper.
- **A typed release-time refusal of an as-plan dependent is posted as a system
  comment on its task** (once per distinct refusal); the task stays `Backlog` /
  `launch_mode='auto'` and is retried on the next sibling settle.
- **`settings.delegation.max_fanout` / `max_depth` are advisory.** No runtime
  reads them; `MAISTER_MAX_ORCHESTRATOR_FANOUT` / `MAISTER_ORCHESTRATOR_MAX_DEPTH`
  are the enforced bounds (owner decision, 2026-09-02).
- **ADR-126 D-3 is narrowed, not reversed:** the grace anchor stays a column and
  a TOP-LEVEL Review still emits no domain event; only delegated children emit.
- **A shipped path tightens.** `run_delegate` with an agent target is now
  refused once the orchestrator's live-child count reaches
  `MAISTER_MAX_ORCHESTRATOR_FANOUT`; previously only depth was bounded. Shipped
  processes ship no `orchestrator` node, so the observed blast radius is nil,
  but this is a behaviour change, not a compatible extension.
- **An agent `mode: run` delegation carrying `title` is now refused** with
  `CONFIG` instead of silently discarding the field.
- **An agent bound to the `run.review` domain-event trigger now also fires on
  delegated Flow children.** That is the intended widening of the event's
  population; every other consumer is provably unaffected (`ralph_loop` filters
  `run.failed`; `cost_rollup_reconcile` and `memory_harvest` filter terminal
  kinds, which exclude `run.review`; `source_reindex` filters brain kinds).
- **`auto_launch_run_plan` widens from a deny-check to an allow-list**
  (`agent | flow`), so `scratch` and any future kind stay rejected by default.
- No new `MaisterError` code, no new env var, no migration, no
  `package.json` script, no compose change. `runs.delegation_snapshot` gains a
  `kind: "flow"` variant and `tasks.delegation_spec` becomes a discriminated
  union whose legacy (`kind`-less) rows read as `"agent"`.

**Residuals (accepted, not fixed):**

- **W3 — death between the carrier transaction and the run transaction** leaves
  a `Backlog`, `launch_mode='manual'` carrier task with no run. No automation
  can claim it: `auto_launch_run_plan` requires `launch_mode='auto'` and the C2
  auto-launch funnel requires a triaged/armed task. An operator abandons it.
- **W7 — a duplicate `run_delegate`** (at-least-once MCP redelivery) produces a
  second governed child. Bounded by the shared fan-out cap; both children are
  visible in `run_collect`. See D6.
- **W11 — an abandoned orchestrator leaves relaunchable carrier cards.** The
  cascade abandons the children's *runs*, not their *tasks*
  (`getUnlaunchedAutoChildTaskIds` selects `launch_mode='auto'` tasks with no
  run; a carrier task is `manual` and has a run), and
  `MANUAL_RUN_STATUS_LAUNCHABILITY.Abandoned` is `"launchable"`. The cards
  therefore show a Launch button. Accepted because **no automation can fire
  them** — only a human clicking a card they can read.
- **W12 — an orchestrator that exits normally leaves un-promoted `Review`
  children.** Nothing reclaims them: `Review` holds no scheduler slot, there is
  no `Review` sweeper, workspace GC only collects
  `DISPOSABLE_WORKSPACE_RUN_STATUSES` (`Done` / `Abandoned`), and the normal
  exit only revokes the token. This is pre-existing (ADR-100) but **amplified**:
  an agent child may be `workspace: none` and run straight to `Done` with
  nothing to park, whereas a Flow child always provisions a worktree and
  therefore always parks. The coordinator contract is "promote or cancel every
  child before finishing", enforced by prompt, not by the engine. Mitigations
  considered and not taken here: (a) a `Review`-age sweeper — needs a policy for
  "how long is too long" that no other status has; (b) auto-promote every
  delegated child — collapses `Review` into "safe to ship", which ADR-126
  deliberately keeps separate; (c) refuse the orchestrator's normal exit while a
  child is unsettled — turns a coordinator bug into a stuck run; (d) **auto-archive
  the child through the existing `workbench-lifecycle` `archive` primitive**
  (removes the worktree, preserves the branch) — the preferred future fix,
  because it reclaims the only scarce resource without asserting anything about
  the diff's fitness.

**Follow-ups:**

- **A durable delegation idempotency key** (closing D6): add
  `runs.delegation_key` plus a partial-unique index, and adopt the winner on
  conflict using the `evaluationBatchItemId` pattern already in
  `launchRunStaged` — `onConflictDoNothing()` → empty insert → re-select the
  winner → return it and compensate this attempt's orphan worktree. That is a
  migration, which this cut deliberately scoped out.
- **A production `maister-plugins` Flow-target example.** Deferred by owner
  decision; Flow-target coverage in this repository uses trusted in-repo
  fixtures only, and no third-party production Flow package enters the
  repository.
- **`workspaceMode: shared` for Flow children** (ADR-102's one-branch,
  one-Review, one-promote assembly model), which requires porting
  `sharedAgentWorktreePath` / `resolveSharedTreeWorkspaceForUpdate` onto the
  Flow launch path.

**Amendments:**

- 2026-09-02 — **Codex adversarial-review fixes.** (F1) `run.review` carries a
  required `cause` (`graph_completed | agent_exit | operator_stop |
  rework_released | sync_returned`) stamped by every writer through the one
  helper (the agent finalizer stamps `agent_exit`); `auto_launch_run_plan`
  auto-promotes only the two completion causes and is fail-closed for a
  missing one — an operator stop still wakes the parent exactly as before but
  can no longer turn a half-done diff into a `local_merge`. (F2) The cascade
  flips rows only, and four callers discarded its `cascadedRunIds` (operator
  stop, drop, the delegated `run_cancel`, the abandon route), so a grandchild
  of a cancelled child kept spending under an `Abandoned` row; every
  tree-cancelling caller now goes through `cascadeAbandonRunTreeAndStopSessions`
  (rows + every cascaded descendant's live session), and the reconcile sweep
  reaps a live session found under an `Abandoned` row — the recovery path for
  a crash or supervisor hiccup between the two. (F3) `run_plan`'s post-commit
  source launch swallowed every refusal into a `202` whose row was
  indistinguishable from a blocked dependent, nothing retried a sole failed
  source, and the parent — counting zero child RUNS — completed its node over a
  dead DAG (the Consequences' assumption that "the parent's cascade abandons"
  those tasks held only when a cascade ran). A partial refusal now carries
  `launchError` on its row plus the release-time system comment and self-heals
  on the next sibling settle; when EVERY source is refused the committed DAG is
  abandoned (parity with the carrier compensation) and the call answers the
  refusal's code, `PRECONDITION` when the codes mix. (F4) The flow snapshot's
  `flowRevisionId` / `resolvedRevision` / engine range came from the route's
  resolve while `runs.flow_revision_id` came from the launcher's own, later
  resolve — a repoint of `flows.enabled_revision_id` in between (an admin
  enable, or a concurrent launch's package-version choice) made the run
  execute one revision while its "immutable" provenance claimed another.
  `launchRunStaged` now writes those fields from the revision it selected,
  exactly as D7 already made it write the branch pair; the builder and the
  launcher input type no longer accept them.
- 2026-09-02 — **Review-driven refinements** (see Consequences): `run_cancel`
  abandons a Flow child; every Review flip of a delegated child emits
  `run.review` through one helper; the failed-launch compensation abandons the
  carrier instead of deleting it; one launchability gate is shared by the
  launcher, the resolver and the board projection (the resolver gaining the
  Ready-runner and stored-manifest checks); `run_plan` refusal codes follow
  `run_delegate`; as-plan release-time refusals are surfaced as system
  comments; the per-node `settings.delegation` knob is documented as advisory;
  the run-tree and board read models learned the `kind: "flow"` discriminant
  (kind-aware target eyebrow, carrier provenance chip).
- 2026-09-01 — **D8 refined during implementation: the decisive admission runs
  inside the LAUNCHER's run-insert transaction, not only at the route.** As
  first written, D8 put the lock, the count, and the carrier-task insert in one
  route-level transaction — but the child RUN is inserted by a *later*
  transaction (`launchRunStaged` / `launchAgentRun` own it), so the lock was
  released before the row the count reads existed. Two delegations issued
  inside that launch window would both have been admitted at `cap - 1`: the
  same "a transaction is atomicity, not mutual exclusion" trap the decision
  exists to close, one level up. `admitDelegatedChild` is therefore called
  again — gated on `input.parentRunId`, so a board launch is untouched — inside
  the transaction that inserts the run, under the same per-orchestrator lock.
  The route's call is retained and re-labelled a **fast path**: it avoids
  minting a carrier task and provisioning a worktree for an obviously over-cap
  request, and it is never the decision. This also means the guard now covers
  the as-plan auto-launcher for free, because every creation edge reaches one of
  those two launchers.

**Alternatives Considered:**

- _Hard-delete the carrier task when the launch fails after the carrier
  transaction_ (the first cut did this): rejected at the 2026-09-02 review —
  `runs.task_id` and `domain_events.task_id` are `ON DELETE CASCADE`, so a
  SELECT-then-DELETE could erase a run inserted concurrently and always erased
  the committed `task.created` fact; the task model's terminal exit everywhere
  else is `Abandoned`.
- _Add a `board_hidden` column to `tasks` so a `mode: run` Flow child has a task
  without a card_: rejected — a migration for a cosmetic axis, and fact 6 shows
  the card count is identical either way; the only thing omitting the relation
  removes is provenance.
- _Launch the Flow child through `launchAgentRun` with a flow-shaped payload_:
  rejected — it would duplicate (and drift from) the entire trust sequence,
  workspace provisioning, graph-state initialization, session set, and
  capability materialization that `launchRunStaged` already owns. REQ-07 is
  precisely that a Flow target gets the same invariants as a user launch.
- _Let the delegation body carry `baseBranch` / `targetBranch`_: rejected —
  every branch reachable this way is already reachable through the project's
  validated default, and accepting one would make branch topology a
  body-controlled locator on a path whose whole point is server-derived trust.
- _Enforce fan-out with a `COUNT(*)` outside a lock (the shipped `run_plan`
  shape)_: rejected — a transaction is atomicity, not mutual exclusion; two
  concurrent delegations at `cap-1` would both read `cap-1` and both commit.
- _Use `SCHEDULER_LOCK_KEY` for the admission lock_: rejected — correct, but it
  serializes every delegation on the whole platform against the scheduler for
  the sake of a per-orchestrator bound.
- _Emit `run.review` unconditionally from the graph runner_: rejected — a
  top-level Flow run reaching `Review` has no orchestrator to route to, and
  emitting for it would put every board run's review into a consumer population
  that only orchestration reads. The agent launcher already gates on
  `parentRunId`; matching it keeps one rule.
- _Delete `auto_launch_run_plan`'s `runKind` check instead of widening it_:
  rejected — the check is what keeps `scratch` (and any kind added later) out of
  the as-plan machinery. An allow-list widens exactly as far as intended.
- _Keep the unreachable `parent.taskId`-absent branch as an assertion_:
  rejected — it is unreachable only because the flow graph runner is the sole
  issuer of an orchestrator token today. It becomes live the moment an agent
  orchestrator exists, where `runs.task_id` may legitimately be null, so it
  stays as a logged graceful path.
