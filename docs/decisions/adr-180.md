# ADR-180: Permission deadline has one owner

> Part of the ADR log — hub, index, and editing rules: [`../decisions.md`](../decisions.md).

**Date:** 2026-09-22
**Status:** Implemented

**As-built operator surface amendment (2026-09-23, P0-4 — Implemented):**
The web and external respond routes expose a bounded `details.reason`
discriminator for refused or delayed answers; the top-level workspace
`reason` and host `ReasonToken` namespaces do not change. MCP preserves the
same public JSON body on `hitl_respond` failures. A claimed but undelivered
row projects `answerState: "answer_stored"` and a sanitized public replay
envelope to the board, inbox, run and scratch cards. These cards show the saved
choice and retry only the identical payload. 202 pending states and a
post-claim 503 render that state immediately. The web uses one
`delivery_unavailable` reason for all host 503 situations; the host does not
provide a more precise discriminator. The precise token/action table, null
semantics and replay exceptions live in
[`hitl.md`](../system-analytics/hitl.md#respond-refusal-reasons-p0-4--implemented),
with request/response schemas in the web and external OpenAPI contracts.
This is a read/response/UI change with no DB migration, new state transition,
or supervisor edit. The terminal flow run's durable cause is deferred to B6:
the existing attempt failure writer cannot add error metadata without
altering the ledger. A crash within the 30-second terminal grace that answers
410/Failed before ADR-177 reconciliation reaches Crashed/Recover is likewise
a separate follow-up. The responding card's feedback names the ended agent
session and recovery action without claiming that human input expired.

**Qualification finding (2026-09-23, separate ADR-180 follow-up):** In the
real-supervisor RED13/RED14 agent cases, `session.prompt` sometimes settles as
`succeeded` even though the terminal witness orders it after the checkpoint.
The current agent grant then takes `kind: "result"`, marks the original HITL
row delivered, and skips the `continue`-only reissued-permission delivery.
The strict `continue` assertions fail intermittently; the affected runtime
code is unchanged from master. P0-4 leaves this classification and every
state transition untouched. Its full integration qualification remains open
until the agent checkpoint handoff is corrected and the complete suite passes.

> **Amends [ADR-006](../decisions.md#adr-006-hybrid-hitl-keep-alive--checkpointresume):**
> the keep-alive window named there is now owned by the web alone. The supervisor
> keeps only an absolute cap, and when that cap fires it performs the same
> graceful checkpoint the manager's route performs.

**Context:** A pending ACP permission had **two** deadline owners that never
talked to each other.

The supervisor arms one `setTimeout` per pending permission at registration
(`supervisor/src/pending-permissions.ts`), sized from
`MAISTER_KEEPALIVE_MINUTES`. It is set once and never extended — the registry
interface has no renew. The web's keep-alive window is the other owner:
`runs.keepalive_until` is bumped by every operator activity on the run page, and
the keep-alive sweeper checkpoints the session only once that column is in the
past.

The two diverge the moment an operator stays active. At `T + 30 min` the host
timer fires and **rejects** the deferred with `HITL_TIMEOUT`. A rejected
permission is a producer fault: `bounded-acp-stream.ts` routes it to
`input.onFailure`, `acp-client.ts` calls `record.abortOutput`, and `spawn.ts`
tears the child down with `SIGKILL` and stamps the prompt
`producer-output-incomplete`. The agent is gone, the ACP handle is not
resumable, and the operator's answer — typed at minute 31 into a page that never
stopped bumping `keepalive_until` — arrives at a session that no longer exists.
`web/lib/services/hitl.ts` reads the resulting `410` as terminal and flips the
run to `Failed` (flow) or `Crashed` (scratch).

The route the manager calls to park a session, `POST /sessions/:id/checkpoint`,
differs from that expiry path by **one call**: it *cancels* each pending
deferred (`{outcome:"cancelled"}`, which the adapter journals for replay)
instead of rejecting it, marks the shutdown intentional, and sends `SIGTERM`
with a grace period. The handle stays resumable. The destructive path and the
correct path were one method call apart.

Graceful supervisor shutdown had the same defect in a second spelling:
`shutdown.ts` called `purgeSession` — a **reject** — before marking the shutdown
intentional, so the supervisor raced its own `SIGTERM` with a `SIGKILL` it
caused itself.

**Decision:**

**The web owns the deadline; the host keeps only an absolute cap.** The
supervisor's per-permission timer stops being a copy of the keep-alive window.
`MAISTER_KEEPALIVE_MINUTES` is re-scoped web-only, and the host reads a new
`MAISTER_PERMISSION_MAX_HOURS` (default **24**, matching
`MAISTER_NEEDSINPUTIDLE_TTL_HOURS`). It is parsed as a positive **float** — the
one deviation from the surrounding `positiveIntFromEnv` convention — because the
integration lane compresses the cap to sub-second values, and an integer-only
parser would leave the timer path entirely unpinned.

**Host give-up is a checkpoint, never a SIGKILL.** The teardown body inside
`POST /sessions/:id/checkpoint` is extracted verbatim into
`supervisor/src/checkpoint-teardown.ts` and reused by the cap timer: cancel every
open deferred with `"checkpoint"`, `markIntentionalShutdown`, stop the output,
`SIGTERM`, await the grace. The route keeps its ADR-166 command envelope, fence
and ledger receipt; the cap has **no** envelope — it is host-internal, carries no
`command.id`, and a throwing teardown is logged, not returned to anyone. The
`delete` and `cancel` teardowns are *not* folded in: they answer different
questions with different post-conditions.

**Graceful shutdown changes order only.** `markIntentionalShutdown` first, then
`cancel` (not `purgeSession`) for every open request, then `SIGTERM`. The
terminal `reason` deliberately stays `"intentional"` — switching it to
`"checkpoint"` would re-classify every shutdown-interrupted step as
`STEP_CHECKPOINTED`, make the lifecycle projector throw `permanent(...)` for a
checkpoint terminal over an uninitialized incarnation (poisoning that run's
projection cursor), and collide with the ADR-177 `turn_lost` arm. A `Running`
flow run keeps the existing ADR-177 `turn_lost` boundary after restart.

**An answer in the race window is a resume, not a failure.** While the registry
entry survives its 30 s terminal grace, `POST /sessions/:id/input` against a
session that terminated **intentionally with its deferreds cancelled** answers
`410` with `details.reason: "session_checkpointed"`. The predicate is an
allow-list (`{"checkpoint", "intentional"}`), never a single-value equality;
`"fenced"` is excluded because a fenced session means a newer driver generation
owns it and `assignment_fenced` is its existing arm. The park cancels the
deferreds before the child has exited, and the terminal lands only after its
output drains: an input inside that window waits for the exit (bounded by the
kill grace) and takes the same arm, and a park that outlasts the grace answers
a retryable `503` rather than the terminal `410`. Web-side, `hitl.ts` reads
that token before the noop-idempotent branch and takes the **existing** idle
resume path of the run's KIND — `markCheckpointed`, then `resumeRun` +
`scheduleResumedSessionDrive` for a flow, the agent idle claim +
`startAgentSession` for an agent — answering `202 {state:"resume-in-progress"}`.
The run is never `Failed` or `Crashed` on that path. After the 30 s grace the
registry entry is gone and `/input` answers the unchanged retryable `503`; the
delivery intent that refusal leaves behind names a command the host never
admitted, so the idle resume **withdraws** it (the same rule the live retry
applies) and re-delivers the stored answer to the resumed session instead of
waiting for a receipt that cannot arrive.

**The checkpoint boundary is proven by the terminal event, not only by the
command.** `permissionCheckpointOrder` proved handoff ordering against the
checkpoint command's **admission** event. That event is emitted only while the
registry still holds the session (`persistReceipt` is gated on a live entry) and
the entry is removed 30 s after the terminal, while the sweep tick is 60 s — so
for a host-initiated checkpoint the command row exists and the admission event
normally does not. That is the ordinary case, not an edge case. The function
therefore accepts a second witness: the session's own
`session.exited{reason:"checkpoint"}` event on the same stream, selected with
`.limit(2)` and requiring **exactly one** match. Absence of both witnesses
returns `"unproven"` — a terminal decision never rests on the absence of a
signal — and the resolved order carries **which** witness proved it
(`boundary: "command" | "terminal"`), so a test can tell a working extension
from a coincidence. A checkpoint command the host acknowledged as already
parked (`alreadyCheckpointed: true`) did not cause the park: its admission sits
after the session's own checkpoint terminal, so it yields to that terminal and
orders a prompt only for a session that ended on its own, where a prompt that
completed before the acknowledgement is a result. The terminal witness
classifies the interruption — the host
commits an interrupted prompt's rejection after the session's terminal, so it
reads `after_checkpoint` — but it authorizes no flow result handoff on its own:
that grant still names a checkpoint command row, so a flow run the host parked
re-prompts through the ordinary resume claim. The **agent** idle claim, whose
readiness used to wait for a checkpoint command that a host-initiated park
never mints, resumes on the terminal witness with a null `checkpointCommandId`.

**The park has a bound that does not depend on the operator's tab.** Removing
the host rejection removes the only bound on a live-looking dead run:
`bumpKeepalive` extends `keepalive_until` for `NeedsInput` with no
session-liveness check, and Pass 1 of the keep-alive sweeper selects on
`keepalive_until < now`. An operator holding a tab open would otherwise keep a
checkpointed session out of Pass 1 forever, so Pass 2's 24 h `Abandoned` rule
could never fire either. Pass 1 gains a **second, targeted** candidate query with
its own `LIMIT`: `NeedsInput` runs whose active session holds a `checkpointed`
incarnation, independent of `keepalive_until`. It is a positive witness —
`run_session_incarnations.state='checkpointed'` is written only for
`session.exited{reason:"checkpoint"}`, and the partial unique index guarantees at
most one per session — and it calls the same `markCheckpointed` CAS. Only
`checkpointed` qualifies: `exited`/`crashed` incarnations belong to the
crash-reconcile paths. The incarnation must belong to the run's **current**
assignment: between `markResumed` (which mints the next assignment) and the
create ack (which retires the prior incarnation) the run is `NeedsInput` with a
`checkpointed` incarnation of the prior assignment, and a park there would
release the resume's fresh assignment under its own feet.

**Diagnostics, not control flow.** The cap-initiated terminal carries
`cause: "permission_cap"` on its `session.exited` payload. It is a **single
literal**, not an enum, because nothing else produces one; it is read by nobody
for control flow; and it must not be spelled as a new `reason` value, because
the SSE decoder validates `reason ∈ {checkpoint, intentional, fenced}` and drops
the whole terminal event otherwise, hanging the driver on an exit it never sees.

**Consequences:**

- An active operator's answer is delivered instead of killing the agent. The
  destructive class the old timer created — `producer_permission_failed` →
  `SIGKILL` → `Failed` — is gone for the deadline path and **unchanged** for
  genuine producer faults (`producer_permission_limit`,
  `producer_permission_invalid`, purge of a dead session).
- Four paths now write `NeedsInput → NeedsInputIdle`: the sweeper's keep-alive
  arm, the sweeper's new checkpointed arm, `markCheckpointedFromExit` on the flow
  driver's own stream, and the race-window answer. They are safe because all four
  go through `idleFromNeedsInput`'s CAS. The invariant is not "one writer" but
  "every writer shares the CAS".
- **Accepted residual: the escalation window.** If the `SIGTERM` grace expires
  and `checkpointSession` falls through to `SIGKILL`, the session was already
  marked `markIntentionalShutdown("checkpoint")`, so the heartbeat still
  classifies the terminal as `session.exited{reason:"checkpoint"}` — while the
  ACP handle's validity is **unproven**. This window has **no dedicated
  control**. Its owner is the existing resume failure classification
  (`resume.ts` → `CHECKPOINT` terminal → `failResumedRun`), and no control may
  assert a clean park in that case.
- **Accepted residual: the evidence read is not index-covered.** The terminal
  witness predicate has no covering index; the closest, `execution_events_run_
  sequence_idx`, leads with `run_id`, so the plan is an index scan on that run's
  events plus a heap filter, with the `payload->>'reason'` deref as an unindexed
  residual. It is a clone of the live pattern beside it, bounded by one run's
  event count, and runs once per resume. An index is the follow-up if latency is
  ever measured, not a precondition — adding one now would make the "no
  migration" claim false and pull in an ERD regeneration.
- `HITL_TIMEOUT` no longer means "the host permission window elapsed". It now
  carries `details.reason: "session_checkpointed"` on a **non-terminal** arm, and
  P0-4's operator-facing copy inherits that discriminator.
- `details.reason` is a closed enum in two spec files and two TS mirrors, and
  the mirror test is one-way (`code ⊆ doc`), so the token lands doc-first.
- A host that loses its manager no longer spends tokens: the agent sits idle
  holding a cancelled-on-teardown deferred until the absolute cap, rather than
  being killed at 30 minutes.
- **No flow grant needs a null `checkpointCommandId`.** A host park needs an
  OPEN deferred, and an input the host has acknowledged has already resolved
  its deferred, so the cap can only park a session on a *second* permission in
  the same prompt — the pre-existing S2.6 non-goal ("repeated or gate
  permission checkpoints remain outside this implemented node path"), which the
  resume refuses at `permission_resume_source_count` exactly as it did before
  this decision. A refused (503) or parked (410 `session_checkpointed`) delivery
  has no acknowledged input and takes the ordinary resume claim, so the
  `!checkpoint` arm of `prepareFlowPermissionResult`
  (`source_checkpoint_uncommanded`) classifies a state no single-permission
  prompt reaches. The agent grant is the one that carries a null
  `checkpointCommandId`, because an agent's idle claim is what a host park
  strands.

**Alternatives Considered:**

- **Host timer as a margin (`timeout = window × k`):** rejected — two owners
  remain and the margin is a heuristic. It makes the race rarer without making
  the losing side non-destructive.
- **An extend route (`POST /sessions/:id/permissions/:requestId/extend`) per
  keep-alive bump:** rejected — a new enveloped command and ledger receipt per
  activity ping, and the race survives a late bump. Once the expiry is harmless,
  no scenario was found that the chosen pair fails and this fixes.
- **Keeping the command-only checkpoint boundary and minting a command row for
  the host cap:** rejected — minting the row is not enough, because the proof
  needs the *event*, and the admission event requires a live registry entry that
  is normally gone by the time the sweep runs.
- **Switching graceful shutdown's terminal `reason` to `"checkpoint"`:**
  rejected — a three-way fanout (step re-classification, a poisoned projection
  cursor, the ADR-177 `turn_lost` arm) for no gain over the ordering fix.
- **A new `runs.status` for a host-parked run, a new route, an injectable test
  clock, a new index, or a migration:** each considered and rejected. The change
  needs none of them; the test windows compress through environment values and a
  DB column that real code already writes.
