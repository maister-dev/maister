# `json` field type widened a shared grammar but missed the HITL submit coercion switch

**Date:** 2026-09-01 16:20
**Files:** web/components/board/hitl-decision-controls.tsx, web/components/board/run-hitl-response.tsx, web/lib/config.ts, .ai-factory/specs/feature-m26-structured-output-run-context.md, docs/flow-dsl.md
**Severity:** high

## Problem

ADR-162 added `json` (accepts any JSON value) to `formSchemaSchema`. That grammar
is shared by graph node `output.result` AND HITL `form_schema`. The HITL form
renders every field as a text input and coerced the submitted string back to its
declared type with an if/else chain:

```ts
if (field.type === "number") { ... }
else if (field.type === "boolean") { ... }
else { response[field.name] = raw; }   // json landed here
```

The chain was not swept for the new type. A HITL field declared `type: "json"`
therefore submitted the operator's raw STRING — and because `json` accepts any
value, the server-side validator **accepted it**. The flow received a string
where the author declared JSON, with every gate reporting success.

Fully reachable, not theoretical: `collectReferencedSchemaPaths` collects
`settings.form_schema`, so the new 3.6.0 floor permits `json` in a HITL schema,
and `hitl-validate.ts` shares the widened validator.

## Root Cause

Two compounding causes.

1. **The widened union was swept for the surfaces the author was thinking about**
   (the Studio builder's type list, the template-variable catalog, the node-output
   seam) and not for the one three modules away — a client component's coercion
   switch.
2. **Nothing could fail.** `HitlFormFieldView.type` is `string`, not the
   field-type union, and the consumer was an if/else chain with an `else`
   fallback. A missing branch is representable, so neither `tsc` nor any test
   objected. The project rule "a map keyed by a closed union whose miss silently
   falls back hides drift" describes this exactly.

What made it *dangerous* rather than merely wrong is a property unique to `json`:
every other unhandled type (`array`, `object`) also falls through to the raw
string, but the validator REJECTS a string for those — loud and actionable.
`json` accepts everything, so the same miss becomes a silent wrong-shape success.
**A permissive new type converts a pre-existing loud gap into a silent one.**

## Solution

Replaced the if/else with `FORM_FIELD_COERCERS: Record<FormSchemaFieldType,
(raw: string) => unknown>` plus a `coerceFormFieldValue(type, raw)` wrapper
exported from the module that already owns `formFieldsFromSchema`. Adding a
grammar type without a coercer is now a **compile error** — proved by deleting
the `json` entry and observing `TS2741: Property 'json' is missing`.

`json` parses with a raw-string fallback (mirroring the existing `number`
fallback, and safe because `json` accepts a string); `array`/`object` keep
submitting the raw string so the server rejects them with an actionable message
instead of this layer guessing a shape.

Also landed in the same pass, from the same review:
- three stale refusal messages in the frozen spec's C-10 table reconciled against
  the shipped strings (the spec had invented a `flow install failed [stage=schema]`
  prefix the code never emits);
- the ADR-162 node-type refusals moved **above** the M26 1.3.0 engine gate, so an
  orchestrator at `engine_min: 1.2.0` is told it needs 3.6.0 rather than 1.3.0 —
  a bump that would not have helped;
- coverage for a `null` element under a typed `items` (rejected — elements have
  no optionality) and under `items: { type: "json" }` (accepted);
- a cost note that `on_mismatch` on a `consensus` node re-runs the whole fan-out.

## Prevention

- **When a change widens a closed union, the sweep is over CONSUMERS THAT BRANCH
  ON IT, not over the modules the feature touches.** `grep -rn 'type === "<any
  existing member>"'` finds them; a per-file review of the diff never will,
  because the missing consumer is by definition outside the diff.
- **Convert the fallback into a compile error in the same pass.** An if/else with
  an `else`, or a `Record<string, …>` with a runtime default, is where union
  drift hides. `Record<Union, …>` turns the next miss into a build failure —
  this is worth doing even when fixing only one member.
- **Rank a new enum member by how it FAILS, not by what it does.** A permissive
  member (`json`, `any`, `unknown`, a wildcard scope) silently absorbs the
  fallback path that every other member would have rejected loudly. Ask "if a
  consumer forgets this member, is the result an error or a wrong value?" —
  wrong-value members deserve the exhaustiveness guard first.
- **A regression test for this class asserts the coerced VALUE, not that the
  coercer ran.** Prove it non-vacuous by restoring the old fallback and watching
  it go red.
