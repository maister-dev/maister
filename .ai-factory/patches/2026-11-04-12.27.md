# Verify the complete Triager handoff and checkpoint interruption evidence

**Date:** 2026-11-04 12:27
**Files:** web/lib/agents/__tests__/agent-queue-terminal.integration.test.ts; web/lib/flows/graph/__tests__/permission-result-failure.integration.test.ts
**Severity:** medium

## Problem

The actual-Supervisor Triager control stopped at accepted qualification with
`enqueue: false`. Separate qualification and automatic-launch tests did not
prove that one real successful operational preparation and terminal publication
queued the selected delivery Flow. Seven permission checkpoint controls also
expected the obsolete generic `ACP_PROTOCOL` error rather than the established
intentional checkpoint classification.

## Root Cause

Acceptance coverage was split at the publication boundary. A first extension
incorrectly assumed the backstop scheduler would create the intent, although
the operational finalizer already performs automatic enqueue and promotion.
Checkpoint tests had retained their older error expectation while the actual
Supervisor contract now distinguishes intentional interruption from adapter
failure and successful completion during checkpoint.

## Solution

Extend TB07 with a real installed trusted CLI Flow and `triage_then_launch`.
The existing actual token-bound machine assessment selects that Flow and runner.
Assert no intent before successful Triager completion, then one durable automatic
intent tied to the actual qualification, evidence SHA, immutable Flow revision
and runner. Invoke the real automatic scheduler job afterward and prove it does
not create another intent. Existing preparation ownership, baseline, operational
result, terminal publication and cleanup assertions remain intact. No fabricated
accepted assessment, launch callback or provider/model request is introduced.

The real whole three-case Supervisor suite passed on the corrected boundary in
`/private/tmp/maister-review-r6-triager-chain-green.log`; invocation
`79872416-67ef-4fec-bc2c-1bacfccbe645` completed with zero process leaks and its
PostgreSQL container stopped. The preceding real run proved the chain itself
but failed the inaccurate `launched === 1` backstop expectation; that is test
correction evidence, not a newly fixed production bug.

For the seven intentional interruptions, require `CHECKPOINT`,
`session_checkpointed`, `stopReason: checkpoint`, and the original command,
Run, assignment epoch, session and canonical terminal event lineage. Preserve
the three successful completion-during-checkpoint controls and all explicit
adapter-failure expectations. The full 23-case permission suite passed in
`/private/tmp/maister-review-r8-permission-green.log`, including all three
successful completion and all three explicit adapter-failure controls.
Invocation `12738067-e974-4b50-87d5-0dfec71ad40f` completed with zero process
leaks and its PostgreSQL container stopped. The original frozen gate supplied
the seven obsolete-expectation failures; the runtime completion correction was
implemented and verified separately. Scoped ESLint and diff checks passed.
These test-only changes add no runtime logging.

## Prevention

Trace the real transition owner before asserting which scheduler call creates
work. Extend a real existing journey across a missing boundary rather than
combining unrelated green tests into an end-to-end claim. When an interruption
classification changes, keep receipt and canonical event lineage strict and
retain distinct successful-completion and genuine-failure controls.
