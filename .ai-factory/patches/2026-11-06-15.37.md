# Release controlled Flow children after failed browser assertions

**Date:** 2026-11-06 15:37
**Files:** web/e2e/flow-target-delegation.spec.ts
**Severity:** low

## Problem

The delegated-Flow browser case could fail before reaching its fixture gate
release, leaving already-running CLI children blocked during later cases.

## Root Cause

Only the successful test path wrote the existing `DELEGATED_FLOW_RELEASE` marker.
The frozen aab070c39 lane failed its exact two-child binding assertion before
that write; its retained safe snapshot showed both eventual child Runs still
Running at their held `touch` nodes. This establishes a cleanup obligation, not
the cause of the binding delay or the separate M38 failure.

## Solution

Reuse one idempotent marker writer on the existing successful release path and
in Playwright `afterEach`. The original wait, ordering, exact counts and timeouts
stay intact. Failure remains recorded before teardown; cleanup does not alter
Runs, database state, capacity or technical runtime policy. The next coordinated
frozen browser lane owns execution qualification; no isolated rerun is claimed.

## Prevention

Every controlled test gate needs an unconditional release path even when an
assertion before the intended release fails. Preserve the behavioral barrier and
its failure evidence while preventing fixture-held work from contaminating the
rest of the lane.
