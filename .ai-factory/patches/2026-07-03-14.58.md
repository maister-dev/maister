# Codex adversarial-review fixes on ADR-126 auto-promotion (starvation, hold-race, auth-order)

**Date:** 2026-07-03 14.58
**Files:** web/lib/scheduler/handlers/auto-promote.ts, web/lib/runs/promote.ts,
web/app/api/runs/[runId]/promotion-hold/route.ts, web/lib/scheduler/jobs.ts,
web/app/api/__tests__/auto-promotion-routes.integration.test.ts,
web/lib/runs/__tests__/auto-promote-race.integration.test.ts,
web/lib/scheduler/handlers/__tests__/auto-promote.integration.test.ts
**Severity:** high

## Problem

A Codex adversarial review of the auto-promotion branch returned three defects,
all in the sweep → merge path:

1. **[high] Sweep starvation.** `runAutoPromoteJob` selected candidates with a
   bare `LIMIT 20` and **no `ORDER BY`**, and its prefilter admitted rows that
   evaluation permanently rejects (configured-but-disabled projects, deny-listed
   / no-lane / ambiguous diffs, non-strict checks). Those rows never mutate, so
   an arbitrary blocked subset re-appeared every tick and an eligible run outside
   the window could be starved indefinitely.
2. **[high] Hold/config race.** The sweep evaluated eligibility seconds before
   calling `promoteRun`; a user promotion hold or a project lane-disable landing
   in that window was **not** re-checked — `promoteRun`'s claim tx re-read run
   `status` only — so the run merged automatically after the safety switch was
   thrown, defeating the Hold UI.
3. **[medium] Auth after body-parse.** `PUT /promotion-hold` parsed and validated
   the request body before `requireActiveSession()`, letting an unauthenticated
   caller probe the body schema (422 before 401).

## Root Cause

1. **Bounded scan with no progress guarantee.** A capped sweep over a set that
   contains never-mutated permanent-skip rows needs *rotation* (a cursor), not
   just ordering — permanent skips are indistinguishable from temporary skips
   (grace / readiness / open-HITL) at the SQL layer, so you cannot simply exclude
   "already skipped" rows, and any fixed order lets an unlucky pileup wedge the
   window.
2. **A shared choke point re-guarded only ONE of its preconditions.** The claim
   tx defends `status='Review'` under a `FOR UPDATE` lock but was never taught
   the auto-promotion-specific guards (`promotion_hold`, project master toggle),
   which are written by *other* transactions (the hold route, the settings route)
   with no lock coordination. A TOCTOU is inevitable unless the authoritative
   claim re-reads them.
3. **Sibling drift after a partial hardening round.** A prior Codex round fixed
   the auth-order on the settings PATCH route (it still carries a
   `// Auth-first (Codex-4)` comment) but the twin `promotion-hold` PUT kept the
   old body-before-auth shape.

## Solution

1. **Durable rotating keyset cursor (F1).** Added a deterministic
   `ORDER BY coalesce(review_entered_at,'infinity'), id`, pushed the master
   toggle into SQL (`(auto_promotion->>'enabled')::boolean IS TRUE`), and added a
   keyset cursor persisted in the seeded singleton job's `scheduler_jobs.target`
   jsonb (`auto_promote.default`, id reused from `jobs.ts` via a new export — not
   a duplicated literal). Each tick resumes after the previous window and resets
   at a short tail to wrap, so every candidate is visited within
   `ceil(N/LIMIT)` ticks. No migration; an absent job row reads null ⇒ head-start.
2. **Attribution-gated supersede recheck (F2).** Inside `promoteWorkspaceRun`'s
   existing claim tx, for `input.attribution?.source === 'auto_promotion'` only,
   re-read the (already-loaded, under-lock) `promotionHold` and re-resolve the
   project config; abort with `MaisterError('CONFLICT', …, { details: {
   autoPromotionSuperseded: 'held' | 'disabled' } })`. The sweep branches on
   `err.details.autoPromotionSuperseded` (NOT the code — a real git merge CONFLICT
   still routes to give-up) to classify it a benign skip: no system hold, no
   give-up comment. Human / scratch / orchestrator promotes never set attribution,
   so they are untouched (proven by the human-with-hold test).
3. **Reorder auth-first (F3).** Moved `requireActiveSession → loadRunProjectId →
   requireProjectAction` above the body parse in the PUT handler, mirroring the
   settings route.

Test-harness note: the pre-existing race test seeded a project with no
`autoPromotion`, which the new F2 gate correctly rejects as disabled — so the
seed was corrected to an enabled config (the realistic precondition for an
attributed promote to exist).

## Prevention

- **A capped background sweep MUST guarantee progress, not just bound work.**
  When a periodic `LIMIT`ed scan runs over rows that can stay non-eligible
  indefinitely without being mutated, add a durable rotating cursor (or otherwise
  guarantee full traversal). Reviewer check: "if the first N rows are permanently
  ineligible and never change, does row N+1 ever get processed?"
- **Re-guard EVERY precondition at the authoritative choke point, not just
  status.** A pre-side-effect claim tx that re-reads one predicate under lock but
  trusts a caller's earlier read of the others has a TOCTOU for each un-rechecked
  predicate written by an out-of-band transaction. List the guards; re-check all
  of them (or the ones cheap enough) under the claim.
- **Prefer `MaisterError.details` (ADR-093) over a new code or a message match**
  when an internal caller needs to distinguish a benign, expected failure from a
  real one — the UI still branches on `code`; the server branches on `details`.
- **When hardening a route pattern, grep the class and fix every sibling in the
  same pass** (skill-context "fix the class" rule). Auth-order was fixed on one
  route and missed on its twin; the sweep here confirmed only `promotion-hold`
  PUT drifted.
- **A new precondition on a shared function breaks tests that seeded the old
  looser state.** Re-run the full consumer suite, not just the new tests
  (here: 44 files / 282 tests across every promote path + the scheduler).
