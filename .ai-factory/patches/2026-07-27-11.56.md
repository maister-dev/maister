# Assistant activity cursor and contract drift hardening

**Date:** 2026-07-27 11:56
**Files:** docs/api/external/operations.openapi.yaml, docs/system-analytics/assistant-activity.md, web/app/api/v1/ext/activity/__tests__/route.integration.test.ts, web/app/api/v1/ext/runs/[runId]/activity/__tests__/route.integration.test.ts, web/lib/ext-activity/__tests__/cursor.test.ts, web/lib/ext-activity/__tests__/pulse.db.integration.test.ts, web/lib/ext-activity/__tests__/run-activity.test.ts, web/lib/ext-activity/cursor.ts, web/lib/ext-activity/run-feed.ts, web/lib/ext-activity/service.ts, web/lib/ext-activity/types.ts, web/lib/runs/run-transcript-projector.ts
**Severity:** high

## Problem

The new assistant-activity surface had multiple replay and contract defects:

- the pulse bootstrapped and replayed `domain_events` with a naive `id > since`
  read, so an older in-flight transaction could be skipped forever once a newer
  transaction committed;
- per-run activity pagination used only `lastMutationId > sinceId`, so equal
  mutation-horizon siblings could disappear across page boundaries;
- the OpenAPI contract declared several runtime-null fields as non-nullable and
  omitted `decision_request` from the emitted `needsYou.kind` enum;
- the route tests still used a lint-invalid `const module = await import(...)`
  pattern.

## Root Cause

This was a shared "cursor treated as a simple scalar" failure across both
assistant-activity surfaces.

- The pulse reimplemented `domain_events` replay without copying the
  established commit-horizon fence from the dispatcher.
- The per-run cursor encoded only the mutation horizon and ignored the stable
  item id needed to order same-horizon siblings.
- The external schema mirrored hand-written assumptions instead of deriving its
  nullability/kind set from the runtime truth already present in code and DB
  schema.
- The transcript projector had a second sibling weakness: it assumed adapter
  monotonic ids were always present, but the replay boundary needed an honest
  fallback when they were absent.

## Solution

- Added the `tx_id < pg_snapshot_xmin(pg_current_snapshot())` horizon to both
  pulse bootstrap-tail selection and replay reads.
- Upgraded run-activity cursors to an opaque `{ lastMutationId, lastItemId }`
  model with encoded stable-item tiebreaking, while preserving the plain
  numeric mutation id for item fields.
- Tightened the transcript projector to preserve real monotonic ids when
  present and synthesize a strictly increasing replay horizon only when a line
  lacks one, so legacy logs still replay honestly.
- Derived `PulseEventKind` from the shared domain-event taxonomy and
  `NeedsYouItem.kind` from the DB `HitlRequest` union.
- Fixed the external contract nullability/kind drift and documented the commit
  horizon plus opaque cursor semantics in the analytics/spec surfaces.
- Added focused regression coverage, including a DB-backed test that proves
  pulse bootstrap no longer skips an older in-flight transaction.

## Prevention

- Treat every replay cursor as a contract with ordering rules, not just a
  single integer field.
- When one cursor reader/writer uses a consistency fence, grep sibling replay
  surfaces and port the same fence in the same pass.
- When an enum or nullable field already exists in code/schema, alias it or
  derive from it instead of hand-mirroring it in a second type.
- Add one DB-backed regression whenever correctness depends on transaction
  visibility or commit order; unit tests alone cannot prove those cases.
