# Stop poisoning the artifact projector over adapter telemetry

**Date:** 2026-09-15 12:20 (Europe/Moscow)
**Files:** `web/lib/projector/artifact-projector.ts`,
`web/lib/projector/__tests__/artifact-projector-shapes.test.ts`,
`docs/system-analytics/execution-event-plane.md`.
**Severity:** high

## Problem

`canonical-artifact-projector-v1` was poisoned on every run that reached it —
15 consumers on the stand, all of them this one projector, while the other 99
consumers were `ready`. The poison positions are at the very start of each run:
`run_sequence` 4 of 6824, 5 of 61, 8 of 10913. A poisoned consumer's cursor
never advances, so from the fourth event onward NOTHING in the run is projected.
One of those runs is formally `Done` with no artifacts projected at all.

## Root Cause

`deriveFromLine` throws on an unrecognised `sessionUpdate` discriminant, and its
own comment promises "the caller can WARN + skip while still advancing". The
caller did the opposite: every non-`ExecutionEventProjectionError` was rewrapped
as `permanentCanonicalProjectionError(...)`, and `permanent = true` poisons the
consumer immediately with no retry and `next_retry_at = null`.

Three frames tripped it across the 15 consumers — `model_advisory` (7),
`usage_update` (6) and `session_info_update` (2) — all harmless telemetry that
derives no artifact. A consumer stops at the FIRST unknown frame it meets, which
is why the poison positions differ per run.

The allow-list was not short by three, it was short by SEVEN. Read against the
`@agentclientprotocol/sdk@1.4.0` schema, it was missing six of the protocol's
own variants — `usage_update`, `compaction_update`, `compaction_summary_chunk`,
`config_option_update`, `plan_update`, `plan_removed` — plus the vendor
extension `model_advisory`. `usage_update` is simply the highest-volume one
(~1600 events in a single run), so it surfaced first. The rest were live
landmines.

The deeper defect is the caller's classification: adapters keep adding frames,
so every future one would poison the projector at its fourth event.

## Solution

- Replace the hand-grown `||` chain with `NON_DERIVING_SESSION_UPDATES`, taken
  from the SDK schema rather than from the shapes that happened to poison a
  consumer: every protocol variant except `tool_call`/`tool_call_update`, plus
  the `model_advisory` vendor extension. An ordinary run logs nothing.
- Give the classifier a typed `UnknownSessionUpdateShape`. The caller WARNs with
  the discriminant — the only thing needed to allow-list the next one — and
  advances, honouring the contract its comment already stated.
- Deliberately NARROWER than "catch everything and skip": only the typed
  unknown-discriminant error degrades to a warning. A malformed event (missing
  `update` payload) and any unexpected error from the derivation itself still
  poison, so a real defect in `deriveFromToolCall` cannot hide as silent
  artifact loss.

## Verification

- RED: the new unit cases failed with the stand's exact error,
  `ExecutionEventProjectionError: canonical artifact event has an invalid shape:
  unknown sessionUpdate shape: model_advisory`, `permanent: true`. The malformed
  case passed before and after.
- GREEN: 17/17. Once warn+skip is in, the allow-list no longer controls the
  poison — it controls LOG VOLUME, so the cases assert silence through a mocked
  logger. Falsified twice, each biting only its own case: dropping
  `usage_update` from the allow-list fails just that shape's silence assertion
  ("expected spy to not be called, called 1 times"); disabling the warn+skip arm
  fails just the unknown-shape case (rejects `permanent: true`).
- `lib/projector` + `lib/execution-host` unit suites; the artifact projector
  integration suite 1/1; `tsc --noEmit` clean.

## Operations

The code fix does not un-poison existing consumers. After deploying, rearm each
one (the mechanism is documented in `execution-event-plane.md`):

```
pnpm --dir web execution:projection:rearm --consumer canonical-artifact-projector-v1 \
  --run <run-id> --event <last_error.eventId> --cursor <last_run_sequence> \
  --error-generation <last_error.errorGeneration>
```

Rearming before the code is deployed re-poisons on the same event.

## Prevention

Derive an allow-list from the protocol, not from the incidents. Three shapes had
been observed; enumerating the SDK's own schema found six more that nothing had
tripped yet. A list grown one outage at a time is a list that schedules the next
one.

A comment that states a failure policy is not the policy. When one function
throws for a caller to classify, the classification belongs to a TYPE, not to a
convention — the caller here rewrapped everything as permanent while its own
source of truth promised warn-and-skip. And a projector's poison stops an entire
run's projection: reserve it for what can never succeed, never for input a newer
peer is allowed to invent.
