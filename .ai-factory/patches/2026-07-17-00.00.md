# An abandoned run could still rebase and force-push; a resolver finalize could strand its claim

**Date:** 2026-07-17 00:00
**Files:** web/lib/runs/sync-target.ts, web/lib/runs/state-transitions.ts, web/lib/runs/reopen.ts, web/lib/runs/promote.ts, web/lib/runs/lifecycle-claim.ts (new), + 3 test files
**Severity:** high

## Problem

A Codex adversarial review of the ADR-140/141 branch-sync code (already FF-merged
into local main) reported 3 findings. Verification confirmed 2, **corrected 1**, and
surfaced 5 siblings.

- **F1 (high, VERIFIED).** `syncRunTarget` checked `runs.status === 'Review'` at
  sync-target.ts:593 on an UNLOCKED read, then ran a git exec and a network
  `git ls-remote` before its claim tx — which locked only `workspaces` and never
  re-read `runs`. `markAbandoned` CASes `runs.status` (with `Review` abandonable) and
  takes no workspace lock, so the two interleaved freely. Reproduced: `syncRunTarget`
  **resolved with `{outcome: "synced", pushed: true}` on a run the user had already
  abandoned** — a force-push onto an abandoned run. In the other order the driver
  resurrected the ledger `failed → rebasing → … → succeeded`, because every phase
  write was unconditional by attempt id, and stamped `review_entered_at` on an
  `Abandoned` run.
- **F2 (high, mechanism VERIFIED / blast radius CORRECTED).** The resolver's success
  finalize was six independent writes — the ONLY terminal path in the file not
  wrapped in a transaction while `settleAttempt`/`abortAttempt`/`failAttempt` all
  cite "ONE transaction — see `settleAttempt`".
- **F3 (medium, VERIFIED).** `reopen.ts` attaches a GC'd worktree (:188) BEFORE its
  state tx (:192), with no compensation. `removed_at` is cleared *inside* the tx, so
  a throw rolled it back while the worktree stayed attached — a shape no sweep
  converges (the GC gates on `removed_at IS NULL`; reconcile skips settled `Done`
  runs), and the retry re-hit `addWorktreeForBranch` → `PRECONDITION` forever.

## Root Cause

**F1 — an invariant asserted in prose and enforced nowhere.**
`releaseSyncClaimOnTerminal`'s own comment states *"a sync can only ever be claimed
by a `Review` run"*. Nothing enforced it: the only status gate sat 52 lines before
the claim, outside the lock. Three internal contradictions prove oversight, not
tradeoff: (1) that comment; (2) the correctly-fenced idiom `failAttemptIfActive`
already existed but was used at exactly ONE of nine call sites; (3) the agent-resolver
path did the CAS properly (`markSyncFromReview` under `FOR UPDATE`) while the
mechanical path — the one that force-pushes — had no equivalent.

**F2 — a divergent copy drifted out of the rule its twin documents.** Two writers for
one fact ("this sync succeeded"): the shared `settleAttempt` and an open-coded
sequence in the resolver. Only the shared one was maintained.

**F3 — the ordering reasoned about one failure direction only.** Its comment says the
attach runs first "so a git failure leaves the run untouched at Done" — correct, and
silent on git-succeeds-then-tx-fails. The most likely trigger is the *hardening*: the
merged-PR re-check added to close the duplicate-PR hole, whose own comment notes the
window is wide **because** the attach ran inside it.

## Solution

**The attempt phase became the durable cancellation signal** — chosen over an
`AbortController` because it survives a restart and reuses a mechanism already
present: `releaseSyncClaimOnTerminal` already stamps `failed` on every non-terminal
attempt when a run terminalizes, so a lost CAS *means* "the run was terminalized".

- `setAttemptPhase` (the choke point all 9 call sites funnel through) now CASes on
  non-terminal and returns `boolean`; `advancePhaseOrCancel` throws `CONFLICT` on a
  loss, cancelling every git side effect below it. The claim tx now re-reads the run
  `FOR UPDATE` and re-runs `assertSyncEligible`, closing the abandon-before-claim
  order outright and serializing the reverse one.
- **Deviation from plan (F1c):** the plan said to restore the worktree on a lost CAS.
  Reading the outer catch showed `abortSyncOperation` + `terminalizeSafetyNet` are
  already idempotent no-ops against an attempt someone else terminalized, and an
  abandoned run's local worktree is inert (never pushed, later GC'd). Throwing is
  sufficient; no restore code was added.
- **Residual, documented not hidden:** the ~1 ms gap between the CAS and the git call
  after it. Closing it fully would mean holding a DB tx across git+network I/O.
- F2: the resolver finalize routes through `settleAttempt` (+ a `flipRunningToReview`
  flag) — ONE terminal-success writer. Verified safe: a rolled-back finalize is
  recovered by the sweep's W3 re-verify→finalize arm (the push is explicit-SHA
  force-with-lease, idempotent), and `deleteSession` runs first so it lands on W3, not
  W2's restore arm. **This dissolves S1** — `succeeded` + `Running` is now unreachable.
- F3: compensating `removeWorktree` on the throw path, best-effort, rethrowing the
  ORIGINAL error (a cleanup failure must never mask the real refusal).

**Do NOT "fix" what the review got wrong.** Two of F2's stated consequences are
refuted in source: the concurrency slot does **not** leak (reconcile frees it via
`promoteNextPending`), and the workspace is **not** blocked from lifecycle ops
(`promote.ts:811` and `canReclaimLifecycle` both break stale claims after 300 s).
Coding against those states would be dead defensive code.

## Prevention

- **A comment asserting an invariant is a lead, not evidence.** Grep whether anything
  enforces it. Here the enforcing lock simply did not exist.
- **When a guarded and an unguarded variant of the same write coexist, the unguarded
  one is a bug queue.** `failAttemptIfActive` vs `setAttemptPhase` shipped side by
  side with the guarded one at 1 of 9 sites. Fix the CLASS at the choke point.
- **A side effect before a transaction needs compensation, or the transaction must
  come first.** Ask both directions: "what if the side effect succeeds and the tx
  fails?" is the one that gets skipped.
- **Verify a review's consequences, not just its mechanism.** 2 of F2's 3 stated
  consequences were refuted by reading recovery code the reviewer never opened.
- **Distrust a test that passes on the first run.** Every new test here was proven to
  fail without its fix (mutation/stash), which caught a control that would have passed
  either way. A missing import in the new fence path was caught by the typechecker
  only because `&&` short-circuited past it in tests — the CAS tests passed while the
  code would have thrown `ReferenceError` in production.
- **Baseline-prove before blaming your diff.** 7 failures in `lib/runs` looked like
  the classic "new precondition broke the seeds" — stashing proved all 7 fail
  identically on main (`auto-promote-race` 4, `shared-tree-auto-launch` 3). The gate
  is zero-NEW-vs-baseline.
