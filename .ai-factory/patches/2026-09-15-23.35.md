# Bounded artifact reads 416'd on every execution object smaller than the reader's budget

**Date:** 2026-09-15 23:35
**Files:** web/lib/execution-host/runtime-objects.ts, web/test-support/fake-execution-host.ts, web/lib/execution-host/__tests__/runtime-objects.test.ts
**Severity:** high

## Problem

A flow run on `aif-dev` failed at the `plan-review` node with `PRECONDITION`
("cannot read its current review artifact"). On the wire:

```
Range: bytes=0-262144   on a 17 049-byte object  -> HTTP/1.1 416
no Range                                          -> HTTP/1.1 200, 17 049 bytes
```

Inverted from the intuition: the read failed on SMALL artifacts and worked on
ones larger than 256 KiB. Capture succeeded (it reads unranged); only the later
re-read failed. Blast radius was wider than the reported node — the same branch
serves `{{ artifacts.<id>.content }}` injection, where `gone` becomes a CONFIG
throw, so any execution-object artifact under the inline cap failed the same way.

## Root Cause

`resolveArtifactContent`'s `execution-object` branch turns the caller's "read at
most `maxBytes`" into a fixed byte range `[0, maxBytes - 1]` and never narrows it
to the object. `maxBytes` is a BUDGET, not a size, so the window routinely lands
past the end.

Every layer below refuses `end >= total`, so the budget could never be expressed
as a range: the supervisor's `objectByteRange` (416), the shared
`parseObjectContentRange` (`end < total`), and the manager's own
`assertRuntimeObjectContentHeaders` (`end !== expectedEnd`). That last one is why
relaxing only the supervisor to a truncated 206 would NOT have worked — the
manager would then have refused the response with a CONFLICT integrity error.
`artifact-content.ts` cannot clamp on its own either: an `execution-object`
locator carries only `objectId`, no size.

It shipped because `web/test-support/fake-execution-host.ts` SILENTLY CLAMPED
`end` to the object size while the real host refused it. Every web test of the
read path was validating against a more permissive host than production. The one
existing execution-object test used `maxBytes: 18` on an 18-byte object — the
single boundary value that is satisfiable — with the transport fully mocked.

## Solution

Clamp at the choke point, in `openRuntimeObjectContent` — the only place holding
BOTH the caller's window and the authoritative catalogue `sizeBytes`, and the
place whose `range` must stay consistent across three consumers (the wire call,
the header assertion, and the digest verification). `clampRangeToCatalogue`:

- explicit `end` past the end + `start === 0` -> read the object whole (also the
  only readable form of a zero-byte object);
- explicit `end` past the end + `start > 0` -> narrow `end` to `total - 1`;
- `start >= total` -> left unsatisfiable for the host to refuse (preserves the
  e2e `bytes=<len>-` 416 case);
- open-ended `bytes=N-` -> untouched, so the download routes keep returning 206.

Then made the fake host mirror `objectByteRange` — refuse a window past the
representation instead of clamping it — so the parity gap that hid this cannot
reopen. The guard was falsified: reverting the clamp turns 2 of the new tests red.

## Prevention

- A "max bytes" BUDGET is not a range. Converting one into `Range: bytes=0-(N-1)`
  is only valid after narrowing it against a known size — otherwise the request
  is unsatisfiable exactly when the payload is small.
- **A lenient test double is a defect, not a convenience.** When a fake and its
  real counterpart disagree about what is refused, every test on that path
  validates fiction. Grep a fake for `Math.min`/`Math.max`/clamping around
  contract boundaries — silent normalization there is where production bugs hide.
- A boundary test that picks the one satisfiable value (`maxBytes === sizeBytes`)
  proves nothing about the boundary. Test strictly inside AND strictly outside it.
- Fix a range/size defect at the layer that owns the authoritative size, not at
  the caller that merely knows a budget.
