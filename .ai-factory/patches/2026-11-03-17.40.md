# Preserve agent target authority through queued admission and physical preparation

**Date:** 2026-11-03 17:40 Europe/Moscow
**Files:** `web/lib/tasks/launch-agent-{resolution,definition,execution}.ts`; `web/lib/agents/{launch,flow-launch-authority,carrier-launch-authority,task-trigger-reservation,accepted-cleanup,execution-quiescence,preparation-ownership,activity-queries}.ts`; accepted-agent cleanup GC callers; shared command admission hooks; agent launch/history UI and integration fixtures.
**Severity:** high

## Problem

Making the Flow launch button available does not close task admission. Standalone code-delivery agents, Flow-driving agent facades, retries, scheduled fires and execution children can otherwise continue through old allocators. A queued response must identify a durable intent, not invent a Run or a human decision. Operational agents and finite taskless execution carriers retain their distinct authority.

Agent preparation also needs the actual resource identity. A repository-less target must not acquire a synthetic Git SHA; a shared writable borrower must not be mistaken for an owner of a pristine per-run checkout. Cleanup and source acknowledgement must survive the same asynchronous boundaries as dispatch.

## Root causes established locally

- The original task-bound agent allocator still called qualification admission directly. Canonical agent bodies and opaque session authority were not sufficient until public task-bound producers were routed through the same durable contract.
- Resolving an accepted frozen runner by injecting its ID changes the resolver's apparent provenance to `launchOverride`. That is a technical lookup mechanism, not the original selection tier. The accepted session now records its authoritative `runnerResolutionTier`.
- Accepted-agent cleanup used a cancellation helper that requires an active assignment. Terminalization correctly releases the assignment, so a genuinely unstarted terminal Run was incorrectly required to have a terminal session incarnation. A separate terminal cleanup proof checks the retained released assignment, positive dispatch evidence and a fresh host observation.
- A physical resource can pass between different valid Runs. `claimAgentPreparation` copied the prior resource owner's immutable `resolvedCommit` into a new Run. In the real writable shared-tree test, a changed shared HEAD then failed with SQLSTATE23514 at checkout. Only same-Run re-entry inherits that commit; a different Run captures its actual current HEAD under the existing physical owner.
- Trigger attempts previously settled only after a Run existed. A truthful queued intent leaves no Run yet. Settling the original attempt as queued must commit with acceptance, and attaching its reserved Run later requires a narrow immutable-settlement exception backed by the exact accepted source witness.
- Attempt history displayed the historical queued outcome and no-Run text without the current owning intent. Held and cancelled accepted invocations now retain historical outcome and project their actual current intent state separately.
- Operational finalization required a terminal session incarnation after an actually rejected session create. The real owned-command reproducer retained its positive host rejection receipt but failed quiescence before settlement could examine it. Quiescence requires the host's strict `sessionCreateQuiescence` version-1 stamp proving `not_started` or `terminated`, plus exact current-assignment and private agent-owner receipt identity, no prompt, handle or incarnation, and a fresh host observation. Historical unstamped rejections, unknown outcomes, created sessions and superseded epochs remain refused. The stamp may be published only from actual pre-spawn or confirmed-exit state; merely rejecting a request and removing its registry entry cannot establish OS process quiescence.
- An accepted V2 receipt has no process-liveness field. Its normalized `inflight:false` caused both owned-create re-entry and generic command recovery to invent `turn_lost`; the reproducer issued a second create while the original fake host process remained. Both consumers now retain accepted create commands. An actual Supervisor-leader SIGKILL disproved the earlier V1 replacement assumption: its initialized adapter survived while restart produced `turn_lost`. Missing registry state and `inflight:false` cannot authorize replacement; a strict positive process-retirement stamp is required for V1 and V2 alike.
- The same refusal evidence governs retries. A historical Failed/released Run with an unstamped rejected create cannot become a verified pre-work source merely because its ledger is failed and inventory is empty. Pre-work retry reuses the exact current-assignment rejection proof; fresh qualification independently rejects unproven failed creates while preserving ordinary confirmed terminal sessions. Both use the existing typed reconciliation refusal and direct users to the original Run and host. All unstamped V1 create receipts remain pending, including the formerly accepted unmarked restart signature. Immutable per-command rejection evidence remains valid if a later generation of the same owner prompts successfully; aggregate no-model settlement separately checks current prompt, handle and incarnation state.

- Operational Stop completed a real DELETE before the canonical exit event reached PostgreSQL. Immediate finalization then correctly refused the still-active incarnation, producing a user-visible 503 for normal cancellation. Stop now waits outside transactions on canonical run wakeups until its fixed monotonic deadline, subscribing before each strict read and performing a final durable read even when another process emits no local wake. It never substitutes DELETE success or an empty inventory for terminal proof, and finalization remains fenced to the assignment observed before waiting.
- The host's actual scoped-pending reason is `session_process_owner_unconfirmed`. A mismatched manager classifier treated that pre-POST readiness condition as an ordinary create failure and exhausted the original command. The controlled HTTP producer reproduced the original command becoming failed; exact reason parity now preserves readiness deferral and its unchanged wire budget.

These findings do not reconstruct the lost inner Git/filesystem exception from the MAI-27 deployment. Production log ordering alone does not prove its original race. No historical assessments or production rows were rewritten.

## Current contract

Task-bound code-delivery targets use a strict agent-versus-Flow request union, frozen package/definition/configuration/runner metadata and the same server-side intent ledger. Public automated agent producers receive `{queued:true,receipt}` and automatic or execution-child admission; a mechanical trigger named `manual` cannot mint a human decision. Actual interactive callers use the opaque session constructor. Operational and taskless immediate allocations retain their existing private execution paths.

A taskless Flow facade may create one fresh internal carrier through its own private branded constructor. Its task retains the required qualification policy. The finite v1-shaped Run witness freezes the actual semantic input and source metadata; it fabricates no accepted assessment and cannot authorize an existing or edited task.

The agent driver owns actual checkout preparation, baseline, materialization and first dispatch under the R3 durable/physical fence. Verified private package captures supply the consumed bytes and reject managed-directory symlink escapes. `none` uses its owned runtime directory without Git. A shared writable target freezes the actual root workspace seed/branch/target and resolves borrowers through the root owner. Its current HEAD may differ from the original seed, and no borrower may delete or recreate that tree.

Accepted cleanup requires a fresh terminal generation, physical ownership and confirmed host quiescence. Crashed resources remain available for resume. Context mounts and GC backstops use the same owner checks. A busy owner leaves a durable cleanup candidate.

Actual cron/domain reservations are loaded from `agent_trigger_attempts`; arbitrary preallocated IDs are refused. Acceptance acknowledges the fire atomically with no Run. Its exact frozen attempt/reserved-ID witness then owns recovery after the old producer deadline. Binding attaches only the real reserved Run. Queued attempt history exposes a safe optional owning-intent reference, its current state and task link.

## Prevention

Pre-incarnation readiness exposed a second owner boundary: generic scratch,
package scratch, consensus verifier/synthesis, gate chat, sync and resume
constructors could lose an accepted input or report a technical failure as a
model assessment before any model started. Their private create intent now
uses closed identities derived from the existing domain records. Initial
scratch/package and sync continuations freeze the next action separately from
the owner; recovery also retains its original dialog state. Admission stores
the complete intent in one INSERT, and migration `0226` forbids later owner,
request or continuation rewrites. Both requesting and stored owner authority
are rechecked on replay. No client flag creates an owner.

The native parked-consensus retirement control found an actual retention
error: `WaitingOnChildren` was omitted, so the host compacted the parent's
aged private create while its lifecycle could still resume. The central
classifier and database guard now retain every nonterminal Run. The existing
terminal and parked-librarian retirement policies remain explicit.

An actual failing atomic INSERT showed Pino serializing Drizzle SQL parameters
containing controlled private prompt/environment sentinels. One shared pure
projection now preserves safe known domain codes and bounded SQL/cause fields
while dropping raw query text, parameters and nested raw causes. The same
policy protects direct admission and domain handoff/rollback adapters.

Real PostgreSQL also confirmed that a lost COMMIT reply can coexist with a
committed queued private create. Its continuation must retain the original
owner and command until durable reconciliation; a generic crash would release
the assignment while another driver could still dispatch that command. The
primary control sends zero create POSTs before the pending result, then replays
the same immutable request and continuation into one create and one scratch
prompt. Known constraint rollback and clean authorization refusals remain
ordinary errors. A failed first lookup may hide an already committed create:
it retains the same owner with the operation key and no invented command ID.
The same real-PG control loses a SELECT reply after the existing row is read,
then repairs the connection and proves the original one-create/one-prompt
continuation in `/private/tmp/maister-private-create-query-unknown-green.log`.
Unknown COMMIT admission yields immediately; its next ordinary continuation
takes the owner lock before reading, with no extra catch-path connection wait.
The finite post-admission sweep also found uncertain reads after an actual
host201: ACK failure followed by outcome-reload failure, receipt201 folding,
and re-applying an already-succeeded create. One guard at the owned-create
boundary now records only real observed/admitted command IDs and retains that
known ID for unknown storage failures. It covers rejection-evidence writes,
failure settlement/reload, replacement/output preparation, succeeded re-ACK,
receipt settlement/application, delivering requeue, live delivery/ACK and its
outcome reload. Known typed authorization, owner fences, intent conflicts and
definitive host refusals keep their domain semantics. The reload path preserves
the safe primary delivery cause and safe secondary query diagnostics. No
branch authorizes a new session or an execution retry from an unavailable read.
Isolated old-boundary controls failed cleanly at the expected pending assertions
in `/private/tmp/maister-owned-create-reload-isolated-red.log` and
`/private/tmp/maister-owned-create-readoption-isolated-red.log`; the same
cohesive-guard control fails receipt folding in
`/private/tmp/maister-owned-create-receipt-fold-isolated-red.log`. The primary
fixture repairs the reads and still dispatches one original create and prompt.
Evidence: `/private/tmp/maister-private-create-commit-unknown-red.log`,
`/private/tmp/maister-private-create-commit-unknown-green.log`, and the coupled
27-case gate `/private/tmp/maister-create-owner-central-final.log`. Migration
fresh/populated/reapply and parked-parent gates are separately recorded in
`/private/tmp/maister-create-owner-migration-parked-final.log` and
`/private/tmp/maister-parked-create-retirement-green.log`.

Freeze authority and target facts where they are decided, and carry them through every later producer, allocator, queue, driver and cleanup boundary. Do not infer original runner selection, human consent, checkout ownership or a successful assessment from a convenient technical parameter. Treat actual source reservations and resource generations as durable identities, not as process-local booleans or lease timestamps. Test source acknowledgement before a Run exists and resource reuse after HEAD changes; per-path happy tests alone miss these transitions.
