# Ancestor-scoped budget guarded by a parent-scoped lock

**Date:** 2026-09-03 14:30
**Files:** web/lib/orchestrator/admission.ts, web/lib/run-results/status.ts, web/lib/runs/run-status-values.ts, web/lib/runs/run-status-sets.ts, web/components/runs/run-public-result-panel.tsx, docs/decisions/adr-165.md, docs/system-analytics/orchestrator.md
**Severity:** critical

## Problem

`admitDelegatedChild` enforced `delegation.budget.max_child_runs` for every
ancestor of the delegating orchestrator, under an advisory lock keyed on the
PARENT run. A tree whose root allowed 4 descendants and already had 2 admitted
2 + 2 more when its two coordinators delegated concurrently — the governance
bound that exists to stop a depth × fan-out blow-up simply did not hold.

It passed every test and every review round because the shipped two-racer raced
two admissions under the SAME parent, which the parent lock does serialize.

## Root Cause

**The lock's scope did not match the invariant's scope.** The invariant is
"ancestor A's subtree ≤ A.max_child_runs" — a property of A's whole subtree —
while the lock was keyed on the immediate parent. Two orchestrators in one tree
hash to different keys, so they never exclude each other; under READ COMMITTED
neither sees the other's uncommitted child rows; both read the same pre-insert
count and both pass.

The author's reasoning (recorded verbatim in the code comment: "checked under
the same lock that already serializes this orchestrator's admissions") was TRUE
and irrelevant — serializing *this* orchestrator says nothing about a sibling
orchestrator counting the same ancestor.

The test missed it for the same reason the code did: the racer was chosen to
contend on the lock that existed, not on the invariant that needed protecting.

## Solution

Take the delegation lock on the TREE ROOT as well, before the budget loop — the
coarsest scope that contains every ancestor, still per-tree rather than a global
mutex. Order is parent-then-root on every path, so no deadlock; when parent ===
root the key repeats and `pg_advisory_xact_lock` is re-entrant.

The new test models production rather than the lock: the winner holds parent +
root and has inserted uncommitted children, and the racer under a DIFFERENT
parent must PARK (asserted through `pg_stat_activity`) and then be refused.

Two adjacent findings fixed in the same pass: a hand-maintained status partition
became derived-from-enum with an explicit ALLOW-LIST readable arm (an unknown
status now reads `pending`, not `valid`), and the result panel shows the payload
size before you expand it.

## Prevention

- **Ask "what is this lock's scope, and what is the invariant's scope?"** They
  must be the same object. A lock on a descendant can never protect an
  ancestor-scoped count. Reviewing the lock's *existence* is not reviewing its
  *key*.
- **A two-racer must contend on the INVARIANT, not on the lock.** Design the
  race from the property that must hold ("this ancestor's subtree stays ≤ N"),
  then pick racers that could both violate it — here, two different parents.
  A racer chosen to hit the lock you already wrote only proves the lock works.
- **Model production in the racer:** the winner must perform the same writes the
  real caller does (insert the children in its uncommitted transaction). A probe
  where neither racer inserts anything "passes" trivially and proves nothing.
- **A comment asserting a guarantee is a claim to verify, not evidence.** "under
  the same lock that already serializes this orchestrator" was accurate about
  the mechanism and silent about the gap.
- **Partition guards:** when a predicate splits a closed enum into arms, derive
  the arms from the enum and make the consequential arm an allow-list, so a new
  value defaults to the safe side.
