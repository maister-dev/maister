# A permission whose answer rides a resume is refused by name, not by an invariant

**Date:** 2026-09-15 17:05 (Europe/Moscow)
**Files:** `web/lib/services/hitl.ts`,
`web/lib/services/__tests__/hitl-permission-ledger.integration.test.ts`.
**Severity:** high

## Problem

Run `841288f9` on the stand: the operator answered a permission
("Yes, and don't ask again"), the verify session was SIGKILLed before the answer
was delivered, and the platform authorized a permission-resume — new assignment
(epoch 2), `action_prompt_ordinal` 1. The HITL row kept `responded_at = NULL`
and its `schema.flowPrompt` still pinned the dead generation
(`commandId 4e8a9bf3`, `assignmentId a4e9be4e`, `promptOrdinal 0`), so the card
stayed actionable in the UI. Every resubmit died deep inside
`lockPermissionSource` as `PromptOwnerInvariantError("permission_attempt_generation")`
— six times across eleven hours, with nothing in the message an operator could
act on.

## Root Cause

After `authorizeNodePermissionResume` the answer IS consumed: it rides the next
prompt instead of a `session.input`. But nothing marks the row, and nothing may:
`lockNodePermissionSource` selects its source with `isNull(respondedAt)`, and
`authorizeNodePermissionResult` / `...Continuation` find their source through it,
throwing `permission_result_source_disappeared` when it returns nothing. So the
obvious remedy — stamp `responded_at` when the resume is authorized — trades this
bug for a regression in the happy path, and the existing
`permission-resume.integration.test.ts:786` depends on the later handoff doing
that stamping. Re-pinning `schema.flowPrompt` to the new generation is no better:
the resubmit would then be ACCEPTED and deliver an answer that is already in
flight.

The missing piece was never a marker on the row. It was that no one ASKED the
question "is a resume already carrying this answer?" — although the predicate
for it, `hasFlowPermissionResume`, already existed and is used by three resume
paths.

## Solution

`respondToHitl`'s permission branch refuses a flow run whose resume is in
flight, with `CONFLICT` + `details.reason = "permission_resume_in_flight"`. It
is placed BEFORE `claimAssignmentForResponse`, the first irreversible act, so a
refused request leaves no trace: no `execution_commands` row, no `deliverInput`,
`response` and `responded_at` untouched. `responded_at` deliberately stays NULL,
so the result/continuation handoff still finds its source.

`respondToHitl` is the shared choke point for both the session route and the ext
route, so neither surface can bypass it.

Ordering note: this depends on the cursor fix in `2026-09-15-16.10.md`. The
predicate requires `resume_attempt.node_id = runs.current_step_id`, and while the
permission pause stamped the session's label over the cursor, the predicate was
silently false — the same defect that was killing runs was also disarming the
guard that now refuses this.

## Verification

- RED: the new case failed; 4 existing passed.
- The first fixture was WRONG, not the code: the `node_attempts_action_resume_check`
  constraint rejected a shortened `action_resume`. Rebuilt it in the exact shape
  `authorizeNodePermissionResume` writes, and asserted the run's active
  assignment is non-null — a null one makes the predicate silently false and the
  guard vacuous.
- GREEN 5/5. Falsified: with the guard disabled the resubmit RESOLVES 200 —
  a second delivery of an answer already in flight (the stand saw 409 only
  because its session was dead; both outcomes are wrong).
- `tsc --noEmit`, `validate:docs:all`, `validate:contracts`, `git diff --check`.
- The full unit run caught a regression the focused suites could not: two
  MOCKED suites (`respond/__tests__/route.test.ts`, `services/__tests__/hitl.test.ts`)
  drive this path through a fake `select` that ignores WHERE and returns every
  row of the table, so the new predicate read as TRUE and 31 cases got a 409
  where they expect 200. The class is in the harness, not the product: both
  suites now control the seam explicitly (`hasFlowPermissionResume` mocked to
  false by default), and the refusal branch stays pinned against a real database
  in the integration suite. 62/62 and 35/35.

## Prevention

When a state change consumes something, ask what still ADVERTISES it as
available. Here the row was consumed by the resume and kept advertising itself
to the UI, and the only thing standing between an operator and a double delivery
was an invariant deep in the owner that could not explain itself.

And when the obvious marker is unavailable because another path depends on it,
look for a PREDICATE over the state you already have before inventing a new
column or a new flag — `hasFlowPermissionResume` was three call sites old.
