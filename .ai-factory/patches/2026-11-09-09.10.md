# Lock native execution ownership before its credential

**Date:** 2026-11-09 09:10 UTC
**Files:** web/lib/brain/knowledge-token-lock.ts; web/lib/brain/knowledge-disclosure.ts; web/lib/brain/knowledge-access.ts; web/lib/brain/__tests__/company-records.integration.test.ts
**Severity:** high

## Problem

A real PostgreSQL barrier probe of native knowledge disclosure and actual Flow token issuance produced SQLSTATE `40P01`. Disclosure locked the credential before its Run, while issuance and terminal revocation locked the Run before updating credentials.

## Root Cause

The source-capture admission path and low-level native identity resolver independently acquired a token SHARE lock before execution ownership. Concurrent rotation or revocation could close the opposite half of the cycle. Correcting only the top-level read helper would leave direct native-principal consumers with the same inversion.

## Solution

Both consumers use one shared lock helper. An unlocked current token lookup locates the execution lock but grants no authority. The helper locks the Run first, then rereads the current credential under SHARE and checks unchanged binding fields, revocation and wall-clock expiry. Existing services still enforce current scopes, professional role, ownership and source restrictions. User credentials remain independent of a fabricated Run. Structured diagnostics identify credential changes without secrets or query parameters.

## Prevention

Derive a shared lock order from all issuers, revokers and readers before changing one consumer. Exercise actual services behind PostgreSQL barriers, not only synthetic lock statements. Hold execution ownership while revoking and prove that a waiting disclosure or direct identity resolution refuses without widening the source capture. Never use the unlocked locator or historical scopes as an authorization result.

## Verification

Three regressions are RED against the original implementation and GREEN with the shared helper: issuance contention, revocation during disclosure admission and revocation during direct identity resolution. The isolated owning consumer batch and repaired built-MCP environment cover 284 unique scenarios; types, scoped lint and independent adversarial review pass. Primary-checkout receipts are retained separately. This independently proven deadlock is distinct from the installed-package credential-rotation failure; the live trace does not establish `40P01` as its cause.
