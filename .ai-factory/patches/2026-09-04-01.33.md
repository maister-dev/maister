# A race test that asserted event-loop timing, and leaked its parked winner into the next test

**Date:** 2026-09-04 01:33
**Files:** web/lib/runs/__tests__/dirty-resolution-race.integration.test.ts
**Severity:** medium

## Problem

`dirty-resolution-race.integration.test.ts` failed 2/4 on main itself, and
identically in isolation, while each failing test passed when run alone:

- "two-racer commit vs discard: the loser conflicts BEFORE any git side-effect
  runs" — `expected +0 to be 1`: at the moment the loser settled, no git helper
  had been called yet.
- "rolls the claim back when the git side-effect fails" — the chat-baseline
  delete spy had been called once although the snapshot had just failed.

## Root Cause

Two defects in ONE test, the second caused by the first.

1. **The assertion described timing, not the contract.** After
   `Promise.race([pa, pb])` the test asserted exactly one git-helper call —
   i.e. that the WINNER had already entered its git side-effect when the loser
   settled. The protocol only guarantees order relative to the claim (the loser
   gets CONFLICT and never touches git). The winner's commit path awaits an
   unmocked worktree-provenance probe (two filesystem calls, both ENOENT on the
   fake path) between the CAS and `snapshotDirtyWorktree`, so the loser's failed
   UPDATE can return first. Which promise the event loop runs first is not a
   contract.
2. **A failed assertion leaked a live promise.** The gate that parks the winner
   was released only on the happy path. When assertion 1 failed, the winner was
   left running; it finished during the NEXT test, against that test's freshly
   reset mocks (`snapshotSpy` now resolves immediately), and its
   `deleteChatCheckpoint` call landed in the rollback test's spy.

The implementation (`resolveDirtyWorktree`) is correct; nothing in the window
of main commits touched it — the timing simply tipped.

## Solution

- The git-helper mocks now signal when the winner ENTERS its side-effect, and
  the test awaits both "the loser settled" and "the winner reached git" before
  asserting the one-call invariant. Order is asserted; timing is not.
- The gate is released in a `finally` and both racers are awaited to
  settlement, so a failure can never leak into the following test.

Verified: the whole file passes 3/3 consecutive runs; each test still passes
alone; a regression that let the loser reach git would still be caught (two
calls, or a non-CONFLICT outcome).

## Prevention

- **Assert order, never "already happened by now".** If a test needs "X has
  happened" it must await a signal for X, not infer it from which promise
  settled first.
- **Every barrier a test creates must be released in `finally`.** A parked
  promise that survives a failed assertion is cross-test contamination waiting
  to happen; the symptom appears in an unrelated test.
- **When a file fails but each test passes alone, look for leakage before
  looking for a product bug.** Run the failing tests individually first — it is
  the cheapest experiment and it discriminates the two immediately.
- A mocked boundary is only as tight as the unmocked async work around it —
  read the code path between the claim and the mock before asserting counts.
