# Observatory ADR-177: five adversarial-review findings — invisible filters, stale link scope, and an unverified denominator

**Date:** 2026-09-21 19:10
**Files:** `web/lib/observatory/views.ts`, `web/lib/observatory/filters.ts`,
`web/lib/observatory/href.ts`, `web/components/observatory/overview-table.tsx`,
`web/components/observatory/observatory-filter-bar.tsx`,
`web/lib/queries/observatory-agentization-core.ts`,
`web/lib/queries/observatory-agentization.ts`, their four test files,
`docs/decisions/adr-177.md`, `docs/screens/{observatory,components}.md`,
`docs/system-analytics/observatory.md`
**Severity:** medium

## Problem

A Codex adversarial review of the ADR-177 branch reported five defects. All five
reproduced in source before any edit:

1. **Overlapping filter edits overwrote each other.** Every commit built its URL
   from the SERVER `current`, which does not change until a round-trip lands.
   Selecting Scratch and then a period preset before the response arrived
   produced a URL with no `runKind` — and the uncontrolled select, re-keyed on a
   value that never changed, went on DISPLAYING "Scratch".
2. **Ledger links did not reproduce the cell's scope.** `runKind` narrows every
   count in the read model, but `runsLedgerHref` never received it: under
   `runKind=scratch` a project row's bucket cells counted scratch runs and
   linked to all three kinds. Separately, the Runs columns passed the COLUMN's
   kind regardless of the ROW's, so a `scratch` sub-row's Flow cell read `0` and
   opened the project's entire flow list.
3. **The empty state hid tasks still in work.** The predicate asked only about
   runs. A task whose only flow run started before the period and is still open
   counts in `tasksInWork` with every run cell at zero — deleting the table that
   carries the number D2 exists to add.
4. **A partly cached period reported a complete rate.** `availability` was
   `insufficient` only for zero buckets, a null value, or unmatched refs —
   never for a period the cache covers in part. `REPO_DELIVERY_WINDOW_DAYS` is a
   ROLLING 365 days that `repo_delivery_scan` DELETEs and rewrites on every
   pass, so a custom range straddling that horizon returned its covered tail and
   published the rate as `ready`.
5. **Harness applied artifact filters it does not render.** `viewKeepsDrilldown`
   treated Quality and Harness as one group, so `artifactKind` / `artifactDefId`
   survived the tab click while the Harness bar shows no artifact control — and
   `loadObservatoryRows` still narrowed `effectiveRunIds` by them.

## Root Cause

Two distinct causes, not five.

**Findings 1, 2 and 3 share one shape: a derived value read from a narrower
source than the thing it describes.** The filter bar derived "the state to patch"
from a server prop that lags the reader. The link derived "this cell's scope"
from the row alone, when a cell is narrowed by three things at once (selection ×
row × column). The empty state derived "nothing happened" from the runs axis,
when D2 deliberately introduced a second axis whose whole point is that it does
not move with the first. In each case the narrower source is right in the common
case and silently wrong at the edge the feature was added for.

**Findings 4 and 5 are the same defect: a filter with no visible control.** The
artifact pair narrowed Harness invisibly; the delivery cache narrowed the
agentization denominator invisibly. Both were locked correctly in the SPEC —
D7's field-per-view table, D1's "the existing insufficient state already covers a
range the cache does not reach" — and both specs were, as written, believed
rather than enforced. D1's sentence was simply false for a partly covered range.

An aggravating factor for 5: ownership was expressed in `observatoryViewHref`,
i.e. in the LINK BUILDER. A rule enforced only where links are built cannot hold
for a bookmark, a pasted URL, or a link built before the rule existed.

## Solution

**Ownership moved to the parse choke point.** `observatoryViewOwns(view, key)` in
`views.ts` is now the single statement of D7's table; `parseObservatorySearchParams`
drops every unowned key there, which is where BOTH the applied `filters` and the
rendered `current` are derived, and `observatoryViewHref` consumes the same
predicate so the URL stays honest too. The view default still reads the RAW
params, so a pre-view drill-down link still lands on Quality holding its keys.
This also closed a sibling the review did not name and a background sweep did:
`getCostSummary` applies `filters.flowId` / `nodeId`, so `?view=overview&flowId=X`
had been narrowing the cost strip behind a view that renders no flow control.

**The filter bar accumulates its in-flight patch** and discards it when the URL
the state represents changes. Patch values are absolute rather than deltas, so
replaying the merged patch onto whichever `current` is live is idempotent.

**Cell links derive from selection × row × column**; where those name different
kinds the cell counts nothing and renders as a plain number, joining the
per-flow sub-row and the Platform row as a third non-reproducible class.

**`rollupAgentization` verifies contiguous coverage** of `[since, until)` before
publishing a rate, folded into the existing `resolution.complete` gate so a
coverage gap reads exactly like an unmatched delivery ref. The walk is
granularity-agnostic (a row count would be exact only while a bucket is one day)
and catches a leading gap, an interior hole and a short tail alike.

No `[FIX]` logging: every touched module is pure, client-safe, or a render path
under this repo's `no-console` boundary, and the skill-context rule puts that
case under "behaviour locked by tests instead".

## Prevention

- **A per-view / per-mode field table is a FILTER contract, not a render one.**
  Enforce it where the URL is parsed, so the applied filters and the visible
  controls come from one predicate. Enforcing it in the link builder leaves every
  URL the builder did not build.
- **When a spec sentence asserts that an existing state "already covers" a new
  case, treat it as a claim to verify, not a fact.** D1's sentence was written in
  good faith and was false the moment custom ranges shipped. Grep the state's
  actual predicate before believing it.
- **A newly added axis needs its own emptiness, its own links, and its own
  tests.** Finding 3 is what happens when a second axis is added to a table whose
  guard clauses still speak only about the first.
- **Falsify every guard, and check WHY it goes red.** Two of the four coverage
  tests first passed against the reverted fix — one because its fixture tripped
  `MIN_GROUP_EXECUTIONS`, the other because a duplicated `merge-sha` made the
  ref match ambiguous. A guard that fails for a reason other than the one it
  names is not a guard. The fixture now keeps both other gates open explicitly.
- **A test that re-renders the same component with the same URL is NOT
  simulating a fresh page** — under this bar's contract that is precisely the
  "response has not landed" state. One existing test relied on it and needed a
  genuine remount.
- **Do not key "the navigation landed" on a transition's pending flag.** A
  transition whose scope schedules no state update settles before the page it
  asked for arrives, so the flag is both wrong in production and unobservable in
  the jsdom lane that CI actually runs.

## Addendum: a sixth defect the review did not name

The unit lane was ALREADY red on two committed assertions in
`app/(app)/observatory/__tests__/page-contract.test.ts` before any of the above
was written — baseline-proved by reversing the `filters.ts` edit and re-running.
An uncommitted working-tree change had flipped repeated-param handling
(`?view=a&view=b`) from "resolve to the default" to "take the first value", with
a reasoned code comment, but its paired committed test and the
`docs/system-analytics/observatory.md` line were never updated. The code was the
correct half — the old `Array.isArray(value) return "overview"` short-circuit
made `parseView` non-nullish, so a repeated `view` both ignored the views asked
for AND skipped `defaultObservatoryView`, landing a flow drill-down on a table
its filters do not touch. Test and doc updated to match; owner confirmed the
direction.

**Prevention:** an increment that changes a parse RULE has three surfaces, not
one — the function, its contract test, and the prose that states the rule. A red
test in the working tree is evidence of an unfinished increment, not noise to
route around; baseline-prove it before attributing it to your own diff, then
classify obsolete vs broken rather than leaving it red.

## Addendum 2: what the full e2e lane said

Full Playwright lane, `--workers=2` (the documented cap for this Mac): 185
passed, 5 failed, 6 flaky, 7.4 m. Four of the five failures are the
`web/CLAUDE.md` baseline set (`platform-agents-page:26`, `review-diff-scopes:43`,
`studio-ai-assistant:69`, plus `forked-package-loop:518`, which that doc records
as load-sensitive). `desk:205` appeared as flaky rather than failed.

**One failure was outside the set and inside the blast radius** —
`observatory-cost-breakdown.spec.ts:117` asserting a `scratch` pseudo-row in the
By-flow cost card. It was NOT ours: it reproduced with all five fixes disabled,
in isolation, at one worker, on a quiet host. Cause: this branch's own D5 work
made the card render `keyLabels?.[key] ?? label`, so a flow-less pseudo-row now
shows the TRANSLATED run-kind name ("Scratch") while a real flow row still falls
back to its raw `flowRefId`. The spec still asserted the bare lowercase key with
`{ exact: true }`. The render is correct and EN/RU parity requires it; the
expectation was stale. Fixed, and falsified by reverting the `keyLabels` lookup.

`m23-observatory.spec.ts:239` ("an uncommitted draft survives a view switch")
flakes at roughly 25%. Measured rather than assumed: 2 failures in 8 on code
with the fixes DISABLED, 1 in 4 with them applied — the same rate, so it is
pre-existing. It is the observable symptom of the half of finding 1's class that
ADR-177 deliberately leaves open: the bar now composes its own overlapping
edits, but a view tab is a server-rendered `<Link>` built from state that
predates an in-flight commit, so a blur-commit racing a tab click can still be
discarded. The "uncommitted" hint is the locked mitigation for that; closing it
properly would mean making the view switch client-owned, which is a design
change, not a fix.

**Prevention:** a spec's failure being in your feature's AREA is not evidence it
is in your DIFF. Disable the fixes and re-run before owning it — and for a
flake, compare the RATE against the unfixed code rather than the pass/fail of a
single run.
