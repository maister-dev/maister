# Keep paged retry previews bound to the displayed runner

**Date:** 2026-11-06 14:43
**Files:** web/components/agents/agent-retry-batch-control.tsx; web/components/agents/**tests**/agent-retry-control.dom.test.ts; docs/system-analytics/agent-activity-history.md
**Severity:** medium

## Problem

After Preview more appended page two, changing runners dropped that page and its
selected work. Preview more itself fetched the default runner despite displaying
a different choice, producing canonical requests and fingerprints the server
correctly refused as mismatched.

## Root Cause

The new runner refresh reused a single history-page loader. The missing runner in
loadMore already exists on master; the branch's frozen canonical request contract
makes its stale runner data observable as a refusal. This is source provenance,
not a claim about historical production behavior. Initial page and selected-source
previews have different pagination metadata: the latter intentionally has no next
cursor, so replacing the former wholesale loses the history window too.

## Solution

A distinct runner-refresh operation posts the exact visible run IDs with the
chosen runner using the existing selected-source contract (at most 100 IDs).
Shared preview application retains explicit choices intersected with eligibility.
The refreshed response supplies current requests/fingerprints while the existing
window supplies its cursor, offset and continuation metadata. No unbounded refetch
or server admission exception is introduced. Appended and next/latest pages carry
the current runner. Clearing the chooser performs no default request; a failed
refresh cannot submit old canonical requests under another displayed runner.

The existing batch DOM journey uses the API's actual 50-row pages and 100-row
visible bound. It failed first because page two requested the default runner;
with only that propagation fixed it failed because the page-two row disappeared
on refresh. Those REDs are retained in
`/private/tmp/maister-r16-retry-paging-red.log` and
`/private/tmp/maister-r16-retry-refresh-red.log`. The final journey preserves empty
and partial selection, keeps selected page-two work, excludes a newly eligible
row, refuses submission during a failed refresh, verifies the accepted POST's
fresh runner/fingerprints/requests, and traverses next/latest windows with that
runner. The existing retry DOM suite passes 13/13 in
`/private/tmp/maister-r16-retry-paging-green.log`.

## Prevention

Review a preview refresh together with appended pages and the outgoing request,
not only its first-page checkbox state. Preserve cursor ownership when using a
selected-source API to refresh a visible history window. Every pagination entry
point must carry the same explicit runner; never relax the server's mismatch
guard to accommodate a stale UI request.
