# HITL saved-answer refusals and permission resume evidence

**Date:** 2026-09-23 14:35
**Files:** `web/lib/services/hitl.ts`, `web/lib/execution-host/agent-permission-handoff.ts`, `web/lib/agents/permission-resume.ts`, `web/components/board/run-hitl-response.tsx`, `web/components/scratch/scratch-conversation.tsx`, `web/components/scratch/scratch-permission-panel.tsx`, `docs/api/web.openapi.yaml`, `docs/api/external/operations.openapi.yaml`
**Severity:** high

## Problem

A saved HITL answer could produce a 503 telling the operator to wait even when an identical retry was required. Scratch viewers could see a retry action they could not use, and plan-review `resume-queued` briefly looked like undelivered permission input. In the checkpoint race, an agent prompt could settle successfully without a confirmed input receipt; the resume classifier treated that prompt result as proof that the answer was delivered.

## Root Cause

The 503 body conflated durable storage with a future delivery trigger. The UI projected delivery state from a response status without respecting the distinct plan-review outcome or the operator's role. The agent resume classifier gave prompt completion order priority over the immutable input receipt, allowing a permission result handoff with no proved answer delivery.

## Solution

The web service and localized HITL copy now identify a saved, pending answer and direct the operator to retry delivery. Board, inbox and scratch cards use the same replay eligibility and pending-state helpers; scratch gates actions by role. Plan-review `resume-queued` renders a read-only recorded state without retry. The agent handoff only selects a permission result after confirmed input, with an invariant guarding that boundary. Contracts, system analytics, UI tests and the real-supervisor deadline tests cover the corresponding wire and state behavior.

## Prevention

- For every saved-answer refusal, trace whether a worker, sweeper or explicit retry actually triggers delivery before writing operator instructions.
- Reconcile all consumers of the HITL read model: board, inbox, run detail, scratch, external API and MCP. Keep host-owned reasons separate from web reasons.
- In checkpoint recovery, require positive delivery evidence before marking a HITL answered; prompt completion alone is insufficient.
- Validate OpenAPI examples against their referenced schemas and keep the reason enums aligned with the TypeScript contract.
