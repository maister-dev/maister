# A checkpointed flow could not answer its SECOND permission

**Date:** 2026-09-17 01:34
**Files:** web/lib/services/hitl.ts, web/lib/flows/graph/permission-resume.ts,
web/lib/flows/graph/gate-permission-resume.ts,
web/lib/services/__tests__/hitl-permission-ledger.integration.test.ts
**Severity:** high

## Problem

Master's A/B lane went red on both Node matrix legs at `ea64cf77`, and stayed
red: three cases across two suites, deterministic on every run since.

```
permission-result-failure > owner-flow-permission-checkpoint-interruption:
  'node'        continues across 'fresh permission'   -> exit=1, expected 0
  'skill_check' continues across 'fresh permission'   -> exit=1, expected 0
permission-resume > owner-flow-repeated-permission:
  completed-source preserves the current resumed source -> matcher timed out 30 s
```

Every one has the same shape: a permission is answered, the session is
interrupted, a permission-resume is authorized, the resumed session raises its
OWN permission — and answering that second one is refused. The third case reads
as a timeout only because its fault barrier waits for the responder to UPDATE
`hitl_requests`, and a refusal never reaches the update.

Behind the suites this is an operator-facing stall: every checkpointed flow that
raises a second permission parks in `NeedsInput` on a card that can never be
answered, which is the very bug 25f41c12 set out to end.

## Root Cause

25f41c12 asks the right question — "is a resume already carrying this answer?" —
through a predicate that cannot express "this". `hasFlowPermissionResume(db,
runId)` is RUN-scoped: `pendingNodePermissionResumeExists()` and
`pendingGatePermissionResumeExists()` match any pending resume on the run's
current node under the active assignment. Neither looks at which permission the
resume carries, though both resume records store `hitlRequestId` and the
`node_attempts` / `gate_results` check constraints require it to be a string.

A run drives one resume at a time, so run scope and request scope coincide until
the resumed session asks something new. From that moment the pending record
carries permission #1's answer while the actionable row is permission #2, and
the guard refuses #2 on #1's evidence.

The four older call sites (`resume.ts`, `resume-driver.ts` ×2,
`resume-recovery.ts`) ask a genuinely run-scoped question — "does this run have a
resume to drive?" — so the predicate itself was not wrong, only reused for a
different question.

Unit coverage could not see it: both mocked suites stub
`hasFlowPermissionResume` to `false` (their fake `select` ignores WHERE), and the
one real-database case seeds `actionResume.hitlRequestId` as the row it then
answers — the only arrangement where run scope and request scope agree.

## Solution

Thread an optional `hitlRequestId` through both predicates as one extra
conjunct (`action_resume->>'hitlRequestId'`, `permission_resume->>'hitlRequestId'`)
and pass it from `handlePermissionResponse`. Omitted, the predicates are
byte-identical to before, so the four run-scoped callers are untouched.

Paired the stand case with its twin in the same suite: a pending resume carrying
a DIFFERENT `hitlRequestId` must deliver, not refuse. Falsified — reverting the
argument at the call site turns the new case red and leaves the original refusal
green, which is exactly the pair the run-scoped guard could not tell apart.

## Prevention

- A guard is only as narrow as the question its predicate asks. "Is a resume
  carrying THIS answer?" and "does this run have a resume?" differ by one
  conjunct and by one production stall; when a fix's prose names a specific row,
  the WHERE clause must name it too.
- Reusing an existing predicate because it "already exists for three call sites"
  imports their scope along with their SQL. Check that the question matches
  before the code does.
- A refusal branch tested only where two scopes coincide proves the branch fires,
  never that it fires on the right rows. Seed the discriminating value.
- A fault barrier that waits on a write reports a refusal as a timeout. When an
  interruption helper times out, ask first whether the work it was waiting for
  was ever attempted.
