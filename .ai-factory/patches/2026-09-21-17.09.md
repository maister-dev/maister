# A drill-down whose target cannot hold the rows it counts, and two vocabularies for one closed set

**Date:** 2026-09-21 17:09
**Files:** web/components/observatory/overview-table.tsx, web/lib/queries/observatory-overview.ts, web/lib/runs/outcome-bucket.ts, web/lib/runs/list-params.ts, web/lib/observatory/drilldown.ts, web/lib/queries/runs-list.ts, web/components/observatory/{observatory-filter-bar,quality-tables,agentization-panel,labels,types,harness-format,autonomy-score-card,cost-breakdown-card,correction-heatmap,sensor-firing-card,signal-cluster-list}.tsx|ts, web/app/(app)/{observatory,projects/[slug]/observatory,runs}/page.tsx, web/messages/{en,ru}.json, docs/decisions/adr-178.md, docs/system-analytics/{observatory,runs}.md, docs/screens/{observatory,components,runs/list}.md
**Severity:** high

## Problem

ADR-178's headline invariant is "a cell's count equals the list it opens, by
construction". The Observatory's **Platform row** — project-less runs, admin
only — rendered all 13 of its numeric cells as links into `/runs` with no
`project=` param. `listRunsPage` is `FROM runs r INNER JOIN projects p ON
p.id = r.project_id`, so a `project_id IS NULL` run is structurally unreachable
there. Verified against a migrated Postgres: seeding one and querying
`{kind:"scratch", bucket:"ResultOnly"}` as a global admin returned
`totalRows = 0`. For an admin with other projects it is worse than a zero — the
missing `project=` does not narrow to platform runs, it widens to every
project's, so the reader gets an unrelated, larger number.

Three docs asserted the opposite as a MUST, and the plan's AC4 said "for **any**
overview cell". The suite that covered the row asserted only the href SHAPE
(`toContain("/runs?kind=scratch&from=...")`), which cannot tell a correct link
from one that opens the wrong population.

Alongside it: the same branch introduced `observatory.overview.kind.*` while the
filter bar kept reading `observatory.agentization.*` — two message copies of one
closed set (flow/scratch/agent), already disagreeing in RU ("Флоу" vs "Flow",
"Черновой" vs "Scratch") on the same screen.

## Root Cause

**The link.** The author had already reasoned the exact case through — three
lines above the bug sits a comment explaining why a per-flow sub-row's cells
open nothing ("the ledger has no flow filter … a count that disagrees with the
cell it came from"). The guard was written as `linkable = kind !== "flow"`:
an exception list enumerating the ONE class in mind, rather than the predicate
("can the ledger reproduce this population?"). The Platform row was added in the
same change-set, satisfied the enumeration, and inherited a link. The
`isPlatform ? undefined : slug` ternary at the call site is the tell — the author
knew the row had no project and dropped the param, without asking what the
ledger does with a run that has none.

**The vocabulary.** `labels.ts` carried a correct, explicit warning for the
bucket names ("a second copy under `observatory.*` is how the two surfaces would
end up disagreeing about what 'PR open' is called") and then, six lines later,
created exactly that second copy for run kinds. A grep for
`agentization\.(flow|scratch|agent)` found the filter bar and missed the
Agentization panel entirely, because it reads `const text = labels.agentization`
and then `text[bucket.kind]` — a local alias defeats a member-access grep. The
TYPE CHECKER found it, once the orphaned fields were deleted.

**Two smaller ones, same shape.** `TASK_IN_WORK_SETTLED_STATUSES` was a second
answer to "is this run settled" living beside the D3 classifier; it said Review
and Crashed are never settled, so one crashed run nobody discarded held its task
in "in work" in every future window forever. And a test asserting three
promotion states are "unreachable" compared a local constant with itself — it
never touched the classifier, and paid a 180 s Postgres container to do it.

## Solution

- `linkable` states the predicate and names both classes it excludes, with the
  reason for each. The Platform cells render as plain numbers; the fuller answer
  (a `project=__platform__` mode over a `LEFT JOIN projects`) went to the
  Phase-2 backlog rather than into a fix pass, because it changes the ledger's
  query shape, param vocabulary and RBAC surface.
- Two regressions, at the two layers the claim spans: an integration test that a
  project-less run is unreachable from `listRunsPage` under any filter (the
  database FACT the render decision rests on), and a render test that no cell of
  that row emits `/runs?`. Both falsified — the render guard against
  `kind !== "flow"`, the database guard against a `LEFT JOIN`.
- One top-level `runKind.*` namespace, mirroring the `runBucket.*` precedent the
  branch itself had set, read by four surfaces plus the ledger; the per-surface
  copies deleted so nothing can re-diverge.
- `runSettledSql` derives "settled" from the D3 bucket, deleting the parallel
  status list; `filtersToParams` moved to a client-safe module and is now CALLED
  by the drill-down builder instead of re-spelled; `period` made REQUIRED on the
  three drill-down components (the compiler then found 8 call sites and one
  second clock).

## Prevention

- **A guard written as an exception list is a bug waiting for its second case.**
  When code excludes one class from a behaviour, write the PREDICATE the
  exclusion serves (`can the target reproduce this?`) and enumerate against it —
  then adding a row type is a compile-or-review event, not a silent inheritance.
- **Review the row types a table can render, not the rows a fixture seeds.**
  `OverviewRowIdentity` is a 4-member union; three were reasoned about.
- **A grep over member access misses aliased reads.** `const text = labels.x`
  then `text[k]` is invisible to `grep "x\.k"`. Prefer deleting the field and
  letting the type checker enumerate consumers — it found the panel a
  two-pattern grep had missed. Record the grep AND the compiler result.
- **An href-shape assertion is not a drill-down test.** Ask "would this pass if
  the link opened a different population?" If yes, assert the count, or assert
  the target cannot hold the rows.
- **Two answers to one question is the defect, wherever it lives** — a second
  status list, a second message key, a second clock, a second serializer. This
  branch had all four, and its own comments had already named the hazard for a
  fifth.
- **A test that compares a local constant with itself is not documentation.**
  If a combination is "unreachable", check whether anything ENFORCES it (here:
  nothing — `promotion_state` is plain `text` with no CHECK), then seed it and
  assert what actually happens.
