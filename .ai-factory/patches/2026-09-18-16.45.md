# Review-fix batch: a claim marker released by only one of three arms, and an idempotency marker read as a skip

**Date:** 2026-09-18 16:45
**Files:** web/lib/runs/crash-recover.ts, web/lib/runs/recover.ts, web/lib/reconcile.ts, web/lib/runs/recover-http.ts, web/lib/flows/graph/{runner-graph,rework-baseline}.ts, web/lib/{scheduler,queries/run}.ts, web/components/runs/run-recover-actions.tsx, web/messages/{en,ru}.json, docs/system-analytics/{flow-graph,observatory}.md, 3 test files
**Severity:** critical

## Problem

`/aif-review` of the ADR-175 branch produced three blocking findings:

1. `runs.resume_started_at` — the crash-recover claim, and the predicate the
   reconcile sweep re-enters a web death on — was released by only ONE of the
   three arms that consume it. `runGraph` CAS-clears it for a `crashResume`
   re-entry; the applied-evidence continuation and the all-settled orchestrator
   resume re-enter without that signal and cleared nothing. A stale marker makes
   `classifyRunReconcile` read the run's NEXT, unrelated crash as an unclaimed
   recover intent and silently re-dispatch a paid ACP turn — replacing the
   `Crashed` row plus "Recover or discard" the operator is supposed to answer.
2. `applyCrashedTurnEvidence` treated an already-applied completion as a row to
   SKIP (`if (command.completionAppliedAt) continue;`), so a second Recover
   after a failed continuation closed the attempt `crash_recover` and bought the
   finished turn again — the exact double-spend the arm exists to prevent.
3. Two analytics surfaces drifted: `flow-graph.md` documented the rework-epoch
   formula as `operatorInterruptCount(runId, nodeId)`, a function the branch had
   RENAMED and widened, and `observatory.md` still defined `correction_rate`
   (prose plus a normative Expectations bullet) without the exclusion set.

## Root Cause

**(1) and (2) are the same mistake in two shapes: a marker was given a meaning
the code enforced in one place and assumed everywhere else.**

For the claim marker, the invariant was even written down — `reconcile.ts`
asserted "the graph CAS-clears that marker the moment a driver takes the
re-entry, so a non-null marker means nobody has." Nothing enforced it. The
sweep grep that would have caught it is `runFlowFn(runId` — four call sites,
two of which pass `crashResume` and two of which do not. The release was
designed against the mechanism (`isCrashResume`) instead of against the
event ("a driver took the re-entry"), so arms that took the re-entry by a
different route were structurally invisible to it.

For the completion marker, `completion_applied_at` answers "is this turn already
in the ledger?" — which on a recovery path is the ANSWER, not a filter. Written
as a `continue`, it fell through to the expensive default (close the attempt,
re-prompt) instead of short-circuiting to the cheap correct one (continue the
graph). The same inversion sat in the transaction: a 0-row completion CAS was
read as "not applied" when it equally means "already applied by a racer".

**(3)** The spec's own "System-analytics contract" table was the checklist for
which docs move with the change, and it listed four surfaces. REQ-20 touched two
more that were not on it. A table used as a checklist is only as complete as the
pass that wrote it, and nothing re-derives it from the diff.

## Solution

- `clearCrashRecoverMarker(db, runId)` in `crash-recover.ts`, called by the two
  arms that re-enter without `crashResume` — **after** `runFlow` returns, never
  before, because while the dispatch is in flight the marker is exactly what
  lets the sweep recover a web death. Guarded on `isNotNull` so it is idempotent.
- `applyCrashedTurnEvidence` now carries `node_attempts.action_completion` on
  the attempt read and returns `"applied"` when the attempt already holds this
  command's completion. The in-transaction 0-row CAS and the
  `PromptOwnerHandoffLost` rollback both re-read the attempt
  (`evidenceAlreadyApplied`) instead of inferring from the row count.
- The command lookup moved into the loop, owner-filtered in SQL
  (`owner_ref->>'nodeAttemptId'`) and `limit(1)`, so it stops pulling every
  turn's whole `request_canonical_json` back to satisfy one match.
- `driveResume` gained the missing `discard-only` arm: `classifyRecover` has
  three outcomes and the dispatch handled two, so a standalone entry (scheduler
  promotion, sweep recover) could dispatch a fresh session for a node
  `POST /recover` answers `409 discard-only` on.
- Docs: `flow-graph.md` and `observatory.md` restated around
  `NON_CORRECTION_DECISIONS`; the two surfaces added to the spec's contract
  table. Four sibling surfaces (`hitl.md`, `run-continuation.md`,
  `configuration.md`, the node-interrupt OpenAPI block) were classified as
  CORRECT AS-IS — each states something about `operator_interrupt` that is still
  true, and `MAISTER_MAX_OPERATOR_RESTARTS` deliberately excludes `crash_recover`.

## Prevention

- **A column that is both a claim and a recovery predicate needs its RELEASE
  sites enumerated, not its write sites.** Grep the consumers
  (`grep -n 'runFlowFn(runId' <driver>`) and classify every one as
  "clears it / relies on a clear / must not clear" before trusting the invariant.
  Ask "what event releases this?", never "which code path releases this?".
- **An invariant asserted in a comment is a lead, not evidence** — this repo's
  own review rules say so, and the comment here was false for two of three arms.
  When a comment says "X always happens", grep for X and count the sites.
- **An idempotency marker on a recovery path is an ANSWER, not a filter.** A
  `continue`/`skip` on "already done" is a code smell when the fall-through is
  the expensive redo. Prefer an early return that reports the work as complete.
- **Never infer "not applied" from a 0-row CAS** — re-read the row. A CAS row
  count says something changed, not what.
- **Re-derive the doc-surface list from the diff at review exit**, not from the
  spec's table: `grep -rn '<renamed symbol>' docs/` catches the class the
  compiler cannot. A doc naming a function the change renamed is unambiguous
  drift.
- Guard added AND falsified: T-CR2 now asserts `resume_started_at IS NULL`
  after an applied-evidence recover. Falsification (2026-09-18 16:49) removed
  ONLY the evidence-arm release and re-ran it — RED at
  `prompt-owners.integration.test.ts:3343` with
  `Expected: null / Received: 2026-09-18T13:49:28.832Z`, i.e. the marker the
  leak leaves behind. Exactly one assertion failed and the test still reached
  that line, so the guard pins the release in ISOLATION rather than riding on
  C3's prompt-count assertions; restoring the call returned it to green. The
  pre-existing reattach sweep test also now asserts `runningIdleSession`
  positively (REQ-18 demanded the counter be asserted, and it was not).
