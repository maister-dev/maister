# Index corrupt runtime paths before supervisor startup inventory

**Date:** 2026-11-02 14:35 Europe/Moscow
**Files:** `supervisor/src/host-state.ts`, `supervisor/src/__tests__/runtime-file-inventory.integration.test.ts`, `supervisor/src/__tests__/_fixtures/runtime-file-inventory.ts`, `supervisor/scripts/benchmark-runtime-file-inventory.ts`
**Severity:** high

## Problem

Supervisor startup waits for runtime file inventory before opening its HTTP
port. The reported stand takes about nine minutes with approximately 30,000
runtime files.

## Root Cause

Inventory tests each retained file's private path for a corrupt object. Neither
the run/state index nor the expiry index supports this predicate:

```sql
SELECT 1 FROM runtime_objects
WHERE private_path = ? AND state = 'corrupt';
```

Without a suitable index, every lookup scans the object catalog. Startup work
therefore grows with the product of file count and historical object count.

## Solution

SQLite schema v15 adds the same nonunique partial index to the fresh schema
and the transactional v14-to-v15 migration, before inventory runs:

```sql
CREATE INDEX IF NOT EXISTS runtime_objects_corrupt_path_idx
  ON runtime_objects (private_path) WHERE state = 'corrupt';
```

The predicate exactly matches both inventory lookups, including the symlink
check. Indexing only corrupt rows avoids storing available, deleted and other
historical objects in this index. A full `(private_path, state)` index would
also support this query but retain every object and incur additional storage
and write costs. The partial index tracks state changes automatically and
permits duplicate paths, preserving the existing nonunique catalog contract.

The inventory implementation, startup ordering, corruption handling, file
checks, reservations and storage accounting are unchanged. Index pages remain
part of the SQLite database/WAL measured by the existing physical budget.
No runtime state is removed. This declarative schema change uses the existing
service logging boundary; it adds no per-file logs.

## Regression validation

Five new integration cases use actual SQLite databases and files:

- Fresh installation and reopening preserve host identity and the indexed plan.
- A populated v14 database initially scans; production opening migrates it to
  v15 before inventory. Catalog rows, file rows, contents and budget survive two
  opens unchanged.
- Real state transitions maintain partial-index membership; duplicate corrupt
  paths remain valid.
- Oversized corrupt files and known corrupt symlinks survive migration and
  reopening with the correct retained-byte charges.

The plan assertions require a `SEARCH` through the named index and reject
`SCAN runtime_objects`. Tests also assert a nonunique partial index.

The five targeted integration files cover 55 cases: inventory, runtime file
budget, physical storage, host identity and runtime object integrity. The first
combined invocation passed 54 cases; the maximum-output producer case exceeded
its existing five-second receipt wait while the benchmark and validators were
running. The complete runtime-file-budget file then passed 9/9 in 1.45 seconds
after the benchmark completed. The other four files passed in the original run.
No timeout or product behavior was changed to obtain this result.

Additional checks passed:

- MCP build; scoped ESLint and Prettier checks.
- `CI=true pnpm validate:docs:all` and `CI=true pnpm validate:contracts`.

## Reproducible benchmark

Run from `supervisor/` with the supported Node 24 runtime:

```sh
pnpm exec node --import tsx scripts/benchmark-runtime-file-inventory.ts
```

The script creates an isolated temporary database with 30,000 objects and
30,000 real 64-byte files, including 300 corrupt objects. It restores the v14
schema, measures the unchanged inventory three times, upgrades through
`openHostState`, measures inventory three more times, and reopens the migrated
database. Setup and teardown are excluded from inventory timings.

Both sides use the production statement cache, connection-local accounting
tables, WAL/FULL settings and physical-storage write wrapper. Assertions verify
object/file counts, unchanged budget and identity, filesystem file count, and
physical state capacity. Temporary state is removed when the script finishes.

Measured locally on Apple M4 Max, Darwin 25.6.0, Node v24.15.0,
SQLite 3.51.3:

| Inventory pass | Before, ms | After, ms |
| --- | ---: | ---: |
| 1 | 158263.892 | 352.585 |
| 2 | 92572.573 | 334.486 |
| 3 | 72590.773 | 342.268 |
| Median | 92572.573 | 342.268 |

Median improvement: **270.47 times**. The full upgrade open, including the
migration, audits and inventory, took **341.570 ms**. Reopening the upgraded
database took **347.236 ms**. The charged and written file budgets remained
**1,920,000 bytes**, with zero unused bytes and no pressure.

Before:

```text
SCAN runtime_objects
```

After:

```text
SEARCH runtime_objects USING COVERING INDEX runtime_objects_corrupt_path_idx (private_path=?)
```

These are local synthetic measurements, not a deployed-stand startup result.
The first baseline samples overlapped validation processes; host load and cache
warming contribute to their spread. The raw samples are retained above instead
of treating the median ratio as a hardware-independent guarantee. The benchmark
does not measure HTTP listen latency or the rest of supervisor initialization.

## Prevention

Inspect the actual SQLite query plan for predicates inside boot-time file
loops. Test both fresh DDL and upgrades of populated persistent databases;
include reopening and state transitions for partial indexes. Keep timing
measurements outside ordinary CI assertions; assert planner behavior and
retained-state correctness deterministically.

Sibling-query sweep:

```text
rg -n "private_path.*corrupt|corrupt.*private_path" supervisor/src
```

`runtime_files.private_path OR temporary_path` is already covered by the
existing unique indexes on those columns and needs no change.
