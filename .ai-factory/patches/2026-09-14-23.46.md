# Give a live agent session its observer back instead of letting the sweep name the death

**Date:** 2026-09-14 23:46 (Europe/Moscow)
**Files:** `web/lib/agents/session-observer-registry.ts` (new),
`web/lib/agents/launch.ts`, `web/lib/reconcile.ts`,
`web/lib/agents/__tests__/{agent-session-supervisor.test.ts,agent-session-replay.integration.test.ts,agent-session-reobserve.integration.test.ts}`,
`web/lib/__tests__/{reconcile-classify.test.ts,reconcile-sweep.integration.test.ts}`,
`docs/system-analytics/{reconciliation-gc.md,execution-prompt-lifecycle.md}`.
**Severity:** high

## Problem

A `run_kind='agent'` run (consensus draft, platform agent, orchestrator child)
has exactly ONE in-process reader of its canonical event stream —
`consumeAgentSession`. When the web process died, or the observer's supervisor
(2026-09-14 22.39) exhausted its retry budget, nothing replaced it: reconcile
classified the run `reattach` and then refused the action —

```
22:04/07/09/11  reconcile: refusing reattach for non-flow run — skipping
```

— four ticks in a row on the stand, ten minutes of a live session nobody read.
When the session finally died the sweep crashed the child as
`agent-session-gone`, and its parked coordinator was killed twelve minutes later
as `orchestrator-stuck`. Both statuses name the sweep that noticed, not the
failure that happened.

The follow-up section of 2026-09-14-22.39 filed exactly this as unclosed.

## Root Cause

- **Nothing owned the replacement.** The `liveSession` arm of
  `classifyRunReconcile` had two outcomes — `skip` for scratch, `reattach` for
  everything else — and `reattach` means "hand the run to its durable graph
  driver", which an agent run does not have. The sweep therefore refused its own
  classification for every non-flow kind and counted it as a skip. The refusal
  was the whole recovery path: a component that can be lost with no replacement.
- **Nothing prevented the opposite either.** Every entry into
  `startAgentSession` / `dispatchStoredAgentTurn` started its own observer, so a
  recovery that added one could have produced two readers of one stream, doubling
  every side effect on it.
- **Re-observation was not safe to perform.** A new observer has no resume point,
  so it re-enters the durable stream FROM THE BEGINNING.
  `recordAgentPermissionRequest` — the unowned twin of
  `recordOwnedAgentPermissionInTransaction`, which has been idempotent all along
  — inserted a fresh `randomUUID()` row on every `session.permission_request` it
  saw. A replay would have asked the human the same question twice and left an
  unanswerable second row behind.
- **The give-up was not durable enough to be named.** Observer exhaustion was an
  ERROR log line and nothing else, so the terminal status written minutes later
  could only cite its own classification.

## Solution

- `lib/agents/session-observer-registry.ts` — the in-process observer registry,
  built on the `syncDriverActive` / `hasSyncDriver` precedent in
  `lib/runs/sync-driver-registry.ts`. Keyed on the HOST session id (the thing an
  observer reads), it is BOTH the mutual exclusion (`claimAgentSessionObserver`
  refuses a second reader; `observeAgentSession` returns false and logs instead
  of starting one) and the discriminant reconcile keys on. Process-scoped and
  deliberately not durable — a restart clears it, which is precisely how a
  post-restart orphan is detected.
- `classifyRunReconcile` gains `agentObserverActive` and, INSIDE the existing
  `liveSession` arm, an agent case: with an observer → `skip` /
  `agent-observer-live`; without → `reobserve` / `agent-observer-gone`. **Branch
  order is unchanged.** Equivalence: both outcomes replace what previously
  classified `reattach` / `live-session` for `runKind === "agent"` and was then
  discarded by the sweep's non-flow refusal — no run that took a different arm
  before takes a different arm now. Scratch keeps `live-scratch-session`; flow
  keeps `reattach`.
- The `reobserve` sweep arm calls `reobserveAgentSession`, which binds the run's
  ACTIVE `execution_assignment_id` (never minting one from a sweep) and starts
  ONE observer. It writes no run state, drives no prompt, and on a fenced
  assignment yields with a WARN — a reader that cannot attach is never a reason
  to tear a live session down. Counted as `summary.reobserved`.
- `recordAgentPermissionRequest` is idempotent on the host's own
  `(supervisorSessionId, requestId)` identity, matching the owned recorder's
  discriminant minus the `agentPrompt.commandId` an unowned row does not have.
- Exhaustion records the typed give-up (`code`, `message`, attempts, resume
  point) in the registry; the sweep's agent crash arm consumes it, so the
  `finalizeAgentRun` reason reads `reconcile: agent-session-gone (observer gave
  up after 10 attempts: EXECUTOR_UNAVAILABLE ...)` when this process saw it.
  After a process death nothing recorded it and the classification stands alone —
  which is honest, not a gap.

## Sibling sweep (recorded, per the "fix the class" rule)

`rg "consumeAgentSession|observeAgentSession" lib/ app/ --glob '!**/__tests__/**'`
→ 3 production call sites, all now behind the one claim: `observeOwnedAgentSession`
(owned turn), the plain-session tail of `startAgentSession`, and the new
`reobserveAgentSession`. `superviseAgentSession` is exported only for the unit
suite; nothing else calls it.

Same-class replay exposures on the observer path, classified rather than
silently widened or omitted:

- `escalateHookTrip` (`session.hook_trip`, disposition `halt`) is NOT idempotent
  on identity — but it is **unreachable** in a re-observe replay: the sweep only
  re-observes a `Running` run with a LIVE session, and an applied halting trip
  checkpoints the session and leaves the run non-`Running` (a failed one crashes
  it). Its own `run.status !== "Running"` precondition is the guard. Left alone —
  widening it would touch the supervisor checkpoint path, which the report puts
  out of scope.
- `session.exited` / `session.crashed` cannot be in a LIVE session's replay.
- `session.update`'s `NeedsInput → Running` flip is a status-guarded CAS and a
  no-op for the `Running` run the sweep re-observes.
- A `run_kind='scratch'` run with a live session stays `live-scratch-session` by
  the report's explicit invariant — its next user message is its continuation
  owner.
- An agent run that is `NeedsInput`/`NeedsInputIdle` with a live, unread session
  is still outside reconcile's `Running`-only allow-list (the keep-alive sweeper
  owns those rows). Not in this fix's scope; noted as the next boundary.

## Assumptions recorded

- **Keyed on the host session id, not `acp_session_id`.** The adapter's resume
  handle is reused across incarnations; the host session id is what an observer
  actually streams, so it is the identity that makes "one observer per session"
  true.
- **The recorded give-up is in-process, not persisted.** The report asks the
  terminal status to cite the refusal "when there is one" — and when the web
  process dies there is none to cite. An in-process ledger covers exactly the
  case that CAN be recorded (an exhausted supervisor in the process that also
  runs the sweep) without adding a column for a value that is null whenever it
  would matter most.
- **`reobserved` is a new `ReconcileSweepSummary` field**, so the one exhaustive
  `expect(summary).toEqual({...})` in `reconcile-sweep.integration.test.ts`
  gained `reobserved: 0`. That is an additive key on a zeroed-summary literal, not
  a relaxed behavioural expectation — no assertion about what the sweep DOES was
  changed, and the decision-table cases are untouched.

## Prevention

When a recovery path REFUSES the action its own classifier produced, that is not
a safe default — it is a hole with a log line in it. Read every `case` of a
decision table for arms that classify one thing and then decline to do it, and
ask what replaces the component in the meantime; "the sweep will notice
eventually" means the status the system finally writes will name the sweep.

And before adding a second consumer of a replayable log, prove idempotency at the
identity the SOURCE controls (here `(sessionId, requestId)`), not at the row id
the consumer mints — a `randomUUID()` per event is a duplicate generator wearing
a primary key. Check the twin that already got this right: the owned recorder had
the exact guard the unowned one lacked.

Third: in a fresh worktree, finish the install before reading any red. Four
assertions across two suites failed on product-looking values (`createSessionCalls()`
empty, `MAISTER_PROJECT_TOKEN` undefined) purely because a postinstall crash left
`mcp/node_modules/.bin` and `mcp/dist` absent. Baseline-proving located it as
"not the diff"; only checking `resolveFacadeLaunch`'s inputs located it as "not
the tree either". A capability that resolves to `null` when unbuilt fails as
absent behaviour, not as a build error.
