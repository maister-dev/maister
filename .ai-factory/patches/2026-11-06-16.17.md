# Give accepted launch deadlines a durable service owner

**Date:** 2026-11-06 16:17
**Files:** task launch worker/wake/dispatch/first-dispatch/agent-execution modules; worker composition/health; scheduler internal promotion result; agent preparation's initial-source validation; existing launch-selection, worker health/system-sweep and native boot suites
**Severity:** high

## Problem

Acceptance's `after` callback requested one fair pool promotion. It did not necessarily serve the triggering intent. A real repository-contention deferral persisted a future `due_at`, but the existing three durable workers did not own that deadline. Progress then depended on another scheduler event. Final browser rows establish delayed binding, but do not reconstruct whether a particular original delay was caused by repository contention, parent-capacity deferral, or another wake selection.

## Root cause

A one-shot notification was treated as sufficient queue activation even though its shared dispatcher could service another request or persist a later retry. The durable queue data existed, but startup/deadline service had no independent registered owner.

Adding the durable service exposed a second ownership boundary: an agent may be `Running` while its intent remains `run_bound` without a first-model dispatch commitment. Its physical preparation owner is still materializing platform files. Repeated scheduler-side integrity probing compared those legitimate in-flight changes against the old generation and held the intent with `launch_agent_integrity_refused`; the rightful owner then failed its dispatch commitment with `launch_worker_fenced`.

Moving that premature probe also exposed a distinct constraint that had to be preserved: a `repo_read` shared repository must still match its accepted HEAD and be clean before the first baseline is captured. A post-generation probe alone cannot reject dirt captured into that baseline.

## Solution

Register a mandatory fourth `taskLaunch` durable worker through the existing composition, interned slots, health and joined shutdown. One service slot per Flow/Agent pool reads PostgreSQL due/lease deadlines, uses advisory event wakes and bounded recovery waits, and enters the existing priority/capacity scheduler. There is no new execution authority, claim engine, queue, schema, client polling or `setInterval`.

Idle slots allow one immediate advisory reread, then anchor repeated no-work hints to the original database-derived deadline. Unrelated projection bursts cannot turn an empty queue into a database query hot loop. The monotonic clock only controls waiting; PostgreSQL still decides whether work is due.

The shared scheduler reports internal durable task-launch progress separately from a returned Run ID. A busy request moved into the future counts as progress, so the bounded drain can serve later work immediately. An explicit no-progress result overrides a non-null existing Run ID. Claim/version churn alone is not progress: the selected owner's post-service state must be committed, removed/nonlive, genuinely future-due, protected by a valid preparation lease, or handed to the Running agent owner. Canonical first-dispatch capacity release uses the existing one-second future deferral, preventing a parent-cap/shared-writer denial from immediately recycling the same binding. `releaseSlotOnIdle` projects its existing result; callers do not gain a public wire field.

Repeated same-reason deferrals refresh their actual PostgreSQL deadline without inventing a public state transition. Both the parent-fanout wait writer and bound repository/availability wait writer retain `stateVersion` and emit no `task.launch_changed` when only deadline/lease metadata changes. The existing database version guard remains unchanged.

A Running agent's preparation belongs to its existing agent continuation owner. Shared pending selection excludes that phase, while direct bound-dispatch re-entry yields safely. The scheduler retains current actor/input/runner checks. The physical preparation owner reuses the existing source validation before initial baseline capture, then retains the mandatory generation/integrity and first-dispatch commitment before create/prompt. No baseline is assumed clean and no technical guard is disabled.

## Prevention

For every persisted deferral, name the deadline/restart owner independently of its live notification. Reuse the same authoritative dispatcher and classify its actual durable progress. When moving an integrity check to its correct physical owner, inventory every branch of the original helper: a post-baseline verification cannot substitute for an initial-source constraint. Exercise both the protected active-owner window and the dirty-source negative with real rows/files.
