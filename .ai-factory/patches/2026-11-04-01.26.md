# Construct consensus prompt-owner registries after module initialization

**Date:** 2026-11-04 01:26
**Files:** web/lib/flows/graph/consensus/draft-prompt-owner.ts; web/lib/workers/runtime.ts; web/lib/workers/**tests**/production-registry.test.ts; web/lib/flows/graph/**tests**/consensus-prompt-owners.integration.test.ts
**Severity:** high

## Problem

The unchanged bounded-output integration suite collected zero tests. The final
failure stack reported `ReferenceError: Cannot access '__vite_ssr_import_14__'
before initialization` in `createAgentPromptOwners`, called by the consensus
draft module while importing the agent launcher. Its database and supervisor
fixtures had not started.

## Root Cause

The consensus draft module constructed its registry at module scope. New
admission dependencies introduced multiple routes back from agent finalization
to the agent launcher, including scheduler/launch claims and qualification
publication/consensus admission. The launcher imports consensus draft handling,
which called the registry factory before the original agent prompt-owner
module's prompt-owner import binding had initialized. The test contained no
module mocks; changing a fake transport or database fixture could not repair
this collection failure. Removing only one reverse import would leave another
route through the same cycle.

## Solution

Expose a pure `createConsensusDraftPromptOwners` factory and call it from the
prompt waiter and runtime composition. Runtime also constructs the production
registry list through a pure factory when starting workers. No registry cache,
mutable global, import-order workaround, dynamic-import workaround, delay or
retry is introduced. The same draft-aware adapter delegates ordinary agent
variants to the existing owner, and the composition still validates all six
schema kinds and refuses duplicates. Existing worker start/stop diagnostics
retain the actual registered owner kinds; the pure factories have no logging
side effects.

## Prevention

Keep registry construction at runtime composition boundaries when its factory
crosses domain imports. Review the complete dependency class rather than
patching the first cycle edge. Keep an unchanged low-level integration suite
in the verification set: importing a high-level entry point first can hide an
ordering-sensitive module failure.

Evidence: RED is the natural full-suite collection stack in
`/private/tmp/maister-web-full-integration-final.log`, lines 86507–86517. The
unchanged complete bounded-output suite, production composition checks and
actual consensus prompt-owner integration suite pass together: 3 files,
54 tests, 300.03 seconds, exit 0, in
`/private/tmp/maister-consensus-registry-cycle-green.log`. Both owned databases
stop normally. Scoped ESLint exits 0 in
`/private/tmp/maister-consensus-registry-cycle-lint.log`; `git diff --check`
passes. This is a locally reproduced import-cycle defect, with no claim about
the original historical MAI-27 filesystem/Git failure or production behavior.
