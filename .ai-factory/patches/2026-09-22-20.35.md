# Scratch resume cursor mixed two number spaces; accepted create receipt had no specified outcome

**Date:** 2026-09-22 20:35
**Files:** web/lib/scratch-runs/events.ts, web/lib/execution-host/owned-session-create.ts, web/test-support/{owned-fixture,real-web,real-supervisor}.ts, scripts/run-stage-ab-tests.mjs, docs/system-analytics/*, .ai-factory/plans/*
**Severity:** critical

## Problem

Two production defects and a family of tests that certified claims their
fixtures could not produce.

1. A scratch follow-up prompt silently dropped the opening events of its turn.
   `run_messages.supervisor_event_id` holds the supervisor's per-session
   `monotonicId` on notice rows but the manager's `run_sequence` on projected
   reply rows. The SSE resume cursor `max()`ed over BOTH, and the supervisor
   drops every event at or below the cursor — replay and live alike. A dropped
   `session.permission_request` leaves no HITL row and leaks the deferred.
2. A host death after the create receipt reached `accepted` but before the turn
   finished (`inflight: false` = turn_lost) had no specified outcome. The fold
   arm threw `SessionCreatePending` without reading `inflight`, and nothing
   advances such a receipt, so the run failed one step past D2a.
3. L1 claimed to prove "no late successful overwrite" by SIGUSR1-ing an adapter
   whose release the cancel had already consumed; D3 compared a cursor to a
   snapshot taken after the writer was blocked; P3 proved a duplicate by log
   grep; D2a/D2b filtered on `row.status === null`, which is true of every
   traffic entry.

## Root Cause

Each defect is the same shape: an INVARIANT WAS MOVED AND ITS READERS WERE NOT
RE-DERIVED.

1. The branch moved scratch reply projection onto the canonical projector. That
   changed what `supervisor_event_id` MEANS on half the rows, but the cursor
   query that reads the column was left addressing the old meaning. The code
   even carries a comment asserting the new invariant ("canonical run sequences
   also key scratch notices") that was never implemented — the author wrote
   down the intended end state and shipped the intermediate one.
2. The receipt-first fold enumerated `404 → reissue` and `completed → fold` and
   treated everything else as "defer". `accepted` is not one state: `inflight`
   splits it into "someone is still working on it" and "nobody ever will".
   Deferring to a party that does not exist is a hang, not a wait.
3. A fixture that cannot produce the condition under test will pass against any
   implementation. In each case the assertion was written from the STORY of the
   scenario rather than from what the fixture could actually emit.

## Solution

1. The cursor now reads only rows in the supervisor's number space,
   discriminated by the role the canonical projector never writes (it inserts
   only `assistant`/`tool`; notices are `user`/`system`). Guarded by a real-PG
   test that FAILS with `expected 7 to be 2` against the unfixed code.
2. `accepted` splits on `inflight`: still-inflight defers as before; a lost turn
   is recorded on the original command and ONE replacement generation is issued
   from the stored bytes, bounded by the same generation ceiling as the
   definitive-refusal arms. Safe because an unfinished create returned no
   session id to fold and a restarted host holds no adapter to orphan. A D2c
   control proves it and fails with the old hang when reverted.
3. Each weak assertion was either anchored to evidence that discriminates (D3
   now compares against the sealed event's own sequence; P3 asserts no second
   `execution_events` row) or the CLAIM was corrected to what the seam can
   prove (L1: one ACP prompt yields one response, so a late success is not
   producible — the control now proves a stray post-settlement signal changes
   nothing).

## Prevention

- When a change moves what a COLUMN means for some rows, grep every reader of
  that column and re-derive each one. A column shared by two writers on
  different clocks is a latent bug until a discriminator exists.
- A comment that states an invariant is a CLAIM to verify, not documentation.
  Two of these defects were visible as a comment contradicting its own module.
- Before accepting "test proves X", ask what the fixture would have to EMIT for
  X to be false, and check it can. Falsify by reverting the fix — a guard that
  stays green against the unfixed code guards nothing.
- An enum arm that "defers" must name who will advance it. If nothing will, it
  is a hang.
