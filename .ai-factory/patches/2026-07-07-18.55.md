# Claude package subagent materialization parity

**Date:** 2026-07-07 18:55
**Files:** `web/lib/capabilities/adapter-home.ts`, `web/lib/agents/dirty-watchdog.ts`, `web/lib/acp-runners/adapter-support.ts`, `supervisor/src/adapter-registry.ts`, `docs/system-analytics/agents.md`, `docs/system-analytics/capabilities.md`, `docs/system-analytics/acp-runners.md`
**Severity:** high

## Problem

Claude package materialization copied package skills but skipped package
capability subagents. That contradicted the product contract for Claude, whose
native `.claude/agents/` surface should receive capability-local subagents from
the same pinned package roots as skills. The stale docs and tests also encoded a
skill-only standalone package-agent rule.

## Root Cause

The shared adapter materialization helper was narrowed to copy only `skills/`
for cwd-dir adapters while it still served both standalone package-agent sessions
and broader project/scratch package materialization. That collapsed an
adapter-specific capability surface into a generic skill-only assumption and left
the dirty-watchdog manifest unaware of `.claude/agents/` paths.

## Solution

Claude cwd-dir materialization now copies both `skills/` and `agents/`, while
Gemini remains skills-only and home-redirect adapters keep their existing skill
homes. The ownership manifest records copied subagent paths, and the
dirty-watchdog restore/filter logic accepts `.claude/agents/...` entries without
deleting user-owned same-name files. The read-only launch gate now uses an
explicit `readOnlySessionSmoke` descriptor instead of a private adapter-name set.
Specs, analytics, and plan text were updated to say Claude materializes
subagents and non-Claude adapters omit them.

## Prevention

- When changing a shared materializer, check every caller category: standalone
  agent, scratch, flow authoring, and flow-node binding.
- Keep materialization contracts adapter-surface driven; `skills` and
  `subagents` are separate surfaces and must not be collapsed into one mode.
- Dirty-watchdog ownership manifests must track every generated path class, not
  only the first generated class added by a feature.
- Tests should include both generated and user-owned entries for each copied
  path class.
