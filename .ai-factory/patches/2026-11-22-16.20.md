# Avoid a deadlock between gate admission and prompt confirmation

- **Date** 2026-11-22 16:20
- **Files** `web/lib/flows/graph/driver-claim.ts`, `web/lib/flows/graph/prompt-owner.ts`, `web/lib/flows/graph/__tests__/driver-claim.integration.test.ts`
- **Severity** high

## Problem

A scheduled Flow sometimes completed its primary prompt and crashed before
submitting its AI gate prompt. The integration test recorded one prompt instead
of two. Repeated isolated runs reproduced PostgreSQL `40P01`.

## Root cause

After host-span settlement, canonical confirmation still has to reduce the
terminal evidence. It holds the run foreign-key lock and can recheck the
assignment foreign key while updating the command. The driver held an
exclusive assignment row lock. Nested gate admission then tried to upgrade the
driver's run lock to an exclusive row lock. Each transaction waited for the
other to release its lock.

## Solution

Use `FOR NO KEY UPDATE` for the active assignment fence and gate admission's
run lock. These locks continue to serialize writes and lease checks while
remaining compatible with foreign-key validation.

## Prevention

The driver integration test holds run and assignment key-share locks through
gate admission and session binding. The original gate lock exceeded the
bounded transaction deadline. The scheduled prompt scenario also ran 40 times
against a real supervisor and PostgreSQL after the fix.

The sibling sweep used `rg -n 'getOrCreateGateEvaluation\(|currentPlacedAssignment\(' web/lib/flows/graph`.
Gate execution is the only caller of the first helper. Both driver claim and
fenced writes use the second. They protect assignment state and preserve the
assignment identity.
