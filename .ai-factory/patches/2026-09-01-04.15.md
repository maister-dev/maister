# Destructive git op ran before the HITL row was claimed

**Date:** 2026-09-01 04:15
**Files:** web/lib/services/hitl.ts, web/lib/runs/node-interrupt.ts, web/lib/flows/graph/ledger.ts, web/app/api/runs/[runId]/rework-claim/claim/route.ts, web/components/runs/node-interrupt-controls.tsx, docs/api/async/outbound-webhooks.asyncapi.yaml
**Severity:** critical

## Problem

The ADR-161 node-interrupt response ran `applyWorkspacePolicy` — `reset --hard`
+ `git clean -fd` under `fresh-attempt` — BEFORE opening the transaction that
locks the `hitl_requests` row and checks `respondedAt`. A replayed request, or
one that lost a concurrent race, destroyed the operator's uncommitted work and
only afterwards discovered the request had already been answered, possibly by a
`resume` that wanted the work kept. It then returned `200 idempotent`.

Four more holes in the same feature: answering after the keep-alive sweeper
idled the run stamped `respondedAt` and reported success while the run stayed
`NeedsInputIdle` forever (bare `scheduleResume` drives `runFlow`, which claims
only `NeedsInput`); the admission CAS guarded `runs.status='Running'` but not
`current_step_id`, so a node finishing during the cross-process checkpoint await
let the transaction rewind the cursor and overwrite a `Succeeded` attempt; the
claim's cap gate counted live runs inside a transaction but without the
scheduler advisory lock; and `restart_from` passed `[targetNodeId]` to
`markDownstreamStale`, which derives nothing.

## Root Cause

One assumption, applied four times: **"inside a transaction" was treated as
equivalent to "serialized", and "same request" as equivalent to "same
decision".**

- The policy-before-transaction ordering carried a comment justifying it as the
  M30 X-ATOMIC ordering — "a crash between the two is idempotent on retry".
  That reasoning holds only for a retry carrying the same payload. It silently
  assumed no *other* payload could arrive, which is exactly what a replay or a
  concurrent responder is. The idempotency argument was about crash recovery and
  was reused, unexamined, as an authorization argument.
- The cap gate's own comment said "Cap gate INSIDE the transaction… a pre-check
  outside the lock would be a TOCTOU". True but insufficient: two transactions
  updating DIFFERENT rows never conflict, so both read the same free-slot count
  and both commit. A count-then-update invariant that spans rows needs a global
  lock; the repo already had one (`takeSchedulerLock`) and two neighbours
  (`claimGraphResumeSlot`, `claimAgentResumeSlot`) that take it first.
- The CAS omitted `current_step_id` because the run was observed as `Running` a
  few lines above — but `checkpointSession` is a cross-process await, and
  `Running` survives the observed node finishing and the next one starting.
- `markDownstreamStale(runId, downstreamNodeIds)` was called with the *target*,
  the one node `downstreamOf` deliberately excludes. Both sibling call sites
  pass `[node, ...downstreamOf(graph, node)]`; this one was written from the
  parameter name rather than from the siblings.

## Solution

- Split policy RESOLUTION (read-only, before the transaction, so the value
  applied is the value persisted) from APPLICATION (after the marker commits,
  by the winner only). The already-delivered branch re-drives it only when the
  arriving payload is byte-identical to the stored decision.
- Resolve the parked attempt INSIDE the lock, after the already-delivered check
  — resolving it earlier made a legitimate retry fail `PRECONDITION`, because
  the first response had already flipped the attempt to `Reworked`.
- Replace bare `scheduleResume` with `claimGraphResumeSlot`.
- CAS on `current_step_id` too, and give `markNodeNeedsInput` a `requireRunning`
  option so a lost attempt-level race rolls the transaction back.
- `takeSchedulerLock(tx)` before `countLiveRuns`.
- `[target, ...downstreamOf(graph, target)]`, lazily imported — a top-level
  import of `runner-graph` pulls the supervisor client into 57 unit tests.

## Prevention

- **A lock is not a gate.** Before trusting a transaction to serialize a check,
  ask what rows it actually locks. If the invariant is global (a count, a cap, a
  quota) and the update is per-row, the transaction serializes nothing — find
  the advisory lock the codebase already uses and take it first.
- **A side effect outside the DB must come after the claim, never before.**
  Order is: lock → verify not-already-done → commit intent → perform effect. An
  "idempotent on retry" comment justifies crash recovery, not admission.
- **`sameDecision`, not `sameRequest`.** An idempotency branch reached by a
  DIFFERENT payload is not a retry — it is a loser, and it must mutate nothing.
- **A CAS must re-assert every value read before an `await` that crosses a
  process boundary**, not just the one that looks most authoritative.
- When calling a helper, read its parameter semantics AND its sibling call
  sites. `markDownstreamStale(runId, downstreamNodeIds)` stales exactly what it
  is given; two neighbours already showed the correct argument.
- Fence with mutation-proof: revert the fix, observe RED, restore. Both the
  idle-resume and cap-lock fences initially passed under a mutation that had not
  actually applied — verify the mutation string matched before believing green.
