# Recover a committed project dependency and preserve its launch constraints

**Date:** 2026-11-24 13:05
**Severity:** high
**Files:** `web/lib/project-dependencies/{executor,worker,flow-links,post-trust-store,material}.ts`, `web/lib/packages/attach.ts`, `web/lib/local-packages/versions.ts`, `web/lib/db/migrations/037{4,5}_*.sql`, project registration, launch, package settings, and Git persistence consumers.

## Problem

The registration parser rejected valid capability coordinates accepted by the manifest. A worker recovering after a successful attachment could fetch its source again and report a failed installation. The native package APIs could return an error after the attachment had already committed. Retrying a Studio cut or undoing a launch in this state could conflict with a newer operator edit. Eligibility checks could also expose skills from a blocked member or schedule setup using authority that had since changed.

## Root cause

Registration and native installation applied different coordinate limits. The worker lacked a durable boundary between committing an installation and publishing its filesystem links. Native writes also lost their repair scope when a declaration was deleted. A flat skill list could not identify which capability provided a skill. Consumers inferred readiness, authority and save success from earlier snapshots or an HTTP response. Content witnesses did not distinguish executable-mode changes.

## Solution

Use the manifest coordinate contract from registration through installation. Commit the attempt checkpoint and the effective state together. Native package writers persist each affected Flow link in the same transaction and the worker completes that projection using current project state. Preserve an occupied user path and expose the pending repair through Settings or Studio. Guard launch compensation with the exact generation and revision that the launch adopted.

Persist per-capability skill exports and use the current eligible provider when reading or materializing project skills. At the setup boundary validate actor authority, selected revision, material identity and executable trust. The skill migration preserves legacy inventory where all providers are eligible. Mixed legacy inventories need verified member data to expose individual skills. Record executable modes and confined links in new material and Git witnesses. Following an ambiguous settings response, compare the persisted generation and requested coordinates before inviting the operator to retry.

## Prevention

Exercise a lost acknowledgement on each side of COMMIT. Change the source or actor after commit, put an unrelated file at one member's destination, and verify both the surviving attachment and the independent sibling. Test manual attach, Studio, the CLI and worker settlement through the same publication mechanism. For a failed launch, check that a competing operator edit survives compensation. On populated migration fixtures, inspect the actual skill IDs offered to a runner.

The sibling sweep for durable Flow link writers used:

```text
$ rg -l 'queueProjectFlowLinks' web/lib/packages web/lib/project-dependencies --glob '!**/__tests__/**'
web/lib/project-dependencies/flow-links.ts
web/lib/project-dependencies/operator.ts
web/lib/project-dependencies/executor.ts
web/lib/packages/attach.ts
```

The first file owns the queue. The other three cover operator, worker and native package writes. Studio and the host CLI reach the native writers. The registration transaction records declarations and has no filesystem publication to enqueue.
