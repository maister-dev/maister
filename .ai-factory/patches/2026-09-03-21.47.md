# Orphans of a dead coordinator were recovered only when Running

**Date:** 2026-09-03 21:47
**Files:** web/lib/reconcile.ts, web/lib/runs/state-transitions.ts,
web/lib/agents/launch.ts, web/lib/__tests__/reconcile-classify.test.ts,
web/lib/__tests__/reconcile-sweep.integration.test.ts,
web/lib/runs/__tests__/budget-watchdog.integration.test.ts,
docs/system-analytics/orchestrator.md
**Severity:** high

## Problem

The reconcile sweep's orphaned-child arm (a child whose delegator parent is
Crashed/Abandoned/missing → crash it) fired only for a **`Running`** child. It
sat below the `runStatus !== "Running" → skip` allow-list, and the candidate
loader fetched only `Running`/`WaitingOnChildren` rows. Every other status a
child can hold under a dead coordinator was never revisited:

- `Pending` — kept its queue place; `promoteNextPending` would START it later
  under a coordinator that no longer existed.
- `NeedsInput` / `NeedsInputIdle` / `Review` — waited forever on a resume or
  promotion decision only the dead parent could make.
- `HumanWorking` — invisible, so nobody was told a person was editing under a
  dead tree.
- a `WaitingOnChildren` sub-orchestrator — its own `orchestrator-waiting` skip
  won (it has pending children), and its grandchildren's orphan arm never fired
  because *their* parent was non-terminal: a whole depth-2 sub-tree left
  running with no recovery at all.

Reachable in production: a `Running` orchestrator that crashes mid-plan via
`worktree-gone` / heartbeat does **not** cascade. A red test proved a `Pending`
child stayed `Pending` across a sweep.

Separately, the budget tree-terminate agent test asserted only
`status === "Failed"` — which the pre-fix raw update produced too — so it could
not tell whether `finalizeAgentRun` actually ran.

## Root Cause

**An allow-list written for one owner hid a second one.** "Reconcile owns
`Running` rows" was true when the sweep only reattached/redispatched live work.
Orphan detection was later bolted onto that path and inherited its scope; the
candidate query was scoped to match. Nobody enumerated the statuses a *child*
can hold when its *parent* dies, because parent death was handled by cascades —
except on the crash paths, which never cascaded.

A second layer had the same shape one level down: `finalizeAgentRun`'s
`Crashed` CAS admitted only `Running | NeedsInput`, so even with the classifier
fixed, an agent child in `NeedsInputIdle` or `Review` was silently refused by
the choke point every crash must go through (token revocation, HITL close,
agent-pool promote).

## Solution

Per-status recovery (owner decision), each outcome matching what the status
means:

- **`Pending` → `Abandoned`** (new `abandon` action; `markAbandoned` admits it).
  Never started ⇒ nothing to recover, and it must not be started later.
- **`NeedsInput` / `NeedsInputIdle` / `Review` → `Crashed`**, like the `Running`
  orphan — recoverable, Recover-or-discard, work preserved. `crashRunningRun`
  gained `fromStatuses` (default `["Running"]`, so no existing caller changes);
  reconcile passes the status it CLASSIFIED the run in, so a run that moved
  loses the CAS instead of being clobbered. The open `hitl_requests` row is
  closed in the same transaction, mirroring the keep-alive TTL abandon.
- **`HumanWorking` → left in place, logged at WARN.** A person holds it.
- **`WaitingOnChildren` under a dead parent → `orphaned-orchestrator`**, routed
  through the stuck path (cascade its own children first, then
  `crashWaitingOnChildren`) — crashing it directly would recreate the orphan
  problem for its grandchildren.
- `finalizeAgentRun`'s `Crashed` source set widened to `NeedsInputIdle` and
  `Review` (both already in its `Abandoned` set).

**The loader is targeted, not widened.** Folding the five statuses into the
main candidate list would pull every paused, queued and reviewing run in the
project through the sweep each tick and let them starve real candidates under
`PER_TICK_LIMIT`. The orphan query loads only children for which
`NOT EXISTS (a parent row that is still alive)` — one predicate covering both a
terminal and a missing parent — small by construction, and it feeds the same
mapping as the main rows.

The agent tree-root test now seeds an `agents` row and its `agent-run:<id>`
token and asserts the two effects only `finalizeAgentRun` produces: the token
revoked and a queued **agent** run promoted (the raw path promoted the flow
pool only).

## Prevention

- **An allow-list is a claim about who else exists.** Before adding an arm
  below `if (status !== X) skip`, ask what the arm should do for every other
  status — here the answer differed by status, which is why the list was wrong.
- **When a parent can die without cascading, enumerate what its children can be
  holding at that moment.** Cascades handle the happy path; crash paths do not.
- **Prefer a targeted loader over widening a hot sweep.** "Load only rows that
  can trip the new arm" keeps cost proportional to the defect, not the table.
- **A choke point's CAS source set must be checked against every caller's
  need** — the classifier was fixed and the finalizer still refused two of the
  three statuses. Run the integration test with the REAL child kind the
  fixture produces (agent), not the kind you assumed (flow).
- **A discriminating test asserts the effect only the new path produces.**
  `status === "Failed"` was produced by the bug too.
- The recovery for a `Review` agent child via `finalizeAgentRun("Crashed")`
  from `Review` is new territory — watch it in dogfood.
