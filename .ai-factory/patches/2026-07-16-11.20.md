# Branch-sync recovery: a permanently-stranded claim, and a sweep that could roll back a landed push

**Date:** 2026-07-16 11:20
**Files:** web/lib/runs/sync-recovery.ts
**Severity:** critical

## Problem

Two defects from the `/aif-review` pass on ADR-139/140, both verified in source
before any edit, and both missed by two prior adversarial rounds:

1. **critical** — a MECHANICAL sync orphaned by a restart at phase `verifying` or
   `pushing` had NO recovery arm. The sweep gated on
   `phase === "starting" || phase === "rebasing"` (`sync-recovery.ts:568`), but the
   mechanical driver writes four non-terminal phases: `starting` (`sync-target.ts:534`),
   `rebasing` (`:625`), `verifying` (`:686`), `pushing` (`:733`). A mechanical sync
   never leaves `Review`, so reconcile — which only owns `Running` rows — never
   classifies it, and every other `releaseSyncClaim` lives in `sync-target.ts` and
   dies with the process. Result: `lifecycle_operation_state='claiming'` was never
   released, `promote.ts:750` and `sync-target.ts:509` refused **forever**, and all
   six lifecycle ops were blocked with no exit but DB surgery. The window spans the
   verify gate (~5 git subprocesses) plus the **network push**.

2. **high** — `setPhaseFailed`/`setPhaseSucceeded` wrote terminal phases with
   `WHERE id = ?` and no phase predicate, acting on a lock-free pre-read, and the
   destructive `restoreWorktree` ran BEFORE them. The W5 duration-cap arm
   deliberately does not consult `hasSyncDriver` (the cap must be able to kill a
   live resolver), so it genuinely races the in-process driver's finalize: a tick
   landing while the driver pushed could `git reset --hard` past a push that had
   already landed on origin and overwrite `succeeded` with `failed`.

## Root Cause

**#1 is an enumeration that silently fell behind its producer.** The phase list was
written when the mechanical path had two phases and was never revisited when
`verifying`/`pushing` were added — the classic "two independent enumerations of one
closed set" drift. Nothing caught it: `phase` is typed `string` throughout
(`setAttemptPhase(…, phase: string)`), the exported `RunSyncPhase` union has zero
importers, and no recovery test ever seeded `verifying` or `pushing` (`grep` in the
recovery suite returned zero matches for both). The arm read as exhaustive because
it named phases positively rather than deriving "whatever is non-terminal".

**#2 is the mirror of a rule the same branch already knew.** `terminalizeSafetyNet`
(`sync-target.ts:404-420`) guards its identical write with
`notInArray(phase, TERMINAL_PHASES)`. The sibling module simply never got it — the
sweep rule's exact failure mode. Compounding it, restore-before-terminalize means
no guard on the WRITE could have prevented the destructive act anyway; the ordering
was the bug, not just the predicate.

## Solution

1. The mechanical arm now keys on `mode === "mechanical" && !hasSyncDriver(runId)`
   and **derives** the phase set instead of listing it — candidates are already
   terminal-filtered and `mode` excludes `agent_running`, so "whatever is left" is
   exactly right and cannot fall behind the producer again. `pushing` is handled
   apart: it is past the point of no return, so recovery ASKS ORIGIN
   (`remoteBranchHead` vs the worktree HEAD) and settles **forward** as
   `succeeded/pushed` when the push had landed, rather than restoring. An unproven
   push is never restored either — an origin read that merely failed is not proof
   the push missed, and the live path's own lease-rejected branch keeps the local
   rebase.
2. `casPhaseFailed`/`casPhaseSucceeded` replace the unguarded writes, predicated on
   the **EXACT observed phase**, not `notInArray(TERMINAL_PHASES)` — a set guard
   still wins against a driver that has merely advanced (`agent_running → pushing`)
   and would let W5 tear down a resolver mid-push. Every arm now CASes FIRST and
   performs side effects only on a win. Making `expectedPhase` a REQUIRED parameter
   turned the sweep into a compile error and immediately surfaced all five call
   sites, including two (`failAgentAttemptToReview`, the no-context path) that a
   grep for the sweep's stated scope would have missed.

## Prevention

- **Never enumerate a closed set positively when you can derive its complement.**
  The arm listed the phases it knew; the producer grew two more. `!terminal + mode`
  is drift-proof — the deny-list-vs-allow-list rule inverted: here the allow-list
  was the bug, because the SET grows on the producer's side, not the guard's.
- **A recovery arm's phase list must be diffed against every `setPhase*` call in the
  driver, in the same review.** Grep the producer, not the arm.
- **"Add the missing case to the cleanup path" is wrong past an irreversible side
  effect.** The instinct that fixed #1 (widen the restore list) would have
  reintroduced the exact divergence the 2026-07-15 patch fixed. Ask of any phase
  added to a rollback arm: *can the external effect already have landed here?* If
  yes it needs a forward-settle branch, not a restore.
- **CAS on the EXACT observed value when the requirement is "reject if it changed
  under me".** A set-membership guard permits within-set transitions, which is
  precisely what a stale pre-read plus an advancing driver produces.
- **Order is part of the guard.** A predicate on the terminal write cannot protect a
  destructive act that runs above it. Claim first, then act.
- A typed `RunSyncPhase` with zero importers is not type safety. Either the column
  and every `setAttemptPhase` take the union, or the union is decoration.
