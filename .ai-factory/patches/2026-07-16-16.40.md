# Closing the ADR-139/140 plan: three of its own findings were wrong

**Date:** 2026-07-16 16:40
**Files:** docs/{decisions,database-schema,error-taxonomy}.md, docs/db/runs-domain.md, docs/api/{web.openapi.yaml,external/operations.openapi.yaml}, docs/screens/runs/flow-run.md, docs/system-analytics/{branch-sync,scheduler}.md, web/lib/db/schema.ts, 5 test files
**Severity:** medium

## Problem

The last 4 open items of the ADR-139/140 review plan (21 partial, 22 partial, 31
partial, 34) — vacuous tests, screens docs describing a UI built elsewhere, and
~12 minor doc/N-items.

## Root Cause

The interesting part is not the items; it is that **three of the plan's own
findings were wrong**, and the plan was itself derived from a verified review
whose file:line were all confirmed in source. Verifying each one before fixing it
was the only reason they were caught:

1. **#31 `workbench.md` "claims a 6th lifecycle matrix column"** — `workbench.md`
   contains ZERO sync references. The claim lives in `workbench-lifecycle.md`,
   which is CORRECT and self-consistent: sync "takes no matrix column" (a UI
   policy action) AND "adds a sixth `lifecycle_operation_name` value" (a DB claim
   value). Two different things; the finding conflated them. Nothing to fix.
2. **#21e "the backfill UPDATE could never touch it — use stepwise replay"** —
   `0103` has NO backfill UPDATE at all. A replay DB would prove that
   `ADD COLUMN` without a DEFAULT yields NULL, i.e. it would test Postgres.
3. **#34 "`SyncRunResponse.behind` nullable — after item 6 the spec becomes
   right"** — the opposite. Backgrounding passes `behind` through untouched (the
   plan's OWN design note for item 6 says "`behind` is known at the cut"), so the
   code never returns null and the spec's `nullable: true` is a phantom that got
   MORE wrong, not less.

The pattern: a finding is an observation plus an inference, and the inference
rots independently of the observation. #31's observation ("the docs describe a UI
that isn't there") was true for `flow-run.md` and false for `workbench.md`;
#34's observation ("spec and code disagree") was true, its predicted direction
wrong.

## Solution

Fixed what was real, refuted what was not, and made two vacuous tests
mutation-proven rather than deleted:

- **#21e**: the real invariant is "nullable + NO default" — provable from
  `information_schema.column_default` on a fresh DB, no replay needed. That
  actually proves what the stepwise replay was wanted for: a pre-existing row
  necessarily reads NULL. The companion test kept its assertion but dropped its
  "(no backfill)" overclaim.
- **#21f**: seeded `withTask: true` on the closed/conflicting candidates. The
  merged-ONLY assertion was structurally unfalsifiable — `task_activity` requires
  a `task_id` and those candidates had none, so the insert was unreachable — AND
  the query was scoped to `merged.taskId`, so it could not have seen a stray row
  anyway. Mutation-proven: making the closed edge write activity now fails it.
- **#21b**: the panel renders `labels.behindAhead` verbatim (PRE-RESOLVED
  server-side), so asserting the fixture's own `"run.behindAhead:3:2"` passed for
  ANY counts. Now renders mismatched counts (9/9) against a distinctive label, so
  only the real passthrough contract satisfies it. Mutation-proven.
- **#22a**: the DB refusal test re-seeded 4 cases the pure test already covers as
  8. `reopenRun` reaches the gate through ONE call site, so one representative
  proves the wiring; the truth table belongs to the pure test.
- **#34**: `CONFIG` (the sync 422) and `CRASH` (two fail-closed throws in
  `sync-resolver.ts`) added to `error-taxonomy.md`; ADR-140's "no new error
  codes" list corrected to include `CONFIG`; 8 stale `0100`/`0101` citations
  moved to journal truth (`0103`/`0104`), grep-to-zero across all forms;
  `workspaces_pr_scan_idx` → `workspaces_pr_state_scan_idx`;
  `run_sync_attempts_run_idx` documented; the `rebasing --> aborted` label
  corrected (it fires on ANY pre-session refusal, not only `agent=false`);
  `ORCHESTRATOR_TOKEN_SCOPES` asserted to lack `runs:sync` (it was safe only by
  spreading `AGENT_TOKEN_SCOPES` — appending it explicitly would fail nothing and
  hand a machine actor the force-push ADR-140 reserves for a human);
  `scheduler.md`'s terminal `Skipped` claim inverted (pr_state_scan is EXCLUDED
  from `isSkip`, so a PRECONDITION records `Failed`; the "skip" is a per-item
  summary counter, not a job status); ext `runId` `format: uuid` dropped to match
  `z.string().min(1)`; the reopen 409 list gained shared-tree + terminal-PR.

## Prevention

- **Re-verify a finding's INFERENCE, not just its file:line.** All three bad
  findings had accurate line numbers. What rotted was the reasoning attached:
  which file, which mechanism, which direction. "Verified in source" on the
  observation does not transfer to the prescription.
- **Ask what a proposed test would actually prove.** #21e's stepwise replay would
  have been real work producing a test of Postgres's `ADD COLUMN` semantics. When
  a fix feels expensive, check whether the invariant is directly queryable —
  `column_default` is one row of SQL and proves strictly more.
- **A test that cannot observe a violation is not a weak test, it is not a
  test.** #21f could not fail: the row it forbade was unreachable, and the query
  could not have seen it. Both had to be fixed. Ask "what would I break to make
  this go red?" — if there is no answer, the test is decoration.
- **A `[...SOMETHING_ELSE]` spread is not an assertion.** Scope sets that are
  safe only by inheritance need their own explicit negative test; the next
  explicit append silently defeats the inheritance.
- **When a plan says "X becomes right after Y", re-derive it after Y lands.** The
  plan's item-6 note and its item-34 prediction contradicted each other; the note
  was right.
