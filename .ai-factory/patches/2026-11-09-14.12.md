# Drain canonical fixture work before database teardown

**Date:** 2026-11-09 14:12 UTC
**Files:** web/lib/tasks/__tests__/launch-agent-admission.integration.test.ts
**Severity:** medium

## Problem

All 6,270 executed assertions passed in the frozen complete integration run, but the command exited 1 with an unhandled pool-after-end rejection. A detached fake terminal delivery attempted to record a projection failure after its test database closed. Vitest's JSON reporter still marked success because its success field does not include this unhandled error; the outer process correctly refused qualification.

## Root Cause

The fake host acknowledges admission and can ingest a terminal event before finishing its prompt/lifecycle projections. The admission suite cancelled its pending intents but omitted the existing `waitForCanonicalEvents` barrier before ending PostgreSQL and restoring runtime paths. Sibling scratch and host-span fixtures already drain this exact boundary. The same source omission exists on master; no separate runtime failure on master is claimed.

## Solution

After per-case intent cancellation, await the existing canonical-event drain; repeat the drain before final resource teardown. Observe drain failure while still attempting environment restoration, database shutdown and root cleanup, then preserve the original failure or aggregate. Keep production projector and shared fake behavior unchanged.

The real PostgreSQL regression holds one durably ingested terminal delivery before its actual projection. It calls the owning cleanup hook and proves that cleanup cannot finish while delivery is held, then verifies both canonical consumer cursors advance. Observe the launch promise immediately, release the barrier before cleanup, independently settle all launched work and restore both ordering spies, preserving all failures.

## Prevention

Treat admission, ingest and completed projection as distinct boundaries. Drain owned producers before retiring their database and filesystem dependencies; reuse existing lifetime barriers. Require command exit 0 and no unhandled errors alongside assertion and JSON results. A passing assertion count or JSON success alone is insufficient qualification.
