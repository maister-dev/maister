# M51 adversarial-review remediation: SSRF via push endpoints, a dead opt-in, a trigger that could not fire

**Date:** 2026-09-13 00:05
**Files:** web/lib/notifications/{push-sender,subscriptions,attention-consumer,digest-trigger}.ts, web/lib/queries/{decisions,portfolio,visible-projects}.ts, web/lib/work/stage.ts, web/lib/authz.ts, web/lib/scheduler/system-sweeps.ts, web/app/api/attention/stream/route.ts, web/app/api/push/subscribe/route.ts, web/app/api/v1/ext/notification-subscriptions/[subscriptionId]/route.ts, docs/system-analytics/{attention,work-stages,notifications,m51-traceability}.md
**Severity:** critical

## Problem

A challenge review over the whole branch returned seven findings. All seven
verified in source — including two classes a prior `/aif-review` pass and a
self-review had both missed:

1. Push delivery bypassed egress control. `web-push` calls `https.request`; the
   endpoint is browser-supplied; nothing validated or pinned it.
2. An open attention stream kept the role captured at connect. A demoted admin
   kept the see-every-project bypass; a deactivated account kept streaming.
3. The delta trigger could not fire for the two commonest decision-openers.
4. Clicking "Enable" in the account panel delivered nothing, ever.
5. A swallowed consumer failure was acknowledged as processed and never retried.
6. Project VIEWERS received decisions whose inline actions answer 403.
7. A terminal task with no run rendered as live backlog work.

## Root Cause

**The unifying cause is a SIBLING that already solved the problem.** Four of the
seven are a second implementation of something the codebase does correctly one
module over, written without looking at it:

- Outbound webhooks resolve the destination and pin the connection
  (`webhooks/destination.ts`, used by `send.ts` AND `subscriptions.ts`). The push
  transport is the same trust shape — a user-supplied absolute URL the server
  then fetches — and got neither half. "It is a push service URL" is an
  assumption about a value the user controls.
- The queue's three list sources take a project set; the fourth resolved its
  own, wider one.
- `PROJECT_ACTION_MIN` already states that all four decision actions need
  `member` while `readBoard` needs `viewer`. The read model scoped by
  `getVisibleProjectIds` anyway, so the authorization model and the read model
  disagreed with nothing to reconcile them.

**The other three are assumptions that were never re-derived after the thing
they assumed changed:**

- ADR-172 D5 says deltas come from a `domain_events` consumer. True when
  written; but `DOMAIN_EVENT_KINDS` has no kind for a HITL opening or a run
  entering `NeedsInput`, and `run.review` is emitted only for runs WITH a parent
  (`emitDelegatedReviewIfChild` returns early on `!parentRunId` — the taxonomy
  comment says so out loud). Nobody checked the trigger against the emitters.
- The opt-in wrote one of the two rows fan-out needs. The delivery suite inserted
  the other by hand, so every test passed while the product path was dead. A
  fixture that constructs a state no production writer produces does not merely
  fail to catch a bug — it actively conceals one.
- `stage.ts` had a doc comment claiming `taskStatus` was reserved for "a future
  divergence". `abandonUnlaunchedTasks` sets `Abandoned` with
  `notExists(runs)` in its WHERE — the divergence had already shipped, and
  `EDGE-STG-03` had written the buggy rule down as an invariant.

## Solution

Push endpoints now take the ADR-077 policy at BOTH ends: refused at
registration, and at send resolved then connected through an `https.Agent` whose
`lookup` returns only the vetted addresses (closing rebinding, which
registration alone cannot). A blocked destination settles `dead`, never retried.

`enablePushForOwner` creates the endpoint and the intent in one transaction.
The stream re-reads role and account status per poll and closes on revocation.
The decision queue scopes by `getActionableProjectIds`, whose role floor is
DERIVED from `PROJECT_ACTION_MIN` via `projectRolesForActions` — a hand-written
`["admin","member"]` would have dropped `owner`, which outranks admin.
`stageOf` honours a terminal task status before triage.

For the trigger, a `system_sweep` backstop re-derives each reader's count
through the SAME `emitDecisionsDelta` the consumer uses — chosen over new event
kinds, which need a migration on a CHECK-constrained column plus emitters in the
run FSM's hot paths. That backstop then made finding 5 answerable without a
second mechanism: per-reader failures stay swallowed (poison-safety) because the
sweep is the retry.

## Prevention

- **Before writing an outbound call, grep for how the neighbouring subsystem
  makes the same call.** Egress policy, destination pinning and auth are
  infrastructure, not per-feature code. If a second transport does not import
  the first one's guard, that is the finding.
- **A feature's only human entry point is part of its test surface.** When a
  test seeds a row the product never writes, ask which writer is missing — a
  hand-seeded precondition is a hypothesis about the app that nothing checked.
- **When an ADR names a mechanism as the trigger, verify the EMITTERS exist.**
  "The consumer wakes on `run.review`" is a claim about a producer; grep it and
  read its early returns.
- **A read model that filters by visibility must be checked against the ACTION
  its items imply.** "Can see" and "can do" are different predicates, and the
  authorization table already distinguishes them.
- **A comment saying a parameter is reserved for a future case is a claim.**
  Grep for a producer of that case before believing it; here one existed.
- **A rule keyed on a COUNT of failures cannot classify a one-element
  population.** "All readers failed" and "the only reader is poison" are the
  same observation — pick a mechanism that does not need to tell them apart.
