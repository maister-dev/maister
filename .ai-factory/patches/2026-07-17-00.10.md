# Patch: Canonical Create Flow Review Fixes

**Date:** 2026-07-17 00:10

## Problem

Initial local-package creation recorded database state before its recovery
journal existed. A crash in that gap left a package row with no safe recovery
evidence. Flow-specific conflicts were also reduced to generic API text, and
the API contract and plan overstated recovery and browser-test coverage.

## Root Cause

The first-Flow workflow used its final working directory as both the mutable
assembly area and the public package path. That made the early persistence
window ambiguous and gave recovery no operation-owned artifact to distinguish
from an existing directory.

## Solution

- Assemble a first Flow in an operation-UUID private staging directory and
  publish it with an atomic rename only after the journal, Flow, manifest, and
  initial Git commit are complete.
- Compensate the unjournaled state by removing only its private stage and row;
  never adopt or remove a final directory without durable evidence.
- Expose a small allowlisted conflict-reason enum to localize actionable Flow
  errors without rendering server messages.
- Document the `rolled_back` recovery outcome and malformed-journal `400`, and
  correct the test inventory to distinguish browser happy-path coverage from
  narrower recovery and refusal tests.

## Prevention

Treat every DB-to-filesystem workflow as an explicit publication protocol:
state must either have a private, operation-owned recovery journal or be
compensable without examining shared files. Validate persisted identifiers at
filesystem boundaries and keep client-visible error details as a closed enum.
