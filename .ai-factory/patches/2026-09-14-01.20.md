# A taxonomy split for COUNTING, reused for INVALIDATING

**Date:** 2026-09-14 01:20
**Files:** web/app/api/attention/stream/route.ts, web/lib/domain-events/taxonomy.ts, web/lib/notifications/attention-consumer.ts, web/lib/notifications/subscriptions.ts, web/lib/webhooks/subscriptions.ts, web/lib/runs/hitl-create.ts, web/lib/queries/decisions.ts, web/app/(app)/page.tsx, web/app/(app)/inbox/page.tsx
**Severity:** high

## Problem

Five defects from one adversarial review, four of which share a shape.

1. `createHitlRequest` — made the single writer of `hitl_requests` in the
   previous fix round — emitted `run.needs_input` unconditionally. A
   project-less local-package assistant run has `runs.project_id IS NULL` and
   `domain_events.project_id` is `NOT NULL`, so the emit aborted the
   transaction, rolled the HITL row back, and the caller cancelled the
   supervisor permission deferred. Assistants could not get a permission
   approved at all.
2. `transport: 'webhook'` was accepted and answered `201`, but no production
   path ever wrote `webhook_subscriptions.owner_user_id`, which the matcher
   requires for a user-scoped event. The intent could never deliver.
3. The domain-event consumer and the `system_sweep` backstop both ran
   read-then-emit on the `decisions` delta under separate leases. Measured
   9 duplicate notifications in 10 attempts.
4. Both decision surfaces printed `queue.count` and rendered HITL cards from a
   second, wider query.
5. The stream's changed-project scan reused the `updates` counter's kind list,
   so run transitions were invisible to it and node progress was never scanned.

## Root Cause

**A list built to answer one question was reused to answer a different one.**

`ATTENTION_EVENT_KINDS` is a *population*: "what happened that I have not
seen", deliberately excluding kinds twinned with a `task_activity` row and
(after the previous round) the two decision-opening kinds, so no fact is
counted twice. The stream's scan asks something else entirely: "did anything
this reader renders move?" Over-counting is a wrong badge; under-invalidating
is a page that silently lies. Borrowing the list imported the exclusion — and
it did not show up in review because for most readers the 15 s counter poll
masked it. Only a project **viewer**, whose `decisions` count is permanently
zero, had nothing to mask it with. Finding 4 is the same mistake in the other
direction: the canonical queue was treated as the source of the *number* while
the *list* kept its own, wider source.

Findings 1, 2 and 3 share a different root: **a choke point added for one
reason inherits every caller's edge cases.** Routing fifteen HITL inserts
through one function was right, and it made the function responsible for the
one caller whose run has no project. `enablePushForOwner` fixed "intent without
a target" for push a round earlier, and the identical hole one table over went
unlooked-for. And "idempotent by construction" held for redelivery of the same
event but not for two callers — a distinction that only matters once a second
caller exists, which the backstop had just become.

## Solution

- `emitNeedsInput` types the read-back `projectId` as `string | null` and
  returns on the null, mirroring the guard already in `scratch-runs/events.ts`.
- `SubscriptionScope` gains `ownerUserId` as a third axis; `scopeFilter` gets
  its own branch for it; `enableWebhookForOwner` writes target and intent in
  one transaction, the target taking the intent's `event_types` so the two
  cannot disagree. One personal target per owner, updated in place — a delete
  would cascade the append-only delivery ledger away.
- `emitDecisionsDelta` wraps read-compare-publish in a transaction and takes
  `pg_advisory_xact_lock(ns, hashtext(userId))` FIRST, so the loser reads the
  winner's committed row as its baseline. Per owner, never global.
- `hitlDecisionsOf(queue.items)` replaces both direct queries.
- `ATTENTION_PLANE_EVENT_KINDS` (the union) is exported from the taxonomy; the
  scan reads it and adds a `node_attempts` branch joined through `runs` and
  bounded to `ACTIVE_RUN_STATUSES`.

## Prevention

- **When reusing a named list, re-read what its name means.** If the list was
  derived to avoid double-counting, it is not an invalidation list. Ask which
  direction the error runs: an extra refetch is cheap, a missed one is a lie.
- **A guard whose failure rate is ~90% still needs repetition.** The
  single-attempt version of the concurrency test passed against the unfixed
  code — 1 run in 10 — and I would have shipped it as proof. Measure the
  failure rate of a race guard against the unfixed code before trusting it, and
  repeat until the miss probability is negligible. Reverting the fix and
  re-running is the only way to learn that number.
- **After adding a choke point, enumerate its callers for the columns it now
  dereferences.** `runs.project_id` is nullable for exactly one run kind; the
  call site that has it already carried the guard, one frame up.
- **When a class of bug is found on one branch of an either/or, check the other
  branch the same day.** "Intent written without its target" was fixed for
  `web_push` and left standing for `webhook`.
- **A count and the list it labels must come from one read, not one query.**
  Sharing the query is not enough if a surface then renders a different list
  beside the number.
