**Severity:** high

## Problem

After a consensus node restarted failed child runs, the portfolio, board, run
page and inbox all 500'd. `runnerAgentFromFields` threw
`MaisterError("PRECONDITION", "Run <id> has no capability agent in runner
snapshot")` from twelve call sites across five read models — `lib/queries/` is
the render path, and one empty column on one session row replaced whole screens
with the root error boundary.

Reported as two bugs. Both were real, and a third sibling and a stale doc claim
came with them.

## Root Cause

Four links, each verified in source (the reporting environment's rows were not
on this host — the local DB had 3 runs, 0 substep sessions, so the DB could not
be the evidence and the code had to be):

1. `execution-host/create-ack.ts:135` — `applyCreateAck` has two branches. The
   UPDATE branch writes only the host/ACP binding onto a row someone else
   pre-inserted. The INSERT branch, taken when no row exists for
   `(run_id, session_name)`, writes `{id, runId, sessionName, hostSessionId,
   acpSessionId, executionAssignmentId, createdAt}` — **no runner columns**.
   Its input type has nowhere to put them: the ack does not carry a runner, and
   `client.ts:449` has `payload.runner` in scope and does not forward it.
2. Commit `508be005` gave each substep its own session name. That did not
   "forget to write the runner" — it changed WHICH branch of `applyCreateAck`
   runs. Substeps previously reused `default`, whose row is pre-inserted at
   launch with a full resolution (`services/runs.ts:1822`); a named substep has
   no pre-inserted row, because `inspectFlowRunners` enumerates only the
   compiled manifest's sessions and a substep name is dynamic
   (`<nodeId>-verify-<round>-<ordinal>`). So the INSERT branch began firing.
3. `runs/active-run-session.ts:69` picks a run's ACTIVE session
   `ORDER BY (acp_session_id IS NOT NULL) DESC, updated_at DESC`. A live substep
   session has a handle and is newest, so it **outranks the node's own session**
   and becomes the row every list/detail query reads. That is why one throwaway
   verifier row reached six screens.
4. `runnerAgentFromFields` threw instead of degrading. The invariant it was
   enforcing is a WRITE-path one and is already enforced there — `docs/
   configuration.md:696` has launch refusing "before worktree creation,
   run/workspace DB writes, or supervisor spawn". Re-asserting it on the render
   path only converted persisted history into a 500.

Nothing backfills such a row: `create-ack.ts:131` is the only
`.update(runSessions)` in production code and it sets the binding alone.

## Solution

Two independent fixes, because either alone leaves a hole — the write fix does
nothing for rows already on disk, and the read fix alone leaves the data wrong.

**Write path.** New `lib/runs/substep-session.ts#ensureSubstepRunSession`
pre-seeds the substep's row with its resolved snapshot before the create
command, `onConflictDoNothing` on `(run_id, session_name)` so a permission
resume re-binding a stable `gate-<id>` row neither 23505s nor clobbers the
binding. Called from all three substep sites. This is the remedy the previous
session's own patch note prescribed and deferred, and the shape
`runs/sync-target.ts:1374` has used since ADR-141.
`ConsensusRoleRuntime` now carries the `RunnerResolution` it already resolved —
`roleRuntimeFromSnapshot` was throwing the snapshot away, which is why a
verifier's deliberately-different runner was the one fact the row could not
record. `runner_id` is passed ONLY from a fresh catalog resolution: it is an FK
to `platform_acp_runners`, so replaying an id off a stored snapshot whose runner
was since deleted would fail the insert. The gate path therefore seeds
`capability_agent` + `runner_snapshot` (what the display actually reads) and
leaves the audit-only `runner_id` null.

**Read path.** `runnerAgentFromFields` returns `AdapterId | null` and logs a
module-local pino `warn` with the run context. The seven DTO `agent` fields were
widened, not the five aliases — an alias should keep meaning "a known agent".
Consumers render a muted placeholder; the `Record<T["agent"], string>` lookup
tables became `Record<NonNullable<...>, string>` with a null branch.

## Prevention

- **A read model degrades; it does not enforce.** An invariant belongs at the
  write boundary that can still refuse. `lib/queries/hitl-stage.ts` had the
  right contract already ("an unresolved step_id degrades to a null type so the
  inbox always renders") — copy it, and when adding a throw to `lib/queries/`
  ask which screen it takes down.
- **Fix the class, not the cited line.** The report named 6 call sites; there
  were 12, plus `executorDisplay` (portfolio.ts:856), a SECOND throw on exactly
  the same rows that would have kept the rail 500ing after the reported one was
  fixed. `grep -rn "runnerAgentFromFields"` and
  `grep -rn "throw new MaisterError" web/lib/queries/*.ts` are the two commands;
  run them, don't assume the report enumerated.
- **A widened return type is enumerated by the compiler, not by a grep.** Making
  it nullable broke 11 of 12 sites and 6 components — and `portfolio.ts:856`
  would have silently rendered the string `"null"` had the throw not been there.
  Let `tsc --noEmit` list them.
- **When a commit changes which BRANCH of a shared writer runs, audit that
  writer's other branch.** 508be005 was reviewed as a naming change; the
  regression was that `applyCreateAck`'s INSERT arm — until then rarely reached
  — populates strictly less than its UPDATE arm.
- **Check the ranking function, not just the row.** The blast radius came from
  `activeRunSessionScalar`'s "live handle first, then newest": a throwaway
  session outranking the real one. A new session kind must be checked against
  every selector that picks "the" session for a run.
- **A deferred consequence in a patch note is a live bug.** The prior note
  recorded this exact gap and scoped it to cost attribution ("buckets it as
  unknown"); it did not foresee the UI crash, which is what made it high
  severity rather than a reporting nit.
- **Falsify the guard.** Both new tests were re-run with the fix disabled: the
  consensus one fails, and the gate integration one fails with `expected null
  not to be null` — the reported bug reproduced against real Postgres.
- Stub fixtures seeded for the looser contract get CORRECTED, never the gate
  weakened: `runtime.test.ts`'s db stub had no top-level `insert`, so 14 tests
  failed until the stub modelled the real
  `insert().values().onConflictDoNothing()` chain.
