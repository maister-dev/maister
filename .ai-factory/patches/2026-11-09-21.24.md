# Archived run attachment protection and historical evidence

**Date:** 2026-11-09 21:24 UTC
**Files:** web/lib/packages/attach.ts, web/lib/packages/run-pins.ts, web/lib/flows/graph/runner-core.ts, their tests, docs/system-analytics/packages.md
**Severity:** high

## Problem

An ended, archived Crashed run continued to prevent package detachment because
the guard used run status alone. Replacing an attachment also risked deleting
historical execution evidence.

## Root Cause

- Historical outcome and ability to execute were conflated. Archive deliberately
  preserves Crashed; archived_at is written before removal finishes.
- The guard checked enabled revisions outside the delete transaction, missing
  old revisions still associated with a member and racing recovery.
- runs.flow_id cascades when a Flow is deleted, unlike immutable revision pins.
  tasks.flow_id restricts deletion. Retaining revisions alone does not retain runs.
- The runner required a mutable Flow before loading its immutable revision, so
  preserving a detached run also requires execution to tolerate absent enablement.

## Solution

Require an ended, revision-pinned crash, finalized archive/removal of every
applicable workspace, preservation evidence, released lifecycle ownership and
no active assignment, unconfirmed incarnation or open execution command. Shared
users inspect their allocator and siblings. Lock run rows inside detach and
serialize attachment mutations. Refusals identify runs and reasons.

Disconnect mutable task/run enablement before deleting Flow rows; retain outcomes,
revision pins, attempts, stdout/checkpoints and archive references. Resolve pinned
execution directly from its retained revision. Refuse removal of enablement still
needed by unfinished legacy runs without an immutable revision.

## Non-obvious assumptions and compatibility

- This checkout is the existing platform delivery attempt, identified by its
  task-attempt branch and complete run.json input. No triage/enqueue tools are
  exposed; do not recursively enqueue it or claim new triage occurred.
- Canonical terminal incarnations plus absence of active assignments/open commands
  provide durable quiescence evidence. Checkpointed means stopped; lost does not
  prove teardown. Retained run_sessions handles alone are historical identifiers.
- Existing records without preservation_outcome qualify only with archive branch,
  commit, timestamp and finalized removal. Clean not_needed archives need no refs.
- Failed lifecycle claims and expired claiming slots require reconciliation;
  expiration alone does not prove an operation finished.
- Removed-member upgrades intentionally continue allowing immutable pinned runs.
  Such runs no longer depend on that mutable enablement; revision GC still refuses
  every historical reference. Unpinned unfinished legacy runs remain protected.
- Explicit reattach after detach remains supported by retained Git references;
  immutable runtime revisions remain authoritative for subsequent execution.

## Regression and verification

Package integration RED/GREEN is **blocked**, not passed: dependency restoration
completed, but Docker setup returned EPERM in the sandbox and EACCES when retried
with escalation. No package regression assertion ran. No deployment DB was used.

The recovery loader regression actually reproduced `flow not found` (1 failed,
4 passed), then passed after the fix (5/5). The graph unit consumer suite passed
41 files / 495 tests. Added isolated PostgreSQL scenarios cover archive boundaries,
legacy records, assignments/sessions, shared users, concurrent recovery, old pins,
terminal outcomes and historical evidence preservation; they still require CI.

## Prevention

Separate outcome, mutable attachment protection and immutable revision retention.
Trace FK deletion effects before calling evidence retained. Exercise recovery
after removing a mutable association, and reproduce races with database lock
barriers rather than sleeps. Report infrastructure failure before assertion
execution separately from a reproduced product defect.
