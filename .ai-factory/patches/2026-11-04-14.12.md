# Keep operation ownership inventory aligned with extracted filesystem helpers

**Date:** 2026-11-04 14:12
**Files:** `web/lib/execution-host/__tests__/fixtures/runtime-data-boundary-inventory.ts`
**Severity:** low

## Problem

The full Web unit gate rejected four unclassified filesystem operation sites after the launch asset error wrappers were extracted. The D10 inventory still named the previous enclosing functions, so its baseline and three mutation controls failed.

## Root Cause

D10 identifies an operation by source, enclosing function, resolved callee, and operation. Reusing a domain wrapper correctly moved actual I/O to a smaller helper, but its operation ownership entries were left at the old callers. Two shared readers/digest wrappers also replaced multiple old physical callsites with one actual callsite.

## Solution

Move entries to `readTaskAgentDefinitionSource`, `taskAgentPackageContentDigest`, `capabilityContentDigest`, and `flowAssetContentDigest`; remove stale prior read/hash callsites. Keep all ownership classes, operation kinds, rationales, wrapper/path decisions, scanner logic, and negative mutation controls unchanged. There are no production changes or exclusions.

## Verification

The unchanged whole nine-case D10 owner reproduces four failures before this inventory-only edit (`/private/tmp/maister-launch-assets-d10-red.log`) and passes 9/9 afterward (`/private/tmp/maister-launch-assets-d10-green.log`). Scoped ESLint with zero allowed warnings and diff whitespace validation pass. This static guard supplements the real filesystem/PG asset regressions; it does not replace their execution boundary proof.

## Prevention

When extracting a filesystem helper, run the operation-scoped inventory owner and move each obsolete source/function/callee tuple to the actual I/O site. Preserve negative controls and ownership policy; never add a file exemption or weaken the scanner to accommodate a refactor.
