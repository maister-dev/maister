# Preserve failed Triager inspection across task launch surfaces

**Date:** 2026-11-04 12:21
**Files:** web/components/agents/task-qualification-source-failure-notice.tsx; web/components/agents/task-qualification-control.tsx; web/components/agents/task-agent-launch-control.tsx; web/components/board/launch-popover.tsx; web/components/agents/**tests**/human-assessment-form.dom.test.ts; web/components/social/**tests**/task-agent-launch.interaction.test.ts; web/e2e/task-launch-gating.spec.ts
**Severity:** medium

## Problem

The authorized task summary contained a current failed qualifier, but its task
assessment panel displayed only an unassessed state. Task-agent launch showed
the failed-publication explanation without a way to inspect the failed Run.
The Flow launch dialog already exposed that link and conservative diagnostics.

## Root Cause

The new `sourceFailure` read-model field was handled independently by launch
surfaces. The assessment panel never consumed it; the agent launch panel used
it only to select a generic label. A presentation-only gap therefore hid an
existing, authorized diagnostic without affecting admission or assessment data.

## Solution

One shared detail presenter renders the failed Run link and the existing EN/RU
pre-model remediation only when `modelStarted === false`. Unknown model-start
state remains unknown. The task panel shows the safe failed-publication copy
and details outside its authoring permission gate; read-only users can inspect
the failure without gaining assessment controls. Agent and Flow launch reuse
the same inference/link rule. No raw cause, stage, source contents or credentials
are rendered, and the linked Run retains its normal read authorization.

Existing DOM integration controls now cover false/null model-start evidence,
read-only task inspection and actual agent/Flow target launch wiring. They
failed on all four missing presentation expectations before the fix. The three
focused DOM suites then passed 23/23, including the existing Flow presentation
and admission behavior controls. Logs are retained in
`/private/tmp/maister-r3-source-failure-red.log` and
`/private/tmp/maister-r3-source-failure-green.log`.

The existing RU manual-after-failed-Triager browser journey now inspects the task
failure link, opens Launch through keyboard Enter, verifies initial dialog focus,
uses Shift+Tab to reach Launch, accepts with Enter, observes its scoped status
announcement and restores opener focus through Escape after cancellation. The
negative/stale assessment and immutable-history assertions remain in the same
journey. Browser verification awaits the coordinated frozen run; DOM green is
not claimed as browser keyboard or end-to-end proof.

## Prevention

When a diagnostic read model gains a new state, audit every existing consumer
and keep a single rule for uncertain evidence. Inspection permission and mutation
permission must remain separate. Extend an existing behavioral journey for
keyboard acceptance rather than adding a second launch narrative or replacing
actual admission with a UI-only assertion.
