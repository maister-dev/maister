# ADR-181 follow-ups: the orphan rescue lost staged work; a stale e2e fake hid F5 until the lane

**Date:** 2026-09-26 15:48
**Files:** web/lib/gc/preserve.ts (`rescueStagedWorkBeforeSnapshot`), web/lib/gc/workspace-reconciler.ts, web/e2e/_seed/bin/fake-gh.cjs, web/e2e/_seed/fake-gh.ts, web/e2e/workbench-git.spec.ts, the D10 inventory fixture, docs (ADR-181 D8, reconciliation-gc, workbench-git, the plan)
**Severity:** medium

## Problem

1. **The orphan rescue lost staged work.** The workspace reconciler rescues a
   trusted orphan worktree (provenance, no run row, past its grace period)
   with `snapshotDirtyWorktree`, an `add -A` commit on the real index. It
   branches `maister/orphan/<claim>/<runId>` at HEAD, then force-removes the
   tree. A file staged and then deleted, or staged and edited again, kept its
   staged version only in the index, and the removal destroyed it. This is F1's
   class; the Codex-fix sweep flagged it (patch 2026-09-26-12.05) and the owner
   asked for it fixed.
2. **The post-merge e2e lane went red on this branch's own spec.**
   `workbench-git.spec.ts:34` got 503 from finalize. F5 made the parked
   finalize read the PR (`gh pr view`), but the e2e fake `gh` answered only
   `pr list` and `pr create`. The read was a transient skip, which is
   EXECUTOR_UNAVAILABLE.

## Root Cause

1. The orphan arm predates ADR-181 D8 and reached `add -A` through a different
   helper (`snapshotDirtyWorktree`, not `preserveWorktree`). So the F1 fix at
   preserve's choke point did not cover it. The sweep found it and classified
   it correctly as the same class, but "not made reachable by the branch" left
   it for later.
2. The fake was written to answer "exactly the calls the GhCliAdapter makes",
   meaning the calls it made then. A new provider call on an existing path left
   the fake stale, and no unit test runs the fake: only the e2e lane exercises
   it. The F5 unit and integration suites all stubbed `getPrState` at the
   module seam, so they could not see the harness gap.

## Solution

1. Preserve's check-and-rescue became one exported helper,
   `rescueStagedWorkBeforeSnapshot({worktreePath, runId})`. When a path is
   staged and changed again, it writes `refs/maister/rescue/<runId>/<n>` with
   the index as second parent and logs it. `preserveWorktree` and the orphan
   arm both call it before their snapshot. The finding's evidence pair
   (`rescue_ref` / `rescue_commit`, CHECK-paired) is unchanged: a second ref
   there would need a migration. A detached rescue commit would break the arm's
   idempotency, since a retry compares the branch to HEAD and quarantines a
   mismatch. The new integration case (staged-then-edited plus
   staged-then-deleted) went red first and was falsified (without the call, it
   alone goes red).
2. The fake records the checkout each PR was created from and answers
   `pr view`. `headRefOid` is the PR branch's tip on that checkout's origin, as
   GitHub reports it, and every view is recorded. The spec asserts that the
   finalize read the PR it declared delivered. Solo 5/5, 2 of them on the
   combined master.

## Prevention

- When a fix lands at a choke point, sweep for code that reaches the same sink
  through another helper (`rg 'snapshotDirtyWorktree\(|"add", "-A"'`), not
  only callers of the choke point.
- A harness fake of an external CLI is part of the contract surface. When a
  change adds a provider call on a path an e2e covers, grep the fakes
  (`rg -l 'fake' web/e2e/_seed`) and extend them in the same change. Have the
  fake fail loudly: "unsupported call" did, and it is what made the red
  readable.
- Module-seam stubs (`getPrState: vi.fn()`) cannot see a harness gap: say so
  in the close-out, and run the e2e spec that covers the path before merging.
