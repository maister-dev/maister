# Branch-sync: irreversible-push rollback, an unswept gate arg, a stale conflict flag, and an unbounded scan

**Date:** 2026-07-15 18:10
**Files:** web/lib/runs/sync-target.ts, web/lib/runs/sync-recovery.ts, web/lib/runs/reopen.ts, web/lib/runs/pr-adapter.ts, web/lib/scheduler/handlers/pr-state-scan.ts, web/lib/runs/__tests__/sync-target.integration.test.ts, web/lib/runs/__tests__/reopen.integration.test.ts, web/lib/scheduler/handlers/__tests__/pr-state-scan.integration.test.ts
**Severity:** critical

## Problem

Four defects an adversarial Codex review raised against ADR-139/140. All four were
verified in source before any edit (per the "Verify the finding before fixing it"
rule) and all four were REAL:

1. **critical** — after `pushWithLease` LANDED, six awaited bookkeeping ops ran with
   `settled` still false. Any throw there hit the catch → `failResolver` →
   `restoreWorktreeToCommit(headShaBefore)`: the LOCAL worktree was reset to
   pre-sync while ORIGIN kept the resolved commit, and the attempt was stamped
   `failed` for a sync that demonstrably happened. Local tree, remote branch/PR,
   and ledger all disagreed; a retry would rebase from a base origin no longer had.
2. **high** — `sync-recovery.ts:305` called `verifySyncGate(worktree, targetSha)`
   with NO branch, so a crash-recovered detached HEAD passed the gate; recovery
   then pushed `ctx.branch` (still at the old commit) and recorded `succeeded` with
   the detached HEAD's sha — a sync reported done while the PR stayed stale.
3. **high** — `hasConflicts: null` (what providers report for a terminal PR) hit the
   "leave as-is" rule, preserving a `true` from the PR's open days. Reopen accepts a
   conflicted PR, but re-promotion's `createOrUpdatePr` is open-PR-only, so a
   closed+conflicted row would silently open a SECOND PR, breaking the documented
   "re-promotion MUST reuse the SAME provider PR" expectation.
4. **high** — the scan processed 50 candidates sequentially with a 60s per-call
   adapter budget against a 300s lease. ~5 slow providers exhaust it: the scheduler
   reaps the attempt as LEASE_EXPIRED and starts a REPLACEMENT scan while the first
   is still writing. The Gitea `getPrState` fetch had NO timeout at all, so one hung
   server could hold the scan indefinitely.

## Root Cause

**#1 is self-inflicted, and the most valuable lesson.** The PREVIOUS review round
found the opposite bug (a throw after the resolver bypassed `failResolver`, stranding
the run `Running`). The fix — route the catch through `failResolver` — was correct for
every PRE-push failure and silently wrong for every POST-push one, because
`failResolver` restores the worktree. **The fix for "we didn't clean up enough" was
applied uniformly to a path where cleanup is impossible.** A force-push is an
irreversible, externally-visible side effect; any handler that "cleans up" after one
is manufacturing divergence, not preventing it. The code had no notion of a
point-of-no-return, so the compensating action could not know it was illegal.

**#2 is a textbook missed sweep** — the exact failure the project's own
"sweep every sibling in the same pass" rule exists to prevent. The previous round ADDED
the `branch` parameter to `verifySyncGate` and wired it with a `sed` matching the
two `sync-target.ts` call sites; the third caller (`sync-recovery.ts`) used a
different argument expression and never matched. The parameter was **optional**, so
neither the compiler nor any test noticed. Optionality is what made the sweep
silent.

**#3** is a null-vs-false conflation: `null` means "unknown", and "leave unknown
alone" is right for an OPEN PR but wrong for a terminal one, where mergeability is
not unknown — it is meaningless. The stale flag then became load-bearing through a
second component (reopen eligibility) that had no reason to distrust it. The
integration test CODIFIED the defect: it asserted `prState:"closed"` +
`prHasConflicts:true` was eligible, because it reached for a conflicted PR without
noticing it had built an unreusable one.

**#4** is a budget never reconciled with its container: the batch size and the
per-call timeout were each chosen sensibly, but their PRODUCT was never compared to
the lease that bounds them.

## Solution

1. `pushCommitted` flag set the instant the push lands. The catch aborts ONLY when
   `!settled && !pushCommitted`; post-push it logs the decisive fields and releases
   the run best-effort (Review + claim + slot) so a landed push can neither be rolled
   back nor deadlock promotion. `headShaAfter` hoisted so the log names what was pushed.
2. Passed `ctx.branch` in recovery **and made the parameter REQUIRED**. This is the
   real fix: the compiler now enforces the sweep and flagged the three remaining
   2-arg callers immediately. A test would have covered one path; the type covers all
   present and future ones.
3. Scanner clears `pr_has_conflicts` whenever the state is terminal (root cause);
   `assertReopenEligible` additionally refuses a merged/closed PR (defense in depth,
   for a lagging or hand-edited row). No contract change — this ENFORCES the existing
   documented expectation.
4. Deadline derived from the ACTUAL lease (`schedulerAttemptTimeoutSeconds()`), not a
   hardcoded number, reserving one worst-case call plus margin; the loop stops
   STARTING candidates at the budget and the cursor resumes from the last one actually
   processed (never advancing past unvisited rows). Added the missing
   `AbortSignal.timeout` to the Gitea fetch.

## Prevention

- **Model the point of no return explicitly.** Once an operation performs an
  irreversible external side effect (force-push, PR create, payment, publish), a flag
  must mark it and every compensating path must consult it. Ask of any catch/rollback:
  *is this reachable after the irreversible step?* If yes, it is a corruption path, not
  a cleanup path. Review checklist: for each `catch` that restores/reverts, list the
  side effects that may already have landed above it.
- **When a fix "adds cleanup", check the sibling branch it now also covers.** Round N's
  fix becomes round N+1's bug when a compensating action is widened without narrowing
  its precondition.
- **Prefer a REQUIRED parameter over a test when sweeping a new argument to N call
  sites.** An optional parameter makes a missed sibling invisible; a required one turns
  the sweep into a compile error. Reach for the type system before reaching for
  coverage. (This is the second consecutive round where an unswept sibling shipped —
  the sweep rule alone is not sufficient when the language permits omission.)
- **`null` is "unknown", not "no".** Any "unknown ⇒ leave as-is" rule needs a companion
  rule for states where the field is MEANINGLESS. Grep for the flag's downstream
  consumers before deciding that leaving it alone is safe.
- **A test can codify the defect.** When a test constructs a state to prove X, verify
  the state itself is REACHABLE and legal — `prState:"closed" + prHasConflicts:true`
  proved "conflicted PRs reopen" using a PR that could never be reused. Assert intent
  with the minimal state that expresses it.
- **Compare a batch's worst case against the lease/timeout that contains it**
  (`batch × per-call-budget vs lease`), and derive the bound from the container's real
  value so the two cannot drift.

## Flagged, NOT fixed (out of scope, same exposure class)

`pr-adapter.ts` `request()` (fetch ~line 497, the `createOrUpdatePr` gitea helper)
also has no `AbortSignal`. Confirmed PRE-EXISTING (`git diff <merge-base>..HEAD` does
not touch it) and NOT on the scan-lease path, so it stays out of this fix per the
sweep rule's "flag same-exposure siblings that are out of scope rather than silently
fixing or omitting them". Worth its own pass.
