# Keep the internal MCP contract in sync with the running release

**Date** 2026-11-21 21:17

**Files** `web/package.json`, `package.json`, `mcp/src/tools.ts`, `mcp/scripts/verify-stdio-contract.ts`, `.github/workflows/ci.yml`, `docs/deployment.md`

**Severity** high

## Problem

MAI-11 Run `f53dd6db-6e51-4b82-b89e-50bbf2780174` finished with `operational_blocked`. The authenticated transcript shows that `core:triager` on Codex read the task and related data. It reported `QUALIFICATION_TOOL_SCHEMA_UNAVAILABLE` and did not call `triage_set`. The Run recorded no qualification candidate or enqueue request.

## Root cause

The source catalog already advertises and forwards `qualification`, `requestKey`, `expectedInputRevision`, and `expectedQualificationRevision`. The launcher accepts an existing `mcp/dist/main.js` or an explicit override. Host update instructions rebuilt Web alone, allowing the installed MCP bundle to outlive its release. The clean Docker build excludes local `dist` directories and previously built only Web. The exact facade process and schema seen by the production adapter still need verification on its execution host.

An older local bundle returned 69 tools through a successful stdio `tools/list`, compared with 104 in the current source. It lacked Knowledge, agent vault, and specialist assignment tools. It returned the full catalog for `company`, `installation`, and `vault` instead of the expected subsets. The old local bundle already had the four `triage_set` fields. The Run transcript is separate evidence of what the model saw in production.

## Solution

Build the default MCP facade with Web from the same checkout. CI compares the built stdio catalog and input schemas with the release source for the default, company, librarian, installation, and vault toolsets. The production image check executes the packaged facade without rebuilding it. The common contract command verifies the generated qualification schema against Zod and compares the parsed schema independently of formatting.

`task_update` now advertises and forwards `expectedRevision`, including zero, so the REST revision check can protect edits. Checking `maxLength` in the MCP/OpenAPI parity test exposed 12 discrepancies across nine tools. MCP now mirrors branch, child key, comment, search, proposal, and clarification limits. OpenAPI reflects the existing activity filter and operator-message behavior.

## Prevention

Every change to an internal MCP tool, its REST input, or its profile membership must ship with a freshly built facade and a passing `tools/list` check on the packaged artifact. On split-host releases and custom `MAISTER_MCP_FACADE_COMMAND` deployments, verify the actual command and arguments on the execution host. A successful `initialize` can report the same server version for different contracts.

```sh
rg -n 'toolNamesForToolset|resolveFacadeLaunch\(|platformOrigin: "maister_facade"' mcp/src web/lib supervisor/src -g '!**/__tests__/**'
pnpm --filter @maister/mcp verify:stdio-contract
```

The resolver serves project agents, agent-backed Flows, and Librarian. The same launch seam injects the installation, company, and vault profiles. The contract test suite also covers launch, human questions, and knowledge schemas. The audit found further gaps in `gate_report` metadata limits and in the propagation of structured refusals for qualification, vault, memory, and stand operations. Those gaps need separate input and error-contract checks.

After deployment, select **Run again → Assess task again** on the failed Run. Use the new Run's transcript and qualification receipt to prove it reread task revisions and evidence and submitted a candidate. Verify publication through the task's recorded assessment.
