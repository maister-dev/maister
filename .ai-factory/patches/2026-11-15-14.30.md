# Review blockers: refuted authz finding, dead ambient floor, aspirational assignment state machine

**Date:** 2026-11-15 14:30
**Files:** web/lib/brain/policy.ts, web/lib/brain/ambient.ts, web/lib/brain/decay.ts, web/lib/brain/recall-ranker.ts, web/lib/brain/__tests__/ambient.integration.test.ts, mcp/src/tools.ts, docs/system-analytics/project-brain.md, docs/system-analytics/specialist-assignments.md, docs/system-analytics/external-operations.md, docs/system-analytics/flow-graph.md, docs/api/external/operations.openapi.yaml, docs/configuration.md, site-docs/concepts/project-brain-and-agents.md, .ai-factory/qa/company-brain-specialist-assignments/T43/release-candidate.json
**Severity:** high

## Problem

A multi-agent branch review (`/aif-review`, 368 commits) raised three blockers:

1. A project `agent` identity was authorized against company knowledge on its own
   company grant only (`knowledge-access.ts` / `knowledge-query-policy.ts`).
2. No application code writes `failed` / `reconciling` / `waiting_children` /
   `waiting_resource` on `specialist_assignments`, while the docs showed them as live.
3. Ambient Brain injection silently stopped working for every new item.

## Root Cause

1. **Refuted. The behavior is designed.** ADR-204 native findings: project professionals
   act on admin-issued company grants (fixture `test-support/native-findings-seed.ts`,
   `findings-access` proposes into a company owner with `can_write_brain` unset).
   The leak the reviewer described (company data in run output) is closed at
   disclosure instead: every agent/execution read requires a complete native capture
   (`lockKnowledgeReadConsumer`), taints `runs.knowledge_access`
   (`recordKnowledgeDisclosure`), and outward disclosure re-authorizes the recipient
   against each `company` restriction (`authorizeOwnerRestriction`). A first fix
   (refuse company owners for `agent`) was written, then REVERTED once the fixtures showed
   the contract.
2. **The docs drifted, not the code.** Making a root-run failure set the assignment to
   `failed` (the review's suggested fix) would have broken both replacement-retry paths,
   which require `subject.status='active'` after the root run ends
   (`company-retry.ts:159`, `project-specialist-retry.ts:159`). The state diagram
   described the designed target. It also showed `waiting_input → queued`, while the
   implemented path is `waiting_input → active` with an input revision bump.
3. **A coupled constant was left behind.** Commit b6c104b5e deliberately removed
   reinforce/supersede from `retain` (CBK-04: similarity never confirms or merges). The
   ambient floor `ambientMinConfidence: 0.4` was defined as "confidence₀ + one
   reinforce step". With no writer able to raise confidence, the floor (0.4) sat above
   every new item (0.3). The comment was renamed "legacy" instead of re-deriving the
   value. The docs (project-brain, OpenAPI, MCP tool text, site-docs, configuration)
   kept describing reinforcement.

## Solution

1. No code change; the finding is rejected with evidence.
2. Docs-truth fix (owner decision): the unwritten transitions are tagged `(Designed)`
   in the diagram and transition table, the `waiting_input → active` edge is added, and
   the current recovery (stay `active` for retry; otherwise cancel → reopen) is
   documented. The T43 manifest's `postQualificationAmendments` entry is updated with
   the new digest and a reason.
3. `ambientMinConfidence` is now 0.3, with a WHY comment that it must not exceed
   `initialConfidence`. The ambient test drops the `confidence = 0.5` simulation, gains
   "fresh item IS injected" (which asserts floor ≤ initial) and "below-floor item NOT
   injected", and was proven RED at 0.4 (5 failures) and GREEN at 0.3 (12/12).
   Reinforcement statements are swept out of every current-contract surface.

Sweep (grep `reinforc|0\.4 |ambientMinConfidence|recurrence promot|recurred`):
- **Fixed:** project-brain.md (policy, state machine, retain flow, ambient, decay,
  E-3/E-4, edge cases, ledger), operations.openapi.yaml (retain description, 200 and
  `reinforced` field), external-operations.md, configuration.md, mcp `memory_retain`
  description, site-docs concept page, flow-graph.md, and the decay.ts / recall-ranker.ts
  comments.
- **Intentionally kept:** `reinforcement_count` / `last_reinforced_at` columns and
  `clusters.ts` (legacy data still read); the `reinforced` response field (API
  compatibility, documented as always false); company-brain CBK-04 text (still true);
  `retain.ts` / `memory-harvest.ts` / `schema.ts` comments mentioning redelivery of
  historical outcomes.

## Prevention

- **Re-derive a dependent constant when you remove its mechanism.** When removing a
  mechanism, grep every constant whose comment defines it in terms of that mechanism
  ("one reinforce above …") and re-derive its value. Renaming the comment to "legacy"
  is not a fix.
- **Read the fixtures before fixing an authz finding.** Before tightening authorization
  on a "principal X reads owner Y" finding, grep the test-support seeds for a fixture
  that grants X on Y. A seeded grant is a contract statement. Then check where disclosure
  is enforced (taint/restriction), not just admission.
- **Check who depends on a state staying put.** Before adding a terminal-state writer,
  grep for readers that REQUIRE the non-terminal state after the triggering event (the
  retry paths' `status='active'`).
- **Docs-only edits to qualified specs** must update the T43 manifest's
  `postQualificationAmendments` (`CT-CBX-05` digest gate in `validate:docs:all`).
