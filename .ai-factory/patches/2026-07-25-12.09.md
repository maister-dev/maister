# Inline idempotency reused a different recipe without a digest check (Codex-3)

**Date:** 2026-07-25 12:09
**Files:** web/lib/evaluations/recipes.ts, web/app/api/projects/[slug]/evaluations/studies/[studyId]/launch-batches/route.ts, web/lib/evaluations/__tests__/recipes.integration.test.ts
**Severity:** high

## Problem

A `/codex:adversarial-review` found that the M2 idempotency fix I had just shipped (`returnExistingOnKeyConflict`) reused the stored recipe on a key conflict **without comparing its `definitionDigest` to the incoming definition**. The launch route preflights the NEW inline definition, then `createControlledRecipe` could substitute the OLD recipe for the same `inline-<idempotencyKey>-<index>` key; because the batch request digest is taken over resolved recipe IDs (not their content), a same-key retry carrying a CHANGED variant returned `deduped` success while launching the previous configuration. A mismatched retry that also ADDED items persisted new recipes before the batch conflict was detected, leaving orphan rows.

## Root Cause

The M2 fix solved "same key + same definition → dedup" but silently also admitted "same key + DIFFERENT definition → reuse the old one". The idempotency key is a promise that *the same request* is safe to retry; it is NOT a promise that *any request under this key* resolves to the stored result. Returning the stored recipe without a content check turned a retry-safety mechanism into a silent-wrong-config launcher — the exact failure mode idempotency keys exist to prevent (a changed payload under a used key must CONFLICT, not silently alias). Secondarily, recipe creation and the batch idempotency record committed in separate transactions, so a rejected replay could leave recipes behind.

## Solution

1. **Digest guard** (`recipes.ts`): on a key conflict under `returnExistingOnKeyConflict`, compare `existing.definitionDigest === contentDigest(definition)`. Match → return the existing recipe (true idempotent replay); mismatch → throw `CONFLICT` ("...with a different definition"). The digest is the same `contentDigest` used to stamp the row, so it is byte-exact and free.
2. **Atomicity** (route): wrap the inline-recipe creation loop AND `createControlledLaunchBatch` in one `getDb().transaction`, passing `tx` to both (each opens a nested savepoint). A rejected replay — digest mismatch on a reused idempotencyKey, or a changed inline definition — now rolls back every recipe created in the request instead of orphaning rows. The drive kick stays post-commit (two-phase).
3. Added a RED-first integration test: same key + changed `executionPolicy.preset` → rejects `/different definition/i`; the existing same-key/same-def test still returns the same id.

## Prevention

- An idempotency/dedup key that resolves to a STORED result must verify the incoming payload matches the stored one (digest/content compare) before aliasing — a "return existing on conflict" branch is a silent-substitution bug unless it is content-guarded. Cover both same-key/same-payload (dedup) AND same-key/different-payload (CONFLICT).
- When one request creates dependent rows (recipes) and then a keyed record (batch) that can reject the request, create them in ONE transaction so a rejection leaves no orphans.
- An adversarial review is worth running on your OWN just-shipped fix — this defect was introduced by the prior `/aif-fix` batch and only surfaced under an independent challenge pass.
