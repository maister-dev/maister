# Read-only ACP smoke evidence probe

**Date:** 2026-07-07 18:29
**Files:** `supervisor/scripts/smoke-acp-adapter.ts`, `supervisor/test/fixtures/mock-acp-compatibility.mjs`, `supervisor/src/__tests__/smoke-acp-adapter-script.test.ts`, `web/components/settings/adapter-support-panel.tsx`, `docs/supervisor.md`, `docs/system-analytics/acp-runners.md`, `docs/screens/settings-acp-runners.md`
**Severity:** high

## Problem

Non-Claude standalone read-only agent launches required cached
`smoke.readOnlySession.status="ok"` evidence, but the smoke CLI could only
write nested `skipped` evidence. The Settings ACP runner docs also promised
separate generic-smoke and read-only-capable signals while the adapter support
panel rendered only one availability dot.

## Root Cause

The implementation treated initialize/newSession smoke as sufficient CLI work
and left read-only permission-wire proof to external/manual evidence. That
created a fail-closed launch gate with no supported evidence producer. The UI
drift came from adding the diagnostics contract without adding a corresponding
details row in the screen component.

## Solution

The smoke CLI now opens an ACP session and, when `--read-only-session` is set,
sends dedicated prompt probes that must observe read allow, write deny, and
ACP `other` deny decisions before writing nested `ok` evidence. Missing
observations produce nested `error` evidence. The mock ACP fixture can derive
permission kind from prompt markers, and a focused regression proves the script
path produces nested `ok`. The Settings adapter details now render generic
smoke and read-only-capable evidence from supervisor diagnostics.

## Prevention

When a launch gate depends on cached diagnostics, the branch must include a
supported producer and a failing regression at that producer boundary. Screen
artifacts that name distinct signals should be paired with UI assertions that
those signals are rendered, not only present in backend diagnostics.
