# Contract prose over-promised what the design delivers (ADR-151 agent mentions)

**Date:** 2026-07-27 09:30
**Files:** docs/system-analytics/agent-mentions.md, docs/decisions.md,
docs/api/web.openapi.yaml, docs/api/external/operations.openapi.yaml,
mcp/src/tools.ts, web/lib/agents/triggers.ts,
web/lib/social/__tests__/social-domain.integration.test.ts
**Severity:** medium

## Problem

An adversarial review returned three findings against a feature whose code was
correct and fully green (unit 6938, all mention integration suites, e2e 4/4).
Every finding landed on the **words**, not the behavior:

1. Three places claimed the comment POST response tells a caller "whether its
   summon was **accepted**" (`agent-mentions.md` Expectation 12,
   `web.openapi.yaml` `postTaskComment`, ADR-151 D11) — while the two
   `MentionedAgentDTO` schemas correctly said "a report, not a guarantee". The
   flag is asymmetric: `false` is a hard negative, `true` only means "resolved
   + operator grant existed at write time". A self-mention returns
   `summonable: true` and never launches.
2. Expectation 9 stated an unqualified "MUST NOT be launched again" for a busy
   agent. The implementation is a read-then-launch serialized only by the
   singleton dispatcher — it holds summon-vs-summon, not summon-vs-manual/
   cron/flow, because no launch path has ever enforced one active run per
   `(agent, task)`.
3. `TaskCommentDTO.body` / ext `CommentDTO.body` return markdown containing
   `[@<id>](/agents/<id>)`, but neither description said so. `/agents/<id>` is
   not a route and `/agents` is admin-only, so any consumer rendering the body
   as plain markdown emits a link to 404/403.

## Root Cause

Two distinct failure modes, both about the seam between design and prose:

- **Aspirational phrasing survived into the contract.** The ADR's *motivation*
  sentence ("so the caller learns whether its summon was accepted") was copied
  forward into an Expectation and an OpenAPI operation description, where it
  stopped being motivation and became a promise. The accurate qualifier lived
  only on the schema, one level down, where a caller reading the operation
  never sees it.
- **An invariant was written at the strength the author wished for, not the
  strength the mechanism provides.** "MUST NOT be launched again" reads as
  global mutual exclusion; the mechanism only serializes one branch. Nothing
  in the review process forces an expectation to name *what enforces it*, so
  an unenforceable MUST passed every gate — validators check syntax and
  anchors, tests check behavior, and neither can see that a sentence claims
  more than the code.
- **Read surfaces were never swept.** The write path documented the mention
  syntax thoroughly (request body, MCP `comment_create`); the symmetric read
  surfaces returning the SAME expanded text got nothing. Classic
  writer-documented / reader-forgotten split.

## Solution

Contract-only; zero behavior change.

- Corrected the three "accepted" claims and stated the asymmetry explicitly:
  `false` is a hard negative, `true` is not a receipt. Extended the MCP
  `comment_create` description, which had caveated only `false`, and told the
  agent to poll runs for real confirmation.
- Scoped Expectation 9 to the mention branch and made it NAME its enforcement
  (`domainEventDispatch: 1` + the CAS lease), added an edge-case row for the
  summon-vs-other-path race, and put a why-comment at the busy check in
  `triggers.ts`. Recorded in ADR-151 D5 the rejected alternative (a DB claim
  over active `(agent_id, task_id)`) with its reason: it would gate every
  launch path and refuse legitimate manual relaunches.
- Documented the stored `[@id](/agents/id)` marker on both read-surface body
  descriptions and on MCP `comment_list`, with the rule for telling it apart
  from a real `KEY-N` task link.
- Pinned the asymmetry with an integration test: an agent mentioning itself
  gets `summonable: true` from the write path and the event still carries the
  id — the consumer's row-3 test owns the no-run half, so the two halves are
  asserted once each with no overlap.

## Prevention

- **An Expectation bullet must name what enforces it.** If a MUST cannot point
  at a constraint, a CAS, a singleton, or a test, it is a wish — either weaken
  it to the scope the mechanism covers or add the mechanism. Reviewing the
  Expectations section against "what makes this true?" catches unenforceable
  invariants that every automated gate misses.
- **Never let motivation prose become contract prose.** A phrase justifying a
  decision in an ADR ("so the caller learns X") describes intent; copying it
  into an Expectation or an operation description turns it into a guarantee.
  When a schema carries a qualifier ("a report, not a guarantee"), the
  operation description that returns that schema needs the same qualifier —
  callers read the operation, not the component.
- **Sweep read surfaces whenever a write surface changes its stored form.** If
  a write path starts persisting a new textual representation, every DTO that
  returns that text is in scope in the SAME pass: `TaskCommentDTO`,
  ext `CommentDTO`, and the MCP list tool here. The request-side docs being
  thorough is precisely what makes the read-side gap invisible.
- **An asymmetric boolean needs both arms documented and one test per arm.** A
  field where `false` is strong and `true` is weak will be read as symmetric
  unless the docs say otherwise; state what each value does and does not
  promise.
- Test-review note: a "self-X" test already existing for a NEIGHBOURING
  concept (task self-mention) reads like coverage of the new one (agent
  self-mention). Grep for the specific actor/entity, not the word "self".
