# A fix that removes a false crash can silently remove a safety net too

**Date:** 2026-09-21 21:55
**Files:** web/lib/reconcile.ts, web/lib/reconcile-evidence.ts, web/lib/reconcile-evidence-db.ts, web/lib/__tests__/reconcile-evidence.test.ts, web/lib/__tests__/reconcile-sweep.integration.test.ts, web/lib/execution-host/__tests__/receipt-probe-loss-evidence.test.ts, web/lib/flows/graph/__tests__/prompt-owners.integration.test.ts, docs/decisions/adr-177.md, docs/system-analytics/reconciliation-gc.md, docs/system-analytics/runs.md
**Severity:** high

## Problem

Four defects, found one at a time by re-running the stage-AB lane. The first
two were introduced by the PREVIOUS patch in this same branch
(`2026-09-21-16.20.md`), which fixed the ADR-177 receipt probe so a lost turn had
to be proven rather than inferred; the third was introduced by the fix for the
second; the fourth is old code this branch made reachable. Each was invisible
until the one before it was fixed.

1. That fix mapped a **v2 `accepted`** receipt — the one shape that carries no
   liveness in either direction — to `pending_ingest`. `pending_ingest` SKIPS
   unconditionally and fires *regardless of grace*. v2 is the production request
   schema, so the whole production path lost the pre-ADR-177
   `agent-session-gone` safety net: a run whose terminal event never arrived
   would be skipped by every sweep, forever, with no writer that owed the next
   move. The fix for a false crash had become a guaranteed permanent stall.

2. The `crashAgentRunMidTurn` fixture asserted `summary.crashed >= 1` in its
   `before_terminal` window and a `decision: 'turn_lost'` close, on the premise
   that the sweep would classify that window as a lost turn. It does not, and
   never did: the fixture kills the **adapter**, so the supervisor records an
   ordinary errored turn. Five `owner-flow-crash-recover` cases failed
   deterministically.

3. The fix for (2) then replaced `summary.crashed >= 1` with
   `summary.crashed === 0`. That counter is **sweep-wide**. It passed every
   targeted re-run and failed the full lane with `expected 3 to be +0`, because
   by the time the fixture runs, its file has seeded dozens of other runs in the
   same database and the sweep crashes several of them legitimately.

4. With every test then passing, the lane STILL exited 1: an **unhandled
   rejection**, `MaisterError: task not found for run <id>`, from a `runFlow`
   the sweep dispatches after promoting a queued run. Reproduced in isolation,
   and absent from master's copy of the same file — so this branch is what
   reaches it.

## Root Cause

**Defect 1 — a two-valued question answered with a two-valued vocabulary.**
The probe's answers were written as "what the receipt said". `pending_ingest`
carries an extra, unwritten meaning that nothing in its name states: *a named
writer owes the next move*. Every other answer either names a writer or proves
a terminal outcome, so folding "nobody is asserted in either direction" into
`pending_ingest` looked like a safe conservative default while actually
asserting something false. The missing class was never "what did the receipt
say" but "how much does this answer bind us" — and the classifier already had
exactly the right member for *not at all*: `none`, the one class that falls
through to the grace anchor, which refuses to crash a turn inside its window
AND still crashes one long past it.

**Defect 2 — a comment hypothesis, promoted to an assertion, never executed.**
The fixture's expectation was rewritten from the previous round's *reading* of
what the probe would do, not from what it did. It was never true. It was only
found by grepping the sweep's own structured log
(`grep -o '"probe":"[a-z_]*"'` → seven `pending_ingest`, zero `turn_lost`),
after a wrong hypothesis about the v2-accepted path had already been stated out
loud. The fixture suppresses the command's terminal columns, so nothing settles
the command either — which is why no later writer rescued it.

**Defect 3 — tightening an assertion without re-checking its SCOPE.**
`>= 1` and `=== 0` read like the same claim with the sign flipped, so the edit
felt local. They are not: `>= 1` is satisfied by any crash anywhere in the sweep
and is therefore insensitive to the other runs in the database, while `=== 0`
is a claim about all of them. Loosening-to-tightening changed which entity the
assertion is *about* — from "somebody" to "everybody" — when the contract being
asserted is about exactly one run. Worse, the targeted re-run used to verify it
(`-t 'owner-flow-crash-recover'`, 5 of 58 tests) removed the very population
that makes the two differ, so the verification could not have caught it.

**Defect 4 — a pre-existing unguarded dispatch that this work made reachable.**
`reconcile.ts` frees a concurrency slot on both crash arms and calls
`promoteNextPending`, OVERRIDING its `runFlow` dispatch with
`void Promise.resolve(runFlow(next))` — no catch. `promoteNextPending`'s own
default catches and logs, and the reattach dispatch fifty lines below in the
same file catches and logs; only this override dropped it. So the defect is old
and it is on master. What is new is the traffic: ADR-177 adds three crash
reasons (`turn-lost`, `stream-lost`, `owner-poisoned`), and every one of them
frees a slot and runs this dispatch. A latent unhandled rejection that nothing
used to reach is now reachable on three new paths — which is why the fix belongs
to this change rather than to a follow-up, even though the line predates it.

## Solution

Added a fifth probe answer, `indeterminate`, for the v2 `accepted` shape alone,
classifying to `none`. The two returns differ by exactly the property that
matters: `pending_ingest` asserts a writer, `indeterminate` asserts nobody and
defers to the rule that governed before the ADR. No other arm moved — a probe
that proves nothing still never yields `turn_lost`, which the suite now pins as
a property over every non-`turn_lost` probe answer rather than as a per-value
list.

The fixture now reads the run's own status after the sweep and asserts it is
still `Running` — a skip writes nothing at all, so `Running` is a skip's
signature, and the claim is scoped to the one run the contract is about. It then
produces the `Crashed` state these Recover cases need directly via
`crashRunningRun(…, 'worktree-gone')`. The `decision` assertion returns to
master's `crash_recover`, correct again because the boundary is no longer what
closes the attempt.

Both `promoteNextPending` overrides in the sweep now go through one
`promoteDispatch` helper that catches and logs, mirroring the reattach dispatch
already in that file. The rejection is now one ERROR line instead of a
process-level unhandled rejection; the suite that exposed it goes from exit 1
(14 passed, 1 error) to exit 0.

Docs: ADR-177's D1 row 9 gains the fourth answer plus a paragraph naming both
receipt shapes that look like a lost turn and are not; `reconciliation-gc.md`'s
evidence-class table moves the v2 case to `none` and gives `pending_ingest` the
ordinary-rejection case; `runs.md` stops claiming the `none` path always has a
dispatch spinning up behind it.

## Prevention

- When a fix narrows a crash condition, ask what now happens to the rows it
  stopped crashing — **for every branch it widened**, not just the one in the
  bug report. A skip is a decision with a failure mode, not the absence of one.
- A skip class earns its name from the WRITER it asserts, not from the receipt
  field it was read out of. If no writer can be named, it is not that class.
- Never promote a comment's reasoning about what production does into a test
  assertion. Run the thing and read its log. A hypothesis that survives only
  because nothing executed it is indistinguishable from a wrong one.
- A fixture that kills the ADAPTER does not simulate a supervisor restart. The
  supervisor is still there to record an ordinary failure; only killing the
  supervisor mid-turn produces `turn_lost`.
- **Assert on the entity the contract names.** A sweep-wide counter cannot
  express a claim about one run. Before tightening a `>=` into an `===`, ask
  what else the number counts — in a suite with no per-test truncate, the answer
  is "every row every earlier test left behind".
- **A green test list is not a green run.** Vitest exits non-zero on an
  unhandled rejection with every test passing, and the summary line still reads
  `438 passed`. Read the exit code and the `Errors` line, never the pass count
  alone.
- **Adding a new way to reach old code inherits that code's defects.** Three new
  crash reasons meant three new callers of an unguarded dispatch. Ask what
  EXISTING paths a new state makes reachable, not only what new code runs.
- **A `-t` filter can delete the population a test depends on.** Verifying a
  contamination-sensitive assertion with a filtered run proves nothing; the
  filter removes the other tests whose rows are the whole point. Run the FILE
  when the assertion's truth depends on what else ran.
