# Shared fixture target branch coupled two e2e promotion scenarios

**Date:** 2026-09-03 16:10
**Files:** web/e2e/_seed/seed-e2e.ts, web/e2e/m18-branch-promotion.spec.ts
**Severity:** medium

## Problem

`m18-branch-promotion.spec.ts:103` ("conflict scenario") intermittently failed
the full parallel e2e suite with `Expected: "CONFLICT" / Received:
"PRECONDITION"` — the promote was refused by a gate before reaching the
`git merge --no-ff` it is written to conflict on. It passed in isolation.

Its sibling `:49` ("merge scenario") failed reproducibly, everywhere, and had
been recorded in the e2e baseline as a real product bug.

## Root Cause

TWO independent defects, both in the test layer, neither in the product.

**1. The fixture coupled the scenarios through one target branch.** All three
m18 scenarios seeded `workspaces.target_branch = "release"` in ONE shared repo.
The run-detail page resolves `reviewedTargetCommit` from the live tip of that
branch AT RENDER (`app/(app)/runs/[runId]/layout.tsx`), the promote sends that
token, and `promoteRun` re-reads the tip and refuses `PRECONDITION` on a
mismatch ("target advanced since review"). The merge scenario's promote MERGES
into `release`, moving the tip. With `fullyParallel: true` the two tests race:
when the merge lands between the conflict test's render and its promote click,
the conflict test's token is stale and the promote is refused before it can
conflict. `--workers=1` never reproduces it — serial order closes the window,
which is why isolation looked clean.

**2. Both tests asserted run status with a page-wide text match.** `:49` used
`getByText("Done", {exact:true}).first()` and `:103` used
`...toHaveCount(0)`. The active-workspaces rail is SHARED CHROME on every page
and renders a hover-only `data-testid="status-tooltip"` span per sibling run —
so `.first()` resolved a HIDDEN span (`toBeVisible` → "Received: hidden") and
the count assertion counted a sibling run's status. `:49` was never a product
bug: its promote returned 200 and the run really did reach `Done`; only the
assertion was wrong.

## Solution

- Each scenario gets its OWN target branch (`release-merge`,
  `release-conflict`, `release-pr`), created off `main` inside
  `provisionM18RunBranch` and stored on that scenario's workspace row. No
  scenario's promote can move another's tip, so the drift window cannot open.
  The fixture exposes `mergeTargetBranch` / `conflictTargetBranch`.
- Both status assertions now read `getByTestId("run-header-status")` — the run's
  own badge — with `toHaveText("Done")` / `toHaveText("Review")`.

Verified: 4/4 with `--workers=1` (the ordering that previously failed BOTH
tests, since the merge lands first) and 4/4 across three parallel runs.

## Prevention

- **A fixture that seeds N runs sharing one mutable git ref couples its tests.**
  When any test performs a WRITE against a shared ref (merge, push, branch
  move), give each scenario its own ref. Ask of every multi-scenario fixture:
  "if scenario A completes first, what does scenario B now see?"
- **Serial passing does not clear a concurrency-coupled test.** `--workers=1`
  closes render→click windows. Reproduce order-dependent flake by asking which
  interleaving opens the window, not by re-running the default configuration.
- **Never assert run status with a page-wide `getByText`.** Shared chrome (the
  active-workspaces rail) renders every sibling run's status, including
  hover-only tooltip spans that are in the DOM but hidden. Scope to the
  surface's own testid.
- **"Reproducible failure" is not "product bug".** Check WHERE the test failed:
  `:49`'s promote returned 200 and only the final assertion failed. A baseline
  entry that says "real bug" is a claim to verify before budgeting a fix.
