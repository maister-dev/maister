# Legacy package schema compatibility

**Date:** 2026-07-14 14:00
**Files:** `web/lib/flows.ts`, `web/lib/packages/__tests__/attach.integration.test.ts`

## Problem

Upgrading a project attachment could fail with `FLOW_INSTALL` when the target
package version had form schemas only inside member-flow directories and no
package-root `schemas/` artifacts. The installer treated an absent root artifact
set as an empty canonical set and rejected every member schema as a collision.

## Root cause

The package-root schema materializer applied its consistency rule regardless of
whether the source package actually supplied root schemas. That rule is correct
for a package that declares root artifacts, but it made legacy package revisions
impossible to install and therefore impossible to upgrade away from.

## Solution

When the source root contains no schema artifacts, preserve member-flow schemas
and continue validating every referenced `./schemas/<name>.json` document in the
installed member revision. When root artifacts exist, retain the strict
byte-identical and no-extra-member-schema checks. The integration regression test
proves that a legacy member schema remains usable while the package cache has no
root schema file.

## Prevention

Schema migration contracts must distinguish an absent source artifact set from a
present canonical source set. Compatibility tests need to cover both branches:
legacy member-only packages can install, while packages that provide root schemas
still reject missing or divergent member copies.
