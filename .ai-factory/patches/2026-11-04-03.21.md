# Give controlled delegation decisions stable operation keys

**Date:** 2026-11-04 03:21
**File:** web/e2e/_seed/test-supervisor.ts
**Severity:** medium

## Problem and cause

The controlled browser peer POSTed a Flow child to the real delegation API
without the now-required `Idempotency-Key`. The API correctly returned HTTP422
`CONFIG` / `delegation_launch_key_required` before creating the child. The
Flow-target browser journey therefore stopped before its actual execution
assertions. The shared producer also supplies the recursive harness's Flow
children; the standalone stub has no delegation producer.

## Correction

The peer now sends `e2e-delegate:v1:<parentRunId>:<childOrdinal>`. Replaying one
decision preserves its identity, sibling ordinals differ, and a newly launched
parent has a new identity. A changed body with the same key remains a server
conflict. Do not generate a fresh random key per transport attempt or derive the
key from mutable request contents. Current parent-bound token authorization,
child proof, audit and truthful queued HTTP202 responses remain server-owned.
The peer does not wait for Run creation.

## Validation boundary

Scoped ESLint and `git diff --check` pass. The coordinated 29-case browser rerun
is pending; no browser GREEN is claimed for this correction. Existing real-route
replay/conflict coverage owns the idempotency matrix, so no duplicate unit test
was added. Coordinator waiting for accepted unbound child intents is a separate
production concern with a separate owner.
