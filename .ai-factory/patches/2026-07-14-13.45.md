# Review-fix pass on flow-ref resolution: unguarded trap, reachable ref collision, lying fixtures

**Date:** 2026-07-14 13:45
**Files:** web/lib/flows/resolve-flow-ref.ts, web/lib/flows/__tests__/resolve-flow-ref.integration.test.ts, web/lib/services/triage.ts, web/lib/services/__tests__/triage.integration.test.ts, mcp/src/__tests__/tools.test.ts
**Severity:** medium

## Problem

`/aif-verify` passed the flow-ref branch on task completion (17/17) and surface
coverage. `/aif-review` plus an adversarial pass then found four real defects
the verify pass had missed:

1. Plan task **T3.1 was marked `[x]` while 3 of its 4 promised test groups did
   not exist**. The `updateTask` pre-built-patch trap — identified, fixed, and
   called out as the subtlest bug in the change — shipped with **zero**
   regression coverage. A revert to `void`/in-place mutation would persist a raw
   `flow_ref_id` into `tasks.flow_id` with no failing test.
2. The resolver's JSDoc asserted *"flows.id is a UUID PK"* to justify a
   no-collision invariant. `flows.id` is `text()`. Worse, the collision is
   **reachable**: `capabilityRefIdSchema`'s `/^[A-Za-z0-9._-]+$/` matches a UUID
   string and `flowEntrySchema.id` is a bare `z.string().min(1)`, so a
   UUID-shaped `flow_ref_id` installs cleanly. The OR-match had `LIMIT 1` with no
   `ORDER BY` → a verdict naming flow A by its published UUID could bind flow B.
3. The resolver **test fixture's comment claimed a cross-project ref collision it
   did not have**, so the strongest R4 case was untested and one test was a
   duplicate of "unknown string misses".
4. The MCP test was partly vacuous: it asserted a pre-existing fact that passes
   with the feature fully reverted, and used a substring match so loose that
   "reference" would satisfy it.

## Root Cause

**Why the trap shipped unguarded:** the verify pass audited *contract surfaces*
(re-derived from the diff, per its own rule) but never re-derived the *promised
tests* from the plan. Surface enumeration and test enumeration are different
sweeps; doing one felt like doing both. The `[x]` was written when the code
landed, not when the tests did.

**Why the false invariant survived:** the comment was written from intent ("ids
are UUIDs") rather than from the schema. Nobody greps a comment. The claim was
load-bearing — it was the stated justification for `LIMIT 1` with no ordering.

**Why the fixture lied:** the comment described the fixture the author *meant*
to write. The assertions still passed, because a fixture with distinct refs can
only ever prove "not found" — the weaker property. A green test over a fixture
that cannot express the dangerous case reads exactly like coverage.

Common thread: **three of the four are self-assessment failures, not coding
errors.** The code was right; the claims about the code were wrong.

## Solution

- Added regressions for `updateTaskVerdict`, `updateTask` (incl. the `null`
  CLEAR half) and `createTask`, then **proved them non-vacuous by neutralizing
  both traps and watching them go RED**, restoring to GREEN.
- `ORDER BY (id = ref) DESC` before `LIMIT 1` — the id match wins
  deterministically instead of depending on Postgres row order; JSDoc rewritten
  to state what the schema actually enforces; covered by a colliding-id test.
- Fixture now gives both projects `aif-bugfix`; the redundant "another project's
  ref" test is replaced by "resolves to THIS project's flow", the only case where
  ref-axis scoping can return the wrong row.
- MCP test pins the exact advertised phrase and fences `run_launch` **and**
  `run_delegate`.
- The concurrent-delete race guard names the resolved id, matching its sibling.

## Prevention

- **`/aif-verify` must re-derive the promised TESTS from the plan, exactly as it
  re-derives contract surfaces from the diff.** A `[x]` task whose plan listed
  explicit test cases is PARTIAL until each case is found in the diff. Checking
  `git diff --name-only | grep test` against the plan's test list is a 5-second
  gate that would have caught this.
- **A comment asserting an invariant is a claim that must be greppable.** Before
  writing "X cannot happen because the schema enforces Y", open the schema. Here
  `text()` vs `uuid()` was the whole argument.
- **Read a fixture's data, not its comment.** If a comment says "collides" and
  the values do not, the test proves the weaker property while reading as the
  stronger one. Ask: *could this fixture fail if the bug existed?*
- **A test that passes with the feature reverted is documentation, not a test.**
  Run the guard-neutralize proof on any regression whose first run is green.
