# Recorded prompts leaked to a runs:read feed and landed ahead of earlier replies

**Date:** 2026-09-17 11:31
**Files:** web/lib/ext-activity/service.ts, web/lib/flows/graph/prompt-record.ts, docs/system-analytics/run-trace.md, web/lib/ext-activity/\_\_tests\_\_/run-activity-prompt-exposure.integration.test.ts, web/lib/flows/graph/\_\_tests\_\_/prompt-record.integration.test.ts
**Severity:** high

## Problem

An adversarial review raised three findings against the run-trace branch. Two
were real, one was not.

1. **(high, real)** The new `user` prompt rows reached
   `GET /api/v1/ext/runs/{runId}/activity`. `loadRunActivitySources` selected
   every `run_messages` row for a run with no role or key predicate, and
   `toRunActivityItem` copied the text verbatim into `action.detail`. That
   endpoint requires only a project-bound `runs:read` token, while the internal
   transcript route requires `readRepoFiles` (member). A resolved prompt can
   embed artifact bodies through `{{ artifacts.<id>.content }}` (ADR-120), so
   repository content became readable one privilege level down — the exposure
   TRC-11 exists to forbid. `CT-TRC-11` covered only the internal route.

2. **(medium, real — and worse than reported)** Prompt rows landed ahead of
   replies that happened before them. For a node with a blocking gate the
   transcript read `node prompt, gate prompt, node reply, gate reply`, and
   sequences are never rewritten, so the misordering was permanent.

3. **(medium, REFUTED)** "The recorder awaits a lookup and a `SELECT FOR UPDATE`
   with no deadline or cancellation, so a stalled lock blocks dispatch forever."

## Root Cause

**#1 — a new writer inherited an old reader.** `run_messages` had exactly one
producer contour (the transcript projector) plus scratch dialog, and every
consumer was written against that contour. Adding a second producer silently
widened every existing reader, and the ext feed's authorization was chosen for
the OLD contents. Nothing in the type system or the tests connects "what may be
written" to "who may read it" — the branch's own `CT-TRC-11` proved the gate on
the route it knew about, which is exactly the shape of a test that certifies the
half you remembered.

**#2 — two writers, one counter, two different clocks.** A prompt is written
eagerly at dispatch; a reply is projected by the canonical worker
(`canonical-run-transcript-v2`) or lazily on read. The graph runner drives only
the ARTIFACT projector at its sync points (`runner-graph.ts:2197`), never the
transcript one — so the gap between a node's turn ending and its gate
dispatching is a few milliseconds of runner work that the worker normally loses.
The shared `run_transcript_states` lock made allocation *safe* (TRC-10) and that
was mistaken for making it *ordered*: the lock serializes writers, it does not
order them by causality. `IT-TRC-05` filtered to `user` rows, so the suite could
not see the interleaving at all.

**#3 — the reviewer read the function, not the handle it is given.** The bound
is real; it just is not in `prompt-record.ts`. `ctx.db` is
`flowDriverDatabase(root, claim, signal)`, whose `query` AND `transaction` both
route through `projectionTransaction`: cumulative deadline, server-side
`statement_timeout`/`lock_timeout`, `pg_cancel_backend`, rollback, plus the
driver's abort signal. All four `runAgentStep` call sites pass it. The genuine
defect was documentary — TRC-08 asserted "never delays" while naming nothing
that enforced it.

## Solution

**#1** — one predicate at the choke point `loadRunActivitySources`, which feeds
BOTH the run feed and the pulse: `isNull(runMessages.promptDispatchKey)`. It
keys on the dispatch key, never on `role`, because a scratch run's `user` rows
are the operator's own dialog and must keep flowing. Restores the pre-branch
exposure surface rather than raising the endpoint's scope, which would have
narrowed a shipped external contract.

**#1 was itself incomplete, and the reader enumeration for #2 is what caught
it.** That function has a SECOND door: when the filtered query matches nothing
it falls back to `getWholeRunTranscriptMessages`, which had no predicate — and
"matches nothing" is exactly a flow run whose only rows so far are its prompts
(node dispatched, nothing projected). So the first fix left the leak reachable
early in every run. `getWholeRunTranscriptMessages` now takes
`includeRecordedPrompts`, defaulted to FALSE: forgetting is safe, remembering is
explicit. Fixing the call site alone would have left the next caller to
rediscover it.

**#2** — anchor prompts to the run's EVENT stream instead of to write arrival.
The dispatcher stamps `supervisor_event_id` with the run's ingested-event
horizon (`-1` before the first event), which is the same column and the same
axis the transcript projector already uses for its own rows
(`supervisorEventId = event.runSequence`) — so no migration was needed. The node
transcript orders on
`(supervisor_event_id, prompt_dispatch_key IS NOT NULL, sequence)`, the middle
term placing a prompt anchored at `E` after the reply projected FROM `E`.

A first attempt instead DRAINED projection before taking the sequence. It
worked, and was rejected on review: it put backlog-proportional work on the paid
dispatch path, made correctness depend on a projector call allowed to fail
silently, and — decisively — only NARROWED the race, because the drain and the
append are separate transactions. Anchoring makes order a property of the data,
so it holds however late projection runs. The whole-run feed is deliberately
left on arrival order: it serves scratch and agent runs whose `user` rows carry
no stream position, and with prompts excluded there is nothing there to reorder.

**#3** — no code change. TRC-08 now NAMES the mechanism, and the function
documents the invariant it depends on (callers pass the driver handle).

Both fixes were falsified. Reverting #1 fails on the SECRET assertion while the
scratch arm still passes. Neutralizing #2's drain fails with
`expected 2 to be less than 1` — the reply at position 2, the gate prompt at 1.
That second RED took two attempts: the first version failed with "reply missing"
because nothing simulated the worker catching up, which would have let a reader
dismiss it; adding a trailing `projectRunTranscript` made the RED the actual
misordering.

## Prevention

- **A predicate on one query is not a filter on the seam.** Before calling an
  exposure closed, follow every branch of the function that serves it — an
  `if (rows.length > 0) … else fallback` is two queries, and the fallback runs
  in precisely the state the predicate creates. Prefer a safe DEFAULT on the
  shared reader over a filter at one call site.
- **A compensating mechanism that narrows a race is not a fix.** Ask whether the
  property holds by construction or only by winning. Draining projection before
  allocating made the window milliseconds; anchoring to the event stream made
  the window irrelevant. Prefer the invariant that does not depend on timing.
- **Changing what a function reads invalidates its test doubles.** Adding the
  horizon read broke `UT-TRC-08`, whose double offered only `transaction` — it
  then failed before reaching the write it exists to pin. A double models a
  surface; widen it with the function.
- **A new writer to a shared table is a review of every READER of that table**,
  not just of the write path. Grep every consumer and ask what authorization
  each was designed for. The discriminator usually already exists — here
  `prompt_dispatch_key` separated the new rows from every old one exactly.
- **A lock that serializes is not a lock that orders.** When two producers share
  a counter, ask what drives each one. If they are on different clocks
  (eager-at-dispatch vs worker-projected), arrival order is not causal order.
- **A test that filters to the rows you added cannot see an interleaving
  defect.** Assert the whole conversation, not your half of it.
- **Refute a finding by reading the code the reviewer did not open.** Finding #3
  was correct about the text of `prompt-record.ts` and wrong about the system,
  because `ctx.db` is not a root pool. Trace what a dependency actually IS at
  the call site before accepting a claim about it — and when the claim turns
  out to be about missing DOCUMENTATION of a real mechanism, fix that instead.
- **A guard's RED must be the defect.** "Missing row" and "wrong order" are
  different failures; if neutralizing the fix produces the weaker one, the test
  is not yet pinned to the behavior it claims.
