# Resolve interactive origin from public HTTP authority

**Date:** 2026-11-04 02:43 (Europe/Moscow)
**Files:** web/lib/tasks/launch-http.ts; existing task-launch-admission HTTP integration suite; task-launch analytics, configuration and OpenAPI contract.
**Severity:** high

## Problem and root cause

The real production-Web native lane refused an authenticated, versioned manual
Flow launch with HTTP 403 `launch_interactive_origin_required`. The fixture had
already fetched its preview and sent Origin, revision, settings token and stable
idempotency key through the canonical intent endpoint.

`web/server.ts` gives Next the bind hostname `0.0.0.0`. Installed Next constructs
its internal request URL from that hostname. Comparing browser Origin directly
with `request.url` therefore compared public `127.0.0.1:<port>` against the
internal bind authority. Correcting only the fixture header would conceal the
same production browser failure.

## Current contract

The shared guard validates every present Host, then resolves the canonical
origin from server-configured HTTP(S) `AUTH_URL`, otherwise actual Host and
request protocol. Host-absent framework Request adapters retain URL authority.
Malformed present Host never selects another authority. Forwarded headers grant
none. Client Origin must exactly equal the serialized canonical origin, and
cross-site fetches remain refused.

Auth.js supports an authentication base path in `AUTH_URL`; the guard preserves
that configuration and uses its origin. Empty configuration remains unset.
Malformed nonempty configuration, credentials, query or fragment produce typed
CONFIG with static diagnostics, without the original URL or parser cause.
Authentication, scoped grants and admission logic remain unchanged.

The same boundary covers all four formerly exposed session mutation paths:
run recovery, individual agent retry, agent batch retry, and fresh operational
or taskless agent launch. Guards run after session authentication and before
decision parsing, authority use or allocation. The fresh-agent guard applies to
the whole route, preserving its existing operational admission contract.
Recover's two Origin diagnostics use the shared safe HTTP projection without
changing its established recovery-result mappings. Legitimate direct-handler
and native boot fixture requests supply their actual Origin.

## Regression evidence

The new grouped case in the existing real-Postgres HTTP integration fixture
first failed with `native custom server: expected 403 to be 202`:
`/tmp/maister-launch-origin-red.log`.

After the fix, all thirteen existing and new HTTP cases passed under Node
24.15.0, maxWorkers=1: `/tmp/maister-launch-origin-green.log`. The new case
covers bind/public-host separation, HTTPS proxy rewriting, configured Auth.js
base paths, empty optional config, Host-absent adapters, IPv6/default-port/case
normalization, ignored forwarded headers, malformed Host/configuration and
missing/noncanonical/cross-site client origins. Refusals leave no intent or Run;
accepted receipts truthfully remain queued with null Run identity. Existing
authorization, replay, cancel/replace and dispatch-commit controls stay green.

The native full-lane failure supplies actual-HTTP RED evidence. A fresh frozen
production-Web run remains necessary to qualify the compiled custom-server
path; route integration success alone does not establish that outcome.

The four mutating-adapter controls also reproduced actual authenticated
cross-origin admission before their fixes: launch/retry/batch returned 202 and
recovery invoked its effect and returned 200. Evidence:
`/tmp/maister-launch-origin-boundaries-red.log`. The four full real-Postgres
consumer files then passed all 61 cases:
`/tmp/maister-launch-origin-boundaries-green.log`. Authentication is stubbed at
the existing session boundary; current user and project grants remain real SQL.
Origin refusals create no retry intent, successor or operational allocation;
same-origin operational launch and canonical manual retry remain covered.

The complete constructor sweep includes guarded launch/concurrent/cancel/
replace/hold/assessment adapters and the guarded HITL restart mutation.
Restart-preview GET constructs a principal only for a read. Internal services
consume opaque principals; external bearer/MCP calls retain their separate
authority and never acquire human authority from Origin headers. This scope
does not redefine scratch or unrelated legacy continuation HTTP contracts.
