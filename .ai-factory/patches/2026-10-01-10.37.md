# Fence scratch permission events at every mutation transaction

**Date:** 2026-10-01 10:37 UTC
**Files:** `web/lib/scratch-runs/events.ts`, `permission-terminal.integration.test.ts`, scratch system analytics
**Severity:** high

## Problem

A delayed scratch permission reopened a stopped or discarded run as
`NeedsInput` and created a new open permission. An old incarnation could also
consume a stored answer belonging to the current resumed turn.

## Root Cause

Taking the run lock serialized writes but did not recheck whether the observed
session still owned an eligible dialog. The terminal consumer had an incarnation
fence; permission insertion and stored-answer rebinding did not. The two
permission transactions also allowed Stop to commit between their checks.

## Solution

Both permission transactions lock run → scratch rows and check current
incarnation identity plus eligible run/dialog status before any mutation.
Stored-answer delivery-failure recovery uses the same fence. Terminal and
permission projection share the incarnation lookup, while retaining their
distinct status rules: the current session's own ended incarnation still
projects its terminal. Structured ignored-event logs include identities and
statuses, never prompt or stored-answer contents.

Input admitted before Stop retains the existing assignment command fence.
An acknowledgement only updates an unanswered row, so it cannot overwrite
Stop's transactional closure. No remote I/O is moved into a database lock.

## Verification

The real-Postgres production-consumer RED report has three intended failures:
late Stop, late Discard, and stale-incarnation stored-answer rebinding
(`/private/tmp/r2-red.json`). Current live permission/dedup is a positive
control. A separate cut control commits production Stop after the first
permission transaction returns; removing only the second guard reproduces
`Review → NeedsInput` with one open row
(`/private/tmp/r2-second-guard-red.json`). The guard was restored immediately.

The full permission-terminal, incarnation-terminal and real-supervisor
idle-resume families pass 40/40 (`/private/tmp/r2-green.json`); full placement
and scratch prompt-owner consumers pass 17/17
(`/private/tmp/r2-consumers.json`). After restoring the second guard, the full
permission and status-emission suites pass 18/18 (`/private/tmp/r2-final.json`),
and the existing service unit suite passes 10/10 (`/private/tmp/r2-unit.json`).
The disjoint integration inventory is 59 cases in six files; overlapping
permission reruns are not counted twice. No production test-only export was added.

## Prevention

Locks order competing mutations; predicates establish whether a mutation is
still valid. Recheck both identity and lifecycle status at every transaction
boundary, including recovery catches. A first-transaction check does not
protect a later transaction. Test the cut between them independently.
