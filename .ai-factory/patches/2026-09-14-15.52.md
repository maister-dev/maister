# Resolve and assign consensus runners before launch

**Date:** 2026-09-14 15:52
**Files:** `web/lib/acp-runners/{resolve,consensus-preflight}.ts`,
`web/lib/flows/graph/consensus/{roles,drafts,runtime}.ts`,
`web/lib/services/runs.ts`, `web/lib/runs/{task-launch-config,launch-progress}.ts`,
`web/app/api/runs/{route,launch-options/route}.ts`,
`web/components/board/launch-popover.tsx`, associated tests, runner provenance
typing, EN/RU messages, and launch/consensus/API contracts.
**Severity:** high

## Problem

A consensus node failed immediately with CONFIG and zero token usage. The
deployed catalog had several ready Claude and Codex runners, while the Flow
declared capability-only planner and independent-reviewer profiles and had no
project role bindings.

## Root Cause

Consensus called the generic slot resolver without the compatible configured
preferences already used for logical sessions. Three matching Claude runners
therefore produced an ambiguity error despite an applicable default. Parent
admission and launch previews inspected logical sessions but omitted consensus
roles; the failure arrived only after entering the node. Settings controls
depended on existing binding rows, so an empty remap list offered no assignment
controls.

## Solution

Use one consensus resolver for preview, parent admission, drafts, verification,
and synthesis. Explicit bindings and concrete references retain priority;
inherited defaults must match the declared capability. Record inherited parent
choices as `runDefault`, not a user override. Inspect all runner-bearing roles
before run/workspace creation and return only safe role identifiers for UI
remediation. Normalize a consensus-only graph's implicit primary session in
both preview paths.

Render role selectors from the Flow manifest in the launch dialog. Project
administrators save each binding through the existing project-scoped API,
including creation of previously absent rows. Save completion invalidates the
preview; stale responses cannot unblock launch. Errors retain the selection and
offer explicit retry. Project membership and binding authorization remain
separate existing policies.

## Verification

- RED: capability-only default regressions failed before the resolver change;
  real PostgreSQL admission tests created runs instead of refusing ambiguous
  participant/synthesizer roles before the guard was added.
- GREEN: all 26 direct integration consumers of `launchRun`/`launchRunStaged`
  passed (286 tests). The focused PostgreSQL/Git suite also proves refusal,
  creation of a binding through PATCH, and successful subsequent admission
  (7 tests).
- Scope sweep: `rg -n 'resolveConsensusRunnerSlot\('
web/lib/flows/graph/consensus --glob '!**/__tests__/**'` finds the shared
  definition and the draft/verifier call sites; synthesis uses the verifier
  resolver. No direct `resolveRunnerSlot` calls remain in consensus runtime.
- Closeout checks cover interactive dialog behavior, resolver/runtime tests,
  documentation/contracts, TypeScript in web/supervisor/MCP, and MCP build.
  The combined focused run passed 210 tests, including six dialog interactions.
  PostgreSQL tests and the ERD validator require local container/IPC access;
  sandbox listen refusal is an environment boundary.

## Prevention

Admission, preview, and execution must resolve the same role set using the same
inputs. A stricter launch precondition needs a reachable UI assignment path,
not only an error label. Exercise actual select/save/refresh interactions,
including rapid selection reversal, failed save, and failed refresh. Preserve
the distinction between inherited defaults and explicit user choices in audit
provenance.
