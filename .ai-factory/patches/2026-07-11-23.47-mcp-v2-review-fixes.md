**Severity:** high

## Problem

`/aif-review` of the MCP-v2 branch produced 4 blockers + 5 suggestions. While
verifying the fixes, the close-out integration run surfaced TWO further
pre-existing branch breaks (stash-confirmed on branch HEAD, not review findings):

1. `runner-graph.matplan.integration` → 4 tests failing with a NULL
   `materialization_plan` (the node never spawned).
2. `effective.integration` → the agent's platform stdio MCP was withheld when it
   should have materialized.

## Root Cause

- **getDb() bypass (the matplan break).** `materializeNodeCapabilities` and
  `launchRunStaged` both call `loadProjectMcpBindings(projectId)` with **no
  injected db**, so the helper falls back to `getDb()`. Every sibling DB call in
  those functions threads the caller's `db`/`_db` (a transaction or a
  test-injected connection); these three did not. In a vitest worker that does
  NOT globally mock `getDb()`, `getDb()` is a different connection than the
  testcontainer `db` passed into `runFlow` — the query hit a connection with no
  `project_mcp_bindings` table and threw, aborting materialization before the
  plan was written. In prod it is a latent transaction-isolation bug: any caller
  running inside a tx would read bindings on a different connection.
- **Dormant column made load-bearing without assertion migration.** The branch
  made `platform_mcp_servers.trust_status` load-bearing (a `source='platform'`
  MCP now materializes only when a trusted `platform_mcp_servers` row exists,
  read live via `loadPlatformTrustByRef`, fail-closed). `effective.integration`
  seeded a `source='platform'` capability_record but NO trusted platform-server
  row, so the trust join failed closed → withheld.
- **Ledger only half-built.** The requirements ledger aggregated package
  requirement-markers + bindings only; the tested `deriveDeclaredRefs` (which
  also handles enabled-flow-revision `settings.mcps` and attached-agent
  `capability_profile.mcps`) was dead in production, so the board under-reported.

## Solution

- Threaded the caller's connection into all three binding-load sites
  (`loadProjectMcpBindings(projectId, db as never)` / `_db`). Fix verified: the
  matplan 4 went green.
- Wired the two missing ledger sources into `getProjectMcpHub` via a new
  `flowManifestMcpRequirements` extractor (compiles the manifest exactly like the
  launch path) + `deriveDeclaredRefs`; migrated the pure `composeProjectMcpHub`
  test to pass `declaredRefs`.
- Seeded a trusted `platform_mcp_servers` row in `effective.integration`
  (the assertion migration the trust change owed).
- Trust route: added `ACCOUNT_INACTIVE`/`PASSWORD_CHANGE_REQUIRED → 403`
  (mirrors its sibling; `requireGlobalRole` throws both).
- Disconnect/disable: `updateBinding` now skips target/overlay re-validation when
  the binding resolves to disabled (a kill-switch must not require the broken
  dependency it disables).
- Extracted the duplicated flow+agent gate composition into one
  `gateAndOverlayMcpServers` helper; removed the orphaned `gateStdioMcpsByExecTrust`.
- Added a bind-time `target.refId === ref_id` guard (the resolver selects by
  (refId, source), so a cross-ref target was silently ignored); reconciled the
  spec/openapi/analytics `CONFIG→409`-vs-422 drift as a class.

## Prevention

- **Grep every `loadX(id)` against a `getDb()`-fallback helper inside a
  db-injected function** (`materialize*`, `launch*`, any fn taking `db`/`_db` or a
  `tx`): a helper with an optional `injected?` param MUST receive it, or it
  silently opens a second connection. Review checklist: "does this DB call use
  the SAME connection as its siblings?"
- **When a dormant column/flag goes load-bearing, grep every test that seeds the
  now-gated entity WITHOUT the gate row** — the behavior change needs an
  assertion migration in the same branch (fail-closed gates turn silent-pass
  fixtures red). Run the FULL integration suite, not a curated subset, before
  claiming "all green."
- A pure helper that is exported + unit-tested but never called from a
  production path (`deriveDeclaredRefs`) is a red flag that a deliverable is
  only half-wired — grep the export's prod callers during review.
- Integration tests that need a live supervisor (:7777) fail with
  `supervisor unavailable (network): fetch failed`; that is an environment gap,
  not a code break — categorize before chasing.
