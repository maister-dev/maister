# Expose manual Launch only when its client interaction is ready

**Date:** 2026-11-06 17:20
**Files:** `web/components/board/launch-popover.tsx`, existing `web/e2e/platform-agents-binding.spec.ts`
**Severity:** medium

## Problem and evidence

The frozen combined browser lane clicked the visible enabled board Launch opener, but no dialog or launch-options request followed. Its trace contains no launch POST, route refresh or page error in that interval. This does not establish a task-intent or worker race. The click preceded the initial attention/librarian effect requests, which is consistent with hydration still being incomplete; the exact component hydration instant was not recorded.

The opener was enabled in server-rendered markup even though it needs client handlers. Installed HeroUI delegates to React Aria: its Button removes the direct DOM `onClick`, and `usePress` only invokes the physical mouse callback after a corresponding recognized press. A missed pre-hydration pointer press can therefore leave a replayed mouse click inert.

## Solution

Reuse the existing `useIsClient` hook in the opener's disabled condition. The server and hydration render expose an unavailable native button; once the client takes over, the existing readiness/busy/domain conditions determine availability. No authority, admission, settings, confirmation or execution behavior changes.

Extend the existing binding journey rather than adding another launch journey. Hold only the actual delivered JavaScript chunk containing the dialog source marker, independent of its hashed filename. Server markup remains observable. Require its opener disabled, release the barrier in `finally`, join route handlers before removing interception, and continue with one enabled click to the actual dialog/options response. Assert zero intent POSTs before confirm and retain the original exact settings and actual Run-binding checks.

## Prevention

Server-rendered controls that require client handlers should expose their actual readiness. Prove the boundary by controlling JavaScript delivery and exercising the same intentional action afterward; a retry-click or a longer visibility timeout does not restore a lost interaction.
