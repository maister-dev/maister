# Close configuration publication binding, recovery and dialog lifetime gaps

**Date:** 2026-10-30 08:43 UTC
**Files:** `web/lib/db/migrations/0198_project_config_attachment_binding_guard.sql`, migration journal/snapshot, DB integration suite, `project-config-persistence/{repository-lock,repository-fence-claim,mutation-error}.ts`, ownership tests/fixture/inventory, `components/projects/config-persist-{banner,control,dialog}.tsx`, onboarding E2E, EN/RU copy, owning SDD/API/DB/screen/traceability documents.
**Severity:** high

## Problem

A shared install update could commit after a new attachment and accepted review
without advancing the export revision. Ordinary Git actions stranded their fence
on process death, and recovery itself could strand an anonymous claim. A focus
refresh to in-sync (or status-read failure) removed the board's active dialog.
Current specification labels and service references contradicted the implemented
contract. Review controls also bypassed the prescribed UI/diff primitives.

## Root Cause

The install trigger only enumerated attachments visible before the concurrent
binding committed. FK key-share locks do not serialize non-key metadata updates.
Ordinary mutations minted an identity no recovery caller could reproduce. The
adoption mutex relied on finally deleting a directory with no recovery owner;
owner replacement staged partial bytes inside the authoritative directory.
The banner coupled dialog/controller lifetime to transient status presentation.
Existing tests covered sequential install changes, known-ID recovery and Settings
journeys, so their green results did not qualify these missing interleavings.

## Solution

A new migration locks semantic old/new attachment install endpoints with sorted
FOR SHARE NOWAIT before project revision updates. Real PostgreSQL barriers cover
both ordering directions and acceptance during a queued metadata write. Ordinary
mutations use a reserved non-v4 identity; exact configuration IDs remain isolated.
A permanent empty SQLite kernel mutex serializes only adoption and releases on
process death. Replacement bytes stage outside the active owner directory; unknown
files remain untouched. The banner keeps its controller/dialog independent and,
after use, retains the opener until explicit dismissal/navigation. HeroUI controls
and the standard diff renderer preserve exact text review. Canonical documentation
and acceptance mapping describe these as-built boundaries without claiming a new
full-suite or hosted run.

## Prevention

Assert real conflicting lock ownership and resulting revisions, not just sequential
row counts. A recovery lock needs its own process-death semantics; test death
inside recovery as well as the original operation. Test banner and permanent
Settings ownership separately when their mount conditions differ. Close the same
journey with an actual focus assertion. Treat current completion labels as claims
requiring source-specific receipts.
