# A substep session that does not name itself claims the run's

**Date:** 2026-09-15 18:28 (Europe/Moscow)
**Files:** `web/lib/flows/runner-agent.ts`, `web/lib/flows/graph/runner-graph.ts`,
`web/lib/flows/graph/gates-exec.ts`, `web/lib/flows/graph/consensus/runtime.ts`,
`web/lib/flows/graph/consensus/__tests__/runtime.test.ts`,
`web/lib/flows/graph/__tests__/gates-exec.integration.test.ts`,
`web/lib/execution-host/events/__tests__/ingest.integration.test.ts`,
`docs/system-analytics/sessions.md`.
**Severity:** critical

## Problem

A consensus node's second round spawned its draft children and the parent run
never moved again. Its `canonical-session-lifecycle-v1` cursor was poisoned, and
everything behind the poison — including the parent's own
`session.exited (checkpoint)` — was never projected, so the platform still
believed a long-dead session was `active`.

The parent's queue, from the stand:

```
seq    4  created be568944  → projected
seq 1760  created a427da10  → UNIQUE violation, poisoned here
seq 1764  exited  a427da10  → never projected
seq 1771  created 6f53ccf2  → never projected
seq 1775  exited  6f53ccf2  → never projected
seq 1778  exited  be568944 (checkpoint) → never projected
```

## Root Cause

`BoundClient.createSession` defaults `sessionName` to `"default"`
(`execution-host/client.ts:440`), and the flow substeps that spawn a session
beside a node never pass one: consensus verify/synthesize
(`consensus/runtime.ts`) and gate evaluations (`gates-exec.ts`) reached
`runAgentStep` with `sessionName` absent, because the field was OPTIONAL on its
context type. So a throwaway verifier process announced itself as a new
incarnation of the run's main logical session, while that session's own
incarnation was still non-terminal (parked, or checkpointed between nodes).

Two things then go wrong, and the loud one is the symptom of the quiet one:

1. `applyCreateAck` rebinds `run_sessions.default`'s `host_session_id` /
   `acp_session_id` to the throwaway process. The node session's resume handle
   is simply overwritten.
2. `projectCreated` inserts a second non-terminal incarnation on that logical
   session, which `run_session_incarnations_active_run_session_uq`
   (`run_session_id` WHERE state IN `created|active|checkpointed`) refuses. The
   refusal is a raw Postgres error, not an `ExecutionEventProjectionError`, so
   `projector.ts:591` classifies it transient (`type: "unexpected_error"`),
   retries to `MAX_TRANSIENT_ATTEMPTS = 5`, and poisons the cursor. Per
   `CLAUDE.md` §2 nothing unfixable may hold the stream — and no retry could
   ever make this event ingestable.

Nothing retires a same-epoch predecessor. `retireSupersededSessionIncarnations`
retires only `assignment_epoch < current` — epochs are minted for
resume/recover/rework/interrupt re-entries, never for a second session inside
one epoch. That is why resume works and a substep does not.

Widening that retirement to same-epoch siblings was considered and REJECTED: the
node's session is genuinely alive, so marking it `lost` would trade a wedged run
for a silent one that resumes a dead verifier. The projector failure is the
alarm, not the defect.

## Solution

`sessionName` is now REQUIRED on `runAgentStep`'s context (and on
`executeNodeAction`'s, which feeds it). Optionality was the whole defect —
`runner-graph` passed a name and the two substep callers silently did not — so
the compiler now enumerates the call sites instead of a test. It found the third
one (`runner-graph.ts:1704`, `string | undefined`) that a grep would not have.

Each substep names itself, which is the shape the branch-sync AI resolver has
used since ADR-141 (`sync-${claim.attempt}`, `runs/sync-target.ts:1323`):

- gate evaluation → `gate-<gateId>`, stable per gate so a permission resume
  re-binds the same row;
- consensus verification → `<nodeId>-verify-<round>-<ordinal>`, one per
  instance; the ordinal rather than the verifier/target id pair because the name
  is a path segment (supervisor `SAFE_PATH_SEGMENT`, ≤128) built from unbounded
  manifest ids;
- consensus synthesis → `<nodeId>-synthesize`.

## Verification

- RED: the consensus guard reported `[undefined, undefined, undefined]` — all
  three substeps of one node nameless, exactly the fallback.
- GREEN: consensus unit 22/22; `gates-exec` + `ingest` integration 44/44; full
  unit lane; `tsc --noEmit` (web + supervisor), `@maister/mcp` typecheck +
  build, `validate:docs:all` (0 fail), `validate:contracts` (5 aligned),
  `git diff --check`, scoped eslint.
- Falsified individually, each biting only its own case: consensus
  `sessionName: "default"` → `expected [ 'default', 'default', …(1) ] to not
  include 'default'` (21 siblings still green); gate `sessionName: "default"` →
  `expected [ 'default' ] to deeply equal [ 'gate-judge' ]` (23 siblings green).
- The ingest case is self-falsifying rather than separately mutated: one fixture,
  two halves — distinct names project two live incarnations, the same name wedges
  the cursor at `state: retrying / type: unexpected_error` and strands the node
  session's own terminal event.

## Sweep

`rg 'createSession\(|runAgentStep\(' web/lib` (non-test), classified:

- **fixed** — `gates-exec.ts:497`, `consensus/runtime.ts:517` (verify), `:816`
  (synthesize): the three substep producers.
- **already-safe** — `runner-graph.ts:1656` (node dispatch, `nodeSessionName`);
  `runs/sync-resolver.ts:246` (`sync-<attempt>`); `scratch-runs/service.ts:1082,
:1697` (explicit `"default"`, single-session runs).
- **intentionally excluded** — `services/gate-chat.ts:928`: it resumes the run's
  OWN session (`resumeSessionId: activeAcpSessionId`) and must keep binding
  `default`; naming it apart would orphan the handle it is continuing.
  `runs/resume.ts:382`, `runs/recover.ts:394`: same — run-continuing respawns,
  and each mints a fresh epoch, so the epoch retirement already covers them.
  `agents/launch.ts:2183, :2944, :3404`: agent runs are single-session by
  construction (`agents/generation-turn.ts:110` and `turn-claim.ts:128` select
  `sessionName = 'default'`).
- **left alone deliberately** — the `?? "default"` fallback in
  `execution-host/client.ts:440`. Closing it at the client would be the wider
  choke point, but it reaches ~91 call sites across 20 test files whose runs are
  legitimately single-session. The seam that could produce the defect is the
  flow substep seam, and that one is now closed.

## Known consequences

- **Per-session cost attribution moves.** Verifier spend used to arrive labelled
  `default` and was booked to the PARENT's runner — wrong whenever the verifier
  runs a different one, which is the point of consensus. It now arrives under
  the substep's name, whose auto-created `run_sessions` row (written by the
  create ack) carries no runner, so `cost-rollups.ts:213` buckets it as
  `unknown`. Bucketed, never dropped. Correct attribution needs the row
  pre-inserted with its resolved snapshot the way `sync-target.ts:1374` does;
  that belongs with a per-substep cost story, not with a hang fix.
- **`loadActiveRunSession` can now pick a finished substep row** (live handle
  first, then newest `updated_at`) — nothing clears `acp_session_id` when an
  incarnation goes terminal. This is pre-existing and shared with
  `sync-<attempt>`; before this fix the same readers got the same wrong handle
  by clobbering, with the node session's own handle destroyed rather than
  merely outranked.
- **Substep names are reserved by convention, not by the loader.** A flow that
  declared a top-level session literally named `gate-<someGateId>` or
  `<consensusNodeId>-synthesize` would have that substep bind its declared row
  and could reproduce the collision. No character separates the two namespaces —
  `sessionNameSchema` and the supervisor's `SAFE_PATH_SEGMENT` are the same
  `[A-Za-z0-9._-]+` — so enforcement would mean pattern-matching declared keys at
  manifest load. Documented in `sessions.md` instead; a hang fix is the wrong
  place to add a DSL refusal.
- `consensus/runtime.ts:54` has a pre-existing unused `hitlRequests`
  destructure (eslint warning). Untouched.

## Operational note

This fixes the cause, not the stands already poisoned. Each wedged run needs the
rearm AFTER deploy:
`pnpm --dir web execution:projection:rearm --consumer canonical-session-lifecycle-v1 --run <id> --event <last_error.eventId> --cursor <last_run_sequence> --error-generation <last_error.errorGeneration>`.

## Prevention

An optional parameter with a sensible-looking default is how a shared identity
gets stolen quietly. When a value names WHICH durable row a write binds, make it
required and let the compiler enumerate the callers — a grep finds the sites you
thought of.

And when a uniqueness constraint fires from a projector, ask first whether the
write was entitled to that row. The tempting repair is always the constraint or
the retirement rule; here both would have converted a stuck run into a corrupted
one.
