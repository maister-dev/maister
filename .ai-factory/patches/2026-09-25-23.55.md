# ADR-181 option C: a force-push dropped the publication's own commits without a word

**Date:** 2026-09-25 23:55
**Files:** web/lib/runs/publication-guard.ts (new), web/lib/worktree.ts (`remoteOnlyCommitCount`), web/lib/runs/{sync-target,promote,promotion-operation}.ts, web/app/api/runs/[runId]/{sync/route,workbench-lifecycle/route-utils}.ts, web/components/workbench/git-panel{,-kit,-update}.tsx, web/components/runs/{review-panel,run-header-promotion-action}.tsx, web/messages/{en,ru}.json, docs (ADR-181 amendment, branch-sync.md, workbench-git.md, execution-policy.md, error-taxonomy.md, screens/runs/{git-panel,flow-run}.md, ru/manual/07-review.md, web + ext OpenAPI)
**Severity:** high

## Problem

The run git panel made ADR-141's sync reachable from every parked status. Its
push is a force-with-lease on the head read at the time of the update, so a
commit that existed only on the published branch — a reviewer's fixup, a
suggestion committed on the PR — left the branch without anyone being asked.
A squashing PR promotion force-updated the PR branch the same way. The owner
chose option C: every force-push of a run branch counts what it would drop,
refuses before anything moves, and only a human in the git panel may confirm
exactly the head it named.

The first draft of the count had its own false positive, found before the
commit: after an update whose push never landed (the mechanical path keeps the
local rebase on a lease or transport failure), the retry was refused — the
remote's copy of the run's OWN commit counted as the publication's.

## Root Cause

- The lease protects against a remote that moved since it was read; it says
  nothing about what the remote already held when it was read. "Force with
  lease" was read as "safe force".
- The draft recognised the run's own commits by `--cherry-pick` (patch id)
  alone. A clean rebase that shifts a hunk's context changes the patch id, so
  the old copy on the remote no longer matched its rebased twin. Only the
  branch's history of heads knows the old copy was the run's.
- The review panel mapped every promote `CONFLICT` to the merge-conflict card
  ("resolve manually: `git merge --no-ff`"), so the new refusal would have
  shown a remediation that does not apply.

## Solution

- One guard (`assertPushKeepsPublication`) before every forced run-branch
  push. After a fetch it counts commits reachable from the lease head and from
  none of: the pushed result's ref, any head the run branch's reflog records,
  a patch-equivalent of the run's own commit; merges do not count. A lease head
  missing after the fetch is a refusal, never a zero.
- Sync: refused before its claim; only the web route's `expectedRemoteHead`
  confirms, only for the workbench admission, and the push leases exactly it.
  Squash PR promotion: refused before the squash, claim released.
- The reflog replaced a dedicated pre-squash ref from the first draft: it
  already records the head a squash (or an unlanded rebase) replaced.
- Panel: the refusal dialog offers the same update onto the publication first,
  or "Overwrite N commits"; the review panel and header name a refused
  promotion as that, keyed on `details.reason`, never on the code.

## Prevention

- **Ask what a lease does not cover.** A lease pins the head that was read; it
  never tells you what that head contains that you lack. Any force-push needs
  its own answer to "what leaves the remote".
- **Patch identity is not commit identity.** Recognising "our own rewritten
  commit" by patch id fails as soon as a rebase changes context lines. Use the
  branch's reflog (every head it had) and keep the patch match as a fallback;
  degrade to refusing, never to guessing.
- **Test the retry, not only the first attempt.** The false positive lived
  only in "the push failed, the local rewrite was kept, the operator retried"
  — reproduce the kept state directly (rewrite locally, do not push) and run
  the operation again.
- **When a new refusal reuses an existing code, sweep every UI branch on that
  code.** A `CONFLICT` with a new `details.reason` fell into a card written for
  merge conflicts; key the UI on the reason and keep a plain-code control.
- **Drive the recommended way out one step further.** The dialog's primary
  action promises the next update asks nothing; a test now runs that next
  update.
