# Preserve authority and receipts across launch transports and continuations

**Date:** 2026-11-03 17:46
**Files:** `mcp/src/tools.ts`, `web/lib/tasks/launch-token.ts`, `web/lib/tasks/launch-continuation.ts`, `web/lib/tasks/launch-budget-authority.ts`, `web/lib/tasks/launch-budget-restart.ts`, `web/lib/agents/task-retry-authority.ts`, `web/lib/orchestrator/delegated-launch-authority.ts`, `web/lib/orchestrator/launch-operation.ts`, external delegate/plan routes and their existing consumers.
**Severity:** high

## Problem

Adding authoritative launch intents exposed older transports and continuation paths that assumed immediate Run allocation. A nullable queued receipt could be mistaken for a Run, retries could reuse old authority, and an agent whose effective definition drives a Flow could accept session options that the Flow cannot honor. Strict MCP schemas also needed validation before removing transport-only fields.

## Root Cause

The launch policy boundary and the physical execution boundary were previously combined. Several callers derived authority from caller labels or an old Run rather than retaining an immutable accepted decision with a current scoped principal. Existing lifecycle tests skipped acceptance or seeded mutable legacy state after INSERT, so they did not exercise the stricter immutable contracts.

The JSON-schema converter's required-only `anyOf` branch also did not enforce the outer strict-object constraints by itself. Compiled stdio coverage reproduced an unknown authority field crossing that boundary. A strict base-object parse and an explicit task-backed key requirement retain both constraints.

## Solution

Keep token-based automation, parent-derived execution children, and fresh interactive retry decisions as separate closed authority constructors. Revalidate current grants and source proof at acceptance and dispatch. Preserve the first dispatch receipt and frozen input during same-Run recovery; a successor receives a fresh intent. Budget restart stages the displayed versioned request before checkpointing and performs terminalization plus accepted successor handoff atomically.

Delegation uses a bounded idempotency key scoped to token and parent, with separate request identity and body digest. Versioned proof strings hash plan item keys; old SHA-only proofs remain historical. Both HTTP and MCP expose a truthful queued intent with null Run identifiers until actual binding. Required success audits run in the acceptance transaction. Effective Flow facades use the existing Flow option allow-list before creating carriers or intents, and retain package pin, agent activity, branch base and execution policy. Taskless facade requests explicitly require task mode instead of falling into the taskless standalone-agent allocator.

## Prevention

- Trace every launch caller through the authoritative acceptance boundary, including fallback-looking operational branches. The inspected production call sites were `delegate/route.ts`, `plan/route.ts`, and `domain-events/auto-launch.ts`: Flow and code-delivery task arms use server-source intents; operational agents and taskless agent runs retain their separate typed launcher. Never convert operational agents into code delivery.
- Keep transport schema tests at the actual compiled stdio boundary. The twelve stdio cases include forged authority fields, bounded keys, structured refusals and queued child receipts; pure schema mirror assertions do not substitute for transport behavior.
- Keep old lifecycle assertions by explicitly binding their queued intent through the real preparation function. The existing delegation/plan consumer suites exercise real PostgreSQL and Git; raw acceptance, idempotency, authorization and refusal tests bypass that test helper. No fabricated Run IDs or model calls are needed.
- Preserve distinct tests: the failed-budget DOM claim case checks choosing another recovery through preview and confirmation; its route unit checks refusal without consuming HITL under a real session boundary. Same-Run recovery's row-lock barrier checks status changing after navigation. The real facade journey checks both zero-effect refusal and the actual pinned Flow Run binding. These cases cover different boundaries instead of repeating the admission matrix.
- Treat assertion errors as fixture findings until the actual DTO is inspected: child authority nests its parent proof, settings use `baseBranch`, and a recommendation becomes an expanded execution policy at Run creation. Do not change the product contract to satisfy an outdated assertion.
- Preserve structured admission and preparation diagnostics. Never log credentials, source contents, or a raw unknown parser/SQL error to the public transport.
