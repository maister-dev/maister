# Task numbering reconciliation and targeted trigger deduplication

**Date:** 2026-10-29 23:39
**Files:** web/lib/services/tasks.ts; web/lib/social/__tests__/social-domain.integration.test.ts
**Severity:** high

## Problem

Internal MCP task creation repeatedly returned `task insert conflicted but no claim row found for agent undefined / trigger undefined`. Reported production state for project `c8c845d5-174c-495e-90e5-b7d78a3a7576` was `next_task_number=6` with existing task numbers through 7.

## Root Cause

The allocator trusted the counter without checking existing numbers. An unrestricted `ON CONFLICT DO NOTHING` suppressed the resulting `tasks_project_number_uq` violation and interpreted every suppressed conflict as a lost agent/trigger claim. The transaction rolled back its allocation, so retries selected the same occupied number.

The origin of the production counter drift is unestablished. Repository inspection finds one production allocator, six callers, and one numbering migration (`0043_social_board.sql`) that initializes the counter consistently. Commit `cdde05fc7` introduced unrestricted task conflict suppression. Commit `65069923a` introduced E2E seed reconciliation; that test incident does not establish production provenance. Historical production audit evidence is required to establish that origin. The owner handles the production counter repair; this fix has not been deployed.

## Solution

Lock the project with `FOR NO KEY UPDATE`, then read the maximum on a fresh READ COMMITTED statement snapshot. Allocate `GREATEST(next_task_number, COALESCE(MAX(number)+1, 1))` and increment the high-water mark in the same transaction as the task and its activity/event. Never renumber existing tasks or lower a counter ahead of the maximum. Log counter reconciliation with structured fields.

Limit conflict suppression to `(agent_id, trigger_event_id) WHERE trigger_event_id IS NOT NULL`. Map other task-insert unique violations to `CONFLICT` with constraint, SQLSTATE, project, and allocated number; retain the original driver error as the cause. Only the winning insert emits `task.created` and activity.

## Validation

49 integration tests passed on isolated real Postgres containers: the existing social-domain and agent-flow-launch suites. Added cases cover counter 6 with tasks 6/7 allocating 8 unchanged, eight concurrent repairs allocating 8..15, an ahead-of-maximum counter, parallel plus sequential trigger dedup with exactly one task/event/activity, and an unrelated operation unique conflict with allocation/event rollback. Typecheck, scoped ESLint and Prettier passed.

## Prevention

Keep task insertion behind the shared allocator. A counter is a high-water mark and must not move backward. Conflict handling must name the exact idempotency arbiter, never assume all unique violations represent the same claim. Keep production causality separate from fixture precedents.
