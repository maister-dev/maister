# Spec and shipped OpenAPI claimed agent-run prompt coverage the code never had

**Date:** 2026-09-17 09:57
**Files:** docs/system-analytics/run-trace.md, docs/api/web.openapi.yaml, docs/system-analytics/README.md, docs/system-analytics/runs.md, docs/database-schema.md, web/lib/db/schema.ts, web/lib/db/migrations/0170_prompt_dispatch_key.sql, web/lib/execution-host/events/\_\_tests\_\_/run-message-allocation.integration.test.ts, web/lib/flows/graph/\_\_tests\_\_/prompt-record.integration.test.ts
**Severity:** medium

## Problem

The run-trace work (TRC-01..12) shipped a requirement, an edge case and a
client-facing OpenAPI schema all asserting that a dispatched prompt is recorded
as a `user` `run_messages` row **for agent runs**:

- `TRC-05` — "**Every** prompt dispatched to an agent is recorded … for **every**
  prompt-owner variant".
- `EDGE-TRC-03` — "An **agent run's** prompt row has `node_attempt_id = NULL`".
- `web.openapi.yaml` `TranscriptMessage` — "On a flow **or agent run** a `user`
  row carries the prompt dispatched to the agent".
- Plus restatements in `run-trace.md` Purpose + Domain entities, the
  `system-analytics/README.md` index row, `runs.md`, `database-schema.md`, the
  `schema.ts` and migration-SQL comments, and two test-file headers.

None of it was true. A standalone `run_kind='agent'` run records no prompt row,
so a client reading the published contract would wait for a row that never
arrives, and `EDGE-TRC-03`'s test seeded a shape no production writer produces.

## Root Cause

Task T2.5 scoped the recorder to one seam — `recordDispatchedPrompt` is called
from exactly one place, the flow dispatch at `runner-agent.ts:1273`. Standalone
agent runs dispatch through a *different* launcher (`lib/agents/launch.ts`,
`createOwnedSession({variant:"agent", turnId, promptOrdinal})`), which writes no
`run_messages` row at all.

The plan's own analysis had enumerated `agent` as a **seventh** prompt owner
alongside the six flow variants. The implementation correctly covered the six;
the prose was written from the plan's *analysis* rather than from the delivered
seam, so it kept the seventh. `DispatchPromptOwner` is a six-variant union —
the type already said what the contract should have said.

This is the "code lands, docs lie" shape, with an aggravating factor: the drift
was invisible to the suite, because `IT-TRC-05` only ever drives a flow run.
A green suite can only falsify claims someone wrote a test for.

The related trap: `EDGE-TRC-03`'s fixture called `appendRunMessage` directly, so
it looked like coverage of a live agent path while actually being a bare
constraint check. A seed no production writer produces is a hole, not a fixture.

## Solution

Narrowed the contract to what the code does, rather than widening the code:

- `TRC-05` now says *every prompt the flow graph driver dispatches*, names the
  six flow owner variants, and marks standalone agent turns out of scope
  (`Phase 2`, per docs R6).
- `EDGE-TRC-03` now states the true invariant — the dispatch-key index declares
  `nulls not distinct` to stay in step with its sequence-key sibling — and
  records that no flow dispatch produces such a row today, so `IT-EDGE-TRC-03`
  pins the constraint *directly* rather than through a producer.
- `TranscriptMessage` scopes the row to a FLOW run and adds an explicit "two run
  classes carry NO such row, and a client must not wait for one" paragraph
  (standalone agent runs; runs predating the contract).
- Every restatement found by the sweep was corrected to match, including the
  `schema.ts` / migration-SQL justification for `NULLS NOT DISTINCT`, which had
  cited the non-existent agent rows as the reason the clause was load-bearing.
  It is now justified as sibling-parity plus a forward guard.
- Both test-file headers now state the scope boundary, so the next reader does
  not re-derive the wider claim from a test name.

The migration SQL was amended in place only after **recording the premise**: the
dev DB is at `0169` (newest applied `created_at` = 1789393328697),
`prompt_dispatch_key` does not exist there, and integration DBs are fresh
testcontainers — so `0170` is applied nowhere durable. The edit is comment-only;
`CT-TRC-12` filters `-->` lines and still passes.

## Prevention

- **A requirement's scope word must come from the seam, not the plan.** Before
  writing "every X", grep the recorder's production call sites and let the count
  write the sentence. Here one `grep -rn "recordDispatchedPrompt("` excluding
  tests would have produced the correct wording on the first pass.
- **A union type is a scope declaration.** When the contract says "every
  variant" and the code's owner union has six arms while the domain has seven,
  the doc is wrong. Diff the prose's enumeration against the TypeScript union.
- **A test that constructs its own subject proves a constraint, not a path.**
  When a fixture calls the store directly instead of driving the producer, say
  so in the test — otherwise it reads as coverage of a live path. Ask "does any
  production writer produce this row?" before filing an edge case as covered.
- **Sweep the class, not the cited line.** Three artifacts were named in the fix
  request; the sweep found nine. Run the grep, paste the output, and re-run it
  after the edits to prove grep-to-zero.
- **Review question for a docs-bearing feature PR:** for each "every / always /
  any" in a new requirement, which call site enforces it?
