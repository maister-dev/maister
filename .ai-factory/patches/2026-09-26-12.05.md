# ADR-181 Codex review: five ways the git panel lost or misdeclared work

**Date:** 2026-09-26 12:05
**Files:** web/lib/worktree.ts (`writeRescueRef`, `remoteOnlyCommitCount`, `mergeOnlyJoinsItsParents`), web/lib/gc/preserve.ts, web/lib/workbench-git/{service,pull-request}.ts, web/lib/workbench-lifecycle/service.ts, web/lib/runs/{pr-adapter,promote,promotion-operation}.ts, web/components/runs/{review-panel,run-header-promotion-action}.tsx, web/components/workbench/git-panel.tsx, web/messages/{en,ru}.json, the D10 inventory fixture, docs (ADR-181 amendments, workbench-git, branch-sync, reconciliation-gc, workspaces, error-taxonomy, screens/runs/{git-panel,flow-run}, ru/manual/07-review, web OpenAPI)
**Severity:** high

## Problem

The owner's `/codex:adversarial-review` of the ADR-181 branch returned five high
findings, all confirmed in source before any edit:

1. **F1 — the rescue lost staged work.** `writeRescueRef` ran `add -A` over a
   COPY of the index and committed that. A file staged at one version and
   edited to another, or staged and since deleted, was rescued at neither
   version, and the `reset --hard` that follows drops the only index holding it.
   `preserveWorktree` (GC, archive, drop, scratch discard) had the same
   `add -A` before its snapshot.
2. **F2 — the publication guard ignored merges.** `rev-list --no-merges` never
   counted a merge on the publication, so a merge that resolved a conflict or
   carried an edit of its own was force-pushed away with a zero count.
3. **F3 — re-attach handed the tree straight back to the GC.** Re-attach nulled
   `scheduled_removal_at`, so the GC fell back to `ended_at + age`. A tree taken
   for age was due again at once, and the next sweep removed it.
4. **F4 — a PR merged on the provider was pushed to again.** A `pull_request`
   promotion (and so a finalize from `Review`) always pushed and then called
   `createOrUpdatePr`. The adapters list only OPEN PRs, so a merged PR got a
   squash, a push and a second PR attempt.
5. **F5 — the parked finalize bound to the wrong thing.** It compared the LATEST
   PUBLICATION to HEAD. Publishing the next commit to another remote left the PR
   at its old head, and the finalize declared the new head delivered. A merged
   PR whose branch was deleted could not be finalized at all.

## Root Cause

- **F1:** "`add -A` captures everything" is true of the working tree and false
  of the index. The index is a third state, distinct from HEAD and the tree, and
  a rescue that destroys it must record it. The design took "tracked +
  untracked" as the whole of the work.
- **F2:** option C's count was written as "merges author no change of their
  own". That holds only for a merge that is exactly git's merge of its parents,
  and is false for exactly the merges a human makes on a PR (conflict
  resolution, a fixup amended into the merge).
- **F3:** the re-attach reused the reopen write (`scheduled_removal_at = null`)
  without asking what null MEANS to the GC. There it is not "no deadline" but
  "the fallback deadline", which is already past for an old run.
- **F4/F5:** both paths reasoned about the local and published branch as a
  stand-in for the PR. The PR is a provider-side object with its own head and
  state. `createOrUpdatePr`'s open-only search, and a publication that can move
  elsewhere, make that stand-in wrong exactly when the PR has moved on.

## Solution

- **F1:** `writeRescueRef` writes the index tree before `add -A` (null for an
  unmerged index, which has no tree). When it differs from both HEAD's tree and
  the rescued tree, it becomes a commit on HEAD and the rescue's second parent
  (`<ref>^2`). `preserveWorktree` writes a rescue ref first when a path is both
  staged and changed again (the only case its snapshot overwrites).
- **F2:** remote-only merges are listed separately and each counts unless it has
  two parents and `git merge-tree --write-tree` of them yields its tree. A
  conflict, an octopus, or a git older than 2.38 counts: refuse, never guess.
- **F3:** `recordReattached` writes, in the same single CAS statement, a fresh
  `now + MAISTER_GC_AGE_DAYS` for a run the GC collects (Done/Abandoned/Failed)
  and null otherwise. A window written on a Review/Crashed run would carry into
  a later `Failed` (which stamps none) and cut it short, and a test pins that
  negative too.
- **F5:** `getPrState` reports `headSha` for all providers. The new
  `readRecordedPullRequest` shares Open PR's provider resolution and classifies
  every non-answer as a refusal, never a state. The parked finalize binds to the
  PR's head: `pr_closed` / `publish_stale` / the new `merged_pr_behind` (EN/RU).
- **F4:** `finalizeMergedRecordedPullRequest` runs after the promotion claim in
  BOTH apply sites (`promoteWorkspaceRun` before the forced-push guard and the
  squash, and `promoteScratchRun`). Merged at HEAD: finalize as it stands.
  Merged elsewhere: `merged_pr_behind`, claim released. Unreadable while the
  scan saw it merged: EXECUTOR_UNAVAILABLE, nothing pushed. The review panel and
  the header's Promote name the refusal.

Every fix went red first and was falsified (mutants for both directions of F2,
the naive always-fresh F3 window, the old publication check for F5, each
classification branch of the PR read, each F4 call site and the head check).

## Prevention

- A rescue before a destructive reset must enumerate ALL THREE states (HEAD,
  index, tree) and test the one where index differs from both.
- A "this kind of commit authors nothing" exclusion needs a PROOF per commit
  (here `merge-tree`), not a rule about the kind.
- Before writing NULL to a column a sweeper reads, grep the sweeper's predicate:
  NULL may select a fallback, not "never".
- A delivery claim (finalize, promote) binds to the provider-side object it
  names (PR number → its head and state), never to a local stand-in for it. List
  every apply site of the shared side effect (`rg promotePullRequestSideEffect\(`),
  since the scratch twin reached it through a second early return.
