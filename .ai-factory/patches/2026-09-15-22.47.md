# `acp_session_id IS NOT NULL` is not liveness — a dead substep outranked its node

**Date:** 2026-09-15 22:47
**Files:** web/lib/runs/active-run-session.ts,
web/lib/runs/__tests__/active-run-session-ranking.integration.test.ts (new),
web/lib/runs/__tests__/{resume-driver,resume-recovery}.test.ts,
docs/system-analytics/sessions.md
**Severity:** medium

## Problem

`activeRunSessionScalar` (and `loadActiveRunSession` / `loadActiveRunSessionsByRunId`)
ranked a run's ACTIVE session `ORDER BY (acp_session_id IS NOT NULL) DESC,
updated_at DESC` and called that "live-handle-first". A FINISHED consensus
verification or gate evaluation therefore outranked the node's own session: it
keeps its handle and carries a newer `updated_at`.

Roughly twenty consumers read that answer, and they are not all cosmetic —
`runs/resume.ts:144` takes the `session/resume` handle from it, plus
`recover.ts`, `resume-driver.ts`, `keepalive-sweeper.ts`, `reconcile.ts`,
`services/hitl.ts` and `gate-chat.ts`.

Proven on real Postgres before any edit (seeded in a transaction, rolled back):
with a node session bound 10 min ago, `checkpointed`, handle `acp-node`, and a
verify substep bound 1 min ago, `exited`, handle `acp-verify` — the old ORDER BY
returns `ztest-verify-1-0 | codex`, the new one returns `ztest-node | claude`.

## Root Cause

`acp_session_id` is the **checkpoint handle**, not a liveness flag. It is
written once by the create ack and deliberately OUTLIVES the process — that is
the whole point of ADR-114 / checkpoint-resume: the adapter's session file
survives the parent's death so `session/resume` can restore context. Nothing
clears it when an incarnation goes terminal, and nothing should.

So the predicate really means "has been prompted at least once / is resumable",
and ranking on it sorts *resumable* sessions first rather than *live* ones. The
second key could not save it: `updated_at` is bumped only by the create ack
(`create-ack.ts:131` is the only `.update(runSessions)` in production code), so
it records "when this session was last bound", and a substep is always bound
later than the node it runs beside.

Before commit `508be005` the bug was masked — substeps reused `default` and
clobbered that row, so there was only ever one row to choose from. Naming
substeps separately did not create the defect; it made it observable.

**My own first proposed fix was wrong** and worth recording: "clear
`acp_session_id` when an incarnation goes terminal". That would have broken
checkpoint/resume outright — `resume.ts` fails the run terminally on a null
handle. The column was never the problem; the predicate reading it was.

## Solution

Rank on the incarnation ledger, which already models liveness exactly: a
non-terminal `run_session_incarnations` row (`created | active | checkpointed`),
the same state set as the partial unique index
`run_session_incarnations_active_run_session_uq`, so at most one per session.

    EXISTS (... rsi.state IN ('created','active','checkpointed')) DESC,
    (rs.acp_session_id IS NOT NULL) DESC,
    rs.updated_at DESC

Three keys, in that order, shared by all three selectors (the correlated-scalar
form aliases the row `rs`; the query-builder form addresses real columns, so the
fragment is parameterized by the session-id reference).

Keeping the handle as the SECOND key is load-bearing, not decoration: within the
live class a `checkpointed` session holding a handle must still beat a
freshly-`created` one that has none, or idle resume reads a null handle and
fails the run terminally. `checkpointed` being non-terminal is likewise what
keeps `NeedsInputIdle` resume working. And a LIVE substep still outranks its
node — correct, because that is exactly what a permission HITL is blocked on.

`loadActiveRunSession` collapsed from two queries to one, and the batch variant
lost its hand-rolled merge rule: rows arrive ordered, so first-per-run wins.

## Prevention

- **Name the predicate, then check the name is true.** The comment said
  "live-handle-first" and the code said "has ever been initialized". Whenever a
  boolean column is used as a proxy for a lifecycle state, ask what clears it —
  if nothing does, it is a watermark, not a state.
- **A column that must survive process death cannot double as a liveness flag.**
  Resume handles, idempotency keys and audit ids are all in this family.
- **Prove a ranking change against real data, both directions.** A stubbed db
  cannot evaluate a correlated `EXISTS`; the ordering was confirmed by running
  the generated SQL on Postgres and by falsifying the new test (reverting the
  ORDER BY makes it fail with `expected 'plan_consensus-verify-1-0' to be
  'default'`). The "live substep still wins" case passes under BOTH orderings —
  that is what shows the fix did not overshoot.
- **Adding an import to a widely-imported module breaks partial `vi.mock`s of
  it.** `runSessionIncarnations` in `active-run-session.ts` failed 14 tests
  across `resume-driver` / `resume-recovery`, which mock `@/lib/db/schema`
  member-by-member. The failure is a module-load error, so the whole file dies
  at once — correct the mock, never the module.
- When changing a selector this widely consumed, run the integration suites that
  depend on the behavior, not only the unit lane: `reconcile-sweep`,
  `persistent-park`, `gate-permission-resume`, `gate-chat` are the ones that
  would have caught a resume regression.
