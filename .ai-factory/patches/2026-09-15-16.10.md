# A session's stepId is a label, not the run's node cursor

**Date:** 2026-09-15 16:10 (Europe/Moscow)
**Files:** `web/lib/flows/runner-agent.ts`, `web/lib/runs/keepalive-sweeper.ts`,
`web/lib/reconcile.ts`, `web/lib/runs/__tests__/time-limit-watchdog.integration.test.ts`,
`web/lib/__tests__/reconcile-sweep.integration.test.ts`.
**Severity:** high

## Problem

Two sweeps that terminalize runs resolved "is this run's agent still alive?" by
matching a supervisor session's `stepId` against `runs.current_step_id`. For a
consensus substep the session is labelled `<node>-verify` / `-synthesize`
(`consensus/runtime.ts:528`, `:819`) and for a gate it is the gate id
(`gates-exec.ts:340`, `:434`), neither of which equals the node cursor. The
lookup therefore missed a LIVE session and both callers read the miss as
"confirmed absent":

- `keepalive-sweeper.ts` max-duration pass — marks the run `Failed`, nulls the
  cursor, fails the attempt, promotes a queued run, all while the agent keeps
  running and spending. The file's own comment calls this the split-brain it
  must avoid.
- `keepalive-sweeper.ts` budget pass (`boundLiveSession`) — same, and it is NOT
  behind an opt-in cap, so it is reachable on any run with a budget.
- `reconcile.ts` — the `liveRunStepSession` guard, whose entire purpose is to
  stop a false `agent-session-gone` crash of a live long-running node, could
  never fire for these sessions.

Separately, `runner-agent.ts` wrote `currentStepId: pctx.stepId` on a permission
pause, stamping the SESSION's label into the run's node cursor — after which
every node derivation (`resolveCurrentNodeKind`, `resolveNodeRecoverInfo`,
`maxDurationMinutesFor`) resolves nothing and the admission fences that compare
`runs.current_step_id` to `node_attempts.node_id` throw or supersede.

## Root Cause

`stepId` was treated as an identity when it is a per-prompt LABEL. The host
overwrites it on every prompt (`supervisor/src/http-api.ts:1133`), and it is
used host-side only for cost attribution, the gate-chat marker, the run-dir
derivation and logging — `host-state.ts` and `registry.ts` never index on it.
Nothing ever guaranteed it equalled the cursor, and five producers deliberately
set something else. The two sweeps nevertheless keyed on it, so the miss
direction — the one that kills a working run — was the default for gates,
consensus substeps, and any run whose last prompt relabelled the record.

The repo had already reached the opposite conclusion twice, in
`session-teardown.ts:56` and `workbench-lifecycle/service.ts:1628` ("never
narrow by stepId, which would spare a live session of a different node"); the
two sweeps simply predate it.

## Solution

- `liveSessionFor` matches the run's live session by `runId` alone. Both callers
  are terminating the WHOLE run, so its live session is theirs to tear down
  whichever node it belongs to.
- The reconcile in-flight guard keys on `runId`. Over-matching costs a skipped
  tick; under-matching kills a working run.
- The permission pause no longer writes `currentStepId`. The cursor belongs to
  the graph runner, which stamped `node.id` before dispatch; `keepaliveUntil`,
  the reason that `.set()` exists, is untouched.
- The producers are deliberately LEFT ALONE: `stepId` keeps its real jobs (cost
  attribution, logs, the `gate-chat-` marker the supervisor parses back). It
  simply stops being a match key.

## Verification

- RED: both new cases failed for the stated reason; 44 existing cases passed.
- GREEN: watchdog + budget + reconcile suites 93/93; gate-permission 6/6.
- Falsified individually, each biting only its own case: narrowing
  `liveSessionFor` back to a label → `expected "spy" to be called 1 times, but
  got 0`; keying the reconcile guard back on the label → `expected 'Crashed' to
  be 'Running'`.
- Sweep (the grep this rule requires, with its classification):
  - producers `gates-exec.ts:340,:434`, `consensus/runtime.ts:528,:819,:1044`,
    `agents/launch.ts` ×5 — **intentionally excluded**, labels by design.
  - consumers `reconcile.ts:1362` — the index survives but has no `.get`
    left; only `.values()` iterations consume it and they filter by `runId`.
  - consumer `sync-recovery.ts:595` (`r.stepId === SYNC_STEP_ID`) —
    **already-safe**: closed producer/consumer pair (`sync-target.ts:1407` sets
    the same constant) that never compares against the cursor.

## Known gap — the cursor fix is NOT pinned by a test

The guard written for it was VACUOUS: with the defect restored, the gate suite
still passed 6/6, because that fixture's pause is re-stamped with `node.id` by
`runner-graph.ts:4733` before the assertion runs. A test that passes on the
broken code is worse than none, so it was removed rather than kept for comfort.
The change stands on the argument that the cursor belongs to the graph runner;
pinning it needs a fixture where a consensus substep takes a permission pause.

## Prevention

Before keying a lookup on a field, ask who WRITES it and whether anything
guarantees the equality you are assuming. Here the writer was the host, on every
prompt, with five producers free to send anything. And when a lookup can be
wrong in both directions, pick the direction whose failure is survivable: this
one chose "declare a live agent absent, then terminalize".

Falsify every new guard. Two of the three here bit; the third did not, and only
running the test against the restored defect revealed that.
