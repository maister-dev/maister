# OpenAPI rejected the app's own requests — twice, same class

**Date:** 2026-07-16 15:20
**Files:** docs/api/web.openapi.yaml, docs/configuration.md
**Severity:** high

## Problem

`/aif-verify` on the ADR-139/140 branch surfaced two blocking spec drifts, both
introduced or missed by the immediately-preceding `/aif-fix` session:

1. `POST /api/runs/{runId}/activity` gained `requireActiveSession` +
   `requireProjectRole`, so it now returns 401/403 via `httpStatusForAuthz`. The
   spec documented only 204/400/404/409/410, and its prose never mentioned auth.
2. `ProjectSettingsPatchBody` is `additionalProperties: false` and lacked
   `syncStrategyDefault` / `syncRunnerId`, which `settings/route.ts:61-62`
   accepts and `project-git-settings-control.tsx:74` actually PATCHes — the spec
   rejected the request the UI sends.

Defect 2 is the EXACT class of review finding #7 (`PromoteRunBody` missing
`autoFinalize`), which the same session had just fixed.

## Root Cause

Not "forgot to update the spec". The real cause is that **the fix session took
the review's finding list as the scope of the defect** rather than as one
instance of it. #7 named `PromoteRunBody`; the session fixed `PromoteRunBody`,
recorded "spec rejects the branch's own request" as the lesson, and never
grepped for the other `additionalProperties: false` bodies on routes the same
branch had changed. The skill-context rule for exactly this ("fix the CLASS, not
the cited line, and RECORD the grep in the fix close-out") was quoted in that
session's own patch — and still not executed as a grep.

Defect 1 has a sharper cause: the session added auth to a route and reasoned
carefully about the CLIENT consequence (it noticed `use-activity-ping` doesn't
stop on 401/403 and fixed that), but never asked what the *contract* consequence
was. Adding a guard to a route changes its status-code surface, which is a spec
edit — the client sweep and the spec sweep are the same thought, and only one
half ran.

Nothing in CI compares routes to the spec, so both defects were invisible until
a human-driven gate looked. This class has now shipped twice and been caught
twice by review/verify — i.e. the process works and the automation is missing.

## Solution

Both fixed in the spec (code was correct in both cases — "code wins"):

- `/activity`: added `401`/`403` via the house `$ref` idiom
  (`components/responses/Unauthenticated` / `Forbidden`, mirroring `/sync`), and
  rewrote the prose to state that auth runs BEFORE the run lookup (so the
  404/409/410/204 shapes cannot be a status oracle), that membership is checked
  on the server-derived `runs.project_id`, that the column is nullable, and that
  the endpoint is a state-changing write.
- `ProjectSettingsPatchBody`: added both fields with their real nullability —
  `syncStrategyDefault` NOT nullable (the column is NOT NULL; "clear" = back to
  `rebase`), `syncRunnerId` nullable (null CLEARS the override).
- `configuration.md`: `MAISTER_PROMOTION_CLAIM_TIMEOUT_SECONDS` claimed it was
  read only by `promoteRun`; it is also read by `canReclaimLifecycle` and now
  derives the ADR-140 sync heartbeat at `window / 4`, so lowering it makes a live
  sync beat proportionally more often. Operator-visible, so it belongs in the
  env table.

The fix ran the class sweep the previous session skipped, mechanically and in
both directions, over every route the branch changed:
- **Class A** (zod `.strict()` field ⊄ spec properties): 1 instance
  (`ProjectSettingsPatchBody`). `PromoteRunBody` clean; both sync bodies inline
  and complete.
- **Class B** (route returns 401/403, spec omits them): 1 instance (`/activity`).
  `/sync`, `/reopen`, `/promote`, `/settings` all document theirs.
No hidden siblings. Also proved all 262 internal `$ref`s resolve, since a
dangling ref is the obvious way to "fix" a spec into being broken.

## Prevention

- **A review's finding list is a sample, not a census.** When a finding names a
  schema/route/field, the unit of work is every peer reachable by the same grep.
  Write the grep, run it, and paste its output into the close-out — "I swept it"
  is not a sweep. The rule existed, was quoted, and was still not executed:
  treat "fix the class" as a command that must produce a command.
- **Adding auth to a route is a contract change.** Any guard that can refuse
  (`requireActiveSession`, `requireProjectAction`, a new zod refinement) adds
  status codes. Grep the route's spec entry in the SAME edit — the client-side
  and spec-side consequences are one thought.
- **`additionalProperties: false` turns a missing property into a rejected
  request**, so an omission is a break, not a doc gap. Every `.strict()` zod body
  has exactly one spec schema; they are a pair and must be edited as one.
- **The guard that would have caught both is mechanical**, and the data says it
  is cheap: 83/85 `.strict()` routes are already specced. Spawned as a follow-up
  task rather than smuggled into this fix. Note the mapping trap: `/api/v1/ext/*`
  is specced in `operations.openapi.yaml`, everything else in `web.openapi.yaml`
  — using one file yields 20 false positives.
- **Verify earns its keep on the diff's contract surface, not the plan's.** The
  plan's docs list named neither of these; both were found by enumerating the
  routes the diff touched and asking what each one's spec says.
