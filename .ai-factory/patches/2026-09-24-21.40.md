# Two throws out of the reconcile sweep: a lock-order deadlock and an unguarded host offer

**Date:** 2026-09-24 21:40
**Files:** web/lib/runs/turn-lost-boundary.ts, web/lib/reconcile-evidence-db.ts, web/lib/runs/__tests__/turn-lost-boundary.integration.test.ts, web/lib/__tests__/reconcile-host-evidence.integration.test.ts, docs/decisions/adr-177.md, docs/system-analytics/{reconciliation-gc,execution-prompt-lifecycle}.md
**Severity:** medium

## Problem

`runReconcileSweep` runs candidates through a `Promise.all`-based `runWithConcurrency`, so any candidate that throws rejects the whole pass; every other candidate then waits a scheduler tick. Two evidence-arm paths could throw:
1. `applyTurnLostBoundary` deadlocked with the flow owner's own lost-turn arm on the same turn — Postgres `40P01` "deadlock detected … while locking tuple in relation runs", reproduced deterministically for both the node and the gate path.
2. `resolvePromptEvidence` offered a stream-lost turn to `reconcilePromptCommand` with no catch; a receipt read failing with an error the transport classifier does not retry (e.g. a `PRECONDITION`) was rethrown.

## Root Cause

1. Two writers of one turn took the same rows in opposite orders. Every owner apply locks run → assignment → session → attempt → gate evaluation (`lockFlowPromptOwner` → `lockCurrentSessionAssignment`, "run-first locks"). The boundary locked the gate evaluation and the attempt first and reached the run only inside `crashRunningRun`. The boundary was written as "the three writes in one transaction" and reviewed for atomicity, never for lock ORDER against its concurrent peer.
2. The resolver's probe had been written to never throw ("a transport blip must never crash a run"), but the offer added later (D-B7) went through a function whose contract is to rethrow non-retryable transport errors to its callers. The new caller inherited a throwing contract it could not afford.

## Solution

1. The boundary's first statement is `SELECT … FROM runs WHERE id = $run FOR UPDATE` (schema read lazily, like `gateResults`, so partially mocked schemas keep importing the module). Both writers now queue on the run row. No 40P01 mapping was added: the order fix removes the cycle rather than papering over it.
2. The offer is `.catch`ed like the probe: WARN `reconcile-evidence-host-offer-failed` with a bounded `causeCode`, no settlement, and the round-2 verdict rule decides from the row (`getCommand` when the offer returned nothing).

Tests: a second pg connection replays the owner's order (run FOR UPDATE, wait until the boundary blocks on the run in `pg_stat_activity`, then attempt/gate FOR UPDATE) — red with 40P01 before, green after, red again with the run lock removed. A fake-host hook fails only the offer's receipt read — red (rejects) before, green after, red again without the catch.

## Prevention

- Every writer that can race an existing writer on the same rows must take the peer's lock order; grep the peer's lock helper (`lockCurrentSessionAssignment` is run-first) before adding `FOR UPDATE`s. A two-connection test that replays the peer's order and waits on `pg_stat_activity` makes a deadlock deterministic.
- A function called from a per-candidate sweep loop must not throw on anything the host or a peer can cause. When a sweep gains a new call into a module whose contract is "rethrow to the caller", wrap it at the call site with the same never-throw rule as its siblings.
- Flag: `runWithConcurrency` in `reconcile.ts` still lets any unexpected per-candidate error reject the pass; per-candidate isolation there is a separate decision.
