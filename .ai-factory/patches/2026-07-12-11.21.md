# Branch gate blockers + agent-L2 settings crash-window (review-fix pass)

**Date:** 2026-07-12 11:21
**Files:** supervisor/vitest.workspace.ts, web/lib/agents/dirty-watchdog.ts, web/lib/capabilities/settings-ownership.ts, web/lib/flows.ts, web/lib/agents/__tests__/dirty-watchdog.test.ts
**Severity:** high

## Problem

Three defects on `feature/agent-runner-parity-package-skills-hardening`, found by
`/aif-review` and confirmed by running the pinned toolchain directly:

1. **Supervisor test suites could not load.** `adapter-smoke-cache.test.ts`,
   `smoke-acp-adapter-script.test.ts`, and `lifecycle.integration.test.ts` each
   loaded 0 tests with `Error: Failed to load url sqlite (resolved id: sqlite)`.
2. **Web `pnpm typecheck` was red** — 3 errors in `web/lib/flows.ts` (302/365/376):
   `Buffer` not assignable to `Uint8Array` on `writeFile`/`Buffer.equals`.
3. **Agent-L2 read-only settings crash window.** `materializeAgentReadOnlySettings`
   wrote the settings file before its ownership marker, so a crash between the two
   writes orphaned a MAIster-created `.claude/settings.local.json` with no marker;
   terminal/GC cleanup then preserved it (uncommitted lease) and future runs
   mislabeled it as user-owned.

## Root Cause

1. `supervisor/src/adapter-smoke-cache-lock.ts` imports `node:sqlite` (Node 26
   builtin). The lockfile-pinned Vite 5.4.21 predates `node:sqlite` in its builtin
   list, so its resolver strips the `node:` prefix and vite-node then fails to load
   bare `sqlite`. `server.deps.external` does not help because vite-node still
   transforms the resolved id.
2. TS 5.6 tightened the iterator lib (`ArrayIterator` with `map`/`filter`/`take`/
   `drop`), but `@types/node@20.9.0` (the pinned version, from before TS 5.6)
   declares `Buffer.entries()` as `IterableIterator`. So `Buffer` is not assignable
   to the lib `Uint8Array`. The branch's new schema-copy code is the first to write
   a `Buffer` (from `readFile` with no encoding), so it is the first to trip a
   latent toolchain-pin incompatibility. Runtime was always correct.
3. Ownership attribution depends on a durable marker, but the marker was written
   *after* the settings file. The journaled capability-settings path already writes
   its operation record before mutating; the agent-L2 path had no equivalent
   ordering or reclaim, so its crash window produced an un-attributable artifact.

## Solution

1. Resolve `node:sqlite` to a virtual module (`enforce: "pre"` Vite plugin) that
   pulls the real builtin via `createRequire` at runtime — Vite only ever
   transforms `node:module`, which it does recognize. Applied to both workspace
   projects. Production is unchanged (imports `node:sqlite` directly on Node 26).
2. Coerce `Buffer` -> `Uint8Array` (`Uint8Array.from(...)`) at the 3 `writeFile`/
   `equals` sites in `flows.ts`. Byte-identical, behavior-neutral.
3. Write the agent-L2 marker **before** the settings file (invariant: a MAIster
   settings file never exists without its marker), and add
   `reclaimAgentL2Settings` (lock-guarded, marker-attributed) so terminal/GC
   cleanup removes this run's orphan even when the lease never committed. An
   agent-L2 marker proves MAIster created the file, so the reclaim can never touch
   user content; a foreign marker is left for its own run.

## Prevention

- A new `node:*` builtin import must be verified under the *pinned* Vite, not just
  Node — the builtin list is version-bound. Externalization config alone is not
  enough; a resolve-to-virtual-module shim is the deterministic escape hatch.
- When a branch's toolchain is pinned below a types/lib boundary (TS 5.6 +
  `@types/node` < 20.14), any first use of `Buffer`-typed `fs` data trips latent
  errors. Run `pnpm typecheck` on every branch that adds binary `readFile`/
  `writeFile` flows, not only string writes.
- Any single-owner filesystem artifact that gates cleanup must write its ownership
  marker **before** the content it guards, and expose a marker-attributed reclaim,
  so a crash mid-write leaves an attributable (removable) artifact rather than one
  mislabeled as user-owned. Mirror the journaled capability-settings discipline.
- A "suite is green" claim requires the suite to actually *load*; a 0-test suite is
  a failure, not a pass.
