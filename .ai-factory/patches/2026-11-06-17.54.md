# Prove launch readiness without a JavaScript interception fixture

**Date:** 2026-11-06 17:54
**Files:** existing bound-agent and task-launch-gating browser owners; R22 acceptance description
**Severity:** medium

## Problem

The complete browser lane exposed two fixture failures after the product's client-readiness guard was added. The binding journey's JavaScript delivery interceptor still produced `Route is already handled` despite joining handlers during removal. The RU keyboard journey attempted `focus()` while the opener was legitimately disabled during hydration, so later enabling did not restore that lost focus action.

## Solution

Remove the interception fixture entirely. Within the existing binding journey, create a scoped browser context using the existing authenticated storage state and configured base URL, with JavaScript disabled. Check the actual serialized native Launch button and close the context in `finally`. Next's streaming protocol keeps some markup in a hidden boundary pending inline reveal JavaScript, so this serialized-markup check deliberately includes that hidden button; it does not claim a visible usable no-JavaScript application.

The normal interactive page remains the proof of visible, enabled, single-click launch: it loads real options, sends no intent POST before confirmation, and preserves all original settings/receipt/actual-binding checks. The existing RU journey now awaits the opener's enabled state before `focus()`, retaining the original focus, Enter, initial dialog focus and focus-restoration assertions. No product source, authority, timeout or retry policy changes.

## Prevention

Prefer direct browser capability controls over intercepting compiled application modules. Separate inspection of serialized server markup from visible client interaction, and await actual interactivity before issuing keyboard focus commands.
