# Assignment cancel: precondition before stop, Review as stopped, unstoppable runs

**Date:** 2026-11-15 08:08
**Files:** web/lib/specialist-assignments/{controls,store,pages,workspace-view}.ts, web/components/specialist-assignments/{assignment-lifecycle,assignment-work}.tsx, web/app/(app)/specialist-assignments/{page,[assignmentId]/page}.tsx, web/lib/http/bounded-json.ts, web/lib/api/private-json.ts, docs/api/{web,external/operations}.openapi.yaml, docs/system-analytics/{specialist-assignments,company-brain-specialists-traceability}.md, docs/screens/specialist-assignments.md, scripts/validate-requirement-coverage.test.mjs, .ai-factory/qa/.../T43/release-candidate.json
**Severity:** high

## Problem

`cancelAssignmentExecution` (from the previous fix round) stopped linked Runs
before it checked whether the assignment could be cancelled at all. A
completed or failed assignment with a live linked Run had that Run stopped, and
then the request answered 409. Separately, every `CONFLICT` from the stop was
swallowed and reported as 202 "stopping". Worse: the project flow operator
stop parks a Run in `Review`, which the shared guard counted as unsettled, so
cancelling any assignment linked to a project flow Run answered 202 forever.
The previous round's mocked-stop test (it set the Run to `Abandoned`) hid this.

## Root Cause

- The terminal-state check lived only in the store's cancel transaction, which
  runs after the side effect. The two-phase split copied the revision and
  authority checks into phase 1 but not the state verdict.
- "Settled" was one predicate (`isTerminalRunStatus`) shared by input changes,
  reopen and cancel, but cancel only needs execution stopped. The real stop
  contract (`stopFlowAfterAuth` → `Review`) was never exercised in a test.
- The catch treated every `CONFLICT` as "another owner is tearing it down",
  but `stopWorkbenchRun` also uses `CONFLICT` for "this status cannot be stopped".

## Solution

- `assertAssignmentCancellable(status)` is the single verdict. Both phases call
  it, and phase 1 calls it before any stop.
- `assertNoUnsettledAssignmentRuns(..., "stopped")` for cancel accepts
  `SETTLED_RUN_STATUSES` (terminal + `Review`). Input and reopen keep `terminal`.
  The owner chose this: the Review diff stays for a human decision.
- Only `company_stop_owned` / `budget_termination_pending` count as settling
  teardown (202). Any other `CONFLICT`/`PRECONDITION` stop refusal that leaves a
  live Run becomes `409 assignment_run_unstoppable`, shown with its own EN/RU copy.
- Input and continue resolve visibility before the revision lock (hidden 404).
- Also in this round: the successor picker filters by target in SQL before the
  LIMIT, the Verify button is computed per operation (it needs retained input
  access), work limitations are codes, all enabled targets load, one JSON body
  reader remains, and `enabledOnly` is documented.
- The previous round's canonical-SQL generator was missing from the
  filesystem-ownership inventory (`runtime-data-boundary-inventory`). It is now
  classified as build tooling.
- Post-qualification spec edits are declared in the T43 manifest
  (`postQualificationAmendments`) instead of rewriting the qualified digests.

## Prevention

- When splitting a guarded mutation into validate → side effect → commit, move
  the WHOLE verdict (state, not just revision/authority) into the validate phase
  through one shared function.
- Test cancel-like flows with the stop's REAL resulting status (flow → Review),
  not a mock that jumps straight to terminal.
- Never classify an overloaded error code (`CONFLICT`) as one meaning. Allow-list
  the reasons that mean "retry later".
- Run `validate:docs:all` (not just `validate:docs`) before claiming the docs
  gates pass: the T43 manifest test pins spec digests, and the previous round
  broke it without noticing. Run the FULL unit lane too: the inventory test
  catches any new `node:fs` callsite, which a focused run misses.
