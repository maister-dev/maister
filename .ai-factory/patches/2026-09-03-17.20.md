# Two safety controls made unreachable by a root-identity convention

**Date:** 2026-09-03 17:20
**Files:** web/lib/runs/keepalive-sweeper.ts, web/lib/scheduler.ts, web/lib/tasks/admission-selector.ts, web/lib/runs/cost-rollups.ts, web/lib/run-results/{collect,ledger}.ts, web/lib/runs/run-result-dto.ts, web/lib/evaluations/objective/{providers,tree-source}.ts
**Severity:** high

## Problem

An adversarial review found five defects that a normal review, a self-review and
a green suite had all passed over. Two were advertised safety controls that
could never fire in production:

1. The ADR-101 tree budget watchdog gated on `candidate.rootRunId ===
   candidate.id`. No production run satisfies that, so token, wall-clock and
   consecutive-failure budgets could not terminate a runaway recursive tree.
2. The per-parent active-children cap read `ref.parentRunId` on the
   `promoteNextPending` edge, but the candidate mappings never set it — so a
   queued child could be promoted past a saturated parent.

Plus: the Lab's consumption metric scored a self-report alone (gameable) over a
denominator including grandchildren the root could never collect; the collect
marker could stamp a revision the caller never received; and the run inspector
could render a payload under a status saying no result was available.

## Root Cause

**One convention, misread three times.** The launchers write `rootRunId =
parent.rootRunId ?? parent.id`, so a DESCENDANT carries the root's id and the
ROOT ITSELF carries NULL. Nothing self-stamps a root. Three separate readers
encoded `rootRunId === id` as "is this the root" — a predicate that is only ever
true in test fixtures that build the row by hand. I had already fixed this in
`getRunTreeCostSummary` a round earlier and still missed the two other
instances, because I searched for the SYMPTOM (a tree query) rather than the
PREDICATE.

**Tests that assert the fixture, not production.** The tree-budget test seeded
`rootRunId: rootId` on its root. It passed for years describing a shape the
system never produces.

**A type that let a required field be forgotten.** `ref: {...} & Record<string,
unknown>` meant `ref.parentRunId` type-checked as `unknown` while nothing set
it. The guard compiled, ran, and was dead. My own review had checked that the
call site EXISTED, not that its input was ever populated.

**A spec that contradicted itself.** `evaluations.md` said the consumption
measure is "the intersection of an engine marker and a self-report — either
alone is gameable" in prose, and "self-report ∩ valid" in its table. The code
followed the table. I wrote both.

## Solution

- Rootness is now PARENTAGE (`parentRunId === null`) plus `hasDescendants`, so
  an ordinary childless run does not gain a second ceiling.
- `queryRunTreeTokens` scopes `id = root OR root_run_id = root`. This had been
  deferred as pre-existing; that deferral did not survive making the gate
  reachable.
- `parentRunId` is a NAMED field of the admission ref, so omitting it is a
  compile error.
- The consumption metric requires BOTH signals; both ratios are scoped to direct
  children. The spec's table now matches its prose.
- The collect marker takes the served row id, carried on an internal companion
  type so the wire body never gains a ledger handle.
- The inspector DTO gates its payload on the derived status.

## Prevention

- **When a fix corrects a convention, grep the PREDICATE, not the symptom.**
  After fixing one `rootRunId === id`, the next action is
  `rg "rootRunId ===|root_run_id ="` across the repo — not "fix the tree query I
  was looking at". Three readers shared one wrong belief.
- **A guard's presence is not its reachability.** Reviewing "is the check
  called?" misses "is its input ever set?". For every guard reading a field off
  a loose payload, trace back to the producer that populates it.
- **`Record<string, unknown>` on a payload type disables the compiler exactly
  where you need it.** Name every field a consumer branches on.
- **A fixture that hand-builds an identity column is a red flag.** Ask "does any
  production writer produce this row?" — if the answer is no, the test is
  describing an impossible world.
- **When spec prose and a spec table disagree, the prose usually carries the
  reasoning and the table carries the shortcut.** Reconcile before implementing;
  the code will follow whichever one is closer to the keyboard.
