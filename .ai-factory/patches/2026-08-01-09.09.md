# Env-e2e adversarial-review batch: compose exit-code flattening, convention-vs-invariant, wrong-revision probes

**Date:** 2026-08-01 09:09
**Files:** web/lib/config.ts, web/lib/__tests__/config.flow-dir-floor.test.ts, web/lib/flows/graph/__tests__/flow-install-dir.integration.test.ts, docs/decisions.md, docs/flow-dsl.md (platform `78458ccc`); packages/env-e2e/flows/env-e2e/{scripts/run-e2e.sh,flow.yaml}, packages/env-e2e/tests/test-run-e2e.sh, packages/env-e2e/README.md, docs/env-e2e/{README.md,specs/2026-07-31-env-e2e-design.md} (plugins `71a4aa1`)
**Severity:** high

## Problem

Codex adversarial review of the env-e2e release surfaced 6 findings. 5 were
real (1 partially): (1) acceptance not reproducible from immutable bytes
(tag pre-dated a live hand-patch; evidence tied to a mutated installed
revision); (2) docker-level runner failures (daemon death, missing image,
broken entrypoint) were classified as test-verdict `fail` → wasted rework
loops; (3) sweep docs allowed downing ACTIVE runs (shared `maister-run-`
prefix); (4) "zero published ports" was a convention, not enforced — one
project override broke the AC-3 collision-freedom invariant; (5) the
`.maister-env-e2e.sh` requirement probe ran against the default-branch
checkout — a branch ADDING the config was wrongly refused at launch;
(6) the `MAISTER_FLOW_DIR` engine floor was documented MUST with no
load-time enforcement (my own integration test used engine_min 3.0.0 and
passed).

## Root Cause

Four distinct reasoning failures:
- **Assumed docker CLI semantics transfer to compose.** They don't: docker
  compose FLATTENS CLI-level errors (125/126/127 territory) to exit 1 —
  verified empirically only when the harness case failed. The classifier
  premise was written from `docker run` knowledge without testing the
  compose path first.
- **Convention where an invariant was needed.** Zero-ports guarded a real
  correctness property (concurrent-run collision freedom) but was enforced
  only in the fixture — nothing stopped a consuming project from breaking
  the invariant for everyone else on the host.
- **Probe context ≠ execution context.** ADR-091 probes run in
  `project.repoPath` (default branch) BEFORE the worktree exists; the
  config file is branch-owned. Probing branch-owned state from the wrong
  revision produces both false refusals and false passes.
- **Docs claiming MUST without an enforcement point.** Every other engine
  capability has a load-time floor gate; the new one shipped without —
  because the ADR said "the `:?` guard covers it" and no one asked "what
  enforces the authoring obligation itself?"

## Solution

- Platform: load-time scan (`declaresFlowDirCommand`) in `loadFlowManifest`
  mirroring the ADR-120 template-scan precedent — cli/check `action.command`
  containing `MAISTER_FLOW_DIR` requires `engine_min >= 3.3.0`, else
  `CONFIG`; gate commands/probes pinned OUT of the scan by test (ADR scope
  v1). Integration-test manifest bumped to 3.3.0.
- Script: classifier = codes 125/126/127 OR non-zero exit + trailing
  `Error response from daemon:` marker → env class; isolation enforcement on
  the RENDERED `compose config` model (published:/container_name:/
  network_mode: host → config-class refusal with matched lines); preflight
  moved before config; probe list reduced to host invariants.
- Docs: sweep = discovery-listing + verify-terminal-before-down + no
  prefix-wide downs; spec amended in place with dated amendment markers.
- Reproducibility: tag re-cut on the fixed tip through the release gate;
  fresh clone of the tag → validator + 12-case harness green from tag bytes.

## Prevention

- When a script branches on an exit code from a WRAPPER tool (compose, kubectl,
  npm), test the wrapper's actual code for each failure shape — never assume
  the wrapped tool's exit-code contract survives the wrapper.
- For every documented MUST, name the enforcement point (load gate, runtime
  guard, test). A MUST with only a runtime symptom is a convention.
- Preflight probes may only assert state that is invariant across revisions
  (host tools); anything branch-owned must be validated from the execution
  revision.
- When docs give a destructive command next to a discovery filter that also
  matches LIVE resources, the verify-before-destroy step belongs IN the doc.
- Release evidence must be reproducible from the tagged bytes: if anything
  was patched live during acceptance, re-cut the tag and re-run the gates
  from a fresh checkout of it.
