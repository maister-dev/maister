## Root Cause

The slice exhausted its budget while passing its completed cases. Deduplicated
logs attribute 375.327s to nine independent cleanup databases and 109.400s to
three suite templates. These costs overlap the recorded suite durations.
Disposable PostgreSQL initialization used VM disk storage; pending main/Brain
lineages required 383/17 transport submissions despite existing per-file batching.
The `container-create-start.durationMs` field measured preparation before `.start()`,
so it could not diagnose actual container startup. This identifies measured setup
costs; it does not prove that eliminating them alone will qualify hosted Intel.

## Solution

Keep fresh invocation-labelled real PostgreSQL 16/pgvector containers and their
existing reaper, readiness, pool and cleanup behavior. Put disposable `PGDATA`
on a fixed 512MiB tmpfs with no disk fallback; retain all three durability
settings. Use 64/32MiB max/min WAL recycling targets so the default 1GiB
checkpoint target does not exhaust this smaller disposable filesystem. These
are soft PostgreSQL targets; the filesystem is the hard cap, and the complete
workload must demonstrate actual capacity. Record preparation separately from
successful SDK startup duration.
The database lifetime still ends at container disposal; production/host-reboot
durability is outside this fixture contract. Web/supervisor restarts keep the
same live database.

Read committed migration metadata with installed Drizzle 0.36.4. Use its pinned
PoolClient transaction and original ledger defaults/high-water selection, with
one simple-query submission containing pending SQL plus each ledger insertion.
Fresh main/Brain lineages take 6/6 submissions; no-op takes 5. Preserve SQL content,
lineage order, hash/timestamp bytes, runtime failure cause and transactional
rollback. Drizzle string escaping handles hashes; newline terminators close
trailing comments. Production migrators and historical partial-upgrade paths
retain their execution paths. No API, database-schema, SQL/journal, product
configuration, deployment or ADR allocation changes are required.

## Prevention

Keep platform-labelled evidence and the exact original owning name sets, strict
`validateLaneReport`, independent preflight and zero-leak checks. Measure real
setup phases before changing process inspection, caching, resource sizes or
budgets. Retain real PostgreSQL settings and test runtime rollback when batching
SQL; parser-only errors cannot prove that prior statements were rolled back.

Owner push remains the checkpoint. After push, verify the exact SHA/merge tree,
all mandatory jobs, full 7/50 reporter plus separate preflight, slice/job timing
and zero leaks. If setup savings do not meet the existing budget, retain failure
and measure the next bottleneck; never weaken cases, increase resources/timeouts,
shard isolation, or report partial suites as green. Linux must requalify the changed
harness on both pinned Nodes before its separate hosting decision. S5.2/S5.3/S5.4
remain open at 42/45; browser lifecycle expansion and production separate-user
deployment remain separate deliverables.
