# Preserve selected launch policy and report the existing reservation

**Date:** 2026-11-03 Europe/Moscow
**Files:** `web/lib/tasks/launch-intent.ts`, `launch-resolution.ts`, `launch-conflict.ts`, `launch-http.ts`, API contracts and focused intent/HTTP regressions
**Severity:** high

## Problem

Review found that an explicit old base commit could incorrectly stand in for current automatic evidence; saved task delivery mode lost to project defaults; and operational Triager runs competed with task delivery. The public contract also omitted supported policy fields, while reservation conflicts did not identify the already accepted work.

## Root Cause

Current evidence and selected immutable execution commit were treated as the same value. Routing resolution did not preserve task-level precedence. Duplicate checks used a broad task/run association instead of the delivery admission domain. Handwritten transport schemas covered only part of the actual nested request.

## Solution

Acceptance resolves current base HEAD independently of the requested execution commit. Automatic admission validates current evidence against current HEAD; manual admission keeps the selected reachable immutable commit. Task delivery mode precedes project defaults, and an explicit launch policy has final precedence. Operational activity is excluded from delivery deduplication; active delivery work remains protected.

Ordinary admission reports a scoped `launch_already_reserved` reference containing only existing intent/run selectors and its actual admission basis. The losing request never receives a successful acknowledgement. Historical work is labeled historical, without inventing a human decision. Public error serialization validates this small reference and never forwards arbitrary error details.

Runner refusal also projects the validated, single-line bounded slot key and label needed to repair the selection. A disabled real runner first reproduced an HTTP error with no actionable slot (`/private/tmp/maister-launch-runner-slot-red.log`); the actual HTTP file now passes 11/11 (`/private/tmp/maister-launch-runner-slot-green.log`). No source input or executable configuration is exposed.

Canonical Zod request schemas generate the built MCP JSON schema. Official API contracts describe complete policy/budget bounds, package choices and the safe conflict reference; adapter parity tests exercise nested fields and reject client authority fields.

## Tests and prevention

Focused real PostgreSQL/Git intent and HTTP tests pass 36/36 (`/private/tmp/maister-launch-conflict-green.log`). The conflict case first failed because the response omitted the existing reference (`/private/tmp/maister-launch-conflict-red.log`). Existing policy, current-evidence and operational-versus-delivery cases exercise the actual service. Official parser, schema and adapter checks pass (`/private/tmp/maister-contracts-current-2.log`); full feature/browser qualification remains tracked in the active plan.

Keep evidence freshness, immutable execution selection and caller authority separate. Compare transport schemas with the complete canonical request rather than testing only a happy-path subset. When a reservation wins, return its identity under current scope without treating the competing request as accepted.

The full Web unit run also exposed a missing composition fixture for the new preparation cleanup sweep. The existing sweep test now supplies that collaborator and verifies it participates once, while its real cleanup behavior remains covered by PostgreSQL/Git integration. The entire composition file passes 20/20 (`/tmp/maister-sweep-composition-green.log`); no production gate was relaxed.
