# Exercise the real browser lifecycle under split Linux users

**Date** 2026-11-24 00:38 MSK

**Files** `web/scripts/smoke-production-split-users.ts`, A/B acceptance plan

**Severity** medium

## Problem

The production-image smoke could pass when the board controls did not work
or the browser stream delivered only its initial marker.

## Root Cause

The smoke visited the board and Run pages while direct requests performed
launch, permission and stop. It treated any SSE bytes as evidence of
permission delivery.

## Solution

Click the board Launch dialog, wait for its exact intent to bind and open
the Run while the adapter is at a fixture gate. Release the adapter after
the browser's live-only stream is ready, then assert the permission event
and visible status. Respond and stop from the browser. Provide an optional
second Supervisor for the current singleton placement control with independent
UID, store and workspace root.

## Prevention

Keep SQL for fault injection and durable correlation. Assert user actions
through controls, their HTTP outcomes and the Run panel. For two live
processes, correlate the selected host with the actual command receipts and
the host shown in the browser.

The browser surface sweep used `rg -n 'run-header-status|pending-input-card|workbench-lifecycle-actions|task-launch-dialog' web/components web/e2e`.
The smoke exercises existing controls. The separate scratch-upload fixture
still uploads over HTTP and verifies the actual Chrome download event.
