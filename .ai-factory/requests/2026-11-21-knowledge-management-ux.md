# Knowledge in MAIster — records, proposal review, and agent memory

Implementation brief for product design, web, and MCP engineering. Audit date: November 21, 2026. A user should be able to find a record or a particular agent’s note, understand where it came from, review a proposed change, and return to the outcome through a permanent link.

**Product decision.** Make Knowledge the common entry point with three views: **Records**, **Awaiting review**, and **Agent memory**. The folder hierarchy already exists within each agent’s vault. Company and project knowledge consists of assertions with revisions, evidence, and decisions. The landing page needs a scope selector and clear links between these objects. Moving all knowledge into a file tree would require a new storage model and is outside this task.

**Existing proposals.** Remove the long feed of drafts from the project overview. Keep pending project proposals actionable and provide permission-checked history with original identifiers and outcomes. Some entries users think of as old “facts” are already published records with legacy metadata. Preserve them without bulk rejection, confirmation, or conversion into notes. Publishing an assertion, confirming a fact, updating agent memory, and creating a project task produce four different outcomes.

## Where the UI loses information or actions

1. **The lists have different pagination behavior.** Both the record catalog and the structured proposal list support `nextCursor`. The shared Inbox queue lists pending items of three kinds, with 20 per page by default and a maximum of 100. The project’s `listProposalRows()` fetches only 25 rows, putting `pending` first and excluding `knowledge_add`, `knowledge_correct`, and rows with source restrictions. The panel calculates its pending count from that slice. With 26 pending proposals it displays 25, and the 26th cannot be opened from the panel. The entire source list appears above the proposals. The live audit found a long source list and an empty proposal overview. Reproduce the 26-row case with fixtures. [Project overview query](../../web/lib/brain/ui-queries.ts) · [Panel](../../web/components/brain/project-brain-panel.tsx) · [Shared queue](../../web/lib/queries/knowledge-memory-reviews.ts)
2. **The handoff to a decision loses context.** A structured proposal’s full page already shows its owner, author, revision, limitations, evidence, original assertion for a correction, and link to the publication. The decision link takes the reviewer to Inbox. There, the `knowledge` preview returns only the assertion, an ordinary `brain` proposal shows draft JSON, and a `vault` proposal shows a paged change. Actions operate on checked rows. A deep link opens the preview without selecting the row. When the row is outside the current page, the reviewer cannot accept that item from the preview. Revoked access, a network failure, and an unavailable resource can look the same. [Proposal page](../../web/app/(app)/knowledge/proposals/[proposalId]/page.tsx) · [Preview data](../../web/lib/queries/inbox-review-actions.ts) · [Review controls](../../web/components/inbox/proposal-reviews.tsx)
3. **Agent memory exists, but its entry points are scattered.** Project memory belongs to the project and qualified `agentId`. Installation memory belongs to the company and `agentId`, with access through a current reviewed binding. The same package can have separate memory in two projects. Installation memory has a page at `/settings/specialists?binding=…&tab=memory` when the active binding has `installationGrant.memoryEnabled`. That page looks for the selected binding among the first 50, so a valid deep link can lose its selection. A catalog definition, Flow persona, or shared-session subagent does not by itself create an independent vault. [Specialist settings](../../web/app/(app)/settings/specialists/page.tsx) · [Domain and access rules](../../docs/system-analytics/agent-memory.md)
4. **The vault already has a browser and editor.** Folders are virtual and their leaves are Markdown notes. History, revert, tags, search, links, and backlinks exist. Permissions govern writes and administrative redaction of a revision’s content. The default note view renders the source as `pre`. Actions targeting the current note remain adjacent to a historical revision. The server knows two reasons for inactivity, `agent_memory_disabled` and `agent_memory_cutover_required`, but the HTTP response loses the machine-readable reason and the UI shows one message. Before cutover, the project compatibility API can read the legacy `memory.md`. [Vault browser](../../web/components/agents/agent-memory-control.tsx) · [Search and links](../../web/components/agents/agent-memory-navigation.tsx) · [HTTP errors](../../web/lib/agent-memory-vault/http.ts) · [Compatibility route](../../web/app/api/projects/[slug]/agents/[agentId]/memory/route.ts)
5. **The server already supports promotion from a note into shared knowledge.** `promoteMemory` captures the exact current revision, hash, and source evidence. A `knowledge` target creates a `knowledge_add` proposal with a `derived_from` relation. A `brain` target creates a project `state` proposal. Both operations return `operationId` and `proposalId`. The note panel offers no corresponding action. The common title `Agent memory proposal` also makes proposals hard to distinguish. [Note promotion](../../web/lib/agent-memory-vault/promotion.ts) · [Note panel](../../web/components/agents/agent-memory-control.tsx)

## Screen requirements

| Priority and screen | Behavior to design and implement |
|---|---|
| **P0. Knowledge entry point** | Switch between Records, Awaiting review, and Agent memory within the existing section. Offer “All accessible”, “Company”, and individual projects. Show a human-readable owner on each row. Preserve scope, filters, and position in the URL. Open the corresponding selection directly from a project or agent. Keep a summary and deep links to the same work in the general Inbox. |
| **P0. Reviewer workspace** | Default to “Needs my decision” and offer history separately. Each row shows the proposed change, kind, destination, project/company, agent or author when available, and time. Place permitted actions, rationale, and outcome beside the material being reviewed. Provide a direct URL for every proposal kind, a return to the selection, and a next-item action. On conflict, offer to reload the current revision while preserving the reviewer’s rationale. Keep batch processing with a result and current authorization check for each item. |
| **P0. Agent memory catalog** | List accessible bindings with owner, qualified name, mode, and available action. A platform definition should link to accessible project attachments and, where authorized, installation memory. Distinguish project and installation vaults with the same name before opening them. Resolve an authorized binding by ID independently of the first list page. Match the specialist settings link to the user’s authority to enter. Use a neutral response for protected resources to prevent enumeration. |
| **P0. Memory availability** | Distinguish an accessible empty root, a disabled attachment, disabled memory, legacy mode before cutover, restricted source access, and temporary failure. Disclose reasons only in an authorized context. In legacy mode, let the owner explicitly view the compatible project memory and see cutover status. Link to the existing setting when the user can enable memory. Retry transient reads at the same path. |
| **P1. Vault browser and revisions** | Keep existing commands. Show paged folders and notes on the left, the selected note with safe Markdown rendering and source in the center, and author, time, revision, history, links, and authorized sources in details. Link each breadcrumb segment. Creating a nested `.md` note creates its virtual folder. Identify the date/version of a historical revision, offer comparison and “Restore as new revision”, and require a return to the current revision to edit it. Before move, recursive delete, clear, or redaction, show the exact scope and consequences. |
| **P1. Turn a note into a proposal** | On a current note offer “Propose as knowledge” or “Propose a project change” for authorized targets. Show destination owner, path, source revision, excerpt, and expected result before submission. Both flows end with a receipt and a link to that proposal. Give each proposal a useful title derived from an accessible note or supplied by its author. Protect restricted paths. Link the published result back to accessible evidence for the exact source revision. |
| **P1. Records and Project Brain** | Distinguish observation/inference, published revision, human confirmation, freshness, and conflicts. Identify missing legacy metadata. Compare a correction against its base revision. Offer a permission-checked picker for exact evidence in addition to manual text capture. Link Project Brain search results to the record or indexed source. Keep index status, a short summary, and links to Sources and Project proposals in the overview. Paginate and filter sources and history. |

### What the human decision means

| Object | Before the decision | After the decision |
|---|---|---|
| New record or correction | Show author, owner, base and proposed revisions side by side, basis, supporting and derived evidence, limitations, missing information, and accessible conflicts. Collect a rationale. | Acceptance publishes an exact revision. Rejection leaves an auditable decision. “Confirm fact” requires separate `knowledge:confirm` authority, an available qualifying `supports` witness, and a reason. Support revocation. |
| Project Brain proposal | Show its kind (`rule`, `skill`, `flow`, `adr`, `roadmap`, or `state`), sources, change, and expected effect. Check authority for the particular kind. | The first three kinds produce an unpublished catalog draft. The others produce a linked task under project rules. Show the actual outcome and link, distinguishing pending, rejected, and applied states. |
| Proposed memory change | Show the owner, agent, operation, old/new paths, and a paged diff across affected notes. For recursive operations, show the number of visible affected items and the version of the selection. | On acceptance, show the applied revision or a conflict with the current state. Rejection preserves the original note content. |
| Librarian card | The conversation owner confirms a specific intent and destination. Explain whether this creates another proposal for review. | Link the card to the resulting proposal and then to its outcome. Personal “remember/forget” actions belong in the personal memory dialog. |

**Design deliverables.** Prepare linked mockups for the catalog, queue with a selected row, decision detail, vault browser, and note → proposal → outcome flow. On wide screens keep the list next to the details. On narrow screens open details as a separate screen and return focus to the row. Preserve HeroUI, EN/RU, both themes, focus after dismissal, and text labels for statuses. Show empty results, insufficient evidence, temporary errors, conflicts, and restricted access. Lazyweb references include Zoho for folder navigation and file lists, Lemni for a filtered inbox with request details, and Jobber for review status and reviewer notes. Use their composition as a reference and MAIster’s own decision rules for behavior. [Lazyweb MCP collection](https://www.lazyweb.com/agentic-search/bd254b27-6fd4-4126-af91-37e5535ce24e)

| Shared queue | Browser routes include `GET /api/inbox/reviews`, `GET /api/inbox/reviews/{kind}/{proposalId}`, and `POST /api/inbox/reviews/decisions`. They support cursors, item versions, keyed replay, and individual batch outcomes. `knowledge_proposals_list` covers structured proposals. `/api/v1/ext/projects/{slug}/memory/proposals` accepts POST for Project Brain. | Reuse the queue service. The first workflow needs only a single-item external decision. Keep human decision tools out of ordinary agent and Librarian toolsets. |
| Human vault browser | Session routes under `/api/projects/{slug}/agents/{agentId}/memory/*` and `/api/specialists/{specialistId}/bindings/{bindingId}/memory/*` cover directory/note reads, commands, history, search, tags, backlinks, and `promote`. Give human integrations a separate personal bearer contract for paged catalog, directory, exact note, and history reads. Share the query logic and reauthorize content reads. Preserve the Librarian token’s turn boundary. Human edits and redaction already have browser routes. Expand external write access only for a specific workflow. |
| Agent and Librarian | `/api/v1/ext/agent/memory/commands` and MCP `memory` operate on the current session’s vault. Other tools include `memory_search`, `memory_tags`, `memory_backlinks`, and `memory_promote`. The compatibility tool `agent_memory_write` covers a single index. Project Brain owns `memory_recall`, `memory_retain`, `memory_clusters`, and `memory_propose`. Name the store and outcome in descriptions and responses. For pending operations return the proposal kind and an authorized status link. The proposing tool may return a bounded delivery status under current authority. Human queue access and decisions on a person’s behalf require personal authority. |

**Data, errors, and events.** A review row needs the composite key `(kind, id)`, version, owner, author, change summary, allowed actions, and time. Replace the single `summary` field in details with typed data for each domain. Record `expectedVersion` and a replay key, returning the original outcome on redelivery. Vault commands use the observed `ifRevisionId` and `ifHash`. Tree operations also use the generation and complete set of selected heads. Distinguish `202 pending` from an applied change, and a conflict from revoked access. Return safe machine-readable inactive reasons to authorized owners. Recheck current source access when reading the outcome as well. Offer retry on timeout or HTTP 5xx during an instance update, and reserve the empty state for a successful read.

Use the existing Inbox and event mechanisms to refresh queue state, the visible counter, and the handoff from a Librarian card. On reconnect, reread the current selection and show the last confirmed outcome. Reuse the existing proposal ledger. First establish whether current domain revisions and receipts cover audit and history. Justify any new indexes or fields with a query plan or a specific missing attribute. Preserve unknowns in old records. Check the scopes available at personal-token issuance, MCP toolset selection, runtime schemas, and the installed client’s actual `tools/list`.

## Delivery order and acceptance

1. **Verify the decision path first.** On a test instance prepare a project, a reviewed installation binding, two users with different permissions, and all three proposal kinds. Capture current behavior for the 26th project proposal and a deep link outside the first Inbox page. Deliver decision details, safe availability reasons, and corrected navigation. **Acceptance:** the deep-linked decision applies to the reviewed version, returns a receipt and accessible result, and returning restores the filter and row.
2. **Catalog and vault browser.** Exercise one qualified agent in two projects and at installation scope, disabled memory, legacy mode, an active empty root, and a binding beyond the first specialists page. Follow folder → note → history → compare → return. Create and rename a nested note, then restore an exact revision using test data. **Acceptance:** deep links open the correct owner, each disclosable unavailable state offers a clear next action, and a concurrent edit conflict preserves the user’s draft.
3. **Publication and history.** From one note create a knowledge proposal and a separate project `state` proposal. Trace the first to the published revision with the exact `derived_from` witness. Test factual confirmation separately with a qualifying `supports` witness. For the second, verify the link to the task actually created. For a vault edit under `review` policy, verify an unchanged head at `202` and a new revision after acceptance. For rejection, verify the reason and unchanged content. For a legacy record without a source, verify that a correction is available and confirmation is unavailable. Replaying the same key returns the original receipt.
4. **Volume and permissions.** With multiple pages and tied timestamps, check stable order, continuation, return navigation, filter changes, current count, and deep links. Accessible history includes items beyond the first 25. Revoke access between list, open, and decision. Recheck authority and withhold restricted names, paths, excerpts, and counts. After redaction the old revision URL must not return its text. Cover a reader, project editor, reviewer, administrator without explicit company authority, and holder of the relevant company grant.
5. **Integration and design parity.** A personal-token external client goes from list to details to an authorized decision, replay, and outcome. A scoped session agent reads its authorized memory and proposes a change. The Librarian receives an owner-confirmation card. Compare advertised MCP tools and schemas with an actual call on the installed version. Update OpenAPI, screen documentation, and EN/RU operator and user guides. Check Firefox, keyboard navigation, 390 px and wide layouts, light/dark themes, an empty queue, slow responses, and recovery from 5xx. Produce a record/revision link or receipt for each successful transition.

Build acceptance on the existing [Company Brain E2E](../../web/e2e/company-brain.spec.ts), [Inbox E2E](../../web/e2e/inbox.spec.ts), [promotion integration tests](../../web/lib/agent-memory-vault/__tests__/promotion.integration.test.ts), and [memory review integration tests](../../web/lib/agent-memory-vault/__tests__/review.integration.test.ts).
