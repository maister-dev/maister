### Expectations name their enforcement; motivation never becomes contract prose; rationales match mechanisms

**Source**: 2026-07-27-09.30, 2026-08-01-09.09, 2026-07-12-10.43, 2026-07-16-14.05, 2026-07-16-16.05, 2026-09-03-17.20, 2026-09-03-15.37
**Rule**: Every Expectation bullet (and every MUST in an ADR or analytics doc) NAMES what enforces it — a constraint, a CAS, a singleton, a load gate, a test; a MUST that cannot point at one is a wish: weaken it to the scope the mechanism covers ("summon-vs-summon, serialized by `domainEventDispatch: 1` + the CAS lease") or add the mechanism. Never let MOTIVATION prose become CONTRACT prose — an ADR's "so the caller learns whether its summon was accepted" copied into an Expectation and an OpenAPI operation description became a false promise; when a schema carries a qualifier ("a report, not a guarantee") the OPERATION description that returns it carries the same qualifier (callers read the operation, not the component). An ASYMMETRIC boolean (`false` hard negative, `true` weak) documents both arms. A rationale that names a mechanism is checked against it: an INVERTED rationale ("target-scoped fetch" as why a lease is safe, documented 8×, while the code is safe for the opposite reason) leads a reader to remove the real guard; a rationale naming a column nothing reads (`pr_state_checked_at`) is drift. When spec PROSE and a spec TABLE disagree, reconcile them — the prose usually carries the reasoning, the table the shortcut. Document an enforcement BOUNDARY where the reader stands (which calls the seam sees, what the backstop covers) as an Edge-cases bullet plus a comment at the exact check; record invariants such as "a refused tree-cancel MUST NOT cascade; a lost CAS after a cascade MUST be surfaced (409 or WARN), never a silent skip" in the domain's Edge cases. Record rejected alternatives with their reason.
