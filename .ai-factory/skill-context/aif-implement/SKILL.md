### Bidirectional contract for config→DB persistence (SET and CLEAR symmetry)

**Source**: M6 adversarial review pass-through (2026-05-28)
**Rule**: A helper that materializes a YAML/config field into a DB column that downstream readers rely on MUST handle BOTH the SET path (`field present` → write resolved value) AND the CLEAR/UNSET path (`field absent` → reset to the column default — usually `null`, `false`, or zero) inside the SAME transaction. Looping `for (entry of config) { if (!entry.field) continue; ... }` is a bug: the previous DB value persists after the operator removes the YAML field, but the reader believes "absent = default". A bug enshrined in an integration test as "documented behavior" is the worst possible outcome — it makes the asymmetry load-bearing.

Concrete pattern (Drizzle, pseudo-code):

```ts
// Wrong — only the SET branch
for (const entry of cfg.entries) {
  if (!entry.field) continue;
  await tx.update(rows).set({ col: resolve(entry.field) }).where(...);
}

// Right — explicit SET and CLEAR in one pass
for (const entry of cfg.entries) {
  const resolved = entry.field ? resolve(entry.field) : null;
  await tx.update(rows).set({ col: resolved }).where(...);
}
```

Mandatory test shape: a round-trip integration case that (a) writes with the field set, asserts the column equals the resolved value, (b) re-runs with the field removed, asserts the column equals the default. Both halves are required.

### Runtime contract symmetry — never half-ship an env/config dep

**Source**: M6 adversarial review pass-through (2026-05-28)
**Rule**: When a server process newly consumes an env var, reads a new config file, depends on a new sidecar binary, or binds a new port, the deployment artifacts in the SAME PR MUST be touched: `Dockerfile`, `compose.yml`, `compose.override.yml`, `compose.production.yml`, `.env.example`. The minimum touch set per change:

| New dependency                               | Files to update                                                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| New env var consumed by web or supervisor    | `.env.example` + the consuming service's `environment:` block in `compose.yml` (+ prod overlay)                                                   |
| New config file read from a host path        | host-path mount (bind or named volume) on the consuming service + a `.env.example` toggle for the host path if it's tunable                       |
| New sidecar binary spawned by the supervisor | dep listed in the consuming package.json (lockfile committed), and `pnpm exec <bin> --help` smoke check covered in CI or a documented manual step |
| New listening port                           | port declared on the service (when reachable from outside) + firewall/expose notes                                                                |

If you intentionally defer runtime wiring, the docs MUST contain an explicit "not supported in Docker — enable by …" callout in both `docs/getting-started.md` and the relevant `docs/configuration.md` section. Silent dev/prod skew is forbidden: tests passing under mocks do not prove the deployment runs the new path.

**Wire contracts span deploy units:** adding a field to a cross-process request body (e.g. `hooksConfig` on supervisor `POST /sessions`) requires the OTHER deploy unit's acceptor schema (`StartSessionRequestSchema`, which ends `.strict()` and `.parse()`s) to change in the SAME commit — even if it only accepts-and-ignores until a later phase; "this phase is web-only" is not a license to draw a phase boundary through a contract. ### Process lifecycle: never trust `subprocess.killed` for escalation

**Source**: M6 adversarial review pass-through (2026-05-28)
**Rule**: Node's `subprocess.killed === true` after `subprocess.kill(sig)` successfully _sends_ the signal — NOT after the child exits. A child that ignores or hangs on SIGTERM sets `killed=true` and `exitedInTime=false`, but the predicate `!exitedInTime && !proc.killed` then evaluates FALSE and SIGKILL never fires; the daemon stays alive and keeps its port bound across supervisor restarts.

Correct pattern:

```ts
// Wrong
if (!exitedInTime && !proc.killed) proc.kill("SIGKILL");

// Right — escalate based on the observed exit event, not `killed`
const exited = new Promise<void>((r) => proc.once("exit", () => r()));
proc.kill("SIGTERM");
const exitedInTime = await Promise.race([
  exited.then(() => true),
  wait(graceMs).then(() => false),
]);
if (!exitedInTime) {
  proc.kill("SIGKILL");
  await exited; // wait for the actual death
}
```

Mandatory test shape: a fixture child that traps SIGTERM (`process.on("SIGTERM", () => {})` ignoring it OR a long-running blocker) and asserts the port is freed / pid is gone after `shutdown()` returns. The cooperative-exit happy path does not exercise this branch.

### Health probes must validate target identity, not just liveness

**Source**: M6 adversarial review pass-through (2026-05-28)
**Rule**: For sidecar/proxy daemons managed by the supervisor, the readiness probe MUST identify the _intended_ service, not merely "something answered on `host:port`". Generic `GET /` returning any non-5xx is insufficient: if the configured port is already occupied and the spawned child fails to bind (`EADDRINUSE`) and exits, an unrelated local HTTP service can answer 200/404 and the manager will transition to `ready`. Later traffic routes into the wrong process and surfaces failures far from the real cause.

Acceptable identity signals (pick one):

1. A target-specific endpoint that the daemon exposes (e.g. `GET /health` returning a known body shape, `GET /version` returning a known name string).
2. A recognizable response header set by the target.
3. A response body matching a known schema, validated before transition.

Additionally, register `child.once("exit", ...)` BEFORE starting the health-probe loop. If the _target_ child exits before becoming ready, abort the probe immediately and surface `EXECUTOR_UNAVAILABLE` (or the equivalent domain error) with the exit code/signal in the message.

Mandatory test shape: a case where another HTTP server is bound to the configured port BEFORE the manager starts the target child. Assert the manager either (a) detects the port is occupied and fails fast, or (b) detects the target child exited before readiness and fails with a target-identifying error. A green test against an empty port does not cover this branch.

### Every committed test MUST execute, and the suite stays green (or is explicitly quarantined) at each phase

**Source**: M10 verify pass-through (2026-05-30)
**Rule**: A committed test that no runner runs gives false confidence; a suite left silently red across phases hides regressions. Two obligations, checked at every phase-completion checkpoint:

1. **No dead tests.** Every committed `*.test.ts` / `*.integration.test.ts` MUST be matched by exactly one runner project's `include` glob and not swallowed by an `exclude`. After adding a test — _especially in a new location_ — prove it runs: `vitest list --project <unit|integration>` must show the file, and it must appear in the run summary's collected set. If a test lands in a new location, update the runner config in the SAME commit.
2. **Phase-green or explicit quarantine.** At each phase checkpoint run the full suite (`pnpm test:unit && pnpm test:integration`, or the project equivalent). The phase is NOT done while a test the phase touched is red. A test red for a reason genuinely outside the phase's scope (pre-existing breakage, or a harness limit like an unresolvable import) MUST be quarantined VISIBLY — a config-level `exclude` or `*.skip` carrying a one-line reason + tracked follow-up — NEVER left silently red and NEVER deleted to "go green". Note: a module that throws at IMPORT time cannot be quarantined with `describe.skip` (the skip never evaluates) — exclude it at the runner-config level instead.

### Cap buffers + fast-path expensive parsers + uncap legitimate listeners — in the SAME commit as the data path

**Source**: 2026-05-26-12.53.md
**Rule**: When implementing a data path that consumes external bytes (subprocess stdout, network stream, file tail), the following defenses are part of the shipping bar, not "Phase 2 hardening":

1. **Cap unbounded line/chunk buffer.** Pick a sane `MAX_LINE_BYTES` (default 1 MB for log-like streams). When `buffer.length > MAX_LINE_BYTES`, emit the truncated line (`buffer.slice(0, MAX_LINE_BYTES)`), log `WARN line-buffer-overflow` with the source, then drop the rest of the buffer. Add a test that drives the overflow path via a fixture (e.g. supervisor uses a `--giant-bytes N` flag on `fake-acp.mjs`).
2. **Fast-path expensive parsers.** If a per-line operation (`JSON.parse` + tree walk) is only needed for ~1% of lines, short-circuit with a cheap substring check first: `if (!line.includes("usage")) return;` before `JSON.parse`. Pick the substring from a stable token the target structure always contains.
3. **Uncap legitimate listener counts.** For per-session `EventEmitter`s with multiple legitimate subscribers (cost tracker + registry auto-subscribe + N SSE consumers), call `emitter.setMaxListeners(0)` right after construction. Node's default 10-listener cap exists to detect leaks, not to enforce a real ceiling.

Each item is a one-line addition. Ship them with the commit that introduces the data path; do not file as "Phase 2 hardening" tickets.

### `logger.flush()` before `process.exit` when transport is async

**Source**: 2026-05-26-12.53.md
**Rule**: In any shutdown handler that calls `process.exit`, await `logger.flush()` (wrap in a promise if needed) before exiting. Otherwise the final log lines — including the shutdown reason — are truncated mid-flight. This applies to pino with pretty-print or transport workers (a worker thread holds the unflushed output) and to any logger whose sink is async (network, batched file writes). Treat it as part of the shutdown template, not a per-service decision.

### Claim the transition FIRST (status CAS), then the unique-constrained write; never mark Failed until execution is confirmed stopped

**Source**: 2026-05-31-22.46 (#1/#2), 2026-06-01-12.55 (#1/#2)
**Rule**: For a state-changing handler OR a background sweep/watchdog that performs a contention guard plus other writes:

1. **CAS before any other uniquely-constrained insert.** Run the status CAS FIRST inside the transaction; only the CAS winner performs the unique-constrained INSERT (e.g. a `node_attempts` row with `UNIQUE(run_id,node_id,attempt)`). A loser then rolls back at the CAS → deterministic mapped 409, never a raw Postgres `23505` surfacing as 500. Placing the constrained insert before the guard inverts this and leaks an unmapped DB error.
2. **A background sweep racing a live single-writer claims atomically.** Use one guarded `UPDATE runs … WHERE status='Running' AND current_step_id = <node> RETURNING`, and ONLY on a non-empty claim mutate the ledger (`markNodeFailed(…, tx)` in the same tx). A predicate-less `markNodeFailed(attempt.id, …)` in a separate statement clobbers a concurrently-`Succeeded` attempt to `Failed` while the guarded run update matches zero rows.
3. **Never mark work terminally `Failed` until its execution is confirmed stopped or confirmed absent.** Key the teardown lookup on the server-owned identity the supervisor tracks — `(record.runId === run.id && record.stepId === run.currentStepId && status === 'live')` — NOT `runs.acp_session_id` (which the graph runner persists only AFTER the node's prompt returns, so it is null exactly during the long/over-cap window the watchdog must act on). A retryable teardown failure (`EXECUTOR_UNAVAILABLE`) leaves the run `Running` to retry next tick (no split-brain); only a confirmed-stopped/absent (404) session proceeds to `Failed`. Matching by exact `stepId` also avoids killing a later node's session after the cursor advanced.

Mandatory tests: a mid-prompt kill with null `acp_session_id` + a live record (matched by runId+stepId), a retryable 5xx that leaves the run `Running`, and the loser of two racing claims getting 409 (not 500).

Session-teardown extensions: a "find the live supervisor session for this run" lookup keys on the server-owned `runId` from `listSessions()` records (status `live`), NEVER on `run_sessions.acp_session_id` — that column is NULL for the entire mid-prompt window (persisted only AFTER the node's prompt returns); use `(runId, stepId)` only for exact-node protection, plain `runId` for "all of this run's live sessions" (stop/terminate). The live process is torn down BEFORE the run flips terminal — assert the call ORDER in a test (`deleteSession` before `markStoppedAndCloseAssignments`, driven by a mid-prompt fixture). A terminal flip meant to STOP external work must actually kill the sessions — a DB-only cascade let a tree keep spending past a hard budget ceiling (kill the root's live session first, `EXECUTOR_UNAVAILABLE` → leave for next tick, then best-effort per cascaded child). Before copying a bail-on-`EXECUTOR_UNAVAILABLE` pattern from a sibling escalation helper, check whether the caller RE-FIRES (budget watchdog ticks again — safe) or fires ONCE (supervisor `hookHalted` — a swallowed failure is terminal). Composite HITL recovery checks run BEFORE normal run-state availability checks; preserve-before-terminal composites use `checkpointSession`, never a generic stop dispatcher.

### Honesty + write-once guard + sparse-default + enforce-external-contracts

**Source**: 2026-06-01-13.16 (#1/#2/#3), 2026-05-31-23.49 (#2), 2026-05-31-22.48
**Rule**: Four habits adversarial review keeps re-finding:

1. **Honest visibility.** A surface that RECORDS a value but does not ACT on it (an enforcement/settings snapshot not yet delivered to the agent) MUST say so in label/UI/docs. An unqualified status word (`Instructed`, `Enforced`) reads as "action was taken" — a false compliance signal. State what the surface does NOT do (e.g. EN+RU "declared intent, recorded for visibility, not yet delivered").
2. **Write-once guard.** A column documented append-only/write-once MUST encode it as a write guard — `UPDATE … WHERE id = ? AND col IS NULL` (+ `.returning()` to log whether the write landed) — not rely on callers writing it once. A `NeedsInput` resume reuses the same attempt row and re-runs the gate, overwriting the first-attempt audit. Prove with a resume/re-entry regression.
3. **Defaults at the non-erasing layer.** A sparse config map MUST stay sparse through the Zod parse (keys `.optional()`, NOT per-key `.default()`); fold the default in at evaluation (`enforcement?.[cls] ?? "instruct"`). A parse-time default expands `{ mcps: "strict" }` into all classes and destroys the "was this explicitly declared?" signal. A test built from a hand-written object literal bypasses parse-time defaults — parse real input through the production schema.

### Concurrency control: a transaction is atomicity, NOT mutual exclusion

**Source**: 2026-06-02-18.44, 2026-06-03-00.52, 2026-06-03-01.27, 2026-06-07-18.35, 2026-06-08-13.13, 2026-06-10-11.42, 2026-06-10-20.48, 2026-06-11-11.54, 2026-06-11-15.00
**Rule**: This GENERALIZES the existing CAS-first rule. For any read-then-write that can run concurrently:

1. **Re-read the guarded state UNDER the lock.** A `SELECT id … FOR UPDATE` that selects only `id` does NOT re-read `status`; re-read `{ id, status }` under the lock before mutating. A pre-check outside the lock is a fast-path optimization, never the decision.
2. **Lock the row whose invariant you protect.** Locking `runs` while the mutation writes `gate_results` does not serialize writers to `gate_results` (`markGateOverridden`/`markDownstreamStale` bypass the run lock). Put the lock/CAS on the row being protected.
3. **CAS on the EXACT observed value**, not a permissive set. `casLiveTransition(d, id, fromStatus, toStatus)` → `UPDATE … WHERE id = $1 AND status = $fromStatus RETURNING id`; 0 rows → throw the mapped domain error (409), never let a raw Postgres `23505` surface as 500. A set CAS (`status IN LIVE_STATUSES`) silently permits within-set transitions.
4. **Inserts:** `insert(...).onConflictDoNothing().returning({id})` → empty → typed 409. Never gate uniqueness on a read-then-write `SELECT` (TOCTOU). Any `onConflictDoUpdate` whose conflict target excludes the owning entity needs an ownership pre-check (or the owner in the key); any bulk DELETE keyed on author-chosen ids needs an ownership predicate.
5. **Append/versioning:** lock a STABLE parent row (`SELECT id FROM runs WHERE id = $1 FOR UPDATE`), not the rows being read — the new row does not exist yet, so `FOR UPDATE` on the read set cannot serialize it. Wrap a "record current" + "supersede prior" pair in ONE `db.transaction`.
6. **Fencing token** when a guard state is re-enterable by a timeout/reclaim: carry a per-attempt stamp in the WHERE (`eq(lastFiredAt, stagedAt)`), not just the state label — else a hung attempt clobbers a newer reclaim's marker and cross-attributes its run id.
7. **Batch loops** staging side-effects must thread accumulated state (`reservedSlots: intents.length`; `capFull = countLiveRuns(tx) + reservedSlots >= cap`) into per-item decisions — a pre-batch snapshot read let cap-3 launch 10 (staged runs create no rows until the claim tx commits).
8. **Claim-before-side-effect** when the side-effect is destructive or racers' effects diverge (irreversible `discard` BEFORE the CAS is a bug; reuse the `promote.ts` 3-phase / `resumeRun` claim-before-spawn-with-rollback shape). Marker-after is acceptable ONLY when every racer's side-effect is idempotent AND identical.
9. `NOT (nullable_col = X AND …)` is a three-valued-logic row-drop (`NULL = 'x'` is NULL, a NULL WHERE term drops the row) — write `IS DISTINCT FROM` / explicit `IS NULL` arms, and re-run the happy-path suite after touching any claim predicate.
   Prove the 409-vs-500 contract with a REAL two-racer test (hold an uncommitted write on a 2nd pg connection, wait on `pg_stat_activity` `wait_event_type='Lock'`, then commit), never a single-threaded one.
10. **Re-assert the selecting predicate in the UPDATE's WHERE.** Under READ COMMITTED the SELECT's view is not the UPDATE's view — an UPDATE acting on a row selected earlier re-asserts the predicate (+ `RETURNING`, fall-through on 0 rows) whenever another writer can flip it; likewise a claim tx re-checks EVERY precondition written by out-of-band transactions (`promotion_hold`, master toggles) under the lock, not just `status` — one TOCTOU per un-rechecked predicate.
11. **Verify a claimed unique-constraint backstop actually applies.** A partial index keyed on a column that is NULL for the racing path is INERT (`runs_auto_task_uq (task_id) WHERE launch_mode='auto'` + targetless `onConflictDoNothing()` was the fix); prove backstops with a CONCURRENT test — "call it twice" passes while the index is inert.
12. **Insert-first claims before filesystem work.** Claim the unique identity via DB INSERT (23505 → CONFLICT) BEFORE scaffolding; give each attempt a UNIQUE path (`${slug}-${uuid8}`) so a loser's cleanup can never `rm` the winner's dir.
13. **`FOR UPDATE` on the parent serializes FK binds.** A guard that reads-then-deletes across an `ON DELETE SET NULL` FK wraps read+mutate in one tx with `.for("update")` on the parent row — it conflicts with the concurrent bind's `FOR KEY SHARE`, so the bind serializes then fails its FK.
14. **CAS mutexes release by token** (the claim timestamp passed to release), never an unconditional clear, with staleness auto-recovery so a crashed holder never wedges the lock.
15. **Guard-on-every-edge.** Grep every transition INTO a guarded state (`tryStartRun` AND `promoteNextPending` are independent Pending→Running edges) and guard each, or factor one shared admit() helper — a guard on one of N edges is a guard on none.
16. **Idempotency-key sharing changes downstream identity.** When a dedup key makes two callers share a `taskId`, every derived identity (branch `task-<id>/attempt-N`) collides — only the claim winner launches; losers converge via a bounded one-shot reselect of the winner's run (`convergeToTriggerWinner`, ≤1s, `deduped` fallback), never state-polling.
17. **Deterministic race tests.** Use a controllable barrier (blocking stub inside the locked tx) or stream-FIFO ordering instead of sleeps; a flaky single-winner test flaking to `[200,200]` is a REAL lost-update bug — read what it flaked TO before blaming infra.
    **Source (additions)**: 2026-07-02-17.52, 2026-07-03-14.58, 2026-06-20-23.22, 2026-06-21-01.26, 2026-06-21-02.04, 2026-06-21-03.05, 2026-06-23-18.38, 2026-06-25-20.14, 2026-06-24-20.47, 2026-06-22-14.06, 2026-06-23-18.25, 2026-06-30-01.37

18. **A lock is not a gate; the lock's KEY equals the invariant's scope.** Before trusting a transaction to serialize a check ask what rows it LOCKS: a GLOBAL invariant (count, cap, quota) with per-row updates serializes nothing — take the advisory lock the codebase already uses (`takeSchedulerLock(tx)` before `countLiveRuns`, as `claimGraphResumeSlot`/`claimAgentResumeSlot` do); a lock keyed on the immediate parent can never protect an ancestor-scoped count (`max_child_runs` over a subtree — two coordinators hash to different keys and both pass under READ COMMITTED) → lock the TREE ROOT too, parent-then-root on every path (re-entrant when equal). A "CAS" over a FILESYSTEM is check-then-act until something serializes it — `atomicWrite*` answers "is the file torn?", never "can two writers both win?"; hold a per-`(project, agent)` `pg_advisory_xact_lock` across read → compare → write (mirror `social/relations.ts`) and return the post-write state captured INSIDE the lock.
19. **A status-guarded CAS is NOT a precondition check.** It fires at the END, so everything irreversible above it has already happened when it refuses; if a handler can refuse, validate BEFORE the first irreversible act (`ABANDONABLE_STATUSES` before the cascade, identical 409) and re-read the value at the MOMENT it matters — a status fetched five awaits earlier is a hint. A refused request leaves NO TRACE. Order is lock → verify not-already-done → commit intent → perform effect: `reset --hard` + `git clean -fd` ran BEFORE the tx locking `hitl_requests`; split policy RESOLUTION (read-only, before the tx) from APPLICATION (after the marker commits, winner only) — an "idempotent on retry" comment justifies crash recovery, not admission. Preconditions protecting irreversible work (a clean committed tree before a version cut) run INSIDE the same exclusive lease as the work, never at the route level before it.
20. **Every call to a status-guarded transition branches on its RESULT** before any dependent effect — grep `crashRunningRun`, `finalizeAgentRun`, `markAbandoned`, `crashWaitingOnChildren` for callers that discard the return; a lost CAS is `skipped` at WARN and touches nothing (materialization cleanup, assignment close, slot promote, counters). State read BEFORE a CAS and acted on AFTER it is covered BY the CAS (guard on `current_step_id`, not only `status` — `Running` survives node A finishing and B starting across a cross-process `await checkpointSession`) or re-read inside the tx; `markNodeNeedsInput({requireRunning})` rolls back a lost attempt-level race; resolve a parked attempt INSIDE the lock after the already-delivered check.
21. **Guarded and unguarded variants of one write coexisting = a bug queue** (`failAttemptIfActive` at 1 of 9 sites) — fix the CLASS at the choke point: `setAttemptPhase` CASes on the EXACT observed non-terminal phase and returns boolean; `advancePhaseOrCancel` throws `CONFLICT` on a loss, cancelling every git side effect below; the attempt phase is the DURABLE cancellation signal (survives restart; a lost CAS MEANS the run was terminalized). A `// NO same-session escape` mutex signals the SAME hazard on every sibling that mutates the resource — generalize to a working-dir mutex and re-read state UNDER it; a mutation on the SHARED parent repo takes `withRepoPromotionLock` and PROVES divergence with `isAncestor` (a dirty parent checkout also fails `merge --ff-only`).
22. **Before inverting an ordering to close a race, enumerate the recovery for the NEW partial state** — a window with a tested backstop beats a narrower window with none (abandon stays cascade-first: reconcile M-2 covers it; the inverted order has an unrecovered window and `auto_launch_run_plan` could launch into an abandoned tree).

### Git mechanics: diff range, immutable refs, worktree isolation, branch-ref sinks

**Source**: 2026-06-02-03.12, 2026-06-04-13.03, 2026-06-05-15.06, 2026-06-09-13.01, 2026-06-09-20.30, 2026-06-01-15.31, 2026-05-31-14.18
**Rule**:

- **2-dot vs 3-dot:** a fixed stored SHA base → `git diff base..branch` (literal tree delta); two MOVING branch tips where excluding the base's own advancement is intended → `base...branch` (3-dot). A `...` against a fixed point silently omits committed changes on a history-rewritten branch (`diffRunWorkspace`/`diffNameStatus` used 3-dot wrongly).
- **Immutable refs for stored evidence:** persist `resolveRefSha` = `git rev-parse --verify <ref>^{commit}` (schema-hardened, no shell), never a live branch NAME — an old artifact renders the wrong diff once the branch advances.
- **Worktree ignore:** materialized run files go in a worktree `.gitignore` (+ `git update-index --skip-worktree` on the `.gitignore` itself), NEVER `.git/info/exclude` — in a LINKED worktree `git rev-parse --git-path info/exclude` resolves to the SHARED common dir (`<main>/.git/info/exclude`) and leaks the rule to every worktree + main. `--skip-worktree` hides changes to TRACKED files only; a freshly-materialized UNTRACKED file needs gitignore. First ask whether the artifact NEEDS to be in the worktree at all (a `command_check` script runs with CWD=worktree, so its logic can stay inline in the manifest — nothing to materialize or leak).
- **Branch-ref validation at EVERY sink:** export `branchNameSchema` and apply a shared `assertSafeBranchRefs(args)` as the first statement of every git/PR adapter (`gh pr create --base`, `glab`, Gitea `base`), sweeping BOTH server-generated `sourceBranch` and request-derived `targetBranch` — a bypass flag (`allowTargetDrift`) must not route around it.
- **Ordering & compensation:** the irreversible/external mutation (`git init` / `git clone` / `git worktree add -b`) is the LAST committed step after all cheap preconditions pass; every compensating `rm`/branch-delete is gated on proof THIS request created the path (`clonedByUs`, `gitStatus === "initialized"`), and failed-launch compensation must delete the branch ref `git worktree add -b` created, not just the worktree dir.
- **Gates run BEFORE irreversible side-effects:** a finalize-tx re-check cannot undo an already-executed `git merge` + push — the failure-terminal/promotability guard runs in the claim tx before ANY git side-effect, and rework-vs-promote serialize on the SAME `workspaces` row `FOR UPDATE`. Ask "if this gate fails, can I undo what already happened?" — if not, move the gate earlier.
- **Ownership state lives in the DB, not a filesystem observation:** deciding allocator-vs-reuser from `listWorktrees` leaves a crash window between `git worktree add` and the row insert — decide from the `workspaces` row, make the insert idempotent (`onConflictDoNothing(worktree_path)`), add orphan-claim + reconcile recovery, and scope teardown with an `allocatedWorktree` flag so it removes only a dir THIS launch created.
- **Proof-of-ownership = exclusive create:** a `rm -rf`/branch-delete compensation flag is set only from an EXCLUSIVE create (non-recursive `mkdir` with `EEXIST` → refuse `PRECONDITION`; `mkdtemp`+rename; `clone -b`), never an idempotent recursive mkdir that can't distinguish create from already-exists.
- **Counter/sequence bumps another feature reads as a budget** (`tasks.attempt_number` as the ralph-loop cap) are side-effects — sequence them after every cheap throwing precondition (launchability, branch allow-list, `resolveBaseCommit`), immediately before the point of no return; grep every reader of the column before accepting a "burned value is meaningless" claim.
- **Relaunch/restart pins to the STORED immutable base commit**, never re-resolves a moving ref.
- **`git check-ignore` is the ground-truth ignore test**, but first branch on `rev-parse --is-inside-work-tree` ("not a git tree" = no leak surface = write; "git tree, not ignored" = skip), and a best-effort `ensureWorktreeGitExclude` has its OUTCOME confirmed before the dependent write.
  **Source (additions)**: 2026-06-22-11.08, 2026-06-22-13.40, 2026-06-18-15.42, 2026-06-30-12.23, 2026-07-04-00.47-experiment-comparison-review-fixes, 2026-06-22-22.14

- **Model the POINT OF NO RETURN explicitly:** once an irreversible external side effect lands (force-push, PR create, publish) a flag (`pushCommitted`) marks it and EVERY compensating path consults it — the catch aborts ONLY when `!settled && !pushCommitted`; post-push it logs the decisive fields (`headShaAfter`) and releases the run best-effort (Review + claim + slot) so a landed push is neither rolled back nor deadlocks promotion; "add the missing case to the cleanup path" past that point manufactures divergence — ask of every catch that restores/reverts which side effects may already have landed above it.
- **A side effect before a transaction needs compensation, or the transaction comes FIRST** — ask BOTH directions; "the side effect succeeds and the tx fails" is the one that gets skipped (reopen attached a GC'd worktree before its tx; a throw rolled back `removed_at` while the worktree stayed attached, and no sweep converges that shape); the compensating `removeWorktree` on the throw path is best-effort and RETHROWS the original error.
- **Rebase INSIDE the source worktree, then fast-forward the parent target** — never check out a branch already owned by a linked worktree from the parent checkout; reject a stale `Maister-Node` trailer when no active node metadata exists, including `git commit -C` reuse.
- **A git RANGE answers a QUESTION** — "what did the reviewer see" (`merge-base..branch`, review artifacts) ≠ "what did the operator add" (`claim_head_sha..branch`); record the second anchor at the ONE insert point both claim shapes share (`node_attempts.claim_head_sha` written by `claimTakeover`); a null head falls back to the old count (a wrong zero would refuse a return that carried work).
- **Bootstrap-then-compensate:** a generated file (`maister.yaml` at registration) is removed on failure ONLY when byte-for-byte unchanged; an existing invalid manifest is never replaced.

### No write may be sequenced after a terminal status flip; required accountability writes share the success tx

**Source**: 2026-06-10-23.44, 2026-06-08-21.13, 2026-06-08-21.45, 2026-06-08-22.26
**Rule**: A terminal row is never re-executed, so an `UPDATE … SET outputArtifactRef` AFTER `markGatePassed`/`markGateFailed` leaves a crash-window where the terminal gate permanently lacks its back-ref. Write every outcome field (back-refs, evidence links, payload columns) in the SAME UPDATE as the terminal transition, or strictly BEFORE it — record the report while the row is still `running` and rely on the re-execution-of-non-terminal-rows recovery path. Required accountability/audit writes are part of the success commit: never wrap `recordTokenAudit()` in `.catch(() => {})` — use `recordRequiredTokenAudit()` that logs `[FIX:token-audit-required]` and RETHROWS (fail-closed), and write the success audit in the SAME transaction as the durable success marker (task create/update, run launch inside the launch tx so audit failure triggers worktree compensation, HITL respond in the delivered-marker tx, idle resume `NeedsInputIdle → NeedsInput` with the 202 audit). A mutating `/api/v1/ext/*` route needs `successAuditInWork: true` — `handleExt` writes the default success audit AFTER `work()`, safe only for read-only routes. Close active `open`/`claimed` assignments from EVERY terminal lifecycle path (promote, discard/abandon, crash, reconcile, keepalive/HITL timeout) through a system actor, in the same status-guarded transaction.

Extensions: a durable outbox row (`emitDomainEvent`/`emitWebhookEvent`) is a persistent write and belongs in the SAME tx as the state change (ADR-086 exactly-once) — never the "notify after commit" bucket (that is for `scheduleResume`-style in-process wakes only); if a sibling terminal path emits in-tx (`run.failed`), the new path (`run.escalated`) must too. A give-up/compensating write re-asserts the state it compensates FOR under its CAS (`holdAndComment` gained `status='Review'` and reports whether it landed — count the give-up metric only then; otherwise classify as a benign lost race), or it corrupts a concurrent winner's terminal record. **Source**: 2026-07-03-16.16, 2026-07-01-12.38, 2026-06-24-03.08, 2026-06-18-15.42, 2026-06-21-02.04, 2026-07-04-13.37-experiment-comparison-review-fix-followup, 2026-06-29-22.01, 2026-06-23-23.16

### Recovery owners for durable interactions; recovery-window tables are normative

**Source**: 2026-07-15-11.19-gate-chat-recovery, 2026-07-14-23.40-flow-review-workspace-findings, 2026-07-14T19-18-32-plan-review-handoff-recovery, 2026-07-16-16.05, 2026-07-16-11.20, 2026-09-03-21.47, 2026-09-03-23.46
**Rule**: Any durable interaction normally settled by an IN-MEMORY callback (a lease timer, a pending gate-chat turn, a persisted-but-unmarked decision answer) needs a RECONCILIATION OWNER after a web-process restart: claim it under a durable recovery lease, cancel the live supervisor prompt, restore the checkpoint baseline, and only then terminalize; a failed recovery stays fenced for retry. A lease expiry is a CANCELLATION DEADLINE owned by the running handler, not a terminal coordinator outcome — the coordinator stays pending until the owner has awaited the prompt, performed L3 restore, and written its terminal abort (a lease can never release the rework fence before L3 settles). Every recovery window is a NORMATIVE table in the ADR/analytics enumerating each `status × mode` cell — the implementation must not define the windows it happens to satisfy: the resolver's own parking spot (`NeedsInput`, `agent_running`) had no arm because reconcile was `Running`-only; a mechanical sync parks in `Review` and had none either. Never enumerate a closed phase set POSITIVELY inside a recovery arm when its complement is derivable (`mode==="mechanical" && !hasSyncDriver` over terminal-filtered candidates) — the set grows on the PRODUCER's side (`starting|rebasing` was written when `verifying|pushing` did not exist) and a stranded claim blocked all six lifecycle ops forever; a phase past the point of no return (`pushing`) gets a FORWARD-SETTLE branch (ask ORIGIN: `remoteBranchHead` vs worktree HEAD → `succeeded/pushed`), never a restore, and an UNPROVEN push is never restored. Under a dead coordinator enumerate what each child can be HOLDING (crash paths never cascade): `Pending → Abandoned`; `NeedsInput`/`NeedsInputIdle`/`Review → Crashed` with the open `hitl_requests` row closed in the same tx; `HumanWorking` → left, WARN; a `WaitingOnChildren` sub-orchestrator → `orphaned-orchestrator` via the stuck path (its own children cascaded first); coordinator death is ANY terminal parent (`Failed` without cascade, `Done` leaving a child), not the `Crashed|Abandoned` pair the cascade writes. Load orphans with a TARGETED query (`NOT EXISTS (a parent row still alive)`), never by widening the hot candidate list (starves real candidates under `PER_TICK_LIMIT`). A new route into an existing arm INHERITS that arm's preconditions — the stuck path's classifier guaranteed `!liveSession`, so `orphaned-orchestrator` must stop the coordinator's own live sessions BEFORE the cascade with E5 semantics (`EXECUTOR_UNAVAILABLE` → leave the whole sub-tree for the next tick).

### Idempotency keys, digests, and canonical payload equality

**Source**: 2026-07-25-12.09, 2026-07-25-11.14, 2026-09-01-04.15, 2026-07-14-23.40-flow-review-workspace-findings
**Rule**: An idempotency/dedup key that resolves to a STORED result verifies the incoming payload matches before aliasing (`existing.definitionDigest === contentDigest(definition)` — the same digest that stamped the row); "return existing on conflict" is a silent-substitution bug unless content-guarded — a changed payload under a used key CONFLICTS; cover same-key/same-payload (dedup) AND same-key/different-payload (CONFLICT). `sameDecision`, not `sameRequest`: an already-delivered branch reached by a DIFFERENT payload is a LOSER, not a retry — it mutates nothing and re-drives only when the arriving payload is byte-identical to the stored decision. Every value feeding a dedup digest is reproducible from the idempotency key (`inline-${idempotencyKey}-${index}`) — never inject `Date.now()`/random ABOVE a dedup. Payload equality for retries compares CANONICALIZED bodies (recursively sorted object keys, array order preserved), never raw JSON serialization.

### Freeze/pin/snapshot features: every read path reads the frozen source; validation lives on the action path

**Source**: 2026-07-26-12.32, 2026-07-25-11.14, 2026-07-24-15.19, 2026-07-27-21.50, 2026-07-11-22.35-m43-review-remediation
**Rule**: "Recorded for provenance" without a SWITCHED read path is the defect shape: for any freeze/snapshot/pin feature enumerate EVERY read path and make it read the frozen source (judge context, pair fan-out, tournament matrix, objective checks, launch resolution all read live membership/revision) — the self-check is a grep for the LIVE accessor (`orderedStudyParticipantIds`, `isNull(removedAt)` inside the execution pipeline, `flow.enabledRevisionId` after a pin exists). A fan-out (pairs, checks) and its aggregation in different modules SHARE one participant-set function derived from the sealed snapshot (`frozenExecutionParticipants()` from `participant_watermarks`, tombstone-inclusive, fail-closed without a snapshot); walk the frozen expected matrix and synthesize empty verdicts so a lost pair keeps `partial`. Apply the hard-warn rule to EVERY un-honorable declared-input class (intent AND `mode:"runner"` pins on non-`session:` slots) and enforce validation ON THE ACTION PATH (the launch route runs `preflightStudyRecipe` and BLOCKS on hard refusal before any write) — an optional preview plus warn-on-one-variant leaves a hole either alone closes; one pure SSOT predicate (`isSeamThreadableSlot`) feeds BOTH the seam and preflight. Mutating pairs are SYMMETRIC: if save is CAS-guarded, delete takes the same `ifHash` (`ifHash: null` matching an absent file IS the idempotent case); when N artifacts describe the SAME BYTES (prompt block, snapshot, hash), normalize ONCE at the source or not at all.

### Activating dormant gates and reasoning about limits, budgets, and coupled defaults

**Source**: 2026-09-03-15.06, 2026-09-03-17.20, 2026-09-03-17.21, 2026-09-01-05.40, 2026-07-12-11.42, 2026-07-15-18.13-trusted-package-flow-enablement, 2026-07-12-23.49-observatory-agentization-review-fixes, 2026-08-01-09.09
**Rule**: When a guard turns out to be DEAD the fix is TWO tasks: re-enable it, then RE-DERIVE every semantic that was never exercised (grep the spec for the enabled feature — it addressed only a parked `WaitingOnChildren` root; a `Running` root's tree breach in the escalate band was swallowed because `pickHigher` keeps the FIRST verdict at an equal rung → promote tree verdicts at CLASSIFICATION, not after arbitration). FIRST search for COMPENSATING WORKAROUNDS — a comment "X never fires, so we also do Y" (`budget-default.ts` seeding BOTH `run` and `tree` ceilings) is a load-bearing dependency on the bug; `rg` the feature name in comments. When a fix corrects a CONVENTION, grep the PREDICATE, not the symptom (`rg "rootRunId ===|root_run_id ="` — launchers write `rootRunId = parent.rootRunId ?? parent.id`, so the ROOT carries NULL, nothing self-stamps; rootness = `parentRunId === null` (+ `hasDescendants` for tree ceilings); tree reads scope `id = root OR root_run_id = root`). A guard's PRESENCE is not its REACHABILITY — trace every field a guard reads off a loose payload back to the producer that populates it (`ref.parentRunId` was never set on the `promoteNextPending` edge). Redundant MEASUREMENT ≠ redundant LIMIT: two ceilings over one meter are two constraints and the stricter binds — skip a meter only when the other ceilings are not stricter (`tree.escalate >= run.escalate && tree.hard >= run.hard`), and skip NARROWLY (tree TOKENS for a childless root; `wallclock` is tree-scope-only, so dropping the scope silently disables lone-run duration bounds). A COUPLED default needs a COUPLED raise — seeding two ceilings from one value must lift both on a raise, only on EXACT equality (the shape `applyDefaultBudgetForUnattended` writes), preserving a deliberately tighter or looser value, and the audit names every `coupledScopes` it changed. Before building a fence, verify it can BLOCK the racing path (`runner-graph.ts` holds zero `claimLifecycleOperation` refs, so a lifecycle claim cannot fence the runner). Ask whether a guard's FAILING state is reachable in production — a refusal whose condition the system never produces (empty `merge-base..branch` on a Review run) is dead code that reads as protection. Adding a scheduler kind fans out to EVERY closed set: registration, lifecycle, `claimDueJobs` CTE, dispatch, admin, OpenAPI, AND the localized admin label map. A trust/gate transition also ADVANCES the rows waiting on it (`trustPackageRevision` left ready member Flows `Installed`) with a one-time repair migration for existing rows; conflict-ignore seeding (`onConflictDoNothing`) has NO reactivation transition — reseed archive-disabled jobs on reactivation while retaining native-threshold disables. Preflight probes assert only state INVARIANT across revisions (host tools); branch-owned config is validated from the EXECUTION revision (ADR-091 probes run in `project.repoPath` before the worktree exists). A hard cut-over needs BOTH a DATABASE backstop against stale binaries (trigger rejecting new legacy-flow runs) AND a post-migration reconciliation of orphaned EXTERNAL resources.

### Process-boundary contracts: single-flight lookups, fake parity, real wire order, fenced binding

**Source**: 2026-09-04-00.21, 2026-07-11-14.47, 2026-07-11-21.30, 2026-07-11-12.25, 2026-07-27-11.56, 2026-07-14-human-ask-review-remediation, 2026-09-03-15.06
**Rule**: A resolver/registrar/LOOKUP MUST NOT await domain sweeps — the registrar awaited `runReconcileSweep` inside the resolver's single-flight promise, the sweep re-dispatched `runFlow`, whose first agent node re-entered the same resolver → a process-wide hang after any supervisor restart; schedule domain work out-of-band (`restarted:true` + the periodic `system_sweep`); self-check: "does anything inside a single-flight promise call back into the same resolver?". When a contract is split across two processes (host handle registry vs web re-adopt policy; released-but-reused paths), rebuild the fake RULE-BY-RULE to the peer's semantics and run ONE scenario table against the fake AND a real peer child (~90 fake-backed suites had proved only the fake's contract). A mock for an ordering-sensitive interceptor emits the REAL adapter sequence — grep the bundled adapter `dist`: `sessionUpdate:"tool_call"` `status:"pending"` streams BEFORE `requestPermission`, and the execution signal is `tool_call_update` `status:"completed"|"failed"`; replay the triple pending→permission→execution, never the author's mental model. A value derived in module A and consumed in service B gets a test at the SEND site (the spy captures `ctx.enforcementProfile` on the outgoing `createSession` body) — derive-unit + accept-schema leave the join unguarded. Derive-then-inject is an ordering bug: appending a value (the maister MCP facade) to a delivered list AFTER a dependent field was derived from it (`enforcementProfile.mcps.allowServers`) updates the dependent field in the same step. Enumerate every CLAIM site and every CATCH site as a checklist when a rule says "every re-entry mints" / "every fenced outcome yields" — grep `forRun(`, `mintPlacement(`, `isFencedError(` and classify each hit; drivers bind by the assignment id their OWN claim minted (`executionFor(runId, {assignmentId})`), never "whatever is active at bind time". A list-then-delete against a peer is a two-step protocol: classify scoped ABSENCE (bound-session 404 → `gone`) separately from transport availability (5xx/network → `EXECUTOR_UNAVAILABLE`) and identity misuse; reject a live same-run session whose ACP id DIFFERS from the stored binding; share ONE deletion-failure classifier (`deleteSession` mapped any non-ok without a recognized body code to terminal `ACP_PROTOCOL` while the supervisor's unhandled-error handler emits exactly `500 {code:"ACP_PROTOCOL"}`). ### Tests written during implementation: seams, seeds, races, and wire assertions

**Source**: 2026-07-16-13.03, 2026-07-22-01.14, 2026-07-16-16.05, 2026-09-03-23.46, 2026-09-04-01.33, 2026-07-27-20.55, 2026-07-27-21.50, 2026-09-03-14.30, 2026-07-21-23.50, 2026-08-06-19.10, 2026-07-16-14.05, 2026-09-03-21.47, 2026-09-03-16.10, 2026-07-13-00.59-unified-test-database-review-remediation, 2026-09-02-12.10, 2026-09-01-04.15, 2026-07-12-22.35-observatory-agentization-final-hardening, 2026-07-11-21.30
**Rule**: Mocks for HOOK-RETURNED functions used in `useCallback`/`useEffect` deps preserve the real hook's STABLE IDENTITY (cache one translator per namespace inside the hoisted `vi.mock` factory) — a fresh function per render looped to a 4 GB OOM; mounted tests that load on effect assert EXACT side-effect counts. When a SHARED service (`launchRun`, a HITL composite, a promotion service) gains a new DB-touching dependency or a required argument, grep its `__tests__` for the fake-db/mock/harness pattern and update EVERY caller test in the SAME change ("unknown table" / "innerJoin is not a function" from a hand-rolled fake DB is the tell; assert the new production ARGUMENT rather than relying on a permissive stub; a new shared React provider sweeps every test render). SEEDS ARE PRODUCTION-SHAPED: never seed a state no writer produces (a claim with no `lifecycle_operation_attempt_id`, a self-stamped `root_run_id`, `prState:"closed"+prHasConflicts:true`, a driverless paused run that is really a post-restart orphan); READ the DB CHECK constraints before seeding (`hitl_requests` requires a task binding only on agent questions); an unusual precondition that makes a guard fire earns a second test in the ordinary shape; correct the seed to the realistic precondition — never weaken the gate. RACES: put the two-racer at the layer that OWNS the invariant (store, not route — racers traversing identical I/O self-serialize), contend on the INVARIANT not the lock (two DIFFERENT parents for an ancestor-scoped count; the winner INSERTS its children uncommitted; assert the racer PARKS via `pg_stat_activity`), assert ORDER via signals (mocks that fire when the winner ENTERS its side-effect) never "already happened by now", cover BOTH orderings, release every barrier in `finally` and await both racers to settlement (a parked winner leaked into the NEXT test's spies), inject through the sweep's `listWorktrees` hook rather than module mocks, and mutation-check by disabling the guard. ASSERTIONS: a wire field exists to reach a client, so at least one test reads it off a real `Response` (`(await res.json()).details`) — a value placed in a mock is not tested; every allow-list/grant gets a POSITIVE test (a deny-only test cannot distinguish "refused" from "broken"); assert the DISCRIMINANT only the new path produces (`status === "Failed"` was produced by the bug too; the token revoked + a queued AGENT run promoted was not); a composition test asserts `errors: []`; pin the INERT/negative contract with `not.toHaveBeenCalledWith(objectContaining({ field: expect.anything() }))`; prefer `toHaveBeenCalledWith(expect.objectContaining(...))` over `mock.calls[0][0]` on a no-param `vi.fn`; role mocks refuse the real role's FULL deny set; run integration tests with the REAL child kind the fixture produces. Seams: a second `vi.mock` of the same module in one file silently SHADOWS the first; lazy-import `runner-graph` (a top-level import pulls the supervisor client into 57 unit tests); a wrapper owning an ephemeral resource has a process-signal contract tested with a SIGTERM-resistant child, plus a cleanup-FAILURE case (`Pool.end()` throws → container still shut down).
