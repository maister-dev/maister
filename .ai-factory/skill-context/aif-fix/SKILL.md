### Renumbering a shared ADR / migration namespace is grep-to-zero, never a global find-replace
**Source**: 2026-06-10-23.57.md, 2026-06-11-12.51.md, 2026-06-11-14.45.md, 2026-06-09-14.23.md, 2026-06-09-18.47.md
**Rule**: When a sibling branch must renumber its ADR/migration because main already claimed the number, NEVER run a global `sed s/ADR-071/ADR-072/`. Two sibling features each own an adjacent number and each mentions the OTHER's number in prose, so a global replace over-reaches (rewrites a legitimate sibling ref like `[ADR-072](#adr-071-…)`) and the separately-scoped ADR vs migration passes desync (under-reach). Procedure:
1. Enumerate every occurrence and classify each by the feature it names; only the renumbered feature's own references change.
2. Run **ONE** pass covering BOTH the ADR number and the migration number together.
3. Finish with **grep-to-zero** across ALL forms: `ADR-NNN`, the lowercase `adr-nnn` **anchor slug as a SECOND sed pass**, `NNNN_name`, AND bare `` `NNNN` ``. `CLAUDE.md` and `.ai-factory/ROADMAP.md` ARE part of the surface (not just `docs/`); exclude `.ai-factory/plans` / `patches` archives and generated `web/.next`.
4. Leave opaque PERSISTED id-segment literals frozen (`runs.…:adr071:rework-comments` is never parsed back to a number; "correcting" it orphans existing rows) — add a one-line WHY comment so a future reader doesn't "fix" it.
5. Verify the migration number against `migrations/meta/_journal.json`, not the prose (`0029` was documented in 5 places but shipped as `0030`).

Do the renumber/re-port as its OWN focused session, AFTER rebasing/merging onto the integration target — never reconcile docs against a branch baseline that is behind main (editing a stale pre-feature copy re-derives corrections main already shipped). macOS BSD-grep gotcha: for glob-unsafe paths like `app/api/[slug]/…`, `grep -rlZE … | xargs -0 perl` malfunctions — use `grep -rlE … | while IFS= read -r f; do perl -pi -e '…' "$f"; done` (quoted `"$f"` prevents `[slug]` shell-globbing; one perl per file).

Extensions (2026-07 batch): grep-to-zero includes PROSE number forms — `pre-NNNN`, `since NNNN`, `as of NNNN` — and prefers number-agnostic phrasing (`pre-ADR-118`) in long-lived comments so they survive the next renumber. Verify with BOTH single-line and whitespace-tolerant patterns (`grep -z` / multi-line) — a load-bearing claim wrapped across two lines evades a naive grep. Docs greps for columns try BOTH snake_case and the Drizzle camelCase field name (`database-schema.md` documents camelCase). Classify every residual hit as frozen-historical (pre-change ADR bodies, dated findings docs — they describe the past and STAY; annotate with a supersession pointer) vs current-contract (rewritten) — rewriting history falsifies it. A migration is a TRIPLE (SQL file + `_journal.json` entry + `meta/<NNNN>_snapshot.json`) — check the newest journal entry has a matching snapshot; frozen SDD/spec files count as migration-number surfaces (reconcile against the as-built file on disk).

### Verify the finding before fixing it
**Source**: 2026-06-22-13.40, 2026-06-23-23.16, 2026-06-22-22.14, 2026-06-18-23.44, 2026-07-02-12.48, 2026-06-25-20.14
**Rule**: Confirm every finding in SOURCE before editing:
1. A reviewer's execution-order inference is checked against the actual lines (side-effect at 666-672 vs gate at 815 was confirmed in source before any edit).
2. A finding's PREMISE ("repo rule X exists") is verified — grep whether the claimed convention actually holds (a claimed "auth-first repo rule" was refuted: parse-before-auth was the universal convention across all 15 admin routes at that time; today auth-first IS the rule — the point is to verify, not assume).
3. A spec-conformant limitation is not a bug — grep the target's own doc comment for a best-effort/never-fail invariant before applying a "fail closed → throw" suggestion ("a write failure never fails the run" made degrade-to-skip the correct fix); document kind-based scope (Known-limitation note + Edge-case bullet) instead of mechanically applying a reviewer's suggestion.
4. When a review claims "X was deleted", establish WHERE X previously lived (`git show HEAD:<path>`, diff old-fixture vs old-deliverable) — the real defect may be that the shipped artifact NEVER had it.
5. A prior fix round's patch note is a CLAIM, not evidence — re-verify asserted guarantees ("worktree-add failures roll the pin back") against the code.

Never add `console.log` to satisfy the template; never add logging deps to modules whose contract forbids them.
