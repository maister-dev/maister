### TDD protocol for every implementation task

1. **SPEC:** select acceptance/edge IDs, exact owning boundary and existing test file. Freeze expected state/HTTP/error outcome first. Prove the runner selects the test; the case title carries its primary ID. Use the shared fixture/scenario table instead of another parallel test suite.
2. **RED:** write or migrate only the next slice's behavioral test, execute it against unchanged production behavior and retain its actual expected-versus-observed failure. Missing imports, a broken fixture, unavailable Docker/DB, an unselected case, or an unrelated timeout is setup failure, not RED. A route's absent required behavior is legitimate RED when the real HTTP assertion demonstrates it. Existing already-correct guarantees get baseline evidence; do not mutate correct code just to manufacture RED.
3. **GREEN:** implement the smallest conforming change, including required migration/DTO/assertion updates; rerun the exact RED cases and their owning regressions. Tests inspect real DB state and Git refs/index/files and, for runner selection, actual launch payload/provenance. Do not change the contract, skip tests, add retries/timeouts, or narrow parameter rows to obtain green.
4. **REFACTOR:** only after green, remove duplication and simplify the changed slice under strict typing and project conventions. Keep projection/patching pure, orchestration and Git/DB effects separate, functions single-purpose, and dependencies explicit. Apply SOLID at those boundaries without introducing classes, generic frameworks or abstractions used only once. Preserve KISS/DRY/YAGNI, existing errors/logging, English comments and existing import/lint style. Rerun the same tests; no change means record that no refactor was necessary.
5. **ACCEPT:** the slice's spec clauses, schema/response invariants and tests agree, with RED/GREEN/refactor commands/exits and revision/source identity retained in normal task evidence. Phase completion additionally requires the full defined suites green and the feature matrix complete. Do not create a separate report framework for these receipts.

Write tests alongside their owning slice, not all future failing cases at once and not after the feature. T10.1 designs the inventory; each T2.1–T9.1/T14.1 owns its RED/GREEN/refactor work and existing assertion migration. T12.1 verifies the complete inventory; it is not the first time acceptance runs.

Test economy: one primary test boundary per invariant. Integration owns semantic status, mutation effects, Git safety, recovery, auth and concurrency; HTTP samples from those same cases feed schema conformance checks; migration coverage owns upgrade/constraint/trigger behavior; Playwright owns user-visible review/navigation/copy/accessibility only. E2E must not replay the complete backend failure Cartesian product. Parameterize paths that enforce the same rule, but use distinct cases for materially different side-effect/crash windows. No snapshot-of-implementation, source-string assertion, trivial accessor test, sleep-based race, coverage-percentage target, or green test that can pass while its enforcing guard is disabled qualifies as new feature coverage. Keep existing useful tests; remove only proven duplicate/obsolete assertions with an identified replacement owner.

## Proposed behavior and safety contract

### Status and ownership

Separate three facts: runtime configuration is applied in the DB; exportable values equal/differ from committed `maister.yaml`; local repository state permits/blocks saving. The repository baseline is the configured local main branch's committed manifest, not `maisterYamlPath` and not an uncommitted working file. For an unborn branch, use an explicit absent-HEAD baseline. Push status is independent of local commit status.

Proposed DTO axes:

- `exportState`: `unverified | missing | in_sync | pending | blocked`.
- `repositoryState`: `ready | dirty | wrong_branch | detached | operation_in_progress | unavailable`, with localized remediation reason codes.
- Latest operation receipt: operation ID, stage, base/commit SHA, target branch, and independent push outcome when authorized to see it.

An equivalent but untracked file is not committed configuration: status remains missing and saving is blocked. A malformed committed manifest yields blocked, never a misleading equality result. `maisterYamlPath` remains a locator for source-aware consumers; it is not persistence provenance. No historical path backfill is required. Existing untracked/bootstrap manifests are user-owned: advise reviewing and manually committing or moving them, then preview again. Do not silently adopt, overwrite, delete, or auto-commit them.

Freshness is explicit: a detailed status access, preview, or confirm reads current Git evidence and returns `observedAt` plus observed branch/HEAD and export revision. Portfolio uses `unverified` with optional `lastObservedExportState`/timestamp when it has only cached evidence; never render cached `in_sync` as confirmed current. Opening Settings/detail or explicitly refreshing re-observes the repository. External edits/pulls do not emit MAIster DB invalidation, so a saved receipt alone cannot establish current equality. No automatic polling is added.

Keep Settings → Git action visible after every save and after banner dismissal. A dismissed banner does not suppress status or access. A no-op save reports that exportable configuration already matches Git, creates no commit, and leaves ordinary repository work unchanged. DB-only setting changes do not falsely create pending-export status.

### Preview and confirmation

Proposed extension of the existing endpoint family:

No repository mutation. |
| `POST /api/projects/{slug}/persist-config` | Confirm `{previewId}` only | Same two gates; reject legacy unbound `{push}` requests with an actionable fresh-preview reason. Return durable commit/no-op receipt. |

| `POST /api/projects/{slug}/persist-config/{operationId}/push/preview` | Empty strict object; prepare a separate immutable outgoing review for a committed receipt | Same two gates; return `pushPreviewId`, recorded SHA, redacted destination, remote baseline and full outgoing ancestor range. Identifiers for every route: `slug` is `url-param`; user/principal is `auth-context`; project ID, canonical repo/common-Git-dir, path, main branch, and export snapshot are `server-state`. `previewId`, `pushPreviewId`, and `operationId` are untrusted body/path operation identifiers: query by ID **and** server-resolved project **and** principal, then reauthorize. The push preview additionally belongs to the exact committed operation. No body-supplied filesystem path, SHA, package/install ID, target branch, message, remote URL, or raw YAML is accepted as authority. Package mutation routes retain existing validated install/attachment identifiers and ownership joins; no widened grants.

Use existing fixed message `chore(maister): persist project config` for the first version and display its exact value. A later editable message would require a new preview. Preserve per-field author defaults and show the current warning. Cancel/expiry before confirmation has no filesystem/Git effect. Never enable confirmation on a truncated diff: refuse oversized previews with guidance to inspect/reduce the manifest. No YAML or diff appears in general logs or scalar portfolio DTOs; detailed API responses are `no-store`.

The review is a server-stored immutable snapshot with a content digest: principal/project; canonical repository and target branch; exact base SHA (or absence); original manifest blob/mode; proposed bytes/blob; complete diff; effective export projection and monotonic export revision; canonical shared index entries/stages/modes/flags and absence; tracked/untracked/ignored target-file state; worktree status; Git operation state; message and author policy. Inspect with optional Git index-refresh writes disabled. Retain byte fingerprints as nonmutation evidence, but do not invalidate a preview for stat-cache-only refreshes with identical canonical index entries. Resolve current author/config policy again before committing if it can affect the reviewed outcome. A bounded preview expiry (10 minutes) limits retention; stored digest inputs contain no retry-time random/time values beyond the separately stored identity/expiry.

On confirmation, reread authoritative DB and Git state under the matching locks. A changed export revision, config digest, branch, HEAD, manifest, index, worktree status, or active Git operation invalidates the review. Return a structured `CONFLICT` reason and require a fresh preview. Same preview + identical request returns its recorded receipt after verification; same key with different bound content conflicts. Expiry prevents a new commit, but never prevents reading/reconciling an already-created commit receipt.

Retain the current supported target: the currently checked-out configured main branch. Initial preview can display blockers and status, but no confirmable review is issued until preconditions hold.

**Implementation design gate:** existing `commitFile` and `ffUpdateLocalBranch` are insufficient by themselves. Prefer an operation-owned staging worktree and normal commit behavior so repository hooks/signing policy are not silently bypassed. Hooks that change proposed bytes/message, add paths, or fail must block publication. If a plumbing approach is required, document its hook/signing semantics in the superseding ADR before implementation. A check-then-rename, process-local mutex, or post-hoc diff check after committing unrelated work does not satisfy this gate.

External Git commands use Git's locks but arbitrary editors do not participate in MAIster's DB lock. Revalidate immediately at the guarded publication seam, use Git's refusal to overwrite changed files, and test edits injected at that seam. Never claim the DB mutex alone protects host files. If a state cannot be safely updated, preserve the private commit and stop with guidance. All recovery writes obey the same file/index protections. Do not broaden this change into automatic repair of arbitrary repository corruption.

Database disconnection never releases the repository ownership directory or the durable active intent. All managed parent mutators enter that common fence. A dead owner can be adopted only by explicit/startup recovery of the same accepted intent after proving the process dead. Unknown ownership stays fenced. No Git effect runs inside a DB transaction.

### Durable stages, failures, retry, and recovery

Proposed `project_config_persist_operations` stores preview intent/immutable digests, principal/project, exact base, proposed content locator or bytes, deterministic private-ref/staging identity, state and error reason, observed commit SHA, local-publication receipt, and independent push attempt/outcome. Add state CHECK constraints and indexes; pending operations must prevent deletion/cascade loss of their recovery evidence. Keep any private staged manifest in existing host-private Git/worktree storage: it is transient operation output, never a new configuration source.

Stages: `previewed → preparing → prepared → publishing → committed`; refusals before publication become `stale | failed`; interrupted/uncertain effects become `recovery_required`. `noop` is a terminal, effect-free preview outcome with no confirmation action. `committed` requires verified branch publication plus commit SHA; a commit in the private ref alone is `prepared`, visibly awaiting safe publication. Known failed commits that produced no commit require a fresh preview after remediation; ambiguous effects always remain recovery_required. A same-key replay of a terminal outcome returns that outcome and does not silently start another attempt. Push attempts have their own immutable review identity and `previewed | pending | succeeded | failed | unknown | stale` lifecycle; aggregate `not_requested` means no accepted push intent. A known failed push is retried through a newly confirmed push review, whereas an unknown result is reconciled before any reissue.

Order: commit preview/accepted intent in DB → create private staging and commit → verify/read back private commit and persist prepared receipt → record publishing intent → verify the durably fenced export revision/repository → guarded target publication → verify actual target/ref/blob/index/worktree → record committed receipt and first path assignment together → release mutation locks → optional separately authorized push. Git and PostgreSQL are not one transaction: recovery, not rollback fiction, closes each window. A DB failure after target publication never deletes the file, resets the branch, or compensates the successful commit.

| Reachable boundary / failure | Outcome and recovery | HTTP contract |
| --- | --- | --- |
| Invalid YAML, coordinates, request, or missing install consistency | No repository effects; actionable CONFIG reason. No guessed defaults or omitted attachments. | 422 |
| Dirty/staged/wrong branch/Git operation, stale/expired preview, another active publication | No new target effect; preserve user state; fresh preview or explicit resume as appropriate. | 409 |
| Death after intent, before/during private staging write | Inspect operation-owned path and private ref; clean only proven private material, then resume identical intent or mark stale. Target remains untouched. | Retry/operation status; never generic success |
| Commit hook/signing/identity/permission failure in staging | No target change; record failure and diagnostic reason; preserve user files/index. Retry same reviewed content only while still valid and after fixing cause. | 409 for precondition; 503 for transient I/O |
| Commit succeeded but acknowledgement/DB prepared receipt failed | Resolve deterministic private ref, verify parent/blob/path-set/message, adopt that exact SHA; never create a second commit. If uncertain, recovery_required. | 503 with operation ID until reconciled |
| Prepared commit exists, target state or config changed before publication | Keep private commit/recovery evidence; do not publish old configuration. Mark stale and require fresh preview. No silent rebase/cherry-pick. | 409 |
| Death during target ref/index/worktree publication | Inspect exact target/ref/index/file states against stored before/after values. Complete forward only for proven operation-owned states with no intervening user edits. Otherwise retain commit and require manual resolution; do not remove an unknown Git lock or overwrite work. | recovery_required / 409 |
| Target publication succeeded, DB finalization failed | Verify operation SHA/blob and target ancestry; finalize path/receipt without another commit, even if later DB configuration differs. Current status may correctly be pending again. | 503 until receipt repair, then 200 |
| Target subsequently advanced | Recognize a proven published operation commit in ancestry; never reset to it. Reconcile historical receipt separately from current semantic status. A private but never-published commit is not accepted solely because its blob matches. | 200 receipt, or 409 if publication cannot be proven |
| Push transport/auth/non-fast-forward rejection | Local commit remains committed; persist push failure and show retry. Never revert local configuration, commit, or path. | 200 committed receipt with failed push outcome |
| Push acknowledged remotely, local push receipt failed | Inspect the remote tip/ancestry and exact outgoing SHA; reconcile success if provable, otherwise unknown and explicit retry. | Receipt remains locally committed |
| Invalid remote / remote changed after outgoing review | No push; show new destination/range and require explicit review again. | 409 |

Recovery owner: a targeted persistence reconciler on explicit recover/accepted-confirm retry and a one-shot startup pass after migration compatibility checks in `web/instrumentation-node.ts`. GET status/receipt and new-preview creation never trigger repository mutations, including hidden recovery of an earlier operation. Startup scans only previously accepted intents, never previewed/noop rows, and never starts a push. It can adopt a proven completed outcome or finish a proven operation-owned partial local publication; starting a new commit after an unused/expired review requires a new preview. Before any new privileged Git write, recheck project lifecycle and the initiating principal's current authority. Revocation/archive stops new effects but never reverses or suppresses reconciliation of a commit that already happened.

The reconciler acquires the same repository lock and operation claim; after process death it acts only once Git child ownership/locks are settled. Use a bounded keyset scan with progress across every nonterminal row and a per-operation error outcome, so a poison row does not suppress later recovery. Startup recovery is observable and independent of unrelated execution-host availability; it adds no timer, watcher or polling loop. A disconnected request/timeout is not proof the subprocess failed. Retain private evidence for recovery_required; remove verified operation-owned staging only after durable finalization. Expired unused previews can be pruned without deleting nonterminal recovery evidence.

Do not automatically retry deterministic preconditions, hooks, conflicts, or commits with uncertain outcomes. Bounded transient external-service retries use warnings and the last failure; Git/network timeout always triggers outcome inspection before reissue. A user retry uses the same operation identity. Push uses explicit recorded commit SHA and destination, never a fresh moving branch ref; show all older unpushed ancestors that this push would also publish. Its own immutable, expiring `pushPreviewId` binds principal/project/operation, commit SHA, canonical remote-URL fingerprint, destination ref, observed remote baseline and complete outgoing range/digest. A changed destination, baseline or outgoing range requires a fresh push review, including after a failed attempt. Lost acknowledgements are reconciled before rejecting/reissuing the old intent. No force push or remote rollback. A failed or unrequested push does not prevent the next independent local configuration commit.

### Contract closure checklist for the specification gate

These are required design outputs of T13.1, not permission to improvise them while coding:

- **API completeness:** specify every body/response with `additionalProperties: false`, explicit nullable/required fields, timestamp format, decimal-string revision and the repository's supported Git hash format. `ready` carries a confirmable preview ID/digest/expiry/diff; `noop` has empty diff, no new commit and no confirm action; `blocked` carries localized reason keys and authorized repo-relative remediation. A recorded committed replay never becomes stale merely because HEAD later advanced. Add examples for each discriminant and each refusal family, invalid/empty/unknown-field bodies, and committed-with-push-failed/unknown receipts. A transient unavailable read is 503, not false missing/in_sync/terminal failure. Bound manifest/diff/request sizes explicitly; oversized content gets a documented refusal, never a partial confirmable preview. Freeze numeric bounds in T13.1 and test just-below/at/above meaningful limits.
- **State completeness:** declare allowed `(state, action)` pairs and preconditions, with separate tables for commit and push. `previewed` is not an accepted intent; only a successful unexpired confirm durably stamps acceptance before effects. `noop`, `stale`, known `failed` and `committed` are terminal outcomes; replay reads them. Resume of `preparing/prepared/publishing/recovery_required` first inspects recorded evidence, authority and expiry rules. A safe fresh review may supersede an unpublished prepared operation under the lock, preserving its private commit; an ambiguous publishing operation cannot be superseded to escape the fence. Distinguish retryable inspection failure from known operation failure. Define the transition owner, durable before/after fields and HTTP result for every table cell; non-allow-listed cells refuse.
- **DB completeness:** freeze proposed `project_config_persist_operations` and `project_config_push_intents` with typed ID/project/principal binding; immutable snapshot digest/bytes or durable content locator; target repository identity/base/blob/mode/message/author policy; export revision; accepted/expiry timestamps; state/attempt/owner fence; observed prepared/published SHA and completion timestamp; structured bounded error and cleanup outcome. Push intent binds its committed parent plus destination fingerprint/ref/remote base/outgoing range and its own acknowledgement/result. CHECK constraints tie successful states to actual receipt fields and failed/unknown states to evidence/reason; immutable fields cannot change under a reused ID. Partial UNIQUE covers exactly commit states `{preparing, prepared, publishing, recovery_required}` per canonical repo, and `{pending, unknown}` push intents per parent/destination. Many unused previews are allowed; a failed push does not occupy the local commit slot.
- **Migration completeness:** main lineage only, with SQL/journal/snapshot/schema and no Brain-schema change. Test clean install and upgrade from the immediate pre-feature lineage using real project/attachment fixtures, preserving all existing values and nullability. Verify no-op/DB-only updates, transaction rollback and direct/non-UI attachment writes against installed triggers, not copied trigger logic in the test. Drizzle no-drift validates modeled structure; PostgreSQL catalogs and behavioral tests validate hand-written functions/triggers/CHECKs. Do not run `db:check` against a developer/production DB for qualification; use the disposable migrated fixture and include its existing Brain lineage when invoking the whole check. No automatic down migration or deletion of project config evidence.
- **Deployment/compatibility completeness:** supported single-host upgrade drains/stops old web writers before applying the migration and starting the new binary. Already-running old binaries can still dirty repositories even if a new schema rejects some DB updates; mixed-version rolling writes are not implicitly supported. Decide whether existing maintenance/writer-capability mechanisms suffice; any broader backstop requires its own explicit contract/wiring. Do not silently change shared writer-capability semantics. Preserve pending evidence across restart/deployment; archive/revocation blocks new effects while permitting metadata reconciliation of completed effects.
- **Publication completeness:** T1.1 freezes the exact safe Git algorithm for normal and unborn HEAD, lock acquisition, shared-index/worktree updates, hooks/signing, and every interruption between them. T4.1 proves it with the planned RED/GREEN cases; discovering it only during T4.1 is too late for SDD. The accepted guarantee is conservative Git-style refusal and explicit recovery when ownership cannot be proved, never an unsupported claim of atomicity across Git/DB/editors.
- **Push completeness:** the issued Git command targets the destination value bound in the push review, not a mutable remote-name lookup after validation. Preserve secret-safe ambient authentication and no-force semantics. Same pushPreviewId after a known result only replays that result; a new network attempt after known failure requires a new confirmed intent. Unknown acknowledgement blocks a new push attempt for that destination until outcome inspection settles it, but does not undo or block independent local commits. Read-only remote inspection may have bounded retries; potentially successful Git mutations are never blindly repeated after timeout. Freeze retry budgets and surface the last failure/context without leaking credentials.
- **Retention and cleanup completeness:** distinguish unused expired reviews, retained committed receipts, unreferenced private prepared commits and nonterminal recovery evidence. Define which owner may prune each and how partial cleanup resumes; cleanup failure is visible but cannot revert a durable commit. Existing run/workspace GC must not classify persistence staging as an orphan run. Private files use existing host-private storage and restrictive permissions; repository content/diffs never enter scalar viewer DTOs or logs. Hard deletion/cascade cannot erase active evidence; explicitly document terminal evidence retention/deletion policy rather than leaving an unbounded accidental cascade or orphan.

Before each production slice, the relevant clauses above must be concrete enough to write its tests without choosing semantics inside the test implementation. Public docs/screens link to the canonical field/API/state contract instead of restating it.
