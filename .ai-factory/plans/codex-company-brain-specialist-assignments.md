### TDD execution and minimal-overlap rules

1. **Prepare:** select one requirement/edge partition and its frozen spec revision; name the exact test file/title/runner and observable oracle. Reuse/extend the primary owner above. Confirm discovery; a missing runner/import/dependency or unavailable target is a harness failure, not RED.
2. **RED:** write the smallest meaningful integration/E2E/contract case that expresses missing required behavior before production edits. Run it against the current implementation and retain command, revision, test ID and assertion failure. For a corrected existing assertion, demonstrate the old behavior violates the new spec. For a new endpoint, a real 404 versus required authorized behavior can establish RED once the route test harness works. For a migration, a populated old-schema query/constraint oracle must expose the unmet invariant before applying the new migration.
3. **GREEN:** implement only that partition, using current services/typed contracts and the smallest schema/API change. Run the same test unchanged; then affected existing owner tests. Do not weaken assertions, skip required cases, fabricate receipts, replace real peers with mocks, increase timeouts or rename unsupported behavior as passing to get GREEN. Necessary spec corrections restart from the revised contract and a valid RED.
4. **REFACTOR:** while tests are green, remove duplication and clarify responsibilities only in the touched scope. Apply SOLID through small cohesive functions/modules and narrow interfaces at real boundaries; no classes/framework layers solely to satisfy an acronym. Follow functional/strict typing, DRY/KISS/YAGNI, existing error/logging/atomic-write/supervisor conventions. Re-run the same primary and affected regression tests; contract and schema behavior must stay unchanged. If no refactor is needed, record the reason and green rerun.
5. **Close:** record RED/GREEN/REFACTOR evidence plus exact implementation/spec revisions in a compact validation artifact at the configured QA root for this plan; it is execution evidence, not duplicated product documentation. Phase exit checks full owning suites/contracts/i18n and relevant live proof. No behavior task is complete before its mapped expectations and edges pass; qualification tasks aggregate already-developed tests and add only previously distinct live/composed risks.

A failed regression or qualification gate returns to its owning behavior slice for a reproducing RED/fix/GREEN/refactor and affected rerun. Do not make the task that fixes a failed gate depend on that gate already passing. T40/T41 are an explicit execute→repair→re-execute cycle; downstream release/documentation completion requires both successful qualification and closed findings.

The tests described in T09/T13/T17/T21/T26/T30/T35/T40 must be introduced RED within their owning earlier implementation tasks, not first written at phase end. Those tasks are regression/qualification checkpoints. This rule also applies to the first work on companion manifests/prompts, deployment wiring and generated MCP schema; assert meaningful install/runtime/wire behavior, not string presence or mirrored helpers.

Test layering: store/service integration owns domain state, transactions, migration and concurrency; a small table-driven HTTP/MCP parity suite owns actual serialization/auth/error routing; browser journeys own interaction, localization, focus, loading/error/retry and navigation; live qualification owns installed content, actual ACP/connector/runtime and independently observed effects. Do not copy the full domain matrix into routes, UI and live suites. Combine compatible sequential checks in a meaningful journey; split when setup, failure oracle or recovery owner differs. Shared input tables are allowed; shared fake implementations of production logic are not. Critical concurrency/crash tests must fail when the corresponding guard is disabled, without imposing a general mutation-testing toolchain.

Task-size rule: split a task before implementation if one RED/GREEN cycle would span unrelated invariants or stores. Preserve the parent ID and assign focused `TNN.N` subtask IDs with exact dependencies; update traceability before adding code. Do not treat a large paragraph as one unreviewable change. ## Contract decisions to freeze in Phase 0

These are proposed implementation decisions. Phase 0 must reconcile them against owning source and complete the normative contracts before code starts; an alternative must amend this plan explicitly rather than silently weaken its acceptance.

### Ownership, access and records

1. Introduce a stable installation company identity. Use a typed owner union `{kind: company, companyId}` or `{kind: project, projectId}` with DB exclusivity/FKs. No dummy project, repository, or shared pseudo-user. Store company identity/grants in the main lineage; Brain ownership references it after main migrations run.
2. Ownership and access are distinct. Preserve existing project membership/attachment gates for legacy project knowledge. Company resources start restricted to explicit user/agent binding grants; company ownership grants no implicit platform-wide read. Define separate read/propose/review/confirm/manage permissions and record restrictions. Agents receive only the intersection of their binding, initiating principal, assignment delegation, target and current grants. Global admin may manage the policy explicitly, not silently turn every member into a reader.
3. Keep stable `brain_items.id` as the record identity. Add immutable accepted revisions and append-only accepted-change events (actor, prior/new revision, proposal, evidence and originating work). Existing item fields may remain the current search projection. An accepted correction advances revision under CAS; deliberate supersession/withdrawal is attributed and retains the old revision. No full bitemporal/validity-interval engine.
4. Content kinds support assertion, observation, decision and procedure, with existing lesson/state-fact kinds readable. A record contains assertion text plus explicit metadata limitations. Company sources can be submitted text/runbooks, captured external sources or execution evidence without a repository. Repository indexing stays project-specific; company records must not try to scan a nonexistent repo.

Keep these state axes independent:

| Axis | Planned values and enforcement |
| --- | --- |
| Record lifecycle | `active`, existing `expired`/`superseded`, additive `withdrawn` if needed; never conflated with truth |
| Assertion basis | `observed`, `inferred`, `unknown`; server tracks attribution, agent may propose basis with evidence/limitations |
| Proposal review | `pending`, `accepted`, `rejected`, optionally explicit `withdrawn`; acceptance is a publication decision |
| Confirmation | `unconfirmed`, `confirmed`, `revoked`; immutable decision records confirmer, policy version, exact record/evidence revisions and reason |
| Evidence disposition | Supporting, contradicting, derived-from or other existing relation; provenance is not a vote |
| Reference resolution | `available`, `stale`, `missing`, `inaccessible`, `unknown`; return a safe unavailable projection without leaking hidden existence |
| Freshness/applicability | Source/observation timestamps when known; policy-derived `current`/`stale`/`unknown` and applicability `known`/`unknown`; row creation is not observation time |
| Retrieval diagnostics | Relevance/confidence/reinforcement remain ranking diagnostics; no transition into confirmed |

“Proposed” is represented by a pending proposal, not assertion basis. Accepting a proposal does not automatically confirm its contents. Default confirmation authority is an explicitly authorized human reviewer, with a separate action; configured verifier identities may confirm only a named, bounded assertion class using server-validated evidence. Ordinary specialists cannot self-assign this authority. A revoked or stale witness leaves the historical decision inspectable and changes current support/applicability; it does not erase history or imply current validity.

### Evidence, deduplication and findings

- An immutable evidence witness contains source identity, source version or captured content digest, locator/selector, observation/source timestamps when known, capture provenance and access classification. Keep current search anchors separate. Reindex/reanchor cannot rewrite a witness; deletion leaves an explicit unavailable witness. Capture only authorized bounded material under retention policy; a digest without retained content can prove identity, not permit fabricated reconstruction.
- Give source observation/version an independence-group identity separately from a witness selector/digest. Multiple chunks/selectors/URLs or derived summaries of the same source observation share that group; changing a selector cannot create independent corroboration. Retain exact witness identities for navigation/provenance. A changed source version is a new version witness, not automatically an independent observation. If independence is unknown, say unknown. Do not attempt generalized semantic merging.
- Submission idempotency uses owner + submitting authority boundary + source delivery/operation identity + canonical payload digest. Canonical JSON sorts object keys and preserves array order. Same key/same payload returns the prior receipt; same key/different payload conflicts. Exact-content dedup is scoped so hidden records do not leak through existence/count/error differences. Distinct contradictory assertions stay distinct, linked by contradiction/conflict relations; only an explicit attributed review can resolve them.
- Recall/get of a known conflicted claim includes accessible opposing-claim references and an explicit unresolved-conflict marker even when the opposing claim falls outside relevance top-K. If evidence budgets prevent expansion, expose incomplete support/limitations and an authorized follow-up handle; do not present one ranked side as resolved truth. An inaccessible opposing claim yields only a policy-safe support limitation, without leaking its hidden identity or contents.
- Define native `evidence_findings_v1` as a bounded shared schema usable by agent profiles and Flow exports: findings with assertion, `observed|inferred|unknown` basis, supporting/contradicting references, explicit missing-evidence entries, limitations, open questions, proposed knowledge changes and child-origin/result-revision links. Empty evidence with an explanation is valid. Do not require a model to manufacture a citation to satisfy structure.
- Model output carries claims and candidate references only. Server enrichment supplies submitting actor, run/attempt, ownership, access and confirmation authority. Validate identities, exact record/result revisions, witnesses, delegation ancestry and current access before publication, collection, context sharing, acceptance and write-back. Malformed/forged references are invalid; stale/missing/inaccessible references have explicit supported projections and cannot satisfy a verification obligation.
- Intermediate reduction includes a bounded selection manifest of exact consumed result/finding IDs and each retained/combined or omitted-with-reason disposition. Every retained/combined finding declares its source finding IDs; the server computes/checks closure of their support, contradiction, missing-evidence and unresolved-question refs. Omitted material remains auditable through exact child revisions. The validator rejects invented references, unaccounted omissions or removed links in that declared closure. It cannot determine semantic equivalence or whether a novel assertion is true: unsupported novel claims remain explicitly inferred/unconfirmed and reviewable, never mechanically verified by the manifest. A manifest exceeding existing output limits requires bounded batches/narrower work, not silent truncation. A root still collects only direct children. An inaccessible original stays private and yields a safe limitation, without a hidden foreign record ID.
- Treat result text and context as derived data. Server-record every source-access restriction before returning its content to an agent, including ambient context and tool retrieval, then conservatively inherit the complete restriction set through its turn/run, result, collected child and context projection. Citation omission cannot lower that set. Before exposing summaries, findings, logs, decisions, notifications, legacy `outputText`, artifacts, transcripts/runtime-object content, exports or result delivery, authorize the recipient for that derived data; otherwise withhold the content with a safe limitation. Define read authorization linearization and prevent adoption of delayed denied/stale responses. This does not revoke knowledge a recipient already legitimately received. No model-controlled declassification or arbitrary classification framework is required.

### Initial pilot connector and effect policy

Choose one narrow first-party connector in `stand-connector/` (new workspace), with a client through `web/lib/execution-host/` and supervisor-owned transport. Initial supported manager: explicitly configured Linux `systemd`, with `system` or `user` scope and exact unit mapping. Other managers fail preflight as unsupported. The configured target may be another MAIster installation; it must not be the executing controller component.

- Deploy an authenticated HTTPS helper on the target. Configure stable stand/installation incarnation, component-to-canonical-service mapping, manager/scope/user, exact permitted actions (`inspect`, bounded `logs`, `restart`, `verify`), credential references, trusted runbook record/revision and health probe. No arbitrary shell, command text, caller-supplied endpoint or unrestricted host bus/socket. Execute fixed service-manager argv with bounded time/output, least privilege and target-side allow-list enforcement.
- Persist platform operation intent before dispatch: operation ID, assignment/work-item/input revision, canonical payload digest, exact target/policy/runbook/authority snapshots, before-state witness, initiator and owner fence. The connector persists the same operation identity and intent before touching the service. This operation journal records external effects, not run attempts.
- Canonical mutation resource key is target incarnation + service-manager namespace/scope/user + actual unit. Aliased component names and different assignments/controllers must converge on that key. Platform durable exclusion and target durable exclusion both protect it; lease expiry does not release an unresolved effect for another restart. Claim renewal/fencing blocks stale workers. A target identity change requires explicit re-resolution.
- Recheck current user/agent/target permissions and assignment fence before dispatch and at the target's pre-effect authorization boundary through a single-use operation-bound authorization check. Fail closed if the authority cannot be checked; snapshots are audit records, not ongoing grants. Define the authorization linearization point and in-flight revocation behavior explicitly. Revocation blocks new dispatch/retry and triggers reconciliation of any already-dispatched effect; it cannot undo an effect already authorized and started.
- Default restart policy requires human authorization unless an administrator explicitly configures a bounded unattended grant for that stand/component/action. Diagnosis remains available under read grants. Keep approval in existing HITL/Inbox machinery, with exact intent/digest so approval cannot authorize a changed target or payload.
- Separate operation effect state (`not_dispatched`, `dispatching`, `confirmed_applied`, `confirmed_not_applied`, `unknown`) from verification state (`not_checked`, `healthy`, `unhealthy`, `inconclusive`) and journal lifecycle. Process exit, HTTP success, model prose and current health alone do not prove the requested restart occurred. Target receipts and service-manager before/after invocation witnesses establish attributable effect only where the evidence supports it.
- Lost response: query the same operation ID and inspect actual state before considering another dispatch. A persisted target receipt can settle a lost ACK. Helper death between effect and receipt may leave causality unknown even if health is green; preserve unknown and require evidence/recovery authority rather than assume success or retry. A retry after proven not-applied still rechecks permission and policy under the same intent rules.
- Reconciliation records an explicit disposition: proved applied, proved not-applied, unresolved hold, or human-authorized successor intent after bounded current-state inspection. The last option does not relabel the original unknown effect as failed/successful: record the inspecting evidence, risk decision/current authority and new operation identity linked to its unresolved predecessor. Atomically transfer the resource exclusion to that successor under a new fence; never merely unlock an unknown operation or replay its ID as a new restart. The policy may refuse a successor when a safe inspection/precondition cannot be established. Acceptance cites the verified successor if allowed, while retaining the predecessor's uncertainty and decision. This supplies actionable recovery without a blind retry or permanent unreviewable lock.
- Post-action verification is a separate platform-issued check with its own observation ID/time, configured health criteria and target identity, after the effect boundary. A specialist cannot attest success itself. Allow healthy/no-action outcomes, failed verification and partial progress without miscounting or manufacturing confirmed effects.
- Inspect/log operations are bounded by duration, bytes and time window. Sanitize secrets/control sequences before logs enter artifacts/results; raw target logs remain target-private. Logs and health material carry source/access labels. Routine unchanged success produces no notification. Incidents group by target/resource/failure condition and remain durable until evidenced resolution.

| --- | --- |

Bounded target status probes during explicit reconciliation are workflow operations. | Durable window/state | Owner after interruption | Required recovery behavior |
| --- | --- | --- |
| Assignment queued; intake committed but launch absent | Existing dispatcher + assignment admission | Reuse receipt and input snapshot; reserve one existing run, obey cap |
| Active coordinator, claim expires or any terminal parent status | Assignment recovery with new epoch | Fence old owner; retain accepted child/result refs; inspect live children and effects before replacement |
| Waiting input, including run NeedsInput/NeedsInputIdle | Existing HITL/agent resume + assignment question owner | Preserve question/input revision; late/duplicate answer cannot resume another assignment; explicit cancel/deferred release on failed persistence |

| Waiting resource | Resource claim owner + dispatcher | No slot consumed while parked; wake on evidenced release, recheck cap/authority; no starvation behind poison intent |
| Intent persisted, no dispatch receipt | Operation reconciler + target receipt | Determine whether dispatched; exact replay uses same identity, never assumes not-applied |
| Dispatched/unknown, including coordinator cancelled/crashed | Operation reconciler, independent of run lifetime | Keep exclusion; query/inspect under read authority; no mutation without current grant and resolved predecessor |
| Applied receipt, verification missing/unhealthy/inconclusive | Verification work item | Run a separate bounded check; retain applied effect; no restart loop disguised as verification retry |
| Awaiting acceptance | Responsible coordinator/human continuation | Revalidate exact results, current access, expected input and evidence; never mark done from child terminal status |
| Completed/failed/cancelled, delivery pending | Existing outbox consumer | Deliver safe result once with receipt; cancellation retains confirmed effects and unknown operations for reconciliation |
| Cleanup failed or evidence source deleted | Existing lifecycle/retention owners | Business outcome unchanged; durable diagnostic; authorized witness/limitations stay inspectable after workspace removal |

Every producer/consumer transaction must enumerate crashes between its DB/host/filesystem/target boundaries and close all linked lifecycle rows atomically where possible. External effects are settled forward using receipts. Cleanup follows terminal commit and never compensates an applied restart. Recovery covers all reachable parked states, not only Running-without-session.
