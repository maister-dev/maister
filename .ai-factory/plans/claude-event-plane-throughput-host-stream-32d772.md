## Outcome and boundaries

After this item the manager reads the host stream continuously into a bounded buffer and commits events in batches — one Postgres transaction and at most one ACK per batch — and the host serves a slow subscriber from its durable outbox on the same connection instead of closing it. An operator can read, on `/admin/execution-host` and in the `system_sweep` summary, how often the host had to pause a subscriber and why any stream closed. A load control proves, with the P0-7/D4 numbers, that the caps' worth of concurrent sessions produce a host-to-manager lag that stays flat, zero transport closes and zero host-span settlements — first on `master` (the RED), then on this branch (the GREEN).

Frozen: ADR-167 D2 semantics (total order per `streamId`, contiguous-only ACK, harmless duplicates and lost ACKs, no ACK waiting on projectors), the "commit → ACK → confirm" order, one claim per host stream, the SSE frame format and `Last-Event-ID` cursor rules, the replay-floor contract (EDGE-EVT-03), the span route (`/runtime-events/span`, D4), the projection quantum, outbox pressure (D6/P1-4), P1-3 hydration/transcript work, AB-07 pacing, `execution_event_skips` semantics, the stall/lost predicates and their thresholds, the 20 `ingest.integration` cases (the request counts 12; the file has 19 `it` sites, one `it.each` of two), the P1/P3 partition expectations.

## Decisions

The normative owner of each contract is listed in the traceability table. Update the specification before the implementation, derive the RED control from the specification's observable requirement, then implement. Every Expectation names its enforcement point.

### D1. Manager — continuous reader, bounded buffer, batch cuts

`consumeRuntimeEventStreamOnce` (`consumer.ts:256-418`) is split into two cooperating tasks inside one pass, still one claim per host stream:

- **Reader.** `for await (const envelope of transport.streamRuntimeEvents(...))` pushes into an in-memory buffer bounded by `INGEST_BUFFER_ROWS = 4 × N` rows and `INGEST_BUFFER_BYTES = 16 MiB` (payload bytes, measured once from `JSON.stringify(payload)` and handed to ingest so the hash/size are computed once). When either bound is reached the reader awaits a "drained" signal from the batcher before pulling the next frame — the socket is then not read, Node's receive window fills, and the HOST pauses the subscriber (D7). That coupling is the design: the durable outbox is the buffer, manager memory is bounded by one buffer.
- **Batcher.** Waits for the first buffered row, then collects until the first of: `N` rows (`INGEST_BATCH_ROWS`, default 200, env-tunable), `B = 4 MiB` payload bytes (`INGEST_BATCH_BYTES`; a single envelope above `B` still forms a batch of one — envelopes are ≤ 1 MiB so this cannot occur, stated for completeness), `T = 250 ms` since the first row of THIS batch was buffered (`INGEST_BATCH_WAIT_MS`; an unref'd timer cleared on every batcher exit, like the reconnect delay at `consumer.ts:531-534`, so an idle pass never keeps a process alive), a `streamId` change (the batch is cut BEFORE the differing envelope), `maxEvents - received` (test option; keeps `maxEvents` exact), the stream ending, or abort. Then `ingestRuntimeEventBatch` (D2), then ACK (D6), then `onProgress()` (D5).
- **Ends.** Stream end (host closed: `disconnect | protocol | floor | shutdown`): the batcher drains what is buffered, commits it, then the pass returns and the outer loop reconnects after `nextReconnectDelayMs` (unchanged, `consumer.ts:36-46`). Reader error (transport failure, `ACP_PROTOCOL` frame error): the batcher drains the buffer first (those frames arrived intact), then the error propagates through the existing `recordConsumerFailure` path. Abort (`input.signal`): the buffer is discarded, nothing more is committed; replay from `lastContiguousSequence` re-serves it. The reader's "drained" wait is a deferred the batcher owns: every batcher exit (abort, batch error, stream end) resolves or rejects it before returning, so the reader can never hang on a batcher that is gone (unit case in `batching.test.ts`).
- Bounds: `T = 250 ms ≤ CLAIM_LEASE_MS / 2 = 15 s` holds by construction; `RECONNECT_MIN_MS = 250` is unrelated and unchanged.
- `RuntimeEventConsumerSummary` gains `batches: number` (committed batches). `received`, `acknowledged` (ACK calls), `duplicates`, `staleEpochs`, `reconnectRequired`, `reconnectReason` keep their meaning.

Why three cuts and not "commit when the socket is idle": the +T latency at low load is invisible behind the projection quantum (~1 s idle wake) and D4's host-span settlement; a fourth cut would add a state the request does not ask for.

### D2. Manager — one batch transaction, one code path

New export `ingestRuntimeEventBatch({ db, executionHostId, envelopes: unknown[], claim?: { streamRowId, owner, leaseMs }, now, logger })` → `{ streamId, results: RuntimeEventIngestResult[] /* same order as input */, contiguousThrough, acceptedCount, staleEpochCount, skippedCount, pendingGapCount, promotedRunIds: string[], claimRenewed: boolean | null }`. `ingestRuntimeEvent` (`ingest.ts:745`) becomes `(await ingestRuntimeEventBatch({ envelopes: [envelope] })).results[0]` — a batch of one — so the 20 `ingest.integration` cases, `ingest-unstorable-payload.integration` (3), `projection-worker.integration` (calls `ingestRuntimeEvent` directly, `:469-499`, `:656`), `commands.integration` (`:140`) and `immutable-commands.integration` keep pinning the batch code, not a sibling path. The fake host (`web/test-support/fake-execution-host.ts:2144-2152` `deliverCanonical`) also calls `ingestRuntimeEvent` per envelope and needs no change.

Inside `db.transaction`, in this order:

1. **Normalize** every envelope before the transaction (`normalizeRuntimeEnvelope`, as today). An invalid envelope records `execution_event_ingest_failures` and throws `ACP_PROTOCOL` for the call, as today (the local-direct transport already refuses invalid envelopes before the consumer sees them; behavior unchanged).
2. **Stream lock** once: `lockOrCreateStream` (`ingest.ts:146-268`, host row read without `FOR UPDATE` — the documented inversion guard at `:150-153` stays); the locked row's `claim_owner` and `claim_expires_at` are selected alongside the watermarks. All envelopes share the stream (D1 cuts on change); a violation is `CONFLICT`.
3. **Lease check** (D5) when `claim` is given: compare the locked row's `claim_owner` to `owner` in memory. A match arms the renewal that step 9's single stream-row write carries; a mismatch sets `claimRenewed = false` and writes nothing about the claim — the batch STILL commits (ingest is idempotent and serialized by the stream lock) and the consumer then reports `claim_lost` exactly as it does today after `claim.streamId !== result.streamId`.
4. **Classify duplicates** in three set queries: skip ledger by `event_id IN (…)`, `execution_events` by `id IN (…)` (per-row exact envelope compare as `existingDuplicate` does today; a mismatch throws `event_identity_conflict` and marks the host unavailable — batch-level, as today), and `execution_events` by `(event_stream_id, host_sequence) IN (…)` for the non-duplicates (a hit throws `event_identity_conflict`). A duplicate WITHIN the batch (the host replayed the same frame twice on one connection — the `duplicate-frame` fault) is classified `duplicate` against its first occurrence by the same exactness rule.
5. **Run locks in a stable order**: read the FIRST pending page now (D3's bounded read from `expected`, `LIMIT PROMOTE_READ_ROWS`) so that a run released by the walk — a previously pending row of ANOTHER run behind the gap this batch fills — is in the lock set; then the distinct run ids of the batch's non-duplicates ∪ that page's run ids, `SELECT id FROM runs WHERE id IN (…) ORDER BY id FOR UPDATE` — one statement, ascending id, taken once BEFORE any insert (trap 1; the 2026-09-24 patch: a writer that can race a peer takes the peer's order — the owner apply's `lockCurrentSessionAssignment` is run-first). Batch ids not returned are unknown runs → one multi-row `INSERT INTO execution_event_skips … ON CONFLICT DO NOTHING` with `reason = 'unknown_run'` (per-row WARN `runtime-event-skipped-unknown-run`, as today); pending-page runs are always known (their rows passed the FK).
6. **Assignments** once: `SELECT … FROM execution_assignments WHERE id IN (distinct assignment ids)`; per envelope the boundary match of `resolveAssignment` (`:270-310`); a non-active match still calls `isBoundHistoricalEvent` per envelope (the rare late-terminal path; unchanged).
7. **One multi-row `INSERT INTO execution_events … ON CONFLICT DO NOTHING RETURNING id`** with `ingest_disposition = 'pending_gap'` for every storable new envelope (values as `ingest.ts:888-914`). The returned id set must equal the classified-new set; a difference is a `CONFLICT` invariant (impossible under the stream lock; asserted, never silently absorbed).
8. **Promotion** once (D3; it returns `contiguousThrough`, the `firstGap` verdict and the counts, and writes NOTHING to the stream row), then consumer seeding once per distinct promoted run (`seedCanonicalProjectionConsumers`, `projection-consumers.ts:18-31`).
9. **One stream-row UPDATE and one host-row UPDATE**, at the end: `last_received_sequence = max(all sequences in the batch, including skipped ones)`, `last_boot_id` of the last envelope, `last_seen_at = now`, `state = 'active'`, `last_contiguous_sequence`, `first_gap_sequence` / `gap_detected_at` / `gap_status`, and `claim_expires_at = now + leaseMs` only when step 3 matched the owner; then `execution_hosts.last_boot_id / last_seen_at / updated_at`. The stream row is written exactly ONCE per transaction — today's path writes it up to three times (`:797-800` or `:850-860`/`:918-926`, then `:593-603`), and every re-UPDATE of a row already written in the transaction re-runs its FK checks and takes `KEY SHARE` on `execution_hosts` (hidden-FK-lock memory).
10. **Per-row dispositions** are assigned AFTER promotion: `duplicate` / `skipped_unknown_run` from step 4-5; an inserted row whose `host_sequence ≤ contiguousThrough` takes the disposition the walk gave it (`accepted` or `stale_epoch`); a row above the watermark is `pending_gap`. For a batch of one this equals today's `sequence > expected ? pending_gap : accepted ? accepted : stale_epoch` (`ingest.ts:944-950`), which the existing 20 cases pin (`:315` held gap + duplicate, `:367` stale epoch, `:1476` skip).

After commit: `runEventWakeBus.wake(runId)` once per distinct promoted run, `wakeProjection()` once per batch (today: once per accepted event, `consumer.ts:395`), one `runtime-event-batch-ingested` INFO (D11).

Lock order of the batch (for the I5 watcher): host row (plain read) → stream row `FOR UPDATE` → runs `FOR UPDATE` ascending (the batch's runs and the first pending page's runs) → inserts (`KEY SHARE` on runs/assignments/hosts/streams) → `execution_events` updates → ONE stream-row update and ONE host-row update (FK re-checks take `KEY SHARE` on the same parents; runs are already held `FOR UPDATE` by this transaction). This is the per-event path's order with the run locks hoisted and taken once; the batch is bounded by `N` so an owner apply or the projector waits at most one batch. I5 replays the peers' own orders against it: the owner apply (`lockCurrentSessionAssignment`, run-first), the projection worker, and the stall repair (`stream-health.ts`, stream row only).

### D3. Manager — bounded contiguity walk

`promoteContiguousPrefix` (`ingest.ts:477-606`) becomes page-bounded and side-effect-free on the stream row — it returns `contiguousThrough`, `firstGap` and the counts, and the caller writes them in D2 step 9 instead of the update at `:593-603`:

- Pending read: `WHERE event_stream_id = ? AND host_sequence >= expected ORDER BY host_sequence LIMIT PROMOTE_READ_ROWS (500)` (keyset by `expected`, served by `execution_events_host_position_uq`); the skip read is bounded the same way (`LIMIT 500`, ordered). The walk consumes the page as today (skips, `pending_gap` check, assignment re-resolution). When the page was FULL and the walk reached its end without a gap, the next page is read from the new `expected` — the LIMIT bounds each read, never the promotion (trap 4).
- `firstGap` becomes one indexed probe: `SELECT 1 … WHERE event_stream_id = ? AND host_sequence > expected LIMIT 1` (today: `rows.some(...)` over the full re-read, `:589-591`).
- Accepted rows are grouped by run: one `UPDATE runs SET next_execution_event_sequence = next + k … RETURNING` per distinct run (every run of the batch and of the FIRST pending page is already locked in D2 step 5; a run first met on a LATER page — only when one batch releases more than `PROMOTE_READ_ROWS` pending rows at once — is locked ascending before that page's allocation, and the D4 in-place retry covers that residual exposure, which I5 measures), then per-row `UPDATE execution_events SET ingest_disposition, run_sequence`. Stale rows keep the per-row update with the `ingestError` merge (`:573-582`).
- Correctness with gaps, skips (`unknown_run`, `payload_unstorable`), stale epochs and quarantined rows is unchanged and pinned by the existing 20 cases plus `ingest-unstorable-payload.integration` (`:135` "keeps the stream walking", `:180`) and `projection-worker.integration:429` ("seeds every run released by another run's stream gap", `acceptedCount === 2`); RED I2 pins the bound.

### D4. Manager — failure isolation inside a batch

| Failure | Where it is caught | Batch outcome |
| --- | --- | --- |
| Unknown run | D2 step 5, before insert | Skip ledger row(s); the rest commits; the walk steps over the hole (today's `:825-880` behavior, batched). |
| Duplicate / in-batch duplicate | D2 step 4 | `duplicate` disposition; `last_seen_at` still advances (today's `:793-813`). |
| Identity conflict (reused id or position with a different envelope) | D2 step 4 | The whole call throws `CONFLICT/event_identity_conflict` and the host is marked unavailable — a host-integrity condition, not a per-event skip (unchanged). |
| Stream identity conflict | `lockOrCreateStream` | Throws `event_stream_mismatch`, host unavailable (unchanged, EDGE-EVT-04). |
| PostgreSQL refuses a payload (`22P05`/`22P02`/`22021`, `unstorablePayloadCode`) | the transaction aborts | If the batch has > 1 envelope: WARN `runtime-event-batch-split` and re-run the SAME envelopes as single-envelope batches in order (idempotent; the committed nothing). The poisoned one reaches `quarantineUnstorableEvent` exactly as today; the others commit. If the batch has 1 envelope: today's quarantine path. |
| Transient transaction failure (`40P01` deadlock, `40001` serialization, connection reset) | the transaction aborts | One in-place retry of the same batch after a 50 ms jitter (WARN `runtime-event-batch-retried` with the SQLSTATE); a second failure propagates to `recordConsumerFailure` and the reconnect path, whose replay from `lastContiguousSequence` is the retry-from-committed-cursor the request names. |
| Any other error | propagates | As today: `recordConsumerFailure`, reconnect. |

No partial commit is ever visible: a batch commits whole or not at all; the dispositions returned describe the committed state.

### D5. Manager — lease, cursor, progress

- **Lease**: renewed in every batch transaction (D2 step 9, gated by the owner check of step 3). A renewal miss is reported after commit as `reconnectReason: "claim_lost"` (the existing enum value), logged by the existing `runtime-event-consumer-reconnect-required` WARN. A killed consumer stops renewing, so a successor still claims after ≤ `CLAIM_LEASE_MS` (the `KILLED_CLAIM_WAIT_MS` convention in the agent `prompt-owners` suite holds).
- **Cursor**: the reconnect cursor stays `claim.afterSequence = lastContiguousSequence` (`consumer.ts:131`, D2 normative). The pre-pass catch-up ACK (`:298-331`) is unchanged.
- **Progress**: `consumeRuntimeEventStreamOnce` accepts `onProgress?: () => void`, invoked after every committed batch and every confirmed ACK; `startRuntimeEventConsumer` passes `() => { loop.lastProgressAt = Date.now(); }`. The pass-end update (`:498-499`) stays for passes that end without a batch.
- **Stall predicate**: `last_seen_at` advances at every batch commit (≤ `T` after the first row of a batch arrives) and on every duplicate, so a trickle never manufactures silence for `findStalledEventStreams` (`stream-health.ts:34-66`) — RED I4a.

### D6. Manager — ACK granularity

After each committed batch whose `contiguousThrough` is above the last ACK sent in this pass: one `transport.acknowledgeRuntimeEvents` then one `recordConfirmedRuntimeEventAck` (`consumer.ts:157-204`, unchanged: separate transaction, owner check, monotonic). ACK mismatch → `ACP_PROTOCOL` (unchanged); a failed record → `ack_record_failed` reconnect (unchanged). Coalescing of a trickling tail is inherent: a batch is cut at most every `T`, so a tail is acknowledged within `T` of its commit with no second timer. ADR-167 D2's "commit → ACK → confirm" order and the "ACK never waits for projectors" rule are untouched; only the granularity moves from one event to one batch.

Host side of the ACK (`host-state.ts:1888-1971`) is unchanged: one `BEGIN IMMEDIATE`, a contiguity walk over `acknowledged+1..through` (now `O(batch)` per ACK instead of `O(1)` per event — the same total work with `N×` fewer fsyncs under `PRAGMA synchronous = FULL`), and the route's `runtimeEventOutboxStats()` log field (`http-api.ts:1950`) runs `N×` less often. Not touched.

### D7. Host — the subscriber pauses and catches up on one connection

`GET /runtime-events` (`http-api.ts:1751-1846`) is re-implemented around a per-connection pump in a new module `supervisor/src/runtime-event-subscribers.ts` (pump + counters; the route stays in `http-api.ts`):

- **Open** (unchanged contract): parse `Last-Event-ID` (409 `invalid_event_sequence` on a malformed cursor); read the FIRST page before writing headers so replay-floor loss and stream identity conflict still answer 409 `replay_floor_lost` / `stream_identity_conflict` (EDGE-EVT-03; `runtime-event-ack.integration` "explicit floor failure"); then `writeHead(200, text/event-stream …)`, register the subscriber, subscribe to the publisher, start the pump with that page.
- **State** per subscriber: `cursor` (the last sequence WRITTEN to the socket, initially the request cursor), `mode ∈ { catchup, live, paused }`, `closed`.
- **Pump** (single-flight): loop { page = `runtimeEventsAfter(streamId, cursor, 500)` (throws → close `floor` or `protocol`); if the page is empty → `mode = live` and return — the flip is synchronous with the read (no `await` between them), which is sound because every notified event is committed before notification; for each event: write the frame (format unchanged: `id: <sequence>\nevent: <type>\ndata: <json>\n\n`), `cursor = sequence`; if `res.write()` returned `false` → `mode = paused`, `subscriberPauses += 1`, `await once(res, "drain", { signal })` where `signal` is a per-subscriber `AbortController` that `close()` aborts (a socket that closes mid-pause must not leave the pump promise pending forever; `once` also rejects on the response's `error`, which the pump turns into `close("disconnect")`), if closed return, `mode = catchup` and continue with a fresh page from `cursor` }. The event whose write returned `false` WAS buffered by Node (trap 5), so `cursor` already covers it.
- **Live listener** (synchronous, never awaits, never queues): ignore when `closed` or `mode !== live`; an event on a FOREIGN `streamId` closes `protocol` (today it is silently ignored and the subscriber idles on a dead stream forever); an event with `sequence ≠ cursor + 1` sets `mode = catchup` and starts the pump (SQLite has the rows); otherwise write it, advance `cursor`, and on `false` pause exactly as in the pump. The publisher (`host-state.ts:957-968`) therefore never blocks on a subscriber and holds no per-subscriber queue: `MAX_RUNTIME_EVENT_SSE_PENDING` and the `pending` array are deleted.
- **No `replay_page` close**: catch-up pages through retained rows on one connection until an empty page, then goes live. **No `slow_client` close**: a full socket pauses the subscriber. Per-subscriber memory is one page (≤ 500 rows / ≤ 1 MiB) plus Node's write buffer (one frame past the high-water mark).
- **Close reasons** (exhaustive): `disconnect` — the client socket closed or errored (`req.raw 'close'`, `res 'error'`); `floor` — a catch-up read threw `replay_floor_exceeded` (a second, lagging subscriber can fall below the floor that the ACKing subscriber's prunes move; EDGE-EVT-03 mid-stream); `protocol` — the host cannot continue the stream under its contract: `stream_identity_conflict` / `stream_corrupt` / `runtime_storage_unavailable` from a page read, or a foreign-stream live event (EDGE-EVT-04 for a subscriber); `shutdown` — the Fastify `onClose` hook (registered next to `http-api.ts:542`) ends every registered subscriber before `main.ts:307-310` force-closes sockets one second later. `close()` is idempotent, unsubscribes, aborts the pause signal — which removes the pending `drain` listener and settles the awaiting pump (the paused subscriber's continuation is a deferred; leaving it armed after close would leak the closure and could pump into an ended response) — counts, ends the response unless the socket is already gone, and logs `runtime-event-stream-closed { streamId, afterSequence, cursor, reason, pauses }`. The unit suite asserts `res.listenerCount("drain") === 0` after a close during a pause.
- Trap 6: a subscriber paused at shutdown or stream replacement is torn down with the connection (`closed` short-circuits the pending `drain` continuation). Trap 7: the manager's claim is unaware of pauses; a paused-then-resumed subscriber is the same pass and the same claim.
- Identifiers (skill-context rule): `Last-Event-ID` — request header, validated by grammar and floor-checked against server state; `streamId` — server-state (`hostState.getRuntimeEventStreamId()`); no body. `POST /runtime-events/ack` is unchanged: `streamId` body-controlled and compared to the current stream (409 `stream_identity_conflict`), `throughSequence` body-controlled and validated contiguous/emitted.

### Crash windows (multi-store rule)

| Window | State left behind | Recovery owner |
| --- | --- | --- |
| Manager dies mid-batch | Postgres rolled back; buffer lost; host retains rows | Reconnect from `lastContiguousSequence`; replay; dedup (EVT-03). Unchanged. |
| Manager dies after batch commit, before ACK | rows committed, host un-ACKed | The next pass's catch-up ACK (`consumer.ts:298-331`; `ingest.integration:395`). Unchanged. |
| Manager dies after ACK, before `recordConfirmedRuntimeEventAck` | host ACKed, `last_ack_confirmed` behind | The next pass re-ACKs; the host answers its current watermark (idempotent, `host-state.ts:1903-1907`). Unchanged. |
| Host dies with a paused subscriber | connection EOF; counters reset at boot ("since boot" is the contract) | Manager reconnects from its durable cursor after backoff; EVT-07. |
| Host stream replaced under a live subscriber | subscriber closed `protocol` | Manager reconnects, the next open answers 409 `stream_identity_conflict`, the existing EDGE-EVT-04 path degrades the stream. |
| Lease lapses while a batch is in flight | batch commits (idempotent); renewal misses | `claim_lost` reconnect; the successor owns ACK from then on; a double ACK is harmless (D2). |

No new window is introduced; batching removes none of the existing ones and needs no new sweep.
