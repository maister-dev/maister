## Ground truth: corrections and additions to the request

The request was re-verified on `8ff196d4`. Its protocol and adapter claims hold (line numbers confirmed; small offsets noted). **The findings below change the work.** Implementers must not re-derive them.

**C1. Route names.** The prompt route is `POST /sessions/:id/prompts` (plural; `http-api.ts:2412`, `supervisor.openapi.yaml:1145`); `execution-hosts.md:544` says `/prompt` — corrected in the same table edit. Delete is `DELETE /sessions/:id`.

**C2. There is no `GET /sessions/:id`.** Only `GET /sessions` (`toSessionListEntry`, `types.ts:1279-1301`) and `GET /sessions/:id/stream` exist. The capability is therefore exposed on (a) the list entry, (b) the create route's 201 body (`http-api.ts:2404`: `{sessionId, pid, acpSessionId}`), and (c) the `session.created` runtime event payload (`runtime-event-publisher.ts:419-433`). No new GET route (surgical). The manager persists it at the create ACK (D-A3), so the steer decision never needs a live host read.

**C3. `run_messages` has no `state` column** (`schema.ts:5200-5251`). The `pending|completed|failed|aborted` CHECK the request cites at `~6482-6486` belongs to `gate_chat_turns`. The scratch queue state is a new nullable `run_messages.delivery` column (Numbering). The row IS the scratch turn's identity (`prompt-owner.ts:140-148` matches `run_messages` id + sequence), so the queue lives on the row that will later own the prompt — no second table.

**C4. The D4 span verifier already skips `session.command` rows** (`prompt-output.ts:288-293`: other sessions, non-`session.*` types and `session.command` are `continue`d before the `source_command_binding` check at `:294-300`; the request's `:178-190` is `assertAcceptedBinding`). `CONSUMER_SIGNAL_EVENT_TYPES` (`prompt-signal-events.ts:7-12`) does not list it either. The steer's `session.update` output carries the **parent's** `sourceCommandId`, because the publisher stamps `record.activePromptCommandId` (`runtime-event-publisher.ts:45, 210`) and a steer never changes it. So **no verifier change is needed**; RED S2's "settled once from the parent's feed, `event_frontier` absent" assertion becomes a **pin**, and the falsification target changes: tamper the host to stamp the steer command id as `sourceCommandId` on one chunk → `source_command_binding` → canonical-only (T2.5). The consumer-signal list stays as it is.

**C5. Neither adapter emits a live user echo for a steer.** Claude drops the steered message's `isReplay` echo (`acp-agent.js:3985-3993`); codex returns `null` for live `userMessage` items (`index.js:24675-24681, 24738-24741`) and uses `createUserMessageChunk` only on history replay. The projector already drops `user_message_chunk` as noise (`lib/run-transcript/transcript.ts:274+`). Trap 4 reduces to a pin: the mock adapter can emit an echo (`--steer-echo`) and S2 asserts exactly one user row.

**C6. Agent runs write no user transcript rows today.** `getAgentRunTranscript` (`lib/runs/run-transcript-projector.ts:205-240`) reads `run_messages`; only the flow dispatcher (`lib/flows/graph/prompt-record.ts:203-207`) and scratch (`lib/scratch-runs/messages.ts:53`) write `user` rows; agent turns never do. A manager-authored steered row would be the first user row an agent transcript ever shows, while the queued fallback's message stays invisible. Owner decision (2026-09-25, Q1: "all"): every agent prompt — initial, resume, rework, message — is recorded at dispatch through the TRC-06 mechanism (`appendRunMessage` + `promptDispatchKey`, bounded content); T3.5 is mandatory. The steered row is the acceptance-time row of D-C4 (C8).

**C7. The ext message operation lives in `docs/api/external/operations.openapi.yaml:1930-2025`** (`operationId: extMessageRun`), not `web.openapi.yaml`. The MCP wrapper is `mcp/src/tools.ts:472-485` (tool) + `:1198-1211` (body mapping).

**C8. `requestVersion: 2` is prompt-only** (`types.ts:566-575`). The steer uses the v1 envelope through `runCommand` (`http-api.ts:673-805`) exactly like `/input` and `/cancel`: fence → `receipts.execute` → `accepted` receipt → execute → `completed | rejected` receipt + `session.command` event (`createCommandEvent`, `:632-643`) → HTTP response. Three readers select "the run's dispatched turn" with no variant filter and would pick a steer row.** (a) The agent continuation worker's Running arm (`agents/continuation-worker.ts:108-128`: `runs.status ∈ {Running, NeedsInput}` with a `claimed|dispatched` turn on the current assignment) would re-drive a run whose only active row is a steer; (b) `startAgentSession` (`agents/launch.ts:2880-2891`) takes the first `claimed|dispatched` turn of the assignment and, because it has a `commandId`, calls `waitForAgentPrompt(steerCommandId)` — a prompt waiter on a non-prompt command; (c) the ADR-180 permission handoff source (`execution-host/agent-pause-source.ts:53-62`) locks `[turn]` with `state = 'dispatched'`, so with a steer row beside the parent the permission could bind to the wrong row and the handoff's own command/owner checks would refuse it. All three (and any future reader) go through one exported allow-list `OWNED_TURN_VARIANTS` (every variant except `steer`) — D-F4, T3.0. The same exclusion applies to `claimAgentMessage`'s `prior_turn` predicate (a) (`turn-claim.ts:114-126`): a steer is not a turn that "runs", so it never blocks the next message and the C10 hazard (a stuck `dispatched` steer blocking the queue) disappears. Writers keyed by turn id (`permission-rejection.ts:100`, `create-failure.ts:79`, `permission-resume.ts:262`, `park.ts:36-37`, `launch.ts:2909` oldest `queued`) are unaffected: a steer row is never `queued` visibly (accepted and issued in one transaction) and never addressed by those paths.

**C26. Definitive failures have no transactional hook.** `deliverCommand` offers `onAck` (`deliverer.ts:200-212`, "result-derived domain writes commit in the SAME tx as the ack") but nothing for a refusal: `markFailed` / `markFenced` run outside any domain transaction (`:262-285`, `:392-401`), as do `foldReceipt`'s rejected/fenced arm (`recovery.ts:279-320`) and `orphan()` (`:344-361`). A crash between `markFailed` and the successor insert would leave ledger `failed` + turn `dispatched` (or scratch row `steered`), a partial state no recovery arm selects (the fold reads `queued|delivering` rows only). D-C5 therefore requires one transaction per terminal path: a new `onReject(tx, error)` hook (run lock first, same order as the ack path, `session.steer` added to the run-lock kinds at `deliverer.ts:404-410`), and `foldReceipt` / `orphan()` gain a per-kind settlement callback executed inside the same transaction as the ledger write. With that, no crash window exists between the ledger and the domain row; T2.3 proves it by simulating a throwing `settleSteerCommand` (the ledger write rolls back and the retry re-runs both).

**C27. The scratch dispatcher must run detached from `afterCommit`.** `sendScratchPromptAndProjectEvents` awaits the WHOLE turn (`waitForScratchPrompt`, `scratch-runs/events.ts:581-586` → `client.waitForPrompt`), and `applyClaimedPromptOwner` awaits `prepared.afterCommit()` (`prompt-owner-application.ts:409`). Awaiting the dispatcher there would hold the previous turn's application, its waiter and the prompt-owner worker for the length of the next turn. D-D3's caller (1) is fire-and-forget with its own catch; the dispatcher's claim (row lock + CAS on `delivery`) is the only synchronous part, and the dispatched turn's completion is owned by its own prompt owner. Note the pre-existing drift the busy arm exposes: the prompt arm of `POST …/messages` answers after the turn completes (`sendScratchUserMessage` returns `stopReason`), while `web.openapi.yaml:5384` says 202 "dispatch started"; the busy arm genuinely answers at acceptance. T0.5 documents both arms; the prompt arm's timing is not changed here.

**C28. Only one web decoder is strict where the supervisor gains a field.** `checkSupervisorDiagnostics` parses `/diagnostics` with a `.strict()` schema (`supervisor-client.ts:396-454`; `smoke` strict at `:411-441`), so a supervisor that emits `smoke.steering` before the web schema knows it turns readiness into "malformed" and blocks launches. `listSessions` casts without zod (`:958`), `createSessionEnveloped` returns `res.body` (`:2055-2067`), and v1 runtime-event payloads are open (`RuntimeEventEnvelopeSchema.payload: z.record`, `runtime-events.ts:276-299`; the `superRefine` checks only v2 schemas and `stdoutSegment`), so `steeringSupported` on `session.created` and `capabilities` on the list entry are safe. The web diagnostics decoder therefore lands first (T1.0) and in the same commit as the supervisor change.

**C29. The transcript projector coalesces open assistant rows across the steer.** Only scratch runs treat `session.command` as a boundary (`transcript-projector.ts:68, 101-102, 139-149`), and that boundary also resets `usageSequence`. For an agent run the open assistant text row absorbs the chunks emitted after the injection, so the steered user row (allocated later) renders after the reply it caused; for a scratch run the usage row restarts mid-turn. D-B8 adds a steer boundary for every run kind: on `session.command{kind: "session.steer", phase: "accepted"}` close `openTextSequence`/`openThoughtSequence` and keep `usageSequence` (a steer is not a new turn).

**C30. Transcript order is manager acceptance order, not adapter order.** Whole-run feeds order by `createdAt, sequence` (`run-transcript-projector.ts:290-296`) and the steered/queued user row is allocated when the manager accepts it; assistant chunks emitted earlier but projected later sort after it. The S2/S4 assertions are therefore stated against a mock that emits its chunks only after the steer is acknowledged, and EDGE-STR-07 records the production semantics ("the row sits where the operator sent it"). Adapter-time exactness would anchor the row to the host `session.command{accepted}` sequence — a follow-up, not this item.

**C31. Contract and test anchors the first draft missed.** `ScratchMessageResponse` requires `stopReason` today (`web.openapi.yaml:19059-19081`) — the busy arm makes it optional. The ext message route has an integration suite (`app/api/v1/ext/runs/__tests__/message.integration.test.ts`), the MCP package pins tools against `operations.openapi.yaml` (`mcp/src/__tests__/tool-contract.test.ts`, `tools.test.ts`), the web `SupervisorEvent` type carries the command-kind union (`supervisor-client.ts:572-592`), and no EN/RU key-parity test exists for the `scratch` namespace (the `page-contract` tests cover other pages) — T4.5 adds one. The e2e seed supervisor holds a prompt in its permission scenario (`e2e/_seed/test-supervisor.ts:2060-2061`), which is how T4.6 reaches a busy dialog without a steer route.

**C32. A steer with content the adapter refuses converts, and the queued prompt fails the same way later.** Codex rejects image blocks on a text-only model inside `assertSteerInputSupported` (`index.js:33300+`) with a `RequestError`; the host maps it to a refusal, the manager queues the message, and the later prompt is refused by the same check — the existing prompt failure path (`markScratchPromptRetryable` / agent turn failure) handles it. EDGE-STR-08; no special case.

## Decisions

Every route below lists its identifiers with the trust label the skill-context rule requires. Two-phase commit, deferred release and crash windows are stated per decision; the normative recovery-window table is D-F1.

### A — Capability, uniformly

**D-A1. The host records the advertisement, interprets nothing else.** `createAcpConnection` (`acp-client.ts:930-1028`) returns `capabilities: { steering: { supported: initResp._meta?.steering?.supported === true } }` alongside `connection`/`acpSessionId`; `registry.attachAcp(sessionId, connection, acpSessionId, capabilities)` stores it on `SessionRecord.capabilities` (`types.ts:1137-1251`). Any other `_meta` key is discarded exactly as today. No adapter id is consulted (locked).
- Log: INFO `acp-capabilities-recorded {sessionId, adapter, steering: boolean}` once per initialize.

**D-A2. Three exposure points, no new GET route (C2).** `toSessionListEntry` adds `capabilities: {steering: {supported}}`; the create 201 body adds `steeringSupported: boolean`; `publishSessionCreated` adds `steeringSupported` to the payload. `/diagnostics` adds `smoke.steering: {supported: boolean | null, checkedAt: string | null}` per adapter from the cache (`null` = no smoke evidence); the smoke script records `init._meta?.steering?.supported === true` into the cache entry.

**D-A3. The manager persists the capability at the create ACK.** `applyCreateAck` (`create-ack.ts:35-210`) — the single writer behind the live ACK, the owned-create replay, the W2 receipt fold and the lifecycle projector — writes `steering_supported` on the incarnation row it inserts (`:164-176`) or, when the row already exists in `created | active`, updates the column when it is NULL. `result` gains `steeringSupported: boolean | null`; the four callers pass it (`client.ts:497` live ACK from the 201 body; `owned-session-create.ts:267` replay; `recovery.ts:219` fold from the receipt body; `lifecycle-projector.ts:107` from the event payload). Per incarnation, never per logical session: a resume spawns a fresh adapter process and re-initializes.
- Identifiers: server-state only (the ACK's own binding).

**D-A4. The mock adapter learns steering behind flags** (`supervisor/test/fixtures/mock-acp-lifecycle.mjs`): `--steering` advertises `_meta.steering.supported: true`; `--steer-outcome injected|promptRequired|startedNewTurn|failed|hang` scripts the answer (default `injected`); `--steer-delay-ms N` holds the answer; `--steer-echo` emits a `user_message_chunk` echo of the steer text before answering. On `injected` the mock emits `agent_message_chunk` `steered:<text>` inside the running prompt (the controlled prompt's `held` loop drains a per-session steer queue before returning) and records the steer in the invocation log (`method: "_session/steering"`, `sha256`, `idleBehavior`). On `startedNewTurn` it starts a detached loop emitting a chunk every 50 ms until `cancel` arrives (logged), which also proves the host cancel. On `promptRequired` it returns without side effects. Without `--steering` the method is not registered, so a bare `extMethod` fails as an unknown method — which is why the host gates on the advertisement, not on trying.

### B — One host command, one rule

**D-B1. `session.steer` is a v1 enveloped, fenced, receipted command on `POST /sessions/:id/steer`**, parsed by `parseCommandBody(req.body, "session.steer", SteerBodySchema)`, run through `runCommand` (sync, `accepted → completed | rejected` receipts, `session.command` events, replay by command id). `SteerBodySchema = { contentBlocks: ContentBlock[] (min 1), parentCommandId: uuid }` (`.strict()`), the same content-block shape the prompt route accepts (owner decision 2026-09-25, Q8: full content blocks, assembled by the same `scratchPromptContentBlocks` / agent text-block path as a prompt — metadata attachments and uploaded runtime objects included, no text-only special case), resolved by `resolvePromptRuntimeObjects` and confined by `contentBlockUriViolation` against the session's roots (`http-api.ts:1121-1141`).
- Identifiers: `id` — url-param; `fence.{hostKey, assignmentId, assignmentEpoch, runId}` — body, validated against server state by `applyFence` (`execution-fence.ts:20-97`); `payload.parentCommandId` — **body-controlled**, compared against server-state `entry.record.activePromptCommandId` (mismatch → refusal, D-B2); `payload.contentBlocks` — body, confined by the server-state roots. No run, step, path or session-name identifier is read from the body.
- Admission: not a teardown kind (`runCommand`'s teardown set unchanged); the assignment must be `active` (manager side, `isAdmissible` default arm).
- Authorization: the same as every supervisor route — `security: []` (`supervisor.openapi.yaml:72`), reachable only from the loopback host and only through `web/lib/execution-host/**` (ESLint fence); the data class of the response is a command outcome with no content, so no new grant, scope or positive-grant test is introduced. The caller-side gates are the existing ones: `runs:delegate` for the ext route, project membership `member`+ for the scratch route.

**D-B2. The host steers only the active owned turn.** Inside `execute`: (1) session `live` with a connection, else `PRECONDITION "session not live"` (as the prompt route); (2) `entry.record.capabilities.steering.supported`, else `SupervisorError("CONFLICT", …, {details: {reason: "steer_unsupported", parentCommandId}})`; (3) `entry.record.activePromptCommandId === parentCommandId`, else `CONFLICT {reason: "steer_no_active_turn", parentCommandId, activePromptCommandId: null | uuid}`. Both refusals write a `rejected` receipt (409 on the wire) and cost no ACP call. `activePromptCommandId` is cleared only after the parent's completed/rejected receipt (`http-api.ts:1064-1069`), so a late steer after the parent completed is refused here (trap 2, RED S6) and never attaches to the next prompt.

**D-B3. The call always opts into `promptRequired`**: `callAcpMethod({method: "steer", run: () => connection.extMethod("_session/steering", {sessionId: acpSessionId, prompt: contentBlocks, _meta: {steering: {idleBehavior: "promptRequired"}}})})` — `AcpMethod` (`acp-client.ts:178`) gains `steer`; the SDK's `extMethod` writes the method name verbatim (`sdk/dist/acp.js:1808-1810`, no prefixing), so the string carries the underscore. Codex ignores `_meta` (`index.js:33422-33431`); the uniform rule rests on D-B5, not on the opt-in.

**D-B4. Every non-`injected` answer is a refusal.** `promptRequired`, `startedNewTurn`, `failed` (C18), an ACP error, or the timeout (D-B7) → `CONFLICT {reason: "steer_no_active_turn" | "steer_timeout", parentCommandId, adapterOutcome}` → `rejected` receipt → 409. `injected` → 200 `{outcome: "injected", parentCommandId, latencyMs}`; the `session.command{completed}` event carries the same body as `result`, and the refusal's `error.details` carries `reason` + `parentCommandId` — the parent link rides the outcome body, so `SessionCommandEventSchema` gains only the kind (no new field).
- Log: INFO `steer-injected {sessionId, commandId, parentCommandId, promptBytes, latencyMs}`; WARN `steer-refused {sessionId, commandId, parentCommandId, reason, adapterOutcome}`.

**D-B5. An unowned turn is cancelled at once.** On `startedNewTurn` the host, before writing the receipt: `await entry.connection.cancel({sessionId: acpSessionId})`, then cancels every pending permission of the session (`pendingPermissions.cancel(sessionId, requestId, "steer-unowned-turn")` over `pendingPermissions.requestIds`, the cancel route's loop at `http-api.ts:2490-2492`) — a permission the unowned turn managed to raise is released, not leaked (deferred-release rule) — and logs WARN `steer-started-unowned-turn {sessionId, commandId, parentCommandId}`. The cancel failing is logged ERROR `steer-unowned-turn-cancel-failed` and the refusal is still written; the session's own lifecycle (parent completed, next owned prompt, or teardown) bounds what is left.

**D-B6. Stdin-order barrier: a prompt never overtakes an unanswered steer.** `SessionRecord.steerInFlight?: Promise<void>` is set by the steer route for the duration of the ACP call (chained when steers overlap) and cleared in `finally`; `executePromptTurn` awaits it (bounded by the same 30 s) before `sendPromptOnConnection` (`http-api.ts:1185`). This closes the window in which a steer whose host check passed is processed by the adapter after the NEXT owned prompt has started and injects into the wrong turn (RED S5c). It never delays a prompt by more than one steer round-trip.

**D-B7. Host ACP bound.** `STEER_ACP_TIMEOUT_MS = 30_000` (constant, `http-api.ts`) races the extension call; on timeout → refusal `steer_timeout` (D-B4), WARN `steer-timeout`, and the barrier is released. The manager's `COMMAND_POLICY["session.steer"].timeoutMs = 45_000` exceeds it so the host always answers first; unknown outcomes (network) retry the same id 3× (0.5 s·2ⁿ) — the host replays or joins the in-flight receipt.

**D-B8. Evidence.** The steer's evidence is its own receipt (`accepted | completed | rejected`) and its two `session.command{kind: "session.steer"}` events; the parent's request digest, receipt and span are untouched (C4). `session.steer` is added to `SESSION_COMMAND_KINDS`, the `session.command` arm, the browser stream allow-list (which exposes `parentCommandId` from `result`/`error.details` as-is) and the AsyncAPI kind enum. The transcript projector gains a **steer boundary for every run kind** (C29): on `session.command{kind: "session.steer", phase: "accepted"}` it closes `openTextSequence` / `openThoughtSequence` and keeps `usageSequence`; the generic scratch boundary on other command kinds is unchanged. The steered user row therefore sits between the assistant text before and after the injection in sequence order, subject to the acceptance-order caveat of C30.

### C — Manager model, persistent agents

**D-C1. `acceptAgentMessage(db, runId, prompt, {requestKey?, mode?: "steer" | "queue"})`**, default `queue` (unchanged path). `sendAgentMessage` returns `{childRunId, messageId, status, messageState, delivery: "steered" | "queued"}`.

**D-C2. Status allow-list** (`turns.ts:82-89`) becomes `{Running, NeedsInput, NeedsInputIdle}` for both modes (C21; owner decision 2026-09-25), written as an exhaustive `satisfies Record<RunStatus, boolean>` map per the fan-out rule; every other status keeps the `PRECONDITION`.

**D-C3. Steer eligibility is decided inside the issue transaction** (run lock → parent turn lock): the parent is the run's `dispatched` turn (partial index guarantees at most one non-steer) whose `execution_commands` row is a `session.prompt` in `state = 'accepted'` on the run's current assignment, and whose `incarnation_id` row has `steering_supported IS TRUE`. Otherwise the message is accepted as an ordinary `live_message | persistent_message` by the existing rule (`turns.ts:90-107`) and answered `delivery: "queued"` — the caller never learns the adapter (locked). `NeedsInput` with a dispatched parent is eligible (the prompt is in flight, blocked on a permission; claude delivers `later`, RED S7). "The run's dispatched turn" is always selected through `OWNED_TURN_VARIANTS` (D-F4), so a steer row is never mistaken for the parent by this path or by any other reader (C25).

**D-C4. The steer transaction (Phase 1 — intent).** Under the locks of D-C3: insert `agent_turns {variant: 'steer', parent_turn_id, ordinal: next, logical_key, prompt, state: 'queued'}` → `client.prepareSteer(tx, hostSessionId, {contentBlocks: [{type: "text", text}], parentCommandId})` (the `prepareInput` template, `client.ts:623-641`: `issue(tx, "session.steer", …)` — the ledger row is `queued` before the wire, admission-checked, envelope built by `buildEnvelope`) → update the steer row to `dispatched` with `command_id`, the parent's `execution_assignment_id / assignment_epoch / run_session_id / incarnation_id` → `appendRunMessage(tx, {runId, nodeAttemptId: null, role: 'user', content, promptDispatchKey: "steer:<commandId>", supervisorEventId: eventHorizon(runId)})` and set `delivery = 'steered'` on that row (C8; the anchor rule of `prompt-record.ts:185-215` keeps it on the projector's axis). Commit. The wire call runs outside any transaction.
- Log: INFO `agent-steer-issued {runId, turnId, parentTurnId, commandId, promptBytes}`.

**D-C5. Settlement (Phase 2 — outcome), one function `settleSteerCommand(tx, command, outcome)`** used by the live path, `foldReceipt` (new `session.steer` arm) and the orphan pass; it dispatches on the domain row the command id links to (`agent_turns.command_id` or `run_messages.steer_command_id`):
| outcome | ledger | steer row | successor | caller answer |
| --- | --- | --- | --- | --- |
| 200 `injected` | `succeeded` (`markSucceeded`, run lock first like input) | CAS `dispatched → applied` | none | `delivery: "steered"`, `messageState: "applied"` |
| 409 definitive (`steer_no_active_turn`, `steer_unsupported`, `steer_timeout`) | `failed` with `last_error.reason` | CAS `dispatched → superseded` | insert `live_message | persistent_message` at the next ordinal (run lock), `logical_key = message:requeue:<steerTurnId>`, `runs.resume_requested_at = coalesce(resume_requested_at, now)` (the `defer()` write, `turn-claim.ts:102-113`); after commit `claimAgentMessage(successor)` → `startAgentSession` when `claimed`, exactly as `sendAgentMessage` does | `delivery: "queued"`, `messageId` = successor, its `messageState` |
| FENCED (`assignment_fenced`) | `fenced` (`markFenced`) | as the definitive row: the message must still reach the run's new generation | as above | as above; the driver writes no run state (E-EH-11 — the conversion touches only turn rows) |
| unknown outcome, budget exhausted (`delivery_budget_exhausted`) | stays `delivering/queued` | stays `dispatched` | none yet — the receipt decides (C19) | `EXECUTOR_UNAVAILABLE` 503 to the caller; the recovery fold settles the row when the host answers |
The CAS predicates (`state = 'dispatched' AND command_id = …`) make Phase 2 idempotent across the live path and the fold; a lost race is logged INFO `steer-settlement-already-applied` and returns the row as found. Nothing is sent twice: a successor is inserted only from a definitive `rejected`/`fenced` receipt, never from an unknown outcome.

**Every ledger terminal write for a `session.steer` command commits in the same transaction as `settleSteerCommand`** (C26): the live ack through `onAck` (existing), the live refusal through a new `DeliverOptions.onReject(tx, error)` invoked inside the `markFailed` / `markFenced` transaction (run lock taken first, as the ack path does for `session.input` / `session.create`), the receipt fold and the orphan pass through a per-kind settlement callback passed into `foldReceipt` / `orphan()` and executed in their (new) transaction. No path writes the ledger's terminal state without the domain row, so the "ledger `failed`, turn still `dispatched`" partial state is unreachable rather than recovered. A settlement that throws rolls the ledger write back; the same-id retry re-runs both.

**D-C6. Same-key retry (C20).** `acceptAgentMessage` looks up `message:request:<key>`; a `steer` row that is `applied` answers `steered`; one that is `superseded` answers with the successor found by `message:requeue:<turnId>` (`queued`); one still `dispatched` answers `messageState: "dispatched"` with `delivery: "steered"` pending — the same accepted row, nothing re-issued. A different prompt under the key is the existing `agent_turn_request_conflict`.

**D-C7. Ext route + MCP.** `POST /api/v1/ext/runs/message` body gains optional `mode` (`steer | queue`, default `queue`); the 200 body gains required `delivery`. `run_message` takes `mode` and passes it through; its description names both deliveries. Mentions (ADR-151) launch through `launchAgentRun` and pulse (ADR-152) is a feed — neither calls `sendAgentMessage`, so both keep `queue` by construction.

**D-C8. Transcript visibility.** `getAgentRunTranscript` passes `includeRecordedPrompts: true` to `getWholeRunTranscriptMessages` (`run-transcript-projector.ts:253-299`): the flag admits the steered rows and the prompts T3.5 records at dispatch (owner decision 2026-09-25); the agent-run transcript is therefore the full dialog, bounded per row by the TRC-06 recorder. The ext-activity fallback keeps its default.

### D — Manager model, scratch

**D-D1. `assertScratchCanAcceptUserMessage` gains a second allow-list arm.** `{WaitingForUser}` → `mode: "prompt"` (today's path, unchanged); `{Starting, Running}` → `mode: "busy"`; terminal statuses and `NeedsInput` keep their `CONFLICT`; a missing host session keeps `PRECONDITION`. The busy arm requires the run's newest owned `session.prompt` command with `owner_kind = 'scratch_message'` and `state = 'accepted'` on the current assignment (the parent), else the message is queued.
- Identifiers: `runId` — url-param; the parent command, incarnation and host session — server-state; body carries content and attachment refs only (unchanged).

**D-D2. Busy transaction.** Under `lockRunRows`: append the user row (`appendScratchMessage`) and attachments as today; if the parent's incarnation has `steering_supported IS TRUE` → `delivery = 'steered'`, `steer_command_id = <id>` from `client.prepareSteer(tx, hostSessionId, {contentBlocks: scratchPromptContentBlocks(prompt, attachments), parentCommandId})`; else `delivery = 'queued'`. The dialog status, `runs.status` and `errorCode` are **not** touched (the dialog stays `Running`); `lastUserMessageAt` is updated. Commit; deliver outside the transaction. `injected` → `settleSteerCommand` (`succeeded`; the row stays `steered`) → response `{ok, messageId, sequence, dialogStatus: "Running", delivery: "steered"}`. A definitive refusal → `settleSteerCommand` flips the row `steered → queued` (CAS on `steer_command_id`), then `dispatchQueuedScratchMessages(runId)` (D-D3) — the turn may already have ended — → response `delivery: "queued"`. `ScratchMessageResponse.stopReason` becomes optional (absent for the busy arm; the prompt arm keeps it).
- Log: INFO `scratch-steer-issued {runId, messageId, commandId, parentCommandId}`; INFO `scratch-message-queued {runId, messageId, reason: "unsupported" | "no_active_turn" | "steer_refused"}`.

**D-D3. One dispatcher, two callers, FIFO, idempotent.** `dispatchQueuedScratchMessages(db, runId)`: transaction under `lockRunRows` → require dialog `WaitingForUser` and the oldest `delivery = 'queued'` row (partial index) → CAS `queued → prompted` on that row, set dialog `Running` + `runs.status = Running` + `currentStepId` (the writes `appendScratchUserMessage` makes today at `service.ts:2147-2161`) → commit → `sendScratchPromptAndProjectEvents` with owner `{variant: "message", messageId, sequence}` and attachments re-read by `messageId` → existing failure handling (`markScratchPromptRetryable` on `EXECUTOR_UNAVAILABLE`, the fenced yield, `markScratchCrashed` otherwise). Callers: (1) `prepareScratchPrompt().afterCommit` (C13) — runs after the previous turn's `WaitingForUser` commit and is **detached** (`void dispatchQueuedScratchMessages(db, runId).catch(warn)`; C27: the dispatcher awaits the whole next turn, and `applyClaimedPromptOwner` awaits `afterCommit`); (2) the refusal conversion in D-D2; (3) the `WaitingForUser` prompt arm of D-D1 when queued rows exist ahead of the new message: the new row is appended `queued` and the dispatcher sends the oldest, so a user who returns after a reload never jumps the queue. The loser of a concurrent dispatch sees `Running` and returns `{dispatched: false}` (C22).
- Log: INFO `scratch-queued-message-dispatched {runId, messageId, sequence, remaining}`; INFO `scratch-queued-dispatch-skipped {runId, reason: "not_waiting" | "nothing_queued" | "cas_lost"}`; WARN `scratch-queued-dispatch-failed {runId, messageId, code}` from the detached catch (the row is already `prompted` and the dialog `WaitingForUser` again through the existing retryable path, so the badge and the next send remain the operator's controls).

**D-D4. The browser queue is deleted.** `scratch-composer.tsx`: remove `autoSendArmed`, the arming in `handleStop` (`:150-161`) and the auto-send effect (`:163-194`); `canSubmitMessage = !!content.trim() && (canUseComposer || agentBusy)`; while busy the primary button is **Send** (enabled) and **Stop** becomes a secondary button beside it; `Cmd/Ctrl+Enter` while busy sends. The response's `delivery` drives an inline notice under the composer and a badge on the row (`delivery === 'queued'` → "Queued"; `steered` → "Steered in"); a refused steer degrades to the queued copy. `interruptTitle` / `draftWhileBusy` lose their auto-send promise (EN/RU).

**D-D5. Local-package assistant runs keep the `WaitingForUser`-only gate** (`sendLocalPackageAssistantMessage`, `service.ts:2312`; separate actor/lock model and one-structured-action-per-reply postprocessing, ADR-097). Owner decision 2026-09-25 (Q4): kept out; recorded as a follow-up in ADR-182 Consequences.

### F — Recovery windows, crash windows, invariants

**D-F1. Normative recovery-window table** (each `status × mode` cell names its arm; copied into `execution-prompt-lifecycle.md`):
| State of the steer command / row | Live owner | Owner after a manager death |
| --- | --- | --- |
| ledger `queued`, no receipt (W1: crash after the intent commit, before the wire) | the issuing request | the command recovery pass marks the non-driverless `queued` row `ORPHANED` today; new: for `session.steer` it calls `settleSteerCommand(orphaned)` → steer row `superseded` + successor / scratch row `queued` (exactly-once: the wire never happened) |
| ledger `delivering`, host receipt exists (W2: crash after the wire, before Phase 2) | the issuing request | `foldReceipt` `session.steer` arm → `settleSteerCommand` |
| ledger `delivering`, host has no receipt (host died mid-steer) | — | the existing `receipt_missing` / `turn_lost` folds mark the ledger; `settleSteerCommand(rejected)` converts (the parent turn is lost too and re-drives through its own path) |
| successor `queued` (W3: crash after Phase 2, before `claimAgentMessage`) | the issuing request | `resume_requested_at` is set → the continuation worker's parked-run arm (`continuation-worker.ts:129-148`) re-drives after the parent parks; a `Running` parent's park re-arms it (`park.ts:36-37`) |
| scratch row `queued`, dialog `Running` | the previous turn's `afterCommit` | the same `afterCommit`, executed by whichever process applies the previous turn's completion (the prompt-owner worker survives a web restart) |
| scratch row `queued`, dialog `WaitingForUser` (W5: crash between the completion commit and the dispatch; W6: same after a conversion) | — | **A4** (scratch re-drive; out of scope by the request; owner decision 2026-09-25, Q2). Interim: the next message send (D-D3 caller 3) and the visible "Queued" badge; the row is never lost |
| host: `steerInFlight` set, adapter never answers | the 30 s bound (D-B7) | a host restart drops the in-memory promise with the session; the receipt the manager folds says `turn_lost` for the parent |

**D-F2. Invariants → enforcement.** At most one non-steer active turn per run → `agent_turns_active_run_uq` (re-created); a steer names its parent → `agent_turns_steer_parent_check`; a steer never owns a prompt → its ledger row has `owner_kind IS NULL` and no application state (the `execution_commands_prompt_owner_required` CHECK is prompt-only); a message is delivered exactly once → successor only from a definitive receipt (D-C5) + the same-key lookup (D-C6) + `run_messages_steer_command_uq`; an unowned turn never runs to completion → host cancel (D-B5) + RED S5b; a prompt never overtakes a steer → D-B6 + RED S5c; the parent's evidence is untouched → C4 pin (RED S2) + the tamper falsification (T2.5); prompt text never leaves the ledger projection → `PAYLOAD_PROJECTION["session.steer"]` keeps `parentCommandId`, `promptBytes`, `contentBlockCount` only.

**D-F3. Lock scope = invariant scope.** FIFO ordinals per run → the run row lock (both `acceptAgentMessage` and the conversion insert); one dispatch per scratch row → the run + `scratch_runs` row locks with the CAS on `delivery`; the host's per-session ordering → the in-memory `steerInFlight` chain on the `RegistryEntry` (the invariant is per host session). Racer tests are designed from the invariant (T3.4, T4.4).

**D-F4. The `steer` variant is invisible to every owned-turn consumer.** One exported constant `OWNED_TURN_VARIANTS` (`agents/turn-variants.ts`: `initial | resume | rework | live_message | persistent_message | consensus_draft`, typed `satisfies readonly AgentTurn["variant"][]` so a new variant fails to compile until classified) is the predicate of: the continuation worker's Running arm, `startAgentSession`'s turn selection, the permission handoff source, and `claimAgentMessage`'s `prior_turn` predicate (a). Steer rows are addressed only by command id (`settleSteerCommand`) and by `parent_turn_id`. Enforcement: the constant's type, T3.0's REDs, and the existing `agent_turns_source_check` (which is where a new variant is added, forcing the classification).
