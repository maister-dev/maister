## Frozen design

### D1. Bytes, bounds, and evidence

Create `web/lib/flows/graph/consensus/text.ts` for pure UTF-8 operations and named constants (reuse an existing equivalent byte-prefix utility if present). Do not use string `.slice()` as a byte count. Preserve Unicode code points and never create replacement characters by cutting a UTF-8 sequence.

- `CONSENSUS_DRAFT_OUTPUT_CAP_BYTES = 1024 * 1024` stays the draft write bound.
- `CONSENSUS_GENERATION_OUTPUT_CAP_BYTES = 1024 * 1024` bounds verifier and synthesis accumulation. Parse the complete retained verifier output, not its raw-artifact excerpt. Continue consuming the verified stream after the text budget is exhausted so terminal status and actual dropped-byte count remain known.
- **`CONSENSUS_PROMPT_TEXT_CAP_BYTES = 64 * 1024` (65,536 UTF-8 bytes)** is the single text-slot bound for `target_draft`, `selected_text`, participant prior draft, and published synthesized `planText`. The cap includes the marker. A 60,000-byte draft passes unchanged. Do not concatenate N individually capped drafts to bypass the selected-text bound; bound the selected-text value as a whole. Preserve the full retained synthesis in its generation artifact even when the published plan is bounded.
- Retain `CONSENSUS_TEXT_CAP_BYTES = 32_000` only for display/raw-artifact excerpts, preferably rename it `CONSENSUS_EXCERPT_CAP_BYTES` so it cannot accidentally govern protocol input or parser accumulation again.
- Exact marker: `\n[consensus text truncated: dropped <N> UTF-8 bytes; cap <C> bytes]`. Select the longest complete-code-point prefix whose bytes plus the marker fit C; N is original bytes minus retained original-content bytes. Marker bytes count toward C. Keep artifact identity in the adjacent typed reference, not inside the marker: this also fits 256-byte field excerpts and avoids a capped raw artifact falsely promising that it contains its own full output. `textBounds.retainedBytes` excludes marker bytes; `bytes = retainedBytes + droppedBytes`. Output retention loss is separate from prompt/excerpt loss. No marker may promise recovery of bytes beyond the 1 MiB retention budget.
- Every truncating boundary emits WARN `consensus-text-truncated` with `{role, participantId, round, bytes, cap}` plus artifact/generation identity and dropped bytes. `bytes` means original UTF-8 bytes, not characters. Re-entry may log again but must not mutate immutable evidence or issue another paid turn.
- Full draft reads return all retained bytes. Debate logs are serialized **after** bounding individual text fields; never cap serialized JSON. Keep all cell identities, parsed status, reasons, axis booleans, artifact references, and omitted counts. The prompt-facing debate value may use smaller excerpt fields to fit its budget; it must remain a parseable JSON document with an artifact reference.
- HITL excerpts are bounded and labeled, with the draft artifact reference beside each excerpt. The full-text link uses the draft child run ID: `GET /api/runs/{draft.runId}/artifacts/{artifactId}/payload`; the route rejects a parent run ID for a child artifact. Extend `ConsensusDraftChoiceView`/`consensusDrafts` to retain `artifactRef` and `artifactRunId` rather than dropping them, and verify full-tail retrieval under the existing access gate. Truncation is separate from `partial`: complete output can be shortened for a prompt without becoming a non-end-turn draft. A write-cap overflow, however, cannot be represented as a complete full draft; retain it as partial with an explicit `output_cap_exceeded` evidence reason and its real stop reason.

**Context rationale and honest limit:** 64 KiB is a conservative engine text allocation, large enough for B1a, substantially below a 200k-token reference context, and small enough to leave space for the rendered node prompt, addressed verdict, bounded round critique, tools, and output. Claude Haiku 4.5 is exercised in runner resolution tests and has a documented 200k context ([Anthropic context documentation](https://platform.claude.com/docs/en/build-with-claude/context-windows)); it is the smallest verified named reference used here, not a platform-wide minimum. `acp-runners/schema.ts` accepts arbitrary non-empty model names and `presets.ts` includes provider/native aliases without context metadata. Therefore there is **no provable smallest context across every configurable supported runner**. Do not invent one or claim this byte cap guarantees that arbitrary base prompts fit. Task 1 records the actual qualification runner/model context and rendered prompt budget; provider context errors remain explicit technical failures, not silent fallback/truncation of the author's prompt. A new model registry, tokenizer dependency, or model-admission floor is outside this item.

### D2. Existing JSON storage and compatibility

Use additive, typed inline `ArtifactLocator` fields: `partial?: boolean`, `stopReason?: string`, `reason?: string`, `truncated?: boolean`, and `textBounds?: {bytes, retainedBytes, droppedBytes, cap}` (use the existing stop-reason union where import boundaries permit). Synthesis locators also carry optional `inputTextBounds` copied from their preparation evidence; `textBounds` describes output loss. Their top-level `truncated` is true if either input or output was truncated, so a short synthesis of a shortened selected draft is still flagged. Verifier rows flag input only; their raw-output artifact flags output only. Mirror both bounds fields in the OpenAPI locator schema. Scope descriptions to consensus artifacts. Generation artifacts preserve output and terminal outcome; do not encode metadata into free-form text or discard it during `recordArtifact` replay.

For `consensus_round_verdicts.disagreements` use a typed legacy/new storage union:

```ts
type ConsensusDisagreementStorage =
  | ConsensusRoundDisagreement[]
  | {
      version: 1;
      rows: ConsensusRoundDisagreement[];
      truncated: boolean;
      textBounds?: ConsensusTextBounds;
    };
```

Here `truncated` describes the target draft actually shown to that verifier; raw-output excerpt truncation is separately on its artifact locator. Extend the TypeScript `$type` annotation only, never the SQL column/default or migration metadata. Normalize at `loadConsensusVerdicts`/`loadConsensusVerdictCell` so runtime/tally still receive `disagreements[]` plus explicit metadata. Old arrays mean no recorded truncation metadata, not a claim that historical text was complete. New writers use the versioned envelope. No reserved axis, fake disagreement row, or overwrite of a completed cell to add flags.

Freeze input metadata before prompt enqueue in a deterministic, internal **input-evidence artifact**, using the existing artifact table and the verdictId/synthesisId plus an `:input` suffix. Its versioned JSON records run/attempt/round/generation identity, source artifact or HITL request identity, the bounded input value's digest and byte bounds, and the UTF-16 start/end span of that value in the rendered prompt; it stores no second full draft. Owner application slices the verified canonical request at that span and checks its digest, exact bound/marker accounting and prompt digest. A missing or malformed new span is a typed invariant failure. Create it under the existing current-owner admission guard before enqueue, compare rather than overwrite on retry, and load it by the exact generation in owner application. A crash after preparation but before enqueue leaves inert evidence: only the main verdict/synthesis record means applied; replay reuses the prepared input and enqueues through the existing logical operation key. Input metadata cannot make a generation look complete. Legacy commands lacking this artifact remain readable with metadata unknown; quiescing consensus before rollout prevents new input using legacy preparation.

Do not put metadata into `execution_commands.payload` or extend `owner_ref`: `execution-host/redact.ts` deliberately stores only prompt byte/count summaries there, and migration `0140_immutable_command_requests.sql` enforces exact owner-ref keys. The full prompt exists in `requestCanonicalJson`; tests use the existing verified `command-request.ts::readPromptRequest` boundary to compare the delivered bounded value/digest with input evidence, without exposing request bodies in DTOs/logs. No direct parsing of the redacted projection, forged marker detection, mutable latest-round lookup, command hash rewrite, or new owner-ref field. T2 freezes the artifact shape and replay invariant; T9 implements it for verifier and synthesis inputs.

Readers: `consensus/ledger.ts` owns normalization; `consensus/prompt-owner.ts`'s generation-exists read selects identity only. Update direct row assertions in `consensus-prompt-owners.integration.test.ts`; preserve the legacy SQL-array roundtrip in `db/__tests__/schema.integration.test.ts`. Mirror locator additions in `docs/api/web.openapi.yaml#ArtifactLocatorInline`.

The migration audit is explicit: `0070_consensus_round_verdicts.sql` creates JSONB disagreements without an array-type CHECK; subsequent migrations do not constrain it to arrays. Preserve its unique cell key and foreign keys. Extend the existing `db/__tests__/schema.integration.test.ts` SQL-array roundtrip with a versioned-envelope roundtrip, then exercise replay through the real owner application. Artifact/input/decision evidence all use existing JSONB rows; `execution_commands` immutable-request and owner-shape checks and `node_attempts_action_resume_check` stay byte-for-byte unchanged. Do not generate a migration, snapshot, journal entry, new index, or ERD entity. If an implementation hits a DB constraint, revise the JSON placement within these constraints; the generic request to inspect migrations does not authorize DDL.

Rollout is one web binary on the supported single host. Quiesce in-flight consensus work before changing writers; do not run an old reader beside envelope-writing code. Rollback must retain the compatibility reader (disable/revert behavior in forward code), or restore a pre-change database backup while stopped. Never flatten stored envelopes or erase partial artifacts merely to run an old binary. No automatic data migration or down-migration is proposed.

### D3. Draft classification and trailer

Use a real discriminated union `complete | partial | unavailable` in `ConsensusDraftEvidence`; retain run status separately. Classification is evidence-based:

| Class       | Required evidence                                                                                                               | Verifier cell                                                                                                   | Human / next round                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| complete    | Non-empty artifact from successful `end_turn`, no lost output bytes                                                             | Normal paid verification (or existing applied immutable cell)                                                   | Pickable; own prior draft                                        |
| partial     | Non-empty retained artifact explicitly marked partial, including successful `max_tokens` / `max_turn_requests` / `refusal` turn | Persist fail-closed `errorCode: draft_partial`, without acquiring verifier capacity or issuing `session.prompt` | Pickable, partial + stop reason; own prior draft + engine reason |
| unavailable | No non-whitespace draft text                                                                                                    | Persist fail-closed `errorCode: draft_unavailable`, no paid verification                                        | Not pickable; engine reason to that participant                  |

Preserve participant order and `pick-draft-N` indexes even when a participant is unavailable: do not filter the choice array or renumber decisions. The UI disables an unavailable choice; existing server validation still rejects an unusable pick. Partial choices remain enabled. Legacy non-empty successful draft artifacts remain readable as complete; legacy failed children without artifacts remain unavailable. Do not infer a legacy failed child's missing text. Terminal parent cancellation/abandon overrides iteration/HITL; retained evidence never resurrects it.

Record a partial artifact and child Failed / `consensus_draft_incomplete` with `stopReason` in the existing owner application transaction. Only no text across **all** drafts triggers `CRASH` / `consensus_no_draft_available`; all-partial rounds have usable text and therefore iterate or escalate. Fail-closed partial cells still participate in unanimity and cannot agree.

The fixed engine trailer, appended last after all rendered draft context, is:

> Return the complete draft as your final message text. File writes are refused in this workspace. Do not reference files as the deliverable. Include the full draft in the final message, even when revising a previous draft.

### D4. Participant-specific prompt composition and strict Mustache

Change `launchConsensusDraftRuns` from one common prompt to a typed collection of `{participantId, prompt}` paired with the resolved participants. Require exactly one prompt for every participant before inserting child rows; missing/duplicate/foreign participants are explicit internal contract errors, never a common-prompt fallback. Preserve deterministic round/participant trigger identity and root-db child dispatch.

The author node prompt is strictly rendered once. Then a **static** engine template is rendered with `withConsensusVars` values; rendered base prompt, all agent text, critique, banners, prior draft, and trailer enter as `consensus.*` VALUES. No author/agent text is concatenated into template source or re-rendered. Round 1 includes base prompt + trailer. Round N+1 has:

1. Rendered base prompt.
2. `Verdict on your previous draft`: only the cell whose target is this participant; parsed rows and failed axes identify the verifier (`axis X judged false by verifier Y`). A `draft_partial` / `draft_unavailable` cell instead yields a drafter-side engine note. Example: `Your round-1 draft was cut by max_tokens after 60000 UTF-8 bytes; deliver a complete draft.` Include the actual stop reason/count, never guess them.
3. `Your previous draft`: only this participant's retained round-N draft, whole under D1; unavailable has an explicit absence note. Never inject another participant's draft body.
4. `Round critique`: deterministic union of parsed material rows (12 maximum), plus parsed failed-axis summaries (12 unique axes maximum in manifest order, verifier/target identities grouped per axis). Each row claim/counter-evidence field is limited to 1,024 UTF-8 bytes and each displayed axis label to 256 bytes with the same labeled-excerpt mechanism; render the whole critique section under the text budget, with omitted-row/axis counts and ledger reference. The predicate below uses the **full** data before any display bound.
5. `Technical verifier failures`: clearly separated technical entries, never presented as judgments about draft content; at most 12 displayed entries with 256-byte field excerpts and an omitted count. Full entries remain in HITL/debate evidence.
6. Fixed engine trailer, last.

Reconstruct this data from immutable round-N cells and round-N draft artifacts on replay; never from process memory or `latestRound` after N+1 has been created. The addressed section uses the same 12-row/12-axis, 1,024-byte row-field and 256-byte label bounds as the union, with explicit omitted counts and the addressed verifier/target identity. Bound each generated section under the same 65,536-byte text budget; reserve the addressed section and own prior draft before union context. Artifact/ledger references retain omitted facts. Author-supplied base prompt size remains outside this allocation and must not be silently cut.

### D5. Empty-critique predicate and HITL

Compute `hasActionableCritique` from the entire round: at least one non-empty material disagreement row from a **parsed** verdict, or at least one declared axis false in a **parsed** verdict, or a drafter-side `draft_partial` / `draft_unavailable` reason. Never use `tally.failedAxes` blindly: fail-closed verifier cells manufacture false axes which are not content criticism.

When agreement is false and `hasActionableCritique` is false, escalate immediately regardless of remaining automatic rounds. `technicalFailures[]` contains `{verifierId, targetParticipantId, parseStatus, errorCode}`; include invalid JSON/schema/missing/unknown axes and host/session errors. If a cell has only parseStatus, use that as its explicit technical errorCode. Partial/unavailable targets are drafter reasons, excluded from verifier-only failures.

A syntactically parsed `disagree` with all axes true and no non-empty rows has no actionable criticism. Classify this inconsistent verdict at the verifier parser as `invalid_schema` with a named technical detail (`empty_disagreement`), not as a new content critique or a gratuitous drafting round. Cover this boundary explicitly; it makes the owner's technical-only definition total without inventing failed axes.

Agreement follows the existing unanimity policy. With actionable critique, `iterate` and rounds remaining re-fan; exhausted rounds or single-pass escalate. An explicit human `re-run-round` uses the last round's full reconstructed per-participant context, including technical notes for a technical-only round. It is human-authorized spending, not an exception to the automatic no-re-fan predicate.

For explicit rerun, pin the source to the delivered server-side HITL request and its round, never `latestConsensusRound` after children may exist. Add `nodeAttemptId` to new consensus HITL schema records alongside their existing round; do not change the response request shape. Before fan-out, persist an immutable decision-intent artifact keyed by HITL request ID with `{version:1,hitlRequestId,nodeAttemptId,sourceRound,targetRound,decision,responseDigest}`; `targetRound = sourceRound + 1`. Resolve the stored request under the run/current-attempt guard and verify the input decision against its stored response. For old schema records without attempt identity, use the existing run/node/attempt lifetime and round to identify a unique delivered request; reject ambiguity explicitly rather than bind it to a newer round. Re-entry first adopts an unfinished intent and the existing deterministic target-round children, including partial fan-out. Once all children are durably registered, record an idempotent applied marker in the existing artifact table and consume the input file. A death before file deletion must only finish cleanup, never launch N+2 or report a false max-round conflict. Keep this protocol inside consensus runtime/ledger, not the shared HITL response service. This is B3e replay acceptance, not a new general decision queue.

At HITL creation, persist a round-scoped debate artifact in the same DB transaction as the HITL row (deterministic ID from attempt + round). `schema.debateLog` references that artifact with `artifactRunId` equal to the parent run, alongside a labeled bounded excerpt. Do not point to the final `debate_log` output that is created only after synthesis. A transaction failure must expose neither a committed HITL reference to a missing artifact nor a delivered decision; preserve the existing file/DB recovery protocol. Full draft links use child run IDs. Re-entry reuses immutable evidence and request identity rather than overwriting the round log.

`consensus_resolution` adds typed `technicalFailures[]`; draft choices add classification, stop reason, artifact ID, and truncation metadata alongside their existing fields. Keep allowed decisions and response validation unchanged. A human may pick a partial draft; selecting it feeds synthesis with the partial label/reason so it is not presented as unanimous agreement. Update the existing inbox card and EN/RU messages to show partial labels, technical failures, excerpt labels, and usable artifact references, without changing P0-4 refusal copy.

### D6. Pending, synthesis failure, recovery, and replay

- Both graph catches treat `ConsensusGenerationPending` exactly like `FlowPromptContinuationPending`: yield without `markNodeFailed`, auto-retry scheduling, or run failure. Preserve driver claim release and owner-application/continuation ordering.
- Missing generation row means pending; an applied incomplete generation is a distinct typed result, never `""` or `null` masquerading as pending. `loadConsensusSynthesis` returns generation identity, retained text, stop reason, completion and truncation metadata. Legacy non-empty synthesis artifacts lacking metadata remain readable as completed historical evidence; legacy empty artifacts are applied incomplete evidence with stopReason recorded as unknown, never an invented end_turn. Missing rows remain pending.
- Both fresh and replayed synthesis paths use one validation rule: an applied non-end-turn/empty generation becomes `MaisterError("CRASH", ..., {details:{reason:"consensus_synthesis_incomplete",stopReason,synthesisId}})`. Emit structured ERROR with this reason and identity; the generation artifact durably contains them and partial text. `markNodeFailed.errorCode` is CRASH. No new run/node error column and no generic P0-4 copy refactor.
- Recovery must work for default consensus configuration **when the latest failed attempt has applied incomplete-synthesis evidence**. Project a typed recovery witness from the generation artifact, its owner command and that exact attempt: node Failed/CRASH, reason `consensus_synthesis_incomplete`, matching run/node/attempt/synthesisId and settled application. Missing, stale or mismatched evidence must not enable this new capability. Share the projection between backend recovery and the run-page capability read; do not add an unconditional consensus branch to `redispatch` or `resume-agent`. Keep established behavior for other crash causes.
- Validate terminal-conflict quarantine before this redispatch branch. Currently `recover.ts` returns from redispatch before `applyCrashedTurnEvidence`, whose quarantine scan in `crash-recover.ts` covers only owner variant `node`. Extend the relevant evidence guard narrowly to consensus verifier/synthesis owners of the affected attempt, including closed-attempt terminal conflicts, and invoke it before fresh work is admitted. A quarantined command must not cause another paid generation. Backend and UI agree on refusal; direct recovery dispatch cannot bypass the guard. ADR-177 owner-poison handling is unchanged.
- Eligible human Recover redispatches a **fresh node attempt** with a fresh deterministic synthesisId; the old generation remains evidence and cannot satisfy the new attempt. This is explicit human recovery, not coordinator auto-retry. Keep the driver fencing and cancellation checks authoritative.
- Existing bounded prompt-owner application retries and ADR-177 poisoning remain authoritative. After exhaustion, run becomes Crashed with owner-poisoned evidence; pending does not keep yielding forever. No new retry budget, polling loop, or worker.

### D7. Shared child wake and crash windows

Extract one shared wake function from `web/lib/domain-events/orchestrator-resume.ts` into a dependency-safe web module (proposed `web/lib/flows/graph/coordinator-wake.ts`). Both the event consumer and post-park path call it with a cause discriminant; the module must not statically import `runner-graph` back into itself. Preserve the existing manifest/node lookup, domain event, status transition, assignment/cap admission and re-drive mechanisms.

Invariant: at most one wake of the current waiting coordinator generation; key the CAS to parent run, `WaitingOnChildren`, and expected current coordinator node and latest parked attempt ID. Capture those identities from the park result for catch-up and load them under the shared wake guard for the event path; a stale caller must not wake a later attempt of the same node. Use the same parent-wide pending-child predicate from the consumer, derived from the existing status concern. Do not introduce a round filter. Preserve the orchestrator consumer's existing exceptional wake rules (including HITL/fail-fast behavior) separately from the zero-pending settled-child catch-up.

After WaitingOnChildren park commits, run exactly one zero-pending catch-up for **both** consensus and orchestrator. Use root DB after the park releases execution assignment; a traversal-scoped DB can already be fenced. The CAS loser returns a typed no-op, not an error and not a second re-drive. A terminal or different-node parent is a no-op. Consumer WARN when it observes a settled child while the parent is Running on either coordinator kind: `child settled before parent parked — catch-up owns the wake`, with parent/child/node identifiers.

Place the runner-side call in `web/lib/flows/runner.ts` immediately after `await withFlowDriver(...)` returns (its `finally` has released the token), and after the unleased `runGraph` branch returns. This is the post-park catch-up outside the fenced traversal; do not perform it inside `runner-graph.ts` with its released assignment. The shared helper keeps the consumer's dynamic import of `flows/runner` to avoid a static cycle.

Reuse `markResumedFromWait`: it holds `takeSchedulerLock`, checks the flow capacity pool, atomically CASes WaitingOnChildren → Running and mints `wait_resume`; capacity refusal leaves `resumeRequestedAt` on the parked parent. Do not treat capacity deferral as a status-CAS loser or bypass admission. The existing continuation worker handles these markers, but its command/action predicates must cover a consensus parent with no verifier command yet. The shared immediate dispatch retains the existing `consensusResume` / `orchestratorResume` entry options. Production tests must prove progress, not only a queued callback.

For restart-safe consensus wake, derive durable intent from the tuple already persisted by the CAS: `runs.status = Running`, current consensus attempt still NeedsInput, active run assignment with `placementReason = wait_resume`, and the attempt's source assignment released with `releasedReason = waiting_on_children`. Require the same host, increasing assignment epoch, matching run/current node/latest attempt, and zero pending children. The existing `node_attempts_action_resume_check` permits only ACP-oriented variants and requires session/command fields; adding a consensus JSON variant there would need a migration and is forbidden. No new intent field is necessary.

Extend `graph/continuation-worker.ts` with a narrow candidate arm for that persisted consensus tuple and no live driver lease; revalidate the tuple on dispatch and enter `runFlow(..., {consensusResume:true})`. Successful graph re-entry atomically marks the reused attempt Running and rebinds its executionAssignmentId to the current wait_resume assignment, consuming the tuple under its driver claim. The worker's Running-node/no-command continuation arm must also admit this current consensus attempt (it currently names ai_coding/judge/orchestrator), so death before the first verifier command does not create another gap. A failed claim/read or process death leaves it retryable; do not mark an in-memory callback as delivered. Separately, select WaitingOnChildren consensus parents with `resumeRequestedAt` set even when there is no parent-owned prompt command yet. Recheck zero pending, use the same capacity-checked `markResumedFromWait`, and then consume the successful-wake tuple. Keep existing marker clearing and orchestrator action-resume behavior unchanged. Cover post-CAS/pre-dispatch death, death during re-entry, capacity deferral, stale current node and terminal cancellation. This reuses existing columns, assignment facts, worker and retry controls; it adds no JSON discriminant, migration, scheduler or retry framework.
