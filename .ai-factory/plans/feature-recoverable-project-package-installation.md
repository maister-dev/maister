# Recoverable project package installation

Branch: `feature/recoverable-project-package-installation`  
Created: 2026-11-23  
Baseline: `22df665aa`  
Status: contracts specified; implementation in progress. Post-registration installation is approved for all three manifest sections.

## Outcome

An administrator registers a valid Git repository and opens the project as soon as registration commits. MAIster records each top-level Flow, capability import and package requested by its manifest. Fetch, member-manifest validation, setup and attachment run after acceptance. If one fails, the project stays usable and independent items can finish. An operator can inspect and retry any failed item, and can correct a package pin in project settings. A separate reviewed action in Settings → Git can publish the corrected `maister.yaml`.

## Settings

- Testing: yes. Use PostgreSQL integration tests, real local Git repositories, the production web harness and one browser journey. Reuse existing suites.
- Logging: structured lifecycle events at INFO, claim/replay detail at DEBUG, actionable terminal failures at WARN or ERROR. Record project ID, declaration ID, generation, attempt, stage and sanitized reason. Exclude credentials, raw process environments and private host paths from ordinary user diagnostics.
- Docs: yes. Establish the contract before code and qualify the English and Russian product surfaces at completion.
- Roadmap linkage: none. This revises shipped M33 package-management and project-registration behavior.

## Evidence and decisions

The observed GitVerse request reached the cached `core/v1.0.1` capability at revision `edac62b8de8d`. The web process failed to load the JS chunk for `node:crypto` while computing the digest. At this baseline, `web/app/api/projects/route.ts` commits the project and owner, installs dependencies while holding the registration lock, then deletes the project on failure. Its outer catch removes a directory created by the request. Two registration suites explicitly require project rollback on a bad package. The triggering exception and the rollback policy need independent fixes.

| Decision | Contract |
| --- | --- |
| Registration boundary | Resolve/clone the source, validate the v2 project manifest and identities, enforce existing role, collision and project runner checks, and finish required local Git initialization. Commit project, owner, project configuration and durable dependency requests together. Return the existing `201 {slug, projectId, gitStatus}`. Release the registration lock without waiting for package I/O. |
| Mixed manifests | Move external work for top-level `flows[]` and `capability_imports[]` past the same commit, so it cannot undo a project or delay its response. Preserve their current install, validation, trust and runtime owners. Persist their registration input and handle failures as scoped bootstrap diagnostics. The new coordinate editor and Git projection in this plan apply to `packages[]` only. Existing v2 schema and project-level reference checks remain pre-commit gates. External source availability, member validity and readiness are per-item outcomes. |
| Desired and actual state | A project-scoped declaration is identifiable even if resolution never produced a platform install. Keep the manifest ID (which can differ from the package name), source, version and optional path. Store the current desired generation, attempt outcome, exact resolved revision when known, and actual attachment separately. The effective attachment, trust, setup and existing readiness checks determine what can run. |
| Recovery | Dispatch through the existing durable web worker runtime. A committed declaration is discoverable after a lost wake-up or process restart. Each item has a bounded retry policy and a visible outcome. Normal retry can address failures of any of the three kinds. An uncertain setup effect has an explicit recovery action. |
| Git | MAIster stores coordinate edits locally in Postgres. Desired coordinates drive the reviewed YAML diff. The existing Settings → Git workflow owns local publication, followed by separately reviewed optional push. Only reviewable configuration changes advance its export revision. |

### HTTP contract to specify in T1

Project-scoped paths below use the `/api/projects` prefix. Define operation IDs, strict request schemas, discriminated response schemas, typed error reasons, redaction rules and examples in `docs/api/web.openapi.yaml`. Verify those examples through real route responses. Reuse standard project errors and the existing package and Git endpoints.

| Operation | Request, response and authority |
| --- | --- |
| `POST /api/projects` | Existing admin-only request and success body. A 201 proves durable project acceptance and ownership of every declaration. The response has no dependency-readiness implication. Keep auth before body validation, existing source/identity failures (409) and invalid project configuration (422). A downstream refusal is observed on the item. |
| `GET /{slug}/packages` | Preserve `attachments` and its current authorization. Add `declarations`, including standalone items, in stable manifest order even when attachments is empty. Each row carries opaque declaration ID, logical ref, kind, desired generation, permitted coordinates, last known outcome, effective revision and separately derived readiness. Return a nullable current attempt for migrated rows with no observed attempt. For an actionable failure expose the exact attempt identity and, for uncertain setup, the server-derived member reference (including kind) and revision needed by recovery. Derive permitted actions from current authority and state in the same read model. Use an explicit nullable actual identity before resolution. SSR and API share the projection. A viewer who can browse installed contents retains access to existing permitted content. The new management diagnostics use the same `managePackages` gate in the API and the server-rendered view. |
| `PATCH /{slug}/dependency-declarations/{declarationId}` | Packages only. Replace the complete editable pin using `{expectedGeneration, source, version, path?}`. Logical ID and kind are immutable. An absent path clears the previous path. Return 200 with the stored desired state. A changed pin advances generation once and becomes pending automatically. With a matching generation an identical pin is a no-op. Compare the expected generation first: replay of an edit with the old generation returns 409 even when its content now matches. The client re-reads the row to recognize a previously accepted edit; no new attempt is created. An edit may be reviewed for Git immediately, even if installation fails. |
| `POST /{slug}/dependency-declarations/{declarationId}/retry` | All three kinds. Accept `{expectedGeneration, expectedAttempt}` for a known retryable failure. Return 202 with the queued attempt identity. A duplicate submission for the same failed attempt and generation returns the same accepted identity even if it has since finished. It cannot enqueue another attempt. Reject superseded generations or a retry against another failure with 409. Provide a stable typed reason for an ineligible state. For a still-current generation check the stored receipt before testing the item’s present retryability, so a lost 202 can be replayed. Trust approval remains with the existing trust endpoints. |
| `POST /{slug}/dependency-declarations/{declarationId}/recover-setup` | Surface `recovery_required` with item, revision and stage. Re-read existing exact completion evidence first. When completion cannot be established, offer a separate explicit admin confirmation to run setup again, after proving that the previous process has stopped. Bind confirmation to the exact setup member, attempt and revision and consume it once. Accept `{expectedGeneration, expectedAttempt, memberRef, resolvedRevision, action: "rerun_setup"}`. Return the exact accepted recovery attempt (202), replay it for an identical submission, and return 409 for a stale identity or a live previous owner. T1 defines the schema and examples. A normal Retry never authorizes replay of an uncertain effect. |

For all new mutations resolve the project from the URL and the declaration from that project. Check active account and current `managePackages`. Editing arbitrary sources and retrying work which can fetch or execute require current global admin authority as well. Revalidate in the worker against the actor who authorized that work. An eligible admin can take over a refused attempt by explicitly retrying. Keep existing project-level catalog attachment and global trust routes at their current privilege levels. Use the shared package HTTP error mapping. Distinguish stale generation/attempt, non-retryable state, live setup owner and active publication via typed reasons on 409. Authenticate and authorize before receipt replay. Cover 401/403, scoped 404 after project authorization, 409 for generation/attempt or publication conflicts, and 422 for invalid kind-specific inputs. Persist only validated, credential-free coordinates. One-off repository clone tokens never enter dependency state, responses or logs. Document one full example sequence in OpenAPI: failed GET → changed PATCH → refreshed GET, and an uncertain GET → recover-setup POST → repeat of the same receipt. A client must be able to construct both commands from authorized response fields alone.

### Persistence and processing contract

- Keep a project-owned declaration head and durable attempts keyed by declaration, generation and attempt number. Use the row created in the registration transaction as the work source. Current state and a retried command's receipt must survive restart. Store a typed immutable input per generation, or equivalent evidence sufficient to compare a replay. A repeated key with different input conflicts. Claim token, lease and recorded effect identity fence the external work. Make the references to actor, project, declaration and actual attachment enforceable by the database. An unresolved declaration has no effective install. A migrated effective attachment has no registration attempt or attributable historical actor. Link its known effective identity but leave attempt/outcome provenance absent. Only a subsequent real command creates an attempt with an actor. Apply attempt/lease/terminal checks to attempt rows, never synthesize successful backfill receipts.
- Match `web/lib/config.ts` and `web/lib/config.schema.ts` exactly. Key declared names by project, kind and logical ID. A Flow and capability import may share an ID. A package ID cannot collide with either, and duplicates in one section fail. Cover the cross-kind rule on every writer with a common project lock/transaction. Keep the original package tag and path, standalone Flow runner and explicit capability trust. Store the validated registration context required by the worker. Load current authority/readiness separately from immutable requested input.
- Specify `pending → running → succeeded | failed | recovery_required`. Bound transient requeues with an attempt budget and a due time. Distinguish retryable errors from invalid manifests, name collisions and permanent input errors. Derive trust, setup and runner eligibility from their own records. Successful attachment awaiting trust can be shown as installed/awaiting trust. Known setup failure is failed at setup even if an attachment exists. Unknown effect requires recovery. On archive stop admission of new effects; on unarchive reconsider outstanding work under current authority. A stale attempt may finish bookkeeping only for itself.
- Index due work and lease expiry. The active claim belongs to a declaration. A separate short project lock protects shared catalog writes. Bound concurrent attempts and advance past blocked items so independent work progresses. Serialize conflicting effects on the same project/member and shared physical cache destination. For competing declarations whose member names are only revealed after fetch, give an already effective attachment precedence; refuse conflicting newcomers with both safe logical refs. For an initial mixed batch apply member attachment in manifest order within each kind, with standalone Flow refs reserved before matching package members. Precedence applies to ready work with known competing IDs. A later recovery can never displace an already effective winner. Document the tie-break at the point a collision becomes observable, and exercise both completion orders.
- Snapshot migration and cutover details in `docs/db/projects-domain.md`: empty DB and upgrade from 0368, SQL/Drizzle parity, indexed keys/checks, deletion rules, ordered locks and rollout/recovery instructions. Stop old writers and drain or recover accepted Git publications before switching mutation/trigger ownership. Backfill without Git/network access, actor impersonation, export-revision bumps or queued side effects. Use one transaction for backfill, validation and enabling new constraints or fail with repairable identifiers. Never label historical standalone attachments as manifest declarations without provenance. Preserve them in their native readers. Reopening the migrated app must not re-run the backfill or republish anything.

## TDD execution rule

For each behavior slice, reference its AC and the governing spec section in the task/checkpoint. **RED** means the test runs and fails on the expected observable mismatch. An unavailable DB, missing binary or unprepared web build is an environment failure. Record the test name, command and failing assertion. **GREEN** means the smallest production change passes that case and the neighboring control cases. **REFACTOR** means simplify shared code while re-running the same tests. Keep strict TS types and single-purpose functions, use existing domain errors, authorization and Git/installer services, and review against SOLID, KISS, DRY and the repository rules. Avoid parallel installers, duplicate SSOTs, new abstraction layers without callers, mocks of the behavior under test, and tests of source strings or trivial getters.

Keep regression cases with the change that makes them green. T2 captures the registration boundary only. Keep a single primary assertion owner per failure: route admission in AC01, item failure and sibling progress in AC03, effects in AC04.
