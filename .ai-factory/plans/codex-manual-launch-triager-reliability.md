Their effect on automation remains visible. `triageStatus='flagged'` from a qualification assessment is advisory to manual launch, including when authored by a human assessor. ### Trusted principal and one server contract

Introduce a server-owned discriminated principal/admission context, separate from the wire request: interactive user, project/user token, agent run, Librarian operation, schedule/domain automation, execution parent. The authenticated adapter constructs it; domain services independently load its referenced durable authority. Never accept `skipQualification`, a body `actorUserId`, `isHuman`, `mode=manual`, or a source string as admission authority.

- Web's explicit launch operation with an active user session and anti-CSRF/same-origin protection can record the one-shot human decision after DB-authoritative RBAC. The normal authenticated API endpoint is that same human-action boundary.
- Bearer API/MCP calls use automatic admission or existing execution-parent derivation. They can submit/propose work without claiming a human decision. A token with `runs:launch` still needs current RBAC, project scope and the appropriate admission basis. Authenticated API calls through the interactive session boundary use the same manual operation as the Web.
- Do not create a new transferable manual-approval/redemption capability in this scope. An agent can propose a launch for the human to perform through the normal Web/API session boundary. Existing intent IDs are status/idempotency references, never bearer authorization, and a worker consumes only authority already stored by that boundary. No client-supplied receipt/actor/source can mint a human decision.
- All adapters call one domain admission operation. Preserve external operation idempotency/audit and scope/action grants; include positive authorized cases, not only denials.

### Immutable intent, snapshots and state

Proposed new `task_launch_intents` record (final naming in Phase 0), distinct from existing `tasks.launch_intent` (`none|triage_only|triage_then_launch`):

- Durable ID, project/task, server actor/principal/provenance, UTC accepted time, channel and operation (`launch|retry|automatic|execution_child`), request/idempotency key and canonical request digest.
- Task `revision`, `qualificationInputRevision`, semantic input digest, launch settings digest; frozen execution input content with statement/source identity and execution-relevant clarifications/references. Store content in access-controlled DB/run input storage, never logs. Explicitly version canonical digest formats.
- Admission basis: manual authorization identity, automatic assessment ID/revision/evidence target+SHA, or scoped parent proof; policy version and optional existing-assessment observation for transparency, never a fake positive decision.
- Selected and resolved Flow/revision/package identity, runner and all resolved session slots/model/profile/reasoning/capabilities, base ref+resolved commit, target and delivery policy, PR delivery choice, execution policy, auto-promotion choice/holds and relevant workspace/isolation inputs. Reference existing immutable snapshots rather than duplicating secret material. Credentials are resolved securely at execution time; credential values are not frozen into provenance.
- Write-once nullable link to the eventual run, successor/source lineage and separate state/dispatch receipts. Intent states are `queued`, `preparing`, `run_bound`, `held`, `cancelled`, `failed`, `settled`; a hold may occur before or after run binding and never removes that link. `settled` means the bound run reached its terminal outcome, not that execution succeeded. Keep existing run status vocabulary. A hold carries a typed reason and remediation.
- Versioned admission snapshot v2 on the run, with a discriminated `manual|automatic|execution_child` basis. Decode historical v1 `legacy|required|execution_child` separately. A run receipt's immutable grant data is never rewritten to reflect later task state; mutable lease/state/dispatch receipts live separately.

Intent acceptance transaction locks task/current intent, rechecks request revision, auth and all deterministic preconditions, reserves the ordinary task delivery slot and commits intent + frozen request + audit/outbox together. Put an authoritative unique/CAS backstop on one live ordinary delivery reservation across manual, C2 and delegated root callers. Existing intentional concurrent relaunch is a separate authorized operation/reservation; a client cannot obtain it by retrying a normal request.

Same principal/key + canonical same payload returns the original intent/outcome. Same key with different payload returns 409. Repeated clicks with different keys and competing auto/manual requests must either return the exact same-request receipt or explicitly report the existing request/run and its basis; never claim the losing manual decision was executed. An existing automatic reservation must not silently overwrite the manual selected settings. Supersession is an explicit cancel/replace operation, retaining both records.

Git and supervisor effects happen after committed intent/claims and outside long DB transactions. Reserve capacity under the existing global scheduler lock and count each reservation/run exactly once across the handoff. A manual queue item does not become C2 work or gain automatic retry authority. Persist actual resolved/executed snapshot identities and outcome after each seam.

The admission reservation is distinct from a capacity slot. `queued|preparing|run_bound|held` retains the ordinary task reservation until cancellation, replacement or terminal settlement; a held request consumes no execution capacity. Scope partial uniqueness to the explicit ordinary-delivery lane, not all task-bound runs: operational Triager and intentionally authorized concurrent execution keep their own lanes. DB fences must prevent a run already bound to an intent from becoming eligible through a raw `Pending` query while its intent is held.

An existing nonterminal v1 delivery run without a new intent also blocks ordinary admission under the same task/run fence; a partial unique index on intents alone cannot cover that population. Migration may record an explicit compatibility hold for unknown input, but never a fictitious manual intent. Same-request replay rechecks live permissions and returns stored authority/outcome; a new key cannot adopt a changed payload by coincidence. An explicit concurrent-relaunch request retains normal global capacity and technical checks and uses its existing separate action; `allowConcurrent` on the compatibility wire is mapped to that operation, never used as a generic duplicate/admission bypass.

## Decisions: preparation ownership (Designed)

The protected resource is the physical run checkout plus its preparation/materialization/baseline generation, not just a prompt command. The lock key is stable for the canonical host/physical checkout path across **all** assignment epochs and incarnations. Store run/incarnation in the durable receipt, not in a changing mutex key for the same path. Separate incarnation locks are safe only for truly separate physical checkout paths. Parent repository Git mutations additionally use the existing common-Git-directory ownership fence where required. A per-task or per-process mutex cannot protect this invariant.

1. Add a durable preparation operation/receipt bound to run, assignment ID+epoch, operation attempt token, physical resource incarnation, resolved input commit, phase, lease expiry/renewal and baseline generation. Claim under existing run/assignment locking patterns before touching filesystem. Reuse workspace lifecycle claims for materialized workspace rows; rowless `repo_read` needs equivalent recorded ownership visible to disposition and recovery. Do not reuse Flow-only driver fields in violation of their constraints.
2. All checkout create/reuse/repair, baseline capture, materialization/generation publication, adoption/session creation handoff and main-workspace disposal share one stable cross-process physical exclusion mechanism. Extend the existing `context-mounts/operational-lock.ts`/SQLite materialization lock pattern outside directories that can be removed. Context-mount locks keep their own ownership; define a fixed lock order and avoid recursive acquisition.
3. After acquiring physical ownership, reload run, exact active assignment/epoch, preparation token/lease, terminal/released state and resource identity. Existing same-owner checkout is validated/reused. Absent baseline is not permission to delete it. Ambiguous/foreign/partially prepared state is preserved or recovered by its journal, never unconditionally removed. A completed receipt is idempotently reused after identity validation.
4. Lease expiry revokes publication authority, not physics. A slow probe renews; a former owner cannot publish or terminalize a successor. A new epoch cannot reuse/remove the old physical checkout until old operations are proven quiescent. Either keep resource identity distinct per incarnation and retain old resources until quiescent, or serialize replacement with a lock whose lifetime actually covers all child operations.
5. **Process-death gate:** today's SQLite lock releases on manager death, but an orphan Git child may survive it. Before choosing the final implementation, prove existing child cancellation/reaping keeps exclusion until completion, or run the operation in a lock-owning helper/host command whose lifetime covers its Git children. A pre-operation DB check plus lease expiry is insufficient. Qualify manager SIGKILL while Git is paused, then restart/takeover; stale children must be unable to mutate the successor resource. This is a required design/reproduction gate, not an assumed property of SQLite.
6. Persist baseline/preparation completion only under token+epoch+resource/status fences; bind/create/prompt through existing durable command and generation-turn ownership. The preparation lock ends only after a durable handoff that cleanup recognizes. Do not hold one mutex for an entire model turn: durable active session/command ownership and host quiescence protect that interval.
7. Terminalization commits terminal state, invalidates publication authority and arms cleanup atomically; filesystem cleanup is after commit. Cleanup waits/defer-refuses while a physical preparer/session/command is active. Stale prepare callbacks reload ownership after awaits and cannot recreate/adopt/prompt after terminal/release. A baseline failure remains a failure; preservation/cleanup errors are subsequent incidents.
8. Recovery uses the existing continuation and disposition owners, with bounded scans/attempts and observable holds. No new filesystem watcher, sleep-based fix, or unbounded retry. Extend existing wake/recovery seams rather than adding a new polling subsystem.

### Structured diagnostics and UI

Record run ID, task ID when present, assignment ID/epoch, driver source, preparation attempt/resource incarnation, stage (`checkout|baseline|materialize|adopt|create|prompt|cleanup`), probe operation (`lstat|open|read|readdir|realpath|git`), bounded duration/counters, typed reason, safe errno/syscall, Git command category/exit/signal, and sanitized bounded cause chain. Worktree logs need matching operation ID and start/end/outcome so owners can be correlated. Do not log credentials, environment values, source contents, remote URL credentials, arbitrary stderr or raw paths. Use logical relative path/category or hashes where enough; privileged sanitized technical evidence can contain necessary safe details.

Persist the earliest failure as primary diagnosis. Keep missing-baseline, publication refusal and cleanup outcomes separately. UI: “Triager could not prepare its workspace. The model did not start; no assessment was produced.” Offer inspect details and the existing explicit Retry action after remediation; show a specific safe cause when known and an honest unknown cause otherwise. Do not convert infrastructure failure into `not_actionable` or mark qualification accepted.

### TDD protocol and requirement acceptance map

For **every** B1–B6 and A1–A6 behavior slice:

1. **RED:** add/adjust the smallest primary integration or browser scenario for a frozen requirement. Execute it on supported runtime/harness and record command + failing assertion + expected/actual behavior in the task's TDD ledger. 2. **GREEN:** implement only enough production behavior to satisfy that scenario and unchanged related contracts. Run the primary test and affected existing suites. Preserve failure assertions, actual effect counts, immutable digests and all negative cases; do not bless the bug by changing expectations to match it.
3. **REFACTOR:** simplify responsibilities/duplication after green. Keep pure classification/digest rules separate from effects, maintain strict types and existing error/logger/atomic-write conventions. Add abstraction only when there is a real shared invariant. Rerun the primary/affected tests and lint/typecheck; no behavior change hidden in refactor. If behavior must change, start a new spec/RED cycle.

Record RED/GREEN/refactor commands and results, not a subjective “TDD done”. V1 reruns integrated acceptance after the slices; it cannot compensate for skipped RED stages.

## Compatibility and migration policy

- Additive schema first under existing upgrade maintenance/writer-capability protocol; stop incompatible writers before enabling v2 admission and preparation. Evolve guard functions through new migrations, never edit `0207`/`0209` in place. Ensure old binaries cannot create new auto work or bypass new manual guards after cutover.
- Preserve every historical run/assessment and immutable v1 receipt byte-for-byte. No backfill calling an old run “human authorized”, and no fabricated input snapshot copied from today's task. Preserve FK evidence; use restriction/retention rather than destructive cascading deletion of intents.
- Already dispatched v1 runs continue via existing snapshot/technical fences where their execution input is provably recoverable; no new qualification gate on the same execution. **`taskAdmissionCheckedAt` alone is not a dispatch witness:** it can precede model/Flow effects and survive pre-execution failure. Compatibility classification must use durable node-attempt/command/session evidence bound to that run and assignment, plus actual immutable input/settings evidence. Neither `Running` nor the checked-at receipt permits taking today's task text as old authorized input. Pre-upgrade queued or checked-but-undispatched requests with incomplete authority require a compatibility hold and explicit relaunch or current auto qualification. An already live session is not killed to repair missing metadata, but a later prompt/resume requiring unrecoverable input is held. Complete v1 work can receive a new linked compatibility record only from provably immutable evidence, without changing its old receipt; P0 enumerates the exact witnesses and completeness predicate, with a checked-before-failure regression test.
- Existing legacy tasks remain historically legacy; new independent automatic launches require accepted/current qualification. Existing `launchIntent=null` is not human approval. Preserve explicit `none`/`triage_only` against qualification routing; manual Launch does not set `triage_then_launch`. Keep already configured automation visible; a manual run gives no new automatic authority after completion.
- Pre-upgrade partially prepared resources need inventory/quiescence before adoption. No baseline is backfilled as successful; restart cannot delete a checkout just because no new ownership receipt exists. Ambiguity becomes an actionable hold.
- Rollback: once v2 records exist, do not run an old writer that cannot understand them. Forward-fix or restore a matched code+DB backup only through a separate authorized operational procedure; no rollback/down migration deleting live intent/claim evidence. This plan executes neither procedure.
