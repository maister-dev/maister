## Decisions and contract boundaries

1. **Navigation and identity.** Keep `/knowledge`, record/proposal permalinks, Inbox filters, and both agent-memory entry points as supported URLs. Design one canonical detail view per review kind reachable from both Inbox and Knowledge. Use `(kind,id)` for a proposal, `(recordId,revision)` for a published assertion, and a stable owner/vault + note ID + revision ID for note history. Direct lookup works outside any list window. A renamed, deleted, or recreated path must never select a different note for a historical link.
2. **Review data and persistence.** Use current domain state for pending work and domain decisions for history. Structured knowledge already stores `resolution`, `resolved_at`, reviewer policy and exact publication. Read ordinary Brain `authoredDraftId`/`taskId`, the vault-origin acceptance-only disposition, and vault proposal/operation revision links. Inbox receipts store a per-user request key, digest, and receipt identity and cannot reconstruct full history. Project the actual domain outcome. Preserve genuinely unknown legacy metadata. Store a new vault decision reason when provided and require a reason for new human rejections under the agreed contract. Add an optional field to the existing vault proposal table. No historical backfill can recreate a missing reason. If a compatibility writer needs a transition window, document the version boundary and explicit unknown rationale. Record any additional field or index only after demonstrating the missing witness or query-plan need.
3. **Read/write authority and input sources.** Session identity or checked global personal-token owner, token kind, scopes and any attested agent/turn identity come from auth context. URLs supply candidate proposal kind/ID, record, project slug, agent, binding, note/revision, or vault selector. Query supplies scope filters, path, cursor and selection. A body supplies decision, reason, observed version, request key, note CAS/hash, subtree generation and selected heads where applicable. Promotion also accepts a target owner/kind as a requested destination. Derive actual owner, project/company relationships, membership, privileges, source restrictions, evidence identity and result links from locked server records. Reauthorize every selected row/revision and its sources on list, detail, diff continuation, mutate, replay and result reads. Validate scoped/signed cursors and cap response sizes. Apply those policies before computing counts or pagination metadata.
4. **Personal-token contracts.** Proposed operations: paged review list/detail and single Brain/vault decision under `/api/v1/ext/inbox/reviews`; catalog, directory/note and revision history/detail reads under a human-owned vault namespace; record-revision list for browser, bearer and MCP. Freeze exact paths and schemas in Phase 0. Restrict new personal methods to appropriately scoped global user PATs; verify owner activity and current token admission. For any response that discloses vault data require the explicit `agent_memory:read` scope, including mixed queues/counts; enforce a separate authorized decision capability for mutations. Provide a successful least-privilege example for each grant. Preserve existing `knowledge_decide` and separate `knowledge_confirm`. A regular execution, project token, or Librarian turn cannot use personal review authority.
5. **Write and retry semantics.** Keep one domain transition and its durable outcome/receipt in the same database transaction under the existing locks. Scope the idempotency key to the real principal. Hash canonical decision inputs including kind, ID, expected version, decision, and reason; preserve command semantics for arrays. Only the original principal/key and matching payload return the authorized original receipt. The vault decision service currently accepts a matching terminal state before checking the version. Enforce a conflict on fresh keys after settlement. V1 batch `status: applied` acknowledges command processing. Derive the typed business outcome independently from the domain decision and its retained references, including acceptance without a projected effect. A changed payload with the same key conflicts. A user can read the subsequent state separately. Verify concurrent reviewers, head changes, lost response after commit, and revocation before replay. Emit existing events via the owning transaction/event mechanism. A pending promotion receipt proves submission, while the destination proposal determines its current review state.
6. **Deployment and compatibility.** Reuse Next.js web, PostgreSQL, current SSE and packaged MCP. No new port, service, mount, or environment variable is expected. Plan an additive main-DB migration for the missing vault metadata, generated as `0365` after local master's `0364_manual_backlog_admission`. Check both migration lineages. Preserve compatibility reads before and after operator-managed cutover. The implementation must not trigger cutover or grant changes as a side effect of browsing. A new MCP operation is delivered only when advertised and callable from the correct installed toolset.

### Decision payloads and compatibility

For a new single decision the JSON body contains `expectedVersion` (1–128 characters), `decision` (`accept` or `reject`), `requestKey` (the existing 8–128 character key format), and `reason` (trimmed, 1–2,000 characters when present). Require a reason for every new single rejection and for both native knowledge decisions. Keep the existing v1 batch validation for older clients. On the new single response expose `kind`, `id`, `reviewedVersion`, `domainState`, `outcome`, `receiptId` and `replayed`. The receipt identifies the command. The result reference identifies the exact domain object. Return current availability for links when access has changed. Preserve the existing native knowledge wire format behind its own adapter.

| Accepted input | Durable outcome and permitted destination |
|---|---|
| Knowledge add/correction | `published_revision` with exact record ID and revision, independently inspectable under current evidence access. |
| Ordinary Brain rule/skill/flow | `catalog_draft` with the stored authored draft ID. |
| Ordinary Brain adr/roadmap/state | `project_task` with the stored task ID. |
| Project Brain state with a retained vault promotion | `accepted_proposal` with proposal ID. Link to the accepted decision. |
| Vault edit | `applied_vault_operation` with operation ID and authorized revision references. Page references for multi-note operations. |

Rejection has outcome `rejected` with an authorized decision reference. It leaves the prior published record, task/catalog and note heads intact. For the new detail variant document both the observed and resulting domain state. Keep v1 `summary`, `allowed`, `nextCursor` and batch statuses readable by old clients. Tests compare a legacy response reader against the additive schema. Use the exact decision object for replay, without inferring its outcome from a subsequently changed note head.

For vault reads, `GET …/{locationId}/view?path=…` resolves the current directory or note at a path. Add `GET …/{locationId}/notes/{noteId}` for an exact current note link, and use the revision-ID path for immutable links. Specify directory pagination and byte-bounded content continuation independently, with cursors bound to the selected owner, stable identity and content version. Let `personal_vault_view` choose the input through a strict path-or-note-ID union. Recheck the source for every returned byte range. If Brain/knowledge detail embeds protected vault content, check its disclosure rights and the explicit vault read scope before including it. Document the allowed reduced representation or concealed-item result for each source policy.

## Per-slice TDD protocol

1. **Specify.** Select a K-ID and one observable behavior. Name its owner, input, authority, post-state, failure semantics and primary test in the relevant contract. Link the task and test to the ID. Resolve disagreements between the contracts before coding.
2. **RED.** Extend the existing narrowest suite that can observe the defect. Run it against the pre-change implementation. Record the command, test name, expected result and actual assertion failure. Runner errors and invalid fixtures require repair first. Keep existing passing behavior as a regression control and drive the changed branch with its own failing assertion.
3. **GREEN.** Make the smallest change that passes the same assertion. Inspect the durable result or observable UI state. Exercise database races on independent connections, transport through the actual handler or built process, and UI through its normal controls.
4. **Refactor.** Apply SOLID, KISS, DRY and the repository conventions to the tested slice. Keep each transition in its domain owner. Rerun the same test and affected suite. Record RED and final GREEN evidence, the K-ID and the tested revision at the checkpoint. Keep checkpoint commits green.
5. **Qualify.** Assign one primary test to each distinct behavior. Parameterize roles, outcomes and boundaries that exercise the same invariant. Exercise a workflow across layers only for a separate contract, such as focus restoration after a transaction already proved durable. Cover size limits at and above their boundaries, empty/last page, malformed input, replay, concurrency and revocation where relevant. Exclude getter tests, static label snapshots and repeated business assertions in every adapter.
