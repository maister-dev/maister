### Decision identity and confidentiality

`RunPendingHitl.schema` deliberately strips raw permission payloads. A gate permission can already carry `flowPrompt` with a validated gate variant, evaluation ID, attempt ID and gate ID in its persisted server-owned envelope. For a positive CHECK-3 path, use the existing Zod schema in `web/lib/execution-host/flow-permission-source.ts` on the server. Match the exact evaluation row, Run, attempt and gate before returning a minimal nullable link identity to the Run detail view. Verify the destination exists in the already authorized Run results. Handle missing, malformed, foreign, superseded or ambiguous witnesses by omitting the link. Inspect the current query before adding a read; batch any necessary reads across pending requests. Keep permission options, command IDs and session details under their existing disclosure rules. This projection is read-only and separate from the mutation-time gate resume checks.

The positive integration fixture pairs a persisted gate permission with its own evaluation and a second attempt using the same gate label. Assert a single link to the correct row, raw permission schema still redacted, and no link for a legacy missing witness or mismatched Run/attempt. Use the loaded authorized results to resolve a destination. If the workbench cannot show row detail but the verified reason exists in the inspector, link to that reason. Otherwise leave the question usable on its own.
