## Design and decisions

### UX-06: Launch configuration

**Composition.** “This launch” shows Flow and exact revision, configured versus effective runner by slot, inherited source, branch/task effects and refusals before Launch. A one-time choice changes a local draft only; “Use configured runner” removes that draft entry. The existing project configuration control, reachable separately or via a clearly labeled action from launch, owns “Save project runner mapping” and names the project, enabled Flow revision and slot. Saving a default leaves any explicit one-time selection intact. When no declared session exists, keep the one-run primary picker; do not offer a durable mapping for a synthetic slot. Keep ordinary launch single-step. Explicitly label Flow/base/target values that are still saved to the task on ordinary launch; leave their legacy write behavior and authority intact. Schedule uses its own pinned-source contract: if a one-time runner draft exists, disable Schedule with instructions to clear it, never silently drop or schedule it. Concurrent and replacement interactive launch honor the draft.

**Wire and source.** Introduce an optional browser-only `flowRunnerDraft: { flowRevisionId, primaryRunnerId?, slots? }` on interactive create/concurrent/replace. `primaryRunnerId` preserves the existing one-run primary plus eligible same-capability preference; `slots` is a bounded map of stable declared non-primary logical-session and runner-bearing consensus role keys. Explicit slot → existing resolution (including one-run primary preference only where it applies). Keep legacy `runnerId` semantics, external/MCP/generated/scheduler schemas, GET preview compatibility and legacy `POST /api/runs` unchanged; those entry points do not accept the new field. Share preview construction between GET and a same-origin, no-store, read-only `POST /api/runs/launch-options` for interactive selections. Build browser-specific request components from a shared typed shape before closing schemas; do not widen an `additionalProperties: false` base with an OpenAPI `allOf` extension that rejects its own new field. Start from `flow_revisions.manifest`, canonical runner catalog, settings and package-cut resolution. Derive preview rows and metadata token from one consistent database snapshot; capture filesystem identity outside that read and let acceptance recheck it. The draft token binds canonical runner selection, revision, effective runner identity/tier and configuration digests; no-draft legacy tokens retain their current semantics. Re-resolve using the same captured input values in the acceptance reservation: compare the digest of the candidate outcome with the token and persist those exact session rows. No token re-read from a different configuration snapshot; no remote Git/filesystem reads under a new database lock. UI ignores out-of-order responses and disables submission until the displayed draft has a matching preview. Branches and policies are explicit in the launch form; validate them on acceptance and capture them through the existing policy/settings path. Do not trust browser-provided identity, tier, model or runner metadata.

**Authority and failure.** `launchRun` plus existing task-edit checks governs the interactive primary; retain `editSettings` for per-slot edits that were admin-only and for all durable mapping writes. Validate ready/enabled, declared capability, static enforcement, package trust/admission, open blockers, replacement/concurrent prerequisites and immutable package revision as the current path requires. Pending or failed draft validation is a localized refusal, not a default substitution. Close (Escape, backdrop or button), target/revision change and reopen discard unsubmitted drafts and abort/fence stale reads; exact-body retries of a submitted uncertain request survive closure via `use-task-launch-intent.ts`. For “try once,” allow draft against the resolved eligible revision, allow persistent Save only against the actual enabled revision. Confirm Save from the PATCH receipt; on definitive failure keep selection, on lost response say “Save not confirmed” and use an intentional refresh/retry. Keep a valid independent launch preview usable when a persistent save fails. Existing PATCH semantics for clear (explicit Pending/unmapped) stay separate from “use configured” and may still block launch.

**Lock and snapshot.** Persistent mapping guard scope is project Flow's enabled pointer plus one revision/slot; check the enabled pointer under the project Flow row lock used by enable/rollback and use the existing unique mapping key for an atomic set/clear. Race a real enabled-pointer swap against Save; race a real mapping/catalog change between rendered preview and acceptance. Before acceptance either show/accept the same effective snapshot or refuse stale without creating an intent or task edit. After acceptance neither a project remap nor a catalog edit can silently change the run: accepted V2 session and consensus entries carry sanitized identity, config digest and tier; launch materialization in `web/lib/services/runs.ts` creates `run_sessions` from those entries; graph consensus `roles.ts` uses the accepted intent and fails closed on unavailable/changed runner. Read effective Run provenance from existing frozen settings/run sessions; do not use current mappings, task default projection or mutable Flow manifest. Preserve evaluation-controlled overrides as separate server authority. No schema version or data migration.

### UX-08: Run outcome and next action

At the top of each detail page: task or agent/scratch context, execution status, compact result/availability and one next action with its reason. Put a pending authorized HITL/claim/review decision first, then a supported terminal remediation or cleanup when applicable, then delivery allowed by existing policy, else the recorded outcome and inspection link. Preserve actual authorization and show a truthful read-only reason when the viewer cannot act. A failed Run may have retained changes and successful intermediate work. The shell should not collapse these into its terminal status.

| Variant | Main column | Details on demand |
| --- | --- | --- |
| Operational agent | Recorded operational outcome, inputs/failures requiring action and conversation; use frozen `runKind`/`agentKind`, then canonical operational projection independent of ordinary result-contract presence. A legacy absence stays unknown. | Agent history and applicable diagnostics/cleanup. Omit Git, Flow and diff placeholders when the execution cannot have them. |
| Coding Flow / code-delivery agent | Task/outcome and decision, then stages where applicable, changes and Results and checks. Show retained work on terminal failure. | Git/Review and delivery actions behind existing policy, artifacts, transcript, diagnostics, history and child Runs. |
| Scratch | Named session, conversation/current turn, retained changes when present and actions specific to scratch. | Existing Files/Diff and lifecycle controls; no invented scratch gate or Flow result. Distinguish interrupting a turn from stopping the Run. |

Keep both Run layouts and their persistent file child panes. Use a collapsed or overlay inspector in constrained space; opening it must leave a usable main reading area or give a single-pane focus path with reliable close/return. Respect explicit `inspector=open|closed` links. Preserve `wb`, `node`, `flow`, `file`, `fileView`, `diffFile`, `diffview`, `diffbody`, `diffFiles`, `scope`, `git`, `peek`, `peekView`, `peekNode`, anchors, child peek close and Back/Forward. Keep existing SSE refresh, accessible reconnect and loading boundary. On degraded optional reads, distinguish unavailable/stale from no result or no applicable action.

### UX-11: Project header and retained workspaces

Default layout: one project identity, concise metrics, primary New Task, secondary scratch entry, compact status/disclosure entry points, existing tabs then task content. Collapse repeated path and configured lists into current details/settings. Keep tab order/keys, filters, role gates and URLs. Move ActiveAgentExecutions and the old unbounded workspace block behind one accessible “Runs and working copies” disclosure (URL state `workspaces=open` and optional selected group; preserve current query keys). Use a bounded panel with incremental group/attempt display; default header height independent of row count. Keep board navigation in place; do not replace the 15 tabs or repurpose global `/work`.

Use a project-scoped typed view over `getProjectPageData` and `getActiveAgentExecutions`: “Executing” counts distinct actual `Running` Run IDs from project Runs (including workspace-less, dedupe by Run ID), with queued/parked/waiting accurately labeled when shown; “Needs a decision” uses project-scoped `getDecisionsCount` and identifies its personal/actionable scope; “Retained working copies” counts the existing project workspace query including failed/review rows and labels archive/on-disk availability separately. The counts can overlap and are not additive; `board.inProd` is a task-column count. Retain the workspace predicates, actor visibility and lifecycle eligibility; do not reuse a storage, scheduler-slot or execution predicate across these concerns. Group by real task ID from a project-scoped join; use canonical task key/title and authoritative Run attempt information when available, else date/Run link. Group standalone agents by canonical source; keep unassociated/scratch work separate with its name. Keep individual Run links and current menu/drawer destinations. Existing lifecycle policy, Workbench actions, shared destructive confirmations and route guards remain the authority. Do not turn a disclosure into a new execution/retention filter.

### UX-21: Configuration in Git (separate review)

One compact project status/control and one focused workflow reused from Settings → Git. Reuse the shared confirmation/dialog frame and existing review, receipts, push-review and recovery controller. Put details, refresh and secondary options inside the workflow, with responsive scroll and visible actions. “Review changes,” “View operation” or “Resolve” is the primary entry as appropriate. Opening may read a receipt or create the existing review preview; opening or dismissing cannot commit, publish, cancel or retry an uncertain operation. Pending responses lock destructive/commit controls and restore focus to a surviving trigger on close.

| Observed axis | Presentation and action |
| --- | --- |
| Unknown/last checked stale | “Status unavailable” or “Last checked …” without claiming clean/success. Secondary Refresh; show observation age and failure in details. |
| Export missing/pending, repository ready | “Configuration changes to review” (runtime settings saved in MAIster and not yet in the target commit); Review shows the exact reviewed `maister.yaml` diff, branch and explicit dedicated commit. |
| Export blocked or repository dirty/wrong branch/detached/unsupported | “Action required” with validated reason and the available next step. Repository/package lock only establishes a blocker; say wait/refresh or inspect an owned operation, never name another actor or infer abandonment. |
| Accepted local operation preparing/prepared/publishing; push pending | “Operation in progress” with receipt when authorized. “Resolve” reserved for explicit recovery-required/unknown or proven retained cleanup, never repeat a still-running effect. |
| Local committed/noop | “Committed locally” only from a matching receipt with SHA; `in_sync`/noop means the observed target commit matches, without proving an operation or push. Show reviewed publication as a separate action. |
| Push succeeded/failed/stale/unknown | “Published” only from a confirmed push receipt for that commit and target; failure preserves the local commit, stale requires fresh review, unknown requires inspecting/recovering the same operation. Never infer publication from branch equality or the status color. |

**Narrow read extension.** Add an opt-in `view=workflow` projection to existing `GET /api/projects/[slug]/persist-config`, guarded by both existing review grants. Return independently classified checkout/export observation and prioritized owned operation/push/cleanup evidence from `receipts.ts` (include unresolved retained cleanup where applicable), with safe operation ID, phase, reason and commit evidence. Prefer the most relevant unresolved owned operation, then latest accepted receipt; status can still convey an independent unowned blocker without revealing identifiers, other actors or ref/remote secrets. A classified repository observation failure leaves checkout unverified but does not hide a readable owned operation from Settings. If the operation cannot be read, show it as unverified, never as absent or resolved. Bare status keeps its existing readBoard grant and response semantics. Scope commit/publication labels to that receipt, never claim current export is pushed when the receipt is for older content. This read is justified because status + ID cannot distinguish live/recovery/push phases without receipt data; writer states and action endpoints are unchanged. Use one status loader per visible entry and existing mount/focus/export-revision/action/manual refresh triggers; no new poll. Keep actor-scoped session-storage recovery locator (and id) on lost mutation response. Replace permanent per-project dismissal with standard accessible close, scoped to observed condition (project/actor + export revision + operation ID/phase/reason as available; exclude observation timestamp); ignore the old Boolean. Suppress only that advisory notice, keep the Settings control independent and visible; a changed actionable condition reappears. Never key success or availability off dismissal.

**Existing durability.** Keep the accepted preview ID/digest, row authorization and version guards, repository fence and ref/index publication protocol in `service.ts` / `publication-state.ts`; reviewed push, private cleanup, startup reconciliation and recovery stay with existing owners. Commit path records acceptance/preparation before local effects and only records `committed` after proving published local state. Push persists its intent before transport and records `succeeded` only from observed remote result. Stale/expired/revoked/conflicting requests return existing refusal without effects; failure/recovery-required and uncertain push keep durable identity, never replay blindly. On lost response, GET is observational; explicit recovery resolves exact recorded old/new state or refuses on ambiguous evidence. No Git side effect introduced by the proposed read extension.

### UX-17: Librarian conversation and Action history (separate review)

**Composition.** Conversation plus composer stays primary. A compact Action history entry opens an independently scrolling, bounded surface with operation and related-task disclosures, keyboard close/return and older-page controls. Opening does not grow the main pane in proportion to history. Above the composer keep only a compact attention count/cue with direct access to actionable entries. Completed actions appear as compact current-context attachments via `TranscriptView.renderAttachments`, coexisting with memory chips, and as rows inside explicit history. The optional related-task context is collapsed by default and contains current-segment links only.

**Current, earlier and legacy.** `librarian_operations.segmentId` is authoritative. For ordinary operation receipts attach only where an authorized owner conversation, same segment and real operation turn link to a displayed trigger/reply; attach once, preferring the actual displayed reply when linked. Card decisions may have been stamped with the latest turn rather than a causal turn: use proven card/message linkage or history only. Task links have nullable message pointers and no segment column: derive from surviving same-conversation linked messages with a consistent segment, else history only. Do not guess from times or current relationships. Keep history paged by stable `(createdAt,id)` for each result collection, owner-scoped, capped and with an opaque validated cursor. Expired or absent refs keep an honest generic receipt.

**Attention and outcomes.** Query available pending confirmations and `admitted`/`unknown` effects across the owner's segments before any history limit, with bounded rows and a count/more path. Pair cards with the proven durable operation association (including the card decision key); a still-pending card with uncertain effect shows “Outcome unknown” and no replay buttons. Ordinary completed/refused/failed entries belong in history. Surface a failure persistently only when an existing domain read proves a current authorized resolution (e.g. an existing recoverable Run needing the viewer); if none can be established, keep the failure in history. Unknown remains discoverable without implying a recover action exists. Refused, failed, pending, unknown and succeeded are distinct; successful historical operation does not imply a successful or currently accessible target. Reject/expired cards may exist without an operation row; retain their disposition from the card ledger and dedupe when an operation row exists. Do not show actions on expired, revoked or unresolved proposals.

**Safe receipts.** Use an allowlisted presentation DTO for kind, time, durable outcome and authorized target(s). Use canonical `projects.taskKey` plus task number, title and direct route for create/triage and related tasks when visible. For relation changes, use durable `taskActivity` linked by `viaOperationId` to both endpoints, applying current authorization per project before serializing. Legacy no-ops lack reliable second endpoint; say detail unavailable, never infer from a current edge. For future successful/no-op relation effects store optional internal endpoint provenance alongside the replay body during existing transaction settlement; preserve replay response and digest. Use explicit EN/RU labels for every supported kind (including `relation_add`, `relation_remove`, `task_launch_replace`, `task_launch_cancel`); generic unsupported-kind label differs from a deleted/restricted target. Use existing read policies for linked Run/task/receipt/memory detail. Redaction must remove hidden title, key, link, identifier and raw error body before JSON, including in pagination and stream.

**Live and durability.** Add owner-only `GET /api/librarian/history/actions`; expose existing history generation in conversation, messages and history reads. Read generation, segment, rows and current authorization within one consistent read snapshot; conversation creation stays at its existing boundary. Preserve existing transcript on same-generation reset, but clear the previous segment's contextual receipts immediately on observing the new segment. A clear (new generation) replaces rather than merges transcript, attachments and history pages; discard any result carrying an older generation or a stale owner/request key. If parallel responses disagree, commit neither mixed view nor transcript; reconcile from the new generation. On access invalidation, remove cached target metadata before reloading; re-resolve deleted targets on the next authorized read. Use the existing owner stream and cadence for `librarian.work`, not another polling loop. Specify a metadata-only change witness with owner-scoped card/operation/task-link changes, generation/segment and visible/actionable grant changes. It must catch an older operation's settlement even when the newest history row and message sequence do not change; a newest-row or count-only fingerprint fails this contract. At T0 compare the owner-scoped compact metadata query against the existing stream baseline and freeze its access plan; never read full receipt payloads or resolve individual target joins per stream tick. Reconnect and opening history always reread authorized state. Reset preserves messages, memory, receipts and task links. Clear removes the existing history classes, detaches receipt links and increments generation; surviving history-only receipts never resurrect messages. Keep the existing reset/clear barriers, reconciliation owner, idempotency and retention windows. No new effects or retries.

## Test-driven implementation protocol

1. **RED.** Choose the next acceptance ID and add or revise the smallest observable test in its owning suite. Run discovery and that exact case (including full setup and fixture teardown). Record runner, test title and observed product assertion failure on the pre-change behavior. A failing import, missing dependency, timeout before the assertion, wrong fixture or skipped case does not count. An unchanged invariant that is already green stays a control; do not force it red or clone it.
2. **GREEN.** Make the smallest production change that implements the agreed specification, then rerun that case and its neighboring controls. Assert durable effects or their absence at the boundary that owns them (intent, mapping, ref/receipt, actual SSE bytes, read DTO, browser behavior). Exercise concurrency with explicit fixture barriers and real competing operations; no arbitrary waits. Use existing deterministic local providers only where the behavior crosses that boundary.
3. **REFACTOR.** Consolidate shared resolvers, typed DTOs and existing components only within the slice. Keep one purpose per function, strict types, dependencies inward, single authoritative predicates, explicit typed failures, and the existing HeroUI/auth/logging conventions. Apply SOLID to responsibilities and dependency boundaries; prefer small composed functions and existing abstractions (KISS/DRY). Rerun the focused tests and phase gates. A contract change discovered in refactoring goes back through the owning specification and RED before changing behavior.

Use one primary assertion owner: PostgreSQL/route integration for authorization, wire shapes, concurrency, persistence and exact provenance; Playwright for user choices, visual hierarchy, focus, navigation and effects as seen in the UI. Browser scenarios use representative backend states; they do not re-enumerate the server refusal matrix. Keep existing unit coverage for contract/pure-parser behavior and update invalid assumptions, without adding render snapshots, helper-call assertions or mock copies of integration tests. Record RED/GREEN/refactor results in the implementation handoff or review for each slice. Commit checkpoints contain green code and tests; transient red commits are unnecessary. No acceptance criterion can be closed by lint or schema validation alone.
