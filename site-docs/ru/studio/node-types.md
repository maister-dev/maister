description: "Выбор подходящего узла исполнения, координации, проверки или участия человека для каждого участка графа."

Flow — ориентированный граф в `flow.yaml`. У каждого узла одна модель
исполнения и явные переходы по исходам. Проверки выполняются на границе узла, но
не являются самостоятельными узлами графа.

## Что потребуется

- Локальный пакет в [Flow Studio](/ru/studio/flow-studio-and-packages).
- Непустой граф `nodes[]`. Старый формат `steps[]` не принимается.

## Исполняемые узлы

| Вид | Назначение | Исполнение и результат |
| --- | --- | --- |
| `ai_coding` | Планирование, программирование и анализ репозитория. | ACP-сессия, при необходимости записываемая рабочая копия, возможности, доказательства и структурный результат. |
| `orchestrator` | Декомпозиция и управление дочерними прогонами. | Долгоживущий координатор ACP может ждать детей и собирать результаты в пределах глубины, числа детей, времени, токенов и ошибок. |
| `consensus` | Независимые предложения, перекрёстная проверка и синтез. | Не менее двух участников работают в областях только для чтения, затем отдельный синтезатор объединяет результат. |
| `judge` | ИИ-оценка, отделённая от реализации. | Отдельный ACP-раннер и возможности судьи; вердикт или структурный результат направляют к принятию, доработке или человеку. |
| `cli` | Сценарий пакета или детерминированная команда, создающая результат. | Команда в рабочей копии, JSON через `MAISTER_OUTPUT_FILE`, ограниченные повторы при временных сбоях. |
| `check` | Детерминированная проверка. | Тот же транспорт команды, но смысл проверки и без политики повторов агента. |
| `human` | Проверка, одобрение, эскалация или передача человеку. | Запрос во Входящие с решениями, ролями, исполнителями, важностью и вариантами доработки. |
| `form` | Сбор типизированных данных для следующих узлов. | Останавливается на форме, не имеет действия и передаёт поля как переменные узла. |

Выбирайте по источнику полномочий. Детерминированный тест — `check`,
интерпретация ИИ — `judge`, ответственность или недостающий деловой контекст —
`human`.

## Общие части узла

| Часть | Назначение |
| --- | --- |
| `input.requires` | Требуемые результаты или актуальные доказательства. Узлы с запросом могут получить тело доказательства. |
| `settings` | Раннер, сессия, возможности, разрешения, ограничения, рабочая область или роли. |
| `action` | Запрос ACP или команда. У формы действия нет. |
| `output.produces` | Доказательства: изменение кода, отчёт тестов, журнал, оценка, план, контрольная точка. |
| `output.result` | Небольшое значение по схеме для следующих узлов и маршрутизации. |
| `pre_finish.gates` | Блокирующие или рекомендательные проверки перед завершением. |
| `finish.human` | Итоговое решение человека. |
| `transitions` | Соответствие исходов следующим узлам или `done`. |
| `rework` | Цели доработки, поведение рабочей копии, предел цикла и передача замечаний. |
| `decide` | Выбор исхода по структурному результату или вердикту. |

## Виды проверок

| Вид | Что подтверждает |
| --- | --- |
| `command_check` | Локальная команда завершилась требуемым образом. |
| `skill_check` | Именованный навык проверки оценил работу. |
| `ai_judgment` | ИИ-оценщик вернул калиброванный вердикт. |
| `artifact_required` | Нужное доказательство существует и выполняются ограничения по изменённым путям. |
| `external_check` | CI или другая система передала подписанный результат через внешний API. |
| `human_review` | Человек изучил работу и выбрал допустимое решение. |

Блокирующая проверка запрещает завершение узла, рекомендательная лишь сохраняет
результат. Вердикт, используемый `decide`, становится входом маршрутизации.

## Сессии и раннеры

Узлы с раннером могут делить именованную сессию или иметь отдельный слот. Общая
сессия сохраняет раннер и разговорный контекст. Разные сессии позволяют
планированию, разработке и проверке использовать разные агенты, модели и
провайдеров. Слоты участников и синтезатора `consensus` тоже явные.

## Доработка и повтор

- `retry_policy` повторяет `ai_coding` или `cli` после выбранных временных
  инфраструктурных ошибок.
- `rework` возвращает граф к предыдущему узлу по решению человека, вердикту или
  ошибке структуры. Нижележащие результаты становятся устаревшими.
- `retry_safe` разрешает оператору заново выполнить узел без сессии после сбоя.
  Включайте только для безопасных повторяемых действий.

Каждый автоматический цикл должен иметь предел и путь к человеку.

## Три канала результата

- доказательство — проверяемый артефакт для проверки и продвижения;
- структурный результат — небольшие данные для следующих узлов;
- обычный вывод и события — диагностика исполнения.

Подробности: [структурные результаты и контекст](/ru/studio/structured-results-and-context).
