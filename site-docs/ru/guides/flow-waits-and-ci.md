Для проверок внутри прогона используйте `check` или `cli`. Если CI работает на
Git-платформе, добавьте после локальных проверок узлы `publish` и `wait`. Во
время ожидания прогон сохраняет рабочую копию и освобождает слот и процесс
агента. Когда условие срабатывает, прогон встаёт в очередь на свободный слот.
Условие и срок видны на графе прогона и в карточке ожидания.

## Опубликуйте ветку и дождитесь проверок

Нужен движок 3.14.0 или новее и включённый Flow проекта. Настройте `origin` с
правом отправки изменений и доступом к результатам проверок. MAIster читает
проверки GitHub, GitLab и Gitea. При запуске разрешите этой ревизии Flow
отправить ветку и открыть PR, если он задан в манифесте. Имя ветки определяется
публичным шаблоном проекта.

Добавьте эти узлы после локальных проверок и направьте их успешный переход в
`publish`. Замените `test` точным названием проверки у провайдера, а `github-main`
идентификатором настроенного источника. В примере любой исход CI оставляет
прогон на ревью. Чтобы повторить проверку на новом коммите, направьте ошибку
в ограниченный цикл доработки.

```yaml
compat: { engine_min: "3.14.0" }
nodes:
  - id: publish
    type: publish
    pr: draft
    transitions: { success: await_ci }
  - id: await_ci
    type: wait
    on: { kind: ci, publication: publish, transport: pull, checks: [test], issuer: github-main }
    timeout: 1800
    transitions: { success: done, failure: done, cancelled: done, timeout: done, stale: done }
```

Чтобы опубликовать только ветку, опустите `pr`. Режим `pr: ready` создаёт PR,
готовый к ревью. Чтобы дождаться изменения состояния PR, укажите
`on: { kind: pr, publication: publish }` и добавьте переходы для `merged`,
`closed`, `conflict`, `timeout`, `cancelled` и `stale`. Результаты CI и PR
привязаны к опубликованному коммиту. При смене коммита направьте `stale` на
ревью или в ограниченный цикл доработки с повторной публикацией.

## Отправьте результат из CI

Для отправки из CI укажите `transport: push`, задайте имя сигнала `name`, а в
`issuer` укажите токен проекта, которому разрешена отправка. У токена должен
быть доступ `waits:signal`. Чтобы узнать адрес доставки, вызовите
`GET /api/v1/ext/projects/{slug}/waits/callback` с `signal`, `ref` и `headSha`.
При повторной публикации с теми же параметрами сохраните исходный адрес.
Передайте `name`, `outcome` и `headSha` методом POST на
`/api/v1/ext/runs/{runId}/waits/{waitId}/signal`. При повторе запроса отправляйте
исходные `Idempotency-Key` и тело. MAIster применит принятый сигнал после
проверки опубликованной ветки. Сигнал для другого коммита не завершит ожидание.

## Управляйте ожиданием

В карточке ожидания откройте срок, исход и историю доставок. При наличии прав
можно передать недостающий сигнал, завершить ожидание с объявленным исходом,
продлить срок или отменить ожидание с переходом `cancelled`. Для каждого
действия сохраняется причина. Поле `timeout` обязательно и задаётся в
секундах. Максимальный срок задаёт `MAISTER_MAX_WAIT_SECONDS`, по умолчанию
семь дней. Продление ограничено пределом, зафиксированным при начале ожидания.

Кроме CI и PR можно ждать таймер, новый комментарий к задаче, завершение или
переход на ревью связанного прогона того же проекта либо именованный сигнал.
См. [виды узлов Flow](/ru/studio/node-types). В промпте агента
`{{ steps.<id>.vars.waitData.content }}` вставляет внешний результат и текст
комментария как данные. В промпте доработки
`steps.<id>.vars.waitData.failedChecks` содержит названия обязательных проверок,
которые не прошли.

## Разрешите автоматическое завершение

С движком 3.15.0 или новее утверждённый Flow может объявить
`autonomous_completion` с ожиданием CI, обязательными блокирующими проверками
и блокирующей ИИ-оценкой. Администратор проекта утверждает источники CI и
задаёт пределы риска, уверенности и размера изменений. Включите возможность
на платформе и разрешите автономное завершение при ручном запуске. Для push CI
укажите `provider_issuer`, чтобы перед доставкой MAIster мог независимо
проверить обязательные результаты на том же коммите.

При выполнении требований MAIster может продвинуть результат или завершить
прогон после подтверждённого слияния PR. Если политика разрешает, объявленный
таймаут или исчерпание доработок может завершить прогон в `Failed`. При
недостающих или устаревших доказательствах прогон остаётся в `Review`.
Автономное завершение можно приостановить для прогона или отключить для проекта
либо платформы. Решение движка видно в прогоне и на рабочем столе. Обычные
[действия проверки и продвижения](/ru/guides/review-and-promote) доступны.
